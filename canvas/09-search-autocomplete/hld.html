A

Problem & requirements

clarify first
functional
  • Given a typed prefix, return the ranked top-K (default 10) matching query suggestions, case-insensitive.
  • Rank by a composite of frequency + recency + trending + personalization.
  • Ingest every completed search; surface trending queries within minutes.
  • Filter a blocklist (offensive/illegal); GDPR deletion of a user's history.
non-functional
  • Latency p99 < 100 ms end-to-end; Trie lookup p99 < 5 ms — every keystroke is a request.
  • Availability 99.99% — never block the user typing; degrade to stale cache / empty list.
  • Cache hit ratio > 90% — popular prefixes (Zipf) absorb the load.
  • Scale 1.4M QPS peak; AP — stale-by-minutes suggestions are acceptable.
B

Back-of-envelope estimation

5B searches/day · ~8 keystrokes each
Searches / day5 B
Autocomplete req / day~40 B
Peak QPS~1.4 M
Unique queries200 M
Trie + top-K~8–10 GB
Cache hit> 90%
Query logs~250 GB/day
Trie servers~9–12
Derivation: 5B searches × ~8 keystrokes = ~40B autocomplete req/day ÷ 86,400 × 3 peak ≈ 1.4M QPS. 200M unique queries → radix-compressed Trie ≈ 5 GB, plus pre-computed top-K (~200 B/node) ≈ 8–10 GB — fits in one JVM heap. Multi-tier cache absorbs ~90%, so only ~140K QPS reach the Trie → ~3 servers × replication = 9–12. → full math on canvas 3 & F · Estimation

D

API design

GET so it's cacheable
EndpointPurposeResponse
GET /api/v1/suggestions?prefix=&limit=&userId=the hot path — ranked top-K (limit ≤ 25, default 10)200 + suggestions[] (query, score, type) / 400 empty prefix
POST /api/v1/internal/search-eventsrecord a completed search (internal, feeds Kafka)202 Accepted + event_id
DELETE /api/v1/users/{userId}/search-historyGDPR — remove a user's history from suggestions200 + deleted_count
POST /api/v1/admin/blocklistblock a query from ever appearing201 Created (effective_immediately)
Why GET, not POST? GET is idempotent and cacheable — CDN/proxy/browser can cache popular prefixes natively. userId is a query param (not header) so it becomes part of the cache key: anonymous users share the high-hit global cache; personalized entries get a shorter TTL.
E

Data model

frequencies feed the Trie
query_frequencies (source of truth for the Trie)
query             STRING   // normalized (PK)
frequency         LONG     // all-time count
recent_frequency  LONG     // rolling last 7 days
trending_score    DOUBLE   // spike 0.0–1.0
last_searched_at  LONG     // epoch millis
language          STRING   // "en","es","fr"
is_blocked        BOOL     // blocklist flag

Rebuilt hourly by Spark from the raw event log; the Trie Builder reads rows with frequency > threshold.

TrieNode (in-memory, JVM heap)
children       Map<Char,Node>    // or radix label
isEndOfWord    boolean           // completes a query
frequency      long              // if end-of-word
topSuggestions List<Suggestion>  // pre-computed top-K
// Suggestion = { query, score, frequency }

Pre-computing top-K (~200 B/node) turns a prefix lookup from O(subtree DFS) into O(L)+O(1). Raw events (search_events) stream via Kafka → S3; per-user history lives in a Redis hash.

F

Key design choices (deep-dived on canvas 3)

defend these
data structure

Compressed Trie + pre-computed top-K

O(L) traversal, O(1) top-K read — no query-time DFS. Beats scanning or on-the-fly ranking. → canvas 2 · LLD

caching

CDN + L1 Caffeine + Redis

Zipf traffic + multi-tier cache absorbs >90%, so only ~140K QPS reach the Trie. → canvas 3

updates & consistency

AP · offline build + hot-swap

No live writes to the Trie (locks kill read latency). Rebuild offline, atomic volatile swap; stale-by-minutes is fine. → canvas 3

Glossary — one-liners

terms used above
Trieprefix tree — each node is a character; a path spells a prefix
Radix / compressed Triemerges single-child chains into one labelled node (~60% fewer nodes)
Top-K pre-computationstore each node's best K suggestions so lookup is O(1) after traversal
Debouncewait ~50–200 ms after the last keystroke before sending a request
Zipf distributiona few short prefixes account for most traffic → highly cacheable
Hot-swapatomically replace the live Trie via a volatile reference — zero downtime
L1 cache (Caffeine)in-process cache on each app node, TTL 60 s, W-TinyLFU eviction
Trending scoretoday's frequency ÷ 30-day average − 1 → boosts sudden spikes
AP (CAP)favour Availability + Partition-tolerance; stale suggestions are acceptable
Completion SuggesterOpenSearch/Elasticsearch FST — an on-disk Trie for >100M-term vocab
