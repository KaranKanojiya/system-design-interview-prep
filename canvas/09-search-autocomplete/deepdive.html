A

Scaling strategy

how to distribute the Trie & cache
serving tier

Stateless → horizontal

The AutocompleteService holds no session state — any replica answers any prefix. Auto-scale on CPU behind the LB (Trie lookup is pointer-chasing, CPU-bound). ~17K QPS peak / 60% target ≈ 12–15 instances.

read replicas

Full Trie per node

Each instance carries a complete Trie copy (~180 MB compressed, 200K terms), so a prefix query never crosses the network. Adding a replica adds read capacity linearly — no coordination.

cache tier

Redis (shared L3b)

Consistent-hash the lang:prefix key across a Redis cluster so any app server hits the same shard. Redis absorbs ~85% of Trie lookups and survives instance restarts.

Trie distribution — pick a strategy as vocabulary grows

Full Trie replica per instance ← chosen ≤ ~10M terms

Every ECS instance deserializes the same S3 snapshot into its own heap. A single-prefix query is answered entirely in-process — no fan-out, no cross-instance calls.

// each node: identical copy, ~180 MB (200K terms)
trie = deserialize(s3://tries/v43/trie.bin)
answer = trie.getTopK(prefix, k)   // O(L), local
verdict
  • Simplest & fastest: sub-ms lookup, no network hop, trivial to reason about.
  • Read scaling is linear — add replicas, add QPS.
  • Ceiling: the whole Trie must fit one heap. Fine at 200K–10M terms; breaks past a single node's RAM.

Shard by first character

Partition the keyspace into 26 shards (a* → shard A, b* → shard B …). The LB routes on prefix[0] so each shard holds only its slice of the Trie.

shard = route( prefix.charAt(0) )
// "w..." → shard W  ·  Kafka is already partitioned this way
verdict — only when it won't fit
  • Lets total vocabulary exceed one node's RAM (each shard is ~1/26th).
  • Skewed shards: "a"/"s"/"t" are far hotter than "z" (Zipf) → uneven load, needs weighting.
  • Adds routing complexity for zero latency gain below ~10M terms — don't reach for it early.

Elasticsearch Completion Suggester

Offload to a managed FST (Finite State Transducer) — a compressed, disk-backed Trie with sharding, replication, and built-in fuzzy matching baked in.

// crossover point ≈ 100M terms
POST /suggestions/_search
  { "prefix": "app", "fuzzy": { "fuzziness": 1 } }
verdict — the 100M+ answer
  • Scales horizontally to 100M+ terms with shard-level replication.
  • Free fuzzy matching (typo tolerance) and NRT (~1 s) refresh — no custom rebuild.
  • Cost: 5–10 ms network hop vs our 1–2 ms in-process, plus cluster ops. Great for production, weaker for showing data-structure depth.
Never update the live Trie: a Spark job aggregates query logs with time-decay, builds a fresh Trie offline, serializes it to S3, and instances hot-swap via AtomicReference.getAndSet() — a single CAS, no locks, no read pauses. Writes are batched offline where nobody is waiting.

Caching deep-dive

55 ms → 14 ms lives here
cache-aside — read path (suggest)
GET autocomplete:{lang}:{prefix} from Redis
  ├─ HIT  → return top-K              // ~0.5–2 ms
  └─ MISS → trie.getTopK(prefix, 10)
             ├─ filter (profanity)
             ├─ rank (freq · time-decay)
             └─ SETEX cache (TTL 5 min) → return

The InMemorySuggestionCache is a LinkedHashMap in access-order (LRU) + a per-entry TTL. Even a total cache outage only degrades to a Trie fallback — never an error.

why LRU + TTL fits Zipf
// prefix popularity follows Zipf's law
"a"      → 50,000 req/s   // never evicted
"app"    →  5,000 req/s   // warm
"apple m"→    200 req/s   // evicted fast

Short prefixes are typed by everyone → they stay hot and survive eviction; long-tail prefixes are seen once and drop out. LRU keeps the hot, TTL bounds staleness (5–10 min is invisible for suggestions).

multi-level cache

Browser → CDN → LRU → Trie

Four layers, each catching a tier of traffic. Weighted average latency ~14 ms vs 55 ms with no cache — a 4× win. The Trie (source of truth) sees only ~3% of requests.

L1 browser  0ms   35% hit
L2 CDN     10ms   50% of rest
L3 LRU     ~0ms   90% of rest
L4 Trie    15ms   the last ~3%
cold start

Cache warming

A restart empties the LRU → first 1,000 users cold-miss (p99 15→25 ms). A cache-warming routine pre-computes the top 1,000 prefixes at startup and after every swap, so 90% of traffic hits warm cache immediately.

for (String p : top1000Prefixes)
  cache.put(p, rank(filter(trie.search(p,30))));
// ~1000 × 15ms ≈ 15 s
invalidation on rebuild

Clear + re-warm

A new Trie means new top-K rankings, so swapTrie() does an atomic swap, then cache.invalidateAll(), then async re-warm. Fully warm again in ~5 min; a brief p99 bump is the only cost.

old = currentTrie.getAndSet(newTrie);
cache.invalidateAll();
runAsync(this::warmCache);   // re-warm top 1,000
Cache the shared, not the personal: key on lang:prefix (~500K entries, 90%+ hit). Per-user keys would explode to billions and kill sharing — apply personalization as a Decorator on the shared top-K, then cache that at userId:prefix with a short 60 s TTL. → full layering on canvas 1 · HLD
C

Bottlenecks & solutions

click a card to open

Subtree DFS on every keystroke

Impact: a plain Trie must DFS the entire subtree under a prefix. Typing "a" (10M matches) means traversing 10M nodes per request — O(subtree), unusable at autocomplete latency.

Fix: the TopK Trie — pre-compute the top-K suggestions at every node. Serving becomes O(L) walk + O(1) return, no DFS. Pay O(L·K) at insert time (offline rebuild, nobody waiting).

Trie too big for one heap

Impact: all 200M raw queries would be ~55–72 GB — won't fit a single JVM. Even a full replica per node has a hard RAM ceiling.

Fix: keep only the top ~200K terms (Zipf: they cover ~80% of searches; single-search queries make bad suggestions anyway) → ~180 MB compressed. Past ~10M terms, shard by first character; past ~100M, move to Elasticsearch's on-disk FST.

Hot short prefixes ("a", "th", "wh")

Impact: 1–2 char prefixes are ~70% of all traffic (Zipf). Hammering the origin for these would swamp both Redis and the Trie tier.

Fix: serve short prefixes from the CDN edge (TTL ~1 h, ~70% hit) and the in-process LRU never evicts them. Client-side debounce (100–200 ms) + minimum-prefix-length ≥ 2 cut request volume ~70% before it ever leaves the browser.

Trie rebuild without downtime

Impact: a full rebuild takes 5–30 min for 200M queries. Locking the serving Trie during that window = zero autocomplete for half an hour.

Fix: blue-green swap. Build the new Trie offline while the old one serves, then AtomicReference.getAndSet(newTrie) — a lock-free CAS. In-flight requests drain on the old Trie, which is then GC'd. Zero downtime, instant rollback to the prior S3 snapshot.

Cold-start latency spike

Impact: after a restart or a swap the LRU is empty; the first ~1,000 users cold-miss to the Trie (p50 2→15 ms, p99 5→25 ms) for a few minutes.

Fix: cache warming — pre-populate the top 1,000 prefixes (~15 s) so 90% of traffic hits warm cache immediately; the rest fills organically within ~5 min.

Trending query not yet in the Trie

Impact: a query that spikes right now (live sports, breaking news) won't appear until the next 15–60 min rebuild — the offline pipeline is too slow for real-time trends.

Fix: a secondary fast path — a Kinesis/Lambda 5-min sliding window detects spikes (e.g. 10× normal) and injects the query straight into Redis for the relevant prefixes with a short TTL, bypassing the Trie. The next scheduled rebuild makes it permanent.

Offensive suggestion leaks across nodes

Impact: if a newly-blocked term reaches Node A but not Node B, users on B still see the offensive suggestion — a legal/compliance risk (the one place staleness is not OK).

Fix: push-based blocklist updates with per-node acknowledgment (seconds, not minutes) applied by ProfanityFilterStrategy. A node that can't be reached during an update is pulled from rotation rather than serving unfiltered content — CP behavior for this one component.

CAP & consistency — why fully AP

grounded in CAP_THEOREM.md
the choice

P is mandatory, so the real decision is A vs C during a partition. Suggestions are inherently stale — they rank past searches. A 5–60 min lag is invisible ("weather" is still the top hit for "wea"), but a blank dropdown makes the whole search bar feel broken. So: availability, always.

  • AP: during a partition each node serves from its local Trie + cache — possibly-stale, never empty.
  • PACELC → PA/EL: partition → Availability; else → Latency. Serve from local cache in 2 ms rather than checking peers for the newest Trie version.
  • Worst case: a trending query shows at rank 5 instead of rank 1 for one rebuild cycle. Nobody notices.
why EL (latency over consistency) at rest
// user types a char every 50–100 ms
consensus read → 20–50 ms   // arrives AFTER next keystroke
local read     → 2–5 ms    // feels instant  ← chosen

// stale trie v42 vs v43 → 95%+ identical top-K

Checking all nodes for the latest Trie version before responding would cost 15–45 ms — more than the whole keystroke budget. Two nodes disagreeing (v42 vs v43) is harmless; they converge on the next swap.

Eventual-consistency window: query counts converge in 1–5 min, rankings in 5–60 min, the Trie structure per 15–60 min rebuild. Losing one query log out of 10M ("weather" 999,999 vs 1,000,000) changes rankings by exactly zero — which is why even the write path (query logging) is AP.

phase-by-phase
  • P1 Clarify (2–3): unique queries/day (sizes the Trie), sub-100 ms latency, personalized vs global, freshness (15–60 min OK?), fuzzy matching, multi-language.
  • P2 Architecture (5–7): four layers — CDN edge (short prefixes, 70%), Redis LRU, Autocomplete Service with in-memory Trie, offline Kafka→Spark→S3 pipeline. Separate the online serving path from the offline rebuild.
  • P3 Trie (8–10 · CORE): basic O(L) → the subtree problem → compressed (Radix) for memory → TopK pre-computation for O(1) serving. Never skip this phase.
…and finish strong
  • P4 Ranking (5–7): raw frequency → time-decay (score = Σ count·0.98^hrs) for trends → personalized blend (0.7 global + 0.3 user) via Decorator.
  • P5 Scaling (5–8): full Trie replica per ECS node, Redis absorbs 85%, hot-swap via AtomicReference, client debounce/prefix-filter/abort/min-length. Add Redis inject path for live trends.
  • P6 Trade-offs (3–5): Trie vs Elasticsearch (100M crossover), offline vs real-time rebuild, and state plainly: the whole system is AP — stale suggestions are harmless.
