B

TopKTrie — the core algorithm

pre-computed top-K = O(1) lookup
insert — update top-K at every ancestor
public void insert(String word, long freq) {
  String w = word.toLowerCase().trim();
  // 1. normal insert builds the path + terminal
  standardTrie.insert(w, freq);

  // 2. walk the path AGAIN, refresh top-K
  TrieNode t = standardTrie.findNode(w);
  Suggestion s = new Suggestion(w, t.getFrequency());

  updateTopK(standardTrie.getRoot(), s);
  TrieNode cur = standardTrie.getRoot();
  for (int i = 0; i < w.length(); i++) {
    cur = cur.getChild(w.charAt(i));
    updateTopK(cur, s);          // O(K) each
  }
}

updateTopK replaces the entry if the word already exists, else adds it only if there is room or it beats the worst, then Collections.sort (score desc) and caps at K. Insert is O(L·K).

worked example — K = 3
// insert "apple" (freq 200)
root,a,p,p,l,e  topK = [apple(200)]

// insert "app" (freq 500)
node 'p' (2nd)  topK = [app(500), apple(200)]
node 'p' (1st)  topK = [app(500), apple(200)]
node 'a'        topK = [app(500), apple(200)]
root            topK = [app(500), apple(200)]

// query getSuggestions("ap", 3)
walk root → a → p        // O(L)
return node.topSuggestions // O(1) — no DFS!
        → [app(500), apple(200)]

A StandardTrie would DFS the whole subtree under ap and sort — O(L + N log N). For a hot prefix like "a" that is millions of nodes per keystroke.

Why pre-compute? Autocomplete is ~99.9% reads and fires on every keystroke, while inserts happen offline during batch rebuilds. TopKTrie deliberately trades a heavier insert (O(L·K), and K is a small constant ~10) for a constant-time lookup at the prefix node. The read path never walks the subtree, so a query for "a" costs the same as a query for "application". Delete is lazy — it clears the terminal but leaves stale top-K lists until the next rebuild (see §C · TrieBuilderService atomic swap).
C

Trie & ranking strategies (Strategy pattern ×2)

swap the algorithm, not the service

StandardTrie — HashMap children, DFS-based lookup. getTrieType() = "STANDARD"

  • insert: O(L) — walk char by char via getOrCreateChild, mark terminal, set frequency.
  • getSuggestions: walk to the prefix node O(L), then collectSuggestions DFS the subtree, sort by score, take top-K — O(L + N log N).
  • When: small datasets, prototyping, insert-heavy rebuilds. The O(N) DFS is the bottleneck TopK removes.

CompressedTrie — radix / Patricia tree: single-child chains merge into one edge with a string edgeLabel.

  • Space: "facebook / face / faq" collapses from 11 nodes to 5 (~55% fewer). Big win when the trie lives in memory.
  • Split on insert: find the longest common prefix, split the existing edge, add an intermediate node.
  • getSuggestions: still a DFS from the match node — O(L + N). Compression saves memory, not lookup time.

TopKTrie — the default. Wraps a StandardTrie and keeps a pre-computed top-K list at every node. the AppConfig production choice

  • insert: O(L·K) — refresh top-K at each ancestor (§B).
  • getSuggestions: O(L) to reach the node, O(1) to return the cached list — no DFS.
  • Cost: O(N_nodes · K) extra memory; delete is lazy (rebuild to purge). The right call for read-heavy, latency-critical serving.

Ranking is a second Strategy axis behind RankingStrategy, held by RankingService:

  • FrequencyRankingStrategy: score = raw frequency; just Collections.sort. Cold-start / anonymous baseline.
  • TimeDecayRankingStrategy: score = freq · e^(-λ·ageHours); half-life = ln(2)/λ (λ=0.01 → ~69 h). Favors fresh/trending queries.
  • PersonalizedRankingStrategy: a Decorator over a base — ×1.5 for the user's past queries, ×1.2 on locale match, then re-sort. Default wiring: Personalized(TimeDecay).

The pattern: TrieService holds a single Trie reference and RankingService a single RankingStrategy — neither ever branches on a type. Switching StandardTrie→TopKTrie, or Frequency→TimeDecay, is one line in AppConfig with zero changes to the facade, controller, or cache. TrieBuilderService builds a fresh trie offline and TrieService.rebuildTrie() swaps the reference atomically (double-buffering) — no downtime, and the rebuild is when stale TopK/delete state gets purged.
D

Data model detail

TrieNode · Suggestion · SearchQuery · Config
TrieNode — the building block
children      Map<Character,TrieNode>  // HashMap
isEndOfWord   boolean
frequency     long            // search count
topSuggestions List<Suggestion> // pre-computed top-K
edgeLabel     String          // CompressedTrie only

A HashMap (not TrieNode[26]) so digits, spaces and unicode all fit, and memory is proportional to real children. topSuggestions is empty for Standard/Compressed and populated by TopKTrie.

Suggestion — the result object (Comparable)
text    String
score   double          // mutable → re-ranking
source  SuggestionSource // POPULAR | TRENDING
                         // | PERSONALIZED | AUTOCORRECT

compareTo → score DESC, then text ASC

equals/hashCode key on text (so a word is de-duped in a top-K list); natural order is score-descending so Collections.sort is used everywhere instead of ad-hoc comparators.

SearchQuery — history record (Builder)
queryText    String
frequency    long
lastSearched LocalDateTime  // time-decay
userId       String         // personalization

SearchQuery.builder(text).userId(u)
   .lastSearched(now).build()

Stored in InMemoryQueryRepository keyed by text. Metadata (frequency, timestamp, user) is exactly what the ranking strategies consume. Built via the Builder pattern to avoid a telescoping constructor.

AutocompleteConfig — tuning (Builder + defaults)
maxResults      int   // 10
maxPrefixLength int   // 50
minFrequency    long  // 2
decayFactor     double // 0.01  (λ)
topKPerNode     int   // 10   → K
cacheSize       int   // LRU capacity
cacheTtlSeconds int

Single source of truth for every knob. AutocompleteConfig.defaultConfig() gives sensible values; the Builder lets tests override only what matters. Passed by constructor into AppConfig.

Two frequency counters, on purpose: the QueryRepository holds the authoritative lifetime frequency (write path, off the keystroke); the trie's TrieNode.frequency + pre-computed topSuggestions are the read-optimized copy rebuilt from that data. The cache is a third, ephemeral layer keyed by prefix. Each layer trades freshness for speed on the read hot path.
E

Request handling sequence

which class does what, in order

GET /autocomplete?q=app  →  the read hot path

Controller.handleSearch("app", userId)
  └─ new SearchContext(userId, "en", "US", now)
  └─ AutocompleteService.getSuggestions("app", ctx)
       1  normalize → "app"; clamp to maxPrefixLength
       2  cache.get("app")                 // LRU + TTL
            present? → return  // CACHE HIT, skip pipeline
       3  trieService.getSuggestions("app", 10)
            [read lock] → TopKTrie → O(1) node.topSuggestions
            empty? → cache.put (negative) → return
       4  for (FilterStrategy f : filters)  // profanity…
              suggestions = f.filter(suggestions)
       5  rankingService.rankSuggestions(suggestions, ctx)
            → Personalized(TimeDecay).rank(...)
       6  trim to maxResults
       7  cache.put("app", ranked)
  └─ [200] formatted suggestion list

The cache short-circuits everything on popular prefixes; on a miss the whole trie → filter → rank pipeline runs once and the result is memoized. The trie read holds only a shared read lock, so thousands of keystrokes proceed concurrently.

POST /query?q=apple  →  record a completed search (write path)

Controller.handleRecordQuery("apple", userId)
  └─ AutocompleteService.recordQuery("apple", userId)
       1  dataCollectionService.recordQuery("apple", userId)
            → queryRepository.incrementFrequency("apple")
            → stamp timestamp (trending window)
            → if userId: repository.save(SearchQuery)
       2  trieService.insertQuery("apple", 1)
            [write lock] → TopKTrie.insert → refresh top-K
       3  for i in 1..len: cache.invalidate("apple".sub(0,i))
            // "a","ap","app","appl","apple" now stale
  └─ confirmation

Writes are rare relative to reads. The write lock briefly blocks readers for the single insert; invalidating every prefix of the word forces the next keystroke on those prefixes to recompute from the updated trie. Periodic full rebuilds (TrieBuilderService) fold accumulated frequencies back in and purge lazy deletes.

F

Design patterns used

GoF-categorized
Creational
  • Builder — AutocompleteConfig.Builder (7 knobs) and SearchQuery.builder(). Optional fields with defaults, no telescoping constructor.
  • Factory — AppConfig is the only class that says new ConcreteClass(); each create*() is effectively a @Bean.
  • Singleton (conceptual) — one shared AutocompleteConfig so every service reads identical tuning values.
Behavioral
  • Strategy ×3 — Trie (Standard/Compressed/TopK), RankingStrategy, FilterStrategy. Three independent axes of variation.
  • Observer — DataCollectionService observes search events to update frequencies/trending, decoupled from serving.
  • Iterator — the trie's DFS traversal collects suggestions without exposing node internals.
Structural (+ arch)
  • Facade — AutocompleteService hides trie + cache + filter + rank behind one getSuggestions().
  • Decorator — PersonalizedRankingStrategy wraps a base ranking, adding boosts transparently.
  • Repository — QueryRepository → InMemoryQueryRepository. Domain never sees storage.
Why they cluster: the three Strategies + Repository + constructor injection deliver the Open-Closed Principle — new tries, ranking algorithms, filters and storage backends are additions, never edits. The Facade keeps controllers trivial; the Decorator lets personalization stack on any base ranking; the Chain-of-Responsibility over List<FilterStrategy> composes filters. → scaling, sharding & the distributed-trie follow-up on canvas 3

Glossary — one-liners

terms used above
Trie (prefix tree)tree keyed by characters; a path from root spells a word, so a prefix maps to a subtree
Top-K pre-computationstore the best K suggestions at every node so a prefix lookup is O(1), not a DFS
Compressed / radix triemerge single-child chains into one edge label to cut node count
Time-decay rankingscore = freq · e^(-λ·age); half-life = ln(2)/λ — fresh queries outrank stale ones
Strategy patterninterchangeable algorithms behind one interface, chosen at runtime
Facadeone entry point (getSuggestions) hiding trie + cache + filter + rank
Decoratorwrap a base object to add behavior transparently (personalization over ranking)
ReadWriteLockmany concurrent readers, one exclusive writer — ideal for read-heavy autocomplete
