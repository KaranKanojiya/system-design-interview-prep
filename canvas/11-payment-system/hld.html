A

Problem & requirements

clarify first
functional
  • Process payments (cards / UPI / bank transfer) with a client idempotency key → exactly-once execution, never a double-charge.
  • Two-phase auth + capture; full & partial refunds that post ledger reversal entries (never mutate the original).
  • Immutable double-entry ledger — every movement = 1 DEBIT + 1 CREDIT of equal amount.
  • Signed HMAC webhooks with retry; status & balance queries; daily reconciliation vs bank files; 135+ currencies; fraud scoring.
non-functional
  • Payment latency p99 < 500 ms (card network is the bottleneck); status query p99 < 50 ms.
  • Availability 99.999% (≈5.26 min/yr) — downtime is direct revenue loss for every merchant.
  • Strong consistency for ledger & payments — a CP system; money cannot be eventually consistent.
  • Zero financial data loss; SUM(debits) = SUM(credits) always. Immutable, append-only audit trail (PCI-DSS / SOX).

E

Data model

ACID · append-only ledger
payments (state machine)
id               VARCHAR(36) PK  // pay_xxx
merchant_id      VARCHAR(36)
idempotency_key  VARCHAR(255) UQ // exactly-once
amount           BIGINT          // cents — no floats
currency         VARCHAR(3)
status           VARCHAR(20)     // INITIATED→…→SETTLED
authorization_code VARCHAR(50)
settlement_id    VARCHAR(50)     // recon lookup
refunded_amount  BIGINT
created_at       TIMESTAMP

UNIQUE index on idempotency_key is the DB-level exactly-once guard. Range-partitioned by created_at.

ledger_entries (append-only)
id             BIGSERIAL PK
transaction_id VARCHAR(36) // pairs debit+credit
payment_id     VARCHAR(36)
account_id     VARCHAR(36)
entry_type     VARCHAR(10) // DEBIT | CREDIT
amount         BIGINT      // always > 0
currency       VARCHAR(3)
created_at     TIMESTAMP   // immutable

Every transaction_id = exactly 2 entries; a trigger enforces DEBIT total = CREDIT total. No UPDATE/DELETE — corrections are new reversal rows.

Supporting tables: payment_transitions (state-change timeline) · merchants (api_key_hash, webhook_secret, settlement_currency) · webhook_deliveries (status, attempt_count, next_retry_at) · idempotency_keys (request_hash, cached response_body, 48 h TTL — Redis primary, PostgreSQL durable backup). → full schema on canvas 2 · LLD
F

Key design choices (deep-dived on canvas 3)

defend these
exactly-once

Idempotency key

Client key → Redis SET NX (PROCESSING/COMPLETED + cached response) with a PostgreSQL unique constraint as the durable guard. A retried charge returns the same result in ~2 ms — never double-charges. → canvas 2 · LLD

accounting

Double-entry ledger

Append-only, immutable; every movement is a balanced DEBIT/CREDIT pair inserted atomically. SUM(debits)=SUM(credits) is the invariant. The single source of truth for all money.

consistency

CP · strong (not AP)

Unlike a URL shortener, money can't be eventually consistent. PostgreSQL/Aurora, single-writer, synchronous replication. Availability comes from active-passive failover + reconciliation, not from relaxing consistency. → canvas 3

Glossary — one-liners

terms used above
Idempotency keyclient-supplied token so a retried request returns the same result, never re-executes
Double-entry ledgerevery movement = one DEBIT + one matching CREDIT; funds never appear or vanish
Auth vs Captureauthorize = hold funds; capture = actually collect them (two-phase)
Exactly-oncea charge executes precisely once despite network retries or crashes
Reconciliationdaily batch matching internal ledger against external bank settlement files
CP (CAP)favour Consistency + Partition-tolerance — money can't be eventually consistent
HMAC-SHA256keyed signature on the webhook payload so the merchant can verify authenticity
Settlement (T+2)funds move from pending → available balance after the bank confirms, ~2 days later
Circuit breakertrips a network adapter open after repeated failures so one card network can't sink the rest
3-D Securestep-up customer authentication for medium-risk transactions
