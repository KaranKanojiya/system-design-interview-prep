A

Scaling strategy

scale ACID without breaking it
app tier

Stateless → horizontal

The PaymentService orchestrator holds no state — idempotency lives in Redis, truth in Postgres. Any instance can serve any request, so auto-scale behind the LB. The bank/card-network call (~200 ms) dominates latency, not CPU.

read replicas

Dashboards only, never decisions

Aurora read replicas have ms–s replication lag. Route display queries (merchant dashboard, reporting, analytics) to replicas; every decision query — balance check, idempotency, refund eligibility — hits the primary with SELECT … FOR UPDATE.

functional partitioning

Split by service first

Before sharding rows, split by concern: Payment, Ledger, Fraud, Webhook, Reconciliation. Card charges are synchronous; settlement, payouts and reconciliation run as async daily batches, so back-office load never competes with the money path.

database partitioning — how to shard a ledger that must stay ACID

Shard by merchant_id ← chosen at scale

Co-locate a merchant's payments, ledger entries and balance on one shard, so the debit + credit + balance update stay inside one single-shard ACID transaction. Balance validation and payouts for a merchant never cross shards.

shard = hash(merchant_id) % N   // merchant's books stay together
verdict
  • Atomicity preserved: double-entry write is local to one shard — no distributed 2PC.
  • Per-merchant balance SUM and reconciliation stay single-shard.
  • Hot merchant risk: a huge merchant can skew a shard → split that merchant onto a dedicated shard.

Hash on payment_id

Route each payment by hash(payment_id) % N. Writes spread perfectly evenly and no single merchant can hot-spot a shard.

shard = hash(payment_id) % N   // even write spread, but…
verdict — avoid for the ledger
  • Cross-shard aggregation: a merchant's entries scatter across all shards, so balance SUM and payout fan out to every node.
  • Debit and credit of one payment can land on different shards → needs distributed transaction. Fine for a payment record store, painful for double-entry books.
  • Good for high-throughput non-financial data (rate-limit counters, sessions).

Single primary + read replicas

Don't shard at all until you must. One Aurora primary handles ~50K TPS — far above real payment-write volume — with replicas fanning out read-only display traffic.

// decisions → primary, always
SELECT balance … FOR UPDATE   // row lock, no replica
// dashboards / reports → replica (lag OK)
verdict — start here
  • Simplest correct design: one writer means no cross-shard transaction problem at all.
  • Vertical scale + replicas carries you a long way; shard by merchant only when the primary saturates.
  • Never read a balance from a replica — replication lag = approve-an-overdraft.
Money-safe scaling rule: scale the throughput (stateless app tier, replicas for reads, functional split) freely, but keep every correctness operation — idempotency, balance, double-entry — on a single authoritative primary/shard inside one ACID transaction.

Caching deep-dive

cache for speed, read the DB for decisions
The golden rule: CACHE for SPEED, read from the DB for DECISIONS. A stale exchange rate on a dashboard is fine; a stale balance that approves a payment is an overdraft someone pays for. Payment caching is deliberately conservative.
idempotency — the most critical cache
SET idem:{key} "PENDING" NX EX 86400
  ├─ OK  → first request → process
  └─ NIL → duplicate → GET & return cached result

after commit: SET idem:{key} "{result}" XX EX 86400

SET NX is an atomic, sub-ms check-and-set — Redis is single-threaded so two racing retries serialise, exactly one wins. Backed by InMemoryIdempotencyRepository in the sim; a Postgres UNIQUE(idempotency_key) is the defence-in-depth safety net.

what you must NEVER cache
// balance check — always primary, always locked
SELECT balance FROM accounts
  WHERE account_id = ? FOR UPDATE;
UPDATE accounts SET balance = balance - ?
  WHERE … AND balance >= ?;   // 0 rows = declined

Payment status, ledger entries, account balances, transaction IDs are never cached. A 2-second stale balance approves a $100 charge against a $50 account → overdraft. 5 ms via FOR UPDATE beats 0.5 ms that is sometimes wrong.

exchange rates · cache-aside

5-min TTL, lock at auth

Forex API is ~100 ms; rates don't move per-second. Cache-aside with a 5-min TTL for display. But at checkout, CurrencyService locks the rate at authorization time and stores it on the payment — settlement uses the locked rate, never the current one.

GET exchange:USD_INR
  MISS → forex API → SET … EX 300
lockRate() → freeze rate on payment
merchant config · read-through

10-min TTL, shared

Webhook URL, API version and notification prefs change rarely and many services read them (Webhook, Payment, Dashboard). Read-through centralises DB access so no two services cache with different logic.

merchant:{id} → cache
  MISS → SELECT … → fill (EX 600)
webhook retries · Redis ZSET

Sorted set by retry time

Score = next-retry epoch, member = delivery id. ZRANGEBYSCORE 0 now pulls everything due — time-based scheduling Kafka can't do cheaply. Delivery status still lives in Postgres.

ZADD webhook:retry {now+delay} {id}
ZRANGEBYSCORE webhook:retry 0 {now}
When Redis dies: idempotency fails fast → 503 (never process without a dedup check; fall back to the DB UNIQUE constraint if the SLA demands it). Exchange rates degrade to last-known in-memory rates; merchant config reads straight from Postgres; webhook retries pause (records are durable in Postgres). Redis Sentinel / Cluster gives 5–30 s auto-failover. → no CDN anywhere on the money path.
C

Bottlenecks & solutions

click a card to open

Crash between bank charge and DB persist

Impact: the card is charged (capture succeeds) but the process dies before the payment + ledger rows commit — the customer paid and we have no record of it.

Fix — three layers: (1) Bank-side idempotency — pass our own key to the bank; on retry the bank returns the original result instead of re-charging. (2) Reconciliation — the daily job spots a bank capture with no matching ledger entry and back-fills it. (3) Transactional outbox — write the DB row and the event in one transaction so no event is lost. This is the #1 interview follow-up.

Concurrent duplicate requests (same idempotency key)

Impact: two identical requests arrive in the same millisecond, both miss Redis, both reach the DB, both call the bank → two authorizations.

Fix: the Postgres UNIQUE(idempotency_key) is the last line of defence — only one INSERT commits, the other gets a unique violation, voids its auth and returns the winner's result. Redis SET NX catches 99% earlier; the DB constraint guarantees correctness for the rest. If the void fails, the hold auto-expires in 7 days and reconciliation flags it.

Redis (idempotency store) down

Impact: without the idempotency check, a retried request risks a double-charge — the single worst failure in the system.

Fix: fail fast, return 503 — never process a payment without a dedup check. This is the CP choice in action: temporary unavailability beats double-charging. Optional fallback to the DB UNIQUE constraint (10 ms vs 0.5 ms, but correct). Redis Sentinel/Cluster keeps failover to 5–30 s.

Ledger write bottleneck

Impact: every payment is a multi-statement ACID transaction (payment + debit + credit + balance) on a single primary — the write ceiling as volume grows.

Fix: functional partitioning (separate ledger service/DB), then shard by merchant_id so each merchant's double-entry stays single-shard. Aurora handles ~50K TPS before you need to shard at all; keep async work (settlement, payouts, reconciliation) off the synchronous path.

Network partition: app ↔ database

Impact: the payment service can take requests but can't reach Postgres — it can't check balance, idempotency, or record the ledger.

Fix (CP, not AP): stop processing, return 503, queue incoming requests in Kafka (durable, ordered) and drain in order when the partition heals — idempotency keys prevent duplicates during the drain. The AP temptation ("accept now, reconcile later") means overdrafts and unbalanced books. Payments are delayed, never incorrect.

Card network / bank timeout

Impact: the authorization request to Visa/NPCI times out — we don't know if the charge succeeded.

Fix: keep the payment in PROCESSING, return PENDING to the client (never SUCCESS, never DECLINE), and let a background job retry with backoff carrying the same bank idempotency key. After ~30 min, expire the payment and fire a payment.expired webhook. We never tell the customer "successful" until the network confirms.

Webhook delivery to a slow / down merchant

Impact: a merchant server that's down or slow would block the payment path if delivery were synchronous.

Fix: deliver async off a queue. WebhookService retries with exponential backoff (1m, 5m, 30m, 2h, 8h, 24h) scheduled in a Redis ZSET; after max attempts move to a DLQ and alert the merchant, who can poll the events API. Every payload is signed with HMAC-SHA256 so merchants verify authenticity.

D

CAP & consistency — why CP

consistency is non-negotiable for money
the choice

A payment system does not have a CAP choice. P is mandatory in any distributed system, and for money the real decision — A vs C during a partition — is always C. Unlike e-commerce, which tolerates a 5-second-stale price, a payment system cannot tolerate a stale balance for 1 ms.

  • CP: during a partition, refuse the request (503) rather than risk a double-charge or overdraft.
  • PACELC → PC/EC: on Partition pick Consistency; Else pick Consistency over Latency — synchronous DB write before responding.
  • Worst case for the customer: "please try again in a moment" — a brief delay, never an incorrect charge.
exactly-once = idempotency + ACID
// 1. dedup lock (atomic, sub-ms)
SET idem:K1 "PENDING" NX EX 86400
// 2. process inside ONE ACID transaction
BEGIN;
  INSERT payment (…, idempotency_key)  // UNIQUE
  INSERT ledger DEBIT  customer_hold
  INSERT ledger CREDIT merchant_balance
  UPDATE balance … WHERE balance >= amt
COMMIT;
// 3. store result against the key
SET idem:K1 "{result}" XX EX 86400

At-most-once loses payments; at-least-once double-charges. Only exactly-once — idempotency key + a single ACID transaction whose UNIQUE constraint serialises racers — is acceptable. If the transaction fails, the whole thing rolls back and the lock is released.

Why append-only double-entry: every operation writes a balanced debit + credit; SUM(debits) = SUM(credits) = 0 at all times is the ledger's "unit test". A refund never deletes the original charge — it adds reverse entries, preserving a complete, immutable audit trail for regulators.

phase-by-phase
  • P1 Clarify (2–3): scale (1M vs 1B/mo), single-step vs authorize-then-capture, payment methods, webhook guarantee, PCI in scope, multi-currency & when to lock FX.
  • P2 Architecture (5–7): five services — Payment, Ledger, Fraud, Webhook, Reconciliation. Lead with idempotency + double-entry ledger. State it's CP.
  • P3 Idempotency (8–10 · THE STAR): two layers — Redis SET NX for speed, Postgres UNIQUE for truth. Walk the crash-between-bank-and-DB scenario and the concurrent-race with auth void.
  • P4 Ledger (5–7): every op = balanced debit+credit, sum = 0, append-only, refunds add reverse entries; daily reconciliation vs bank statement.
…and finish strong
  • P5 Scale & edges (5–8): fraud as chain of responsibility (velocity → amount → geo → ML), webhooks with HMAC + backoff + DLQ, multi-currency with rate locked at auth.
  • P6 Trade-offs (3–5): CP vs AP (money path CP, dashboards AP), SQL vs NoSQL (ACID for ledger), sync vs async (card sync, settlement async), own HSM vs third-party tokenizer.
  • Elevator pitch: idempotent pipeline, two-layer dedup, double-entry ledger, state machine, fraud chain, HMAC webhooks, daily reconciliation, CP, PCI via vault.
  • Never skip P3 — the idempotency deep-dive is ~50% of this interview.
Green flags: lead with idempotency · two-layer dedup · double-entry sum = 0 append-only · explain the crash scenario (bank-side idempotency + reconciliation) · fraud as a chain · integer cents · CP for money, AP for dashboards. Red flags: no idempotency key · floating-point money · mutable ledger (UPDATE/DELETE) · single "balance" field · no reconciliation · making the whole system AP · webhooks without signatures.
