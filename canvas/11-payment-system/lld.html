B

Double-entry bookkeeping — the core algorithm

LedgerService.recordPayment
the code (condensed)
public void recordPayment(Payment p) {
  String source = p.getCustomerId() != null
      ? p.getCustomerId() : PLATFORM_ACCOUNT_ID;
  String merchant = p.getMerchantId();

  // Entry 1 — DEBIT source (+amount = money OUT)
  LedgerEntry debit = new LedgerEntry(
      p.getPaymentId(), source,
      +p.getAmount(), DEBIT,
      p.getCurrency(), "…");

  // Entry 2 — CREDIT merchant (−amount = money IN)
  LedgerEntry credit = new LedgerEntry(
      p.getPaymentId(), merchant,
      -p.getAmount(), CREDIT,
      p.getCurrency(), "…");

  ledgerRepository.save(debit);
  ledgerRepository.save(credit);
  accountRepository.findById(merchant)
      .ifPresent(a -> a.credit(p.getAmount()));
}

Entries are immutable — to reverse a charge you append the opposite pair (recordRefund), never edit history.

worked example — Alice pays Acme $100.00
// processPayment → capture → recordPayment
DEBIT  CUSTOMER-001   +100.00   // money OUT
CREDIT MERCHANT-001   -100.00   // money IN
                      ────────
             per-txn sum = 0.00  ■ balanced

// settlement adds the platform fee (2.9% + $0.30)
DEBIT  PLATFORM       +96.80
CREDIT MERCHANT-001   -96.80   // net to merchant
DEBIT  PLATFORM        +3.20
CREDIT PLATFORM-FEE    -3.20   // our revenue
                      ────────
             per-txn sum = 0.00  ■ balanced

verifyBalance() → Σ(all entries) = 0.0000

Every money movement is two (or more) entries summing to zero. The system-wide invariant Σ(all entries)=0 is the single check that proves no money was created or lost.

Why double-entry? A naive balance += amount has no audit trail, no cross-reference, and drifts silently. With paired signed entries you get: an audit trail (every dollar traceable to a paymentId), error detection (the sum must be 0 — how banks catch bugs), and reconciliation (match the internal ledger against the processor). The Account.balance field is just a fast cache; the entries are the source of truth. Production swaps double for BigDecimal so the sum is exactly zero.
C

Processors & fraud checks (Strategy pattern ×2)

swap the rail / detector, not the service

CreditCardProcessor — simulates a Visa/MC gateway. name() = "CreditCardProcessor" · handles CREDIT_CARD, DEBIT_CARD, BANK_TRANSFER

  • Two-phase: authorize (hold funds) then capture — modelled as PROCESSING → AUTHORIZED → CAPTURED for real card flows.
  • Realism: ~95% success, ~200ms latency; declines carry ISO-8583 codes — 51 insufficient-funds, 59 suspected-fraud, 91 issuer-unavailable.
  • Returns a Transaction (never throws) with status APPROVED / DECLINED / ERROR.

UPIProcessor — simulates an NPCI collect request. name() = "UPIProcessor"

  • Single-phase / instant settlement: no separate auth — the state machine goes PROCESSING → CAPTURED in one shot.
  • Realism: ~98% success, 100–500ms.
  • Best for markets where real-time rails dominate.

WalletProcessor — deducts a pre-funded balance atomically. name() = "WalletProcessor"

  • No external network → 50–200ms, ~99% success (highest — nothing to decline but insufficient balance).
  • Single-phase like UPI.
  • Ideal for closed-loop / stored-value use cases.

FraudCheckStrategy — a second Strategy axis, chained by FraudService (defence in depth):

  • RuleBasedFraudCheck: amount threshold, velocity limit, merchant blacklist — cheap, deterministic, explainable.
  • MLFraudCheck: simulated model returning a 0.0–1.0 risk score against a ~0.7 threshold — catches subtle patterns.
  • Combine: FraudService runs all strategies, takes the max score, and fails if ANY fails — collecting every reason.

The pattern: PaymentService holds a Map<PaymentMethod,PaymentProcessor> and never branches on rail — it does processors.get(method).processPayment(payment). FraudService holds a List<FraudCheckStrategy> and iterates. Adding a PayPalProcessor or a GeoFenceFraudCheck is a new class + one line in AppConfig — zero changes to the services (Open-Closed Principle).
D

Data model detail

Payment state machine + the records
Payment — guarded state machine
paymentId      String   // PAY-uuid, immutable
merchantId     String   // immutable
customerId     String   // nullable
amount         double   // > 0 (BigDecimal in prod)
currency       Currency // USD/EUR/GBP/INR/JPY
method         PaymentMethod
status         PaymentStatus  // guarded ↓
idempotencyKey String
processorTxnId String   // set post-processor

Valid transitions (each method throws on an illegal move):

INITIATED  → PROCESSING | CANCELLED
PROCESSING → AUTHORIZED | CAPTURED | FAILED
AUTHORIZED → CAPTURED   | CANCELLED
CAPTURED   → SETTLED    | REFUNDED
SETTLED    → REFUNDED
FAILED / REFUNDED / CANCELLED = terminal
the supporting records
// LedgerEntry — immutable, signed
entryId, transactionId, accountId
amount        double  // +DEBIT / −CREDIT
type          LedgerEntryType
currency, description, createdAt

// IdempotencyRecord — 24h TTL
key, paymentId, responseStatus
responseBody, createdAt, expiresAt

// WebhookEvent — delivery tracking
eventId, eventType, paymentId, merchantId
payload, status, attempts / maxAttempts(5)
nextRetryAt  // exp. backoff 1→2→4→8→16s

Accounts are typed CUSTOMER / MERCHANT / PLATFORM / SETTLEMENT; Account.balance is a cached read, reconciled against ledger entries.

Immutability where it counts: a Payment's identity & amount are final — only status moves, and only through the guarded methods. LedgerEntry and IdempotencyRecord are write-once. That combination (fixed money + append-only ledger + guarded state) is what makes the system auditable and double-charge-proof.
E

Request handling sequence

which class does what, in order

POST /payments  →  process a payment

PaymentController.processPayment(req)
  └─ PaymentService.processPayment(merchant, amount, cur, method, idemKey, customer)
       1  idempotencyService.checkAndGet(idemKey)   // synchronized
            present? → DuplicatePaymentException     // return cached
       2  new Payment.Builder()...build()            // status = INITIATED
       3  fraudService.checkPayment(payment)         // rules + ML
            !passed? → payment.fail(); record idem; throw FraudDetectedException
       4  processor = processors.get(method)
          payment.startProcessing()                 // INITIATED → PROCESSING
          txn = processor.processPayment(payment)    // APPROVED / DECLINED / ERROR
       5  "APPROVED"? → payment.capture()            // → CAPTURED
                        ledgerService.recordPayment(payment)   // DEBIT + CREDIT
                      : payment.fail()               // → FAILED
       6  paymentRepository.save(payment)
          idempotencyService.record(idemKey, id, status, body)
       7  webhookService.dispatchWebhook("payment.succeeded"|"payment.failed", payment)
  └─ [201 Created]  Payment

Idempotency is checked first and recorded even on fraud-block, so a retry of a blocked payment is also rejected — never reprocessed.

POST /payments/{id}/refund  →  refund (full/partial)

PaymentController.refundPayment(id, amount, reason)
  └─ RefundService.processRefund(paymentId, amount, reason)
       1  payment = paymentRepository.findById(id)   // else PaymentException
       2  guard: status ∈ {CAPTURED, SETTLED}        // can only refund taken money
          guard: 0 < amount ≤ payment.amount
       3  refund = new Refund.Builder()...build()    // PENDING
          refund.startProcessing()
       4  txn = processor.processRefund(refund, payment)
       5  "APPROVED"?
            → refund.complete()
              ledgerService.recordRefund(refund, payment)  // reverse pair
              payment.refund()                       // CAPTURED/SETTLED → REFUNDED
              webhookService.dispatchWebhook("refund.completed", payment)
            : refund.fail(); dispatchWebhook("refund.failed", payment)
  └─ [200 OK]  Refund

The refund reuses the same processor that took the payment and appends reverse ledger entries — the ledger stays balanced.

Webhook delivery  →  at-least-once with backoff

WebhookService.dispatchWebhook(eventType, payment)
  1  payload = buildPayload(...)                     // JSON
  2  event = new WebhookEvent(type, paymentId, merchantId, payload)  // PENDING
  3  sig = HMAC-SHA256(payload + merchant.apiKey)    // authenticity + integrity
  4  deliver → 200? event.markDelivered()
              : event.recordAttempt(false)
                attempts < 5 ? schedule nextRetryAt = now + 2^(n-1)s
                             : status = EXHAUSTED     // alert
  ── background ──
  deliverPendingWebhooks(): retry FAILED events whose nextRetryAt has passed

Delivery is at-least-once, so the merchant must dedupe on eventId. Backoff caps at 5 attempts (1, 2, 4, 8, 16s) before EXHAUSTED.

F

Design patterns used

GoF-categorized
Creational
  • Builder — Payment.Builder / Refund.Builder. Many fields (currency, metadata, idempotencyKey); build() validates required merchantId & positive amount.
  • Factory — AppConfig is the only class that says new ConcreteClass() (composition root).
  • Singleton (conceptual) — one CurrencyService is the single source of exchange rates.
Behavioral
  • Strategy ×2 — PaymentProcessor (Card/UPI/Wallet) and FraudCheckStrategy (Rule/ML). Two independent axes of variation.
  • State — Payment guards its lifecycle; each transition method throws on an illegal move.
  • Chain of Responsibility — FraudService runs a list of checks, defence in depth.
  • Observer — WebhookService reacts to payment events and notifies merchants off the hot path.
Structural (+ architectural)
  • Facade — PaymentService hides the 7-step subsystem behind one method.
  • Repository — 6 repos (Payment, Ledger, Merchant, Account, Idempotency, Webhook) decouple domain from storage.
  • Template-style flow — every processor follows validate → process → respond; the skeleton is fixed, the body varies.
Why they cluster: Facade + Strategy + Repository together deliver the Open-Closed Principle — new rails, new fraud detectors, and new storage backends are additions, never edits to the facade. State + Builder keep the Payment immutable and impossible to double-capture; the synchronized IdempotencyService and double-entry LedgerService keep the money correct. → concurrency, exactly-once & reconciliation trade-offs on canvas 3
