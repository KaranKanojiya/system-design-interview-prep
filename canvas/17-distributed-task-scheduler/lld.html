from engine/SchedulerEngine.java
public List<Task> tick() {
  Instant now = Instant.now();
  List<Task> readyToDispatch = new ArrayList<>();

  // Step 1: Check CRON tasks — if next fire time has passed, re-enqueue a clone
  for (Map.Entry<String, CronSchedule> entry : cronTasks.entrySet()) {
    String taskId = entry.getKey();
    CronSchedule schedule = entry.getValue();
    Instant lastFired = cronLastFired.getOrDefault(taskId, Instant.EPOCH);

    Optional<Instant> nextFire = cronParser.getNextFireTime(schedule, lastFired);
    if (nextFire.isPresent() && !nextFire.get().isAfter(now)) {
      cronLastFired.put(taskId, now);
      // The actual task re-creation is handled by the service layer;
      // we signal readiness by including the taskId in the result
    }
  }

  // Step 2: Check dependency-waiting tasks — move any that are now ready
  Set<String> completedIds = new HashSet<>();  // populated externally via markCompleted
  Set<String> nowReady = dependencyResolver.getReadyTasks(completedIds);
  for (String readyId : nowReady) {
    Task task = waitingOnDeps.remove(readyId);
    if (task != null) {
      task.updateStatus(TaskStatus.QUEUED);
      taskQueue.enqueue(task);            // O(log n) heap insertion
    }
  }

  // Step 3: Drain the queue into the dispatch batch
  while (!taskQueue.isEmpty()) {
    taskQueue.dequeue().ifPresent(readyToDispatch::add);
  }

  return readyToDispatch;
}
Why tick() is single-threaded: the TaskQueue (java.util.PriorityQueue) and the internal Maps (waitingOnDeps, cronTasks, cronLastFired) are not thread-safe by design. The scheduler runs tick() on one dedicated loop thread; concurrency lives in the repositories (ConcurrentHashMap) and the strategies (AtomicInteger for RoundRobin). This gives you deterministic ordering with zero locking overhead in the hot path.
from engine/DependencyResolver.java — Kahn's algorithm (verbatim)
public List<String> getTopologicalOrder() {
  if (hasCycle()) {
    throw new DependencyCycleException(
        "Dependency graph contains a cycle — topological sort impossible");
  }

  // 1. Build in-degree map and adjacency (dependsOn -> dependents)
  Map<String, Integer> inDegree = new HashMap<>();
  Map<String, Set<String>> dependents = new HashMap<>();

  for (String node : dependencies.keySet()) {
    inDegree.putIfAbsent(node, 0);
    dependents.putIfAbsent(node, new HashSet<>());
  }
  for (Map.Entry<String, Set<String>> entry : dependencies.entrySet()) {
    String taskId = entry.getKey();
    for (String dep : entry.getValue()) {
      // dep -> taskId (dep must run before taskId)
      dependents.computeIfAbsent(dep, k -> new HashSet<>()).add(taskId);
      inDegree.merge(taskId, 1, Integer::sum);
    }
  }

  // 2. Seed the queue with zero-in-degree nodes
  Queue<String> queue = new ArrayDeque<>();
  for (Map.Entry<String, Integer> entry : inDegree.entrySet()) {
    if (entry.getValue() == 0) queue.add(entry.getKey());
  }

  // 3. BFS — peel off zero-in-degree nodes
  List<String> order = new ArrayList<>();
  while (!queue.isEmpty()) {
    String node = queue.poll();
    order.add(node);
    for (String dependent : dependents.getOrDefault(node, Collections.emptySet())) {
      int newDegree = inDegree.merge(dependent, -1, Integer::sum);
      if (newDegree == 0) queue.add(dependent);
    }
  }

  return order;
}
Why guard with hasCycle() first: Kahn's algorithm will silently return a partial order if a cycle exists — the cycle nodes never reach zero in-degree and are dropped. Doing the DFS 3-coloring check (O(V+E)) upfront lets us fail loudly with a DependencyCycleException that names the involved tasks, instead of silently losing them. Two O(V+E) passes total; still cheap even for 100 K-task DAGs.

public class ExponentialBackoffRetryStrategy implements RetryStrategy {

  private final long initialDelayMs;
  private final long maxDelayMs;
  private final double multiplier;

  public ExponentialBackoffRetryStrategy(long initialDelayMs, long maxDelayMs, double multiplier) {
    if (initialDelayMs <= 0)                 throw new IllegalArgumentException("initialDelayMs must be positive");
    if (maxDelayMs < initialDelayMs)         throw new IllegalArgumentException("maxDelayMs must be >= initialDelayMs");
    if (multiplier <= 1.0)                   throw new IllegalArgumentException("multiplier must be > 1.0");
    this.initialDelayMs = initialDelayMs;
    this.maxDelayMs = maxDelayMs;
    this.multiplier = multiplier;
  }

  @Override
  public boolean shouldRetry(Task task, int attemptNumber, String errorMessage) {
    return attemptNumber <= task.getMaxRetries();
  }

  @Override
  public long getRetryDelayMillis(int attemptNumber) {
    // 1. Compute base delay: initialDelay * multiplier^(attempt-1)
    double baseDelay = initialDelayMs * Math.pow(multiplier, attemptNumber - 1);

    // 2. Cap at maxDelay
    long cappedDelay = (long) Math.min(baseDelay, maxDelayMs);

    // 3. Apply ±10% jitter to prevent thundering herd
    double jitterFactor = 0.9 + ThreadLocalRandom.current().nextDouble() * 0.2;
    return (long) (cappedDelay * jitterFactor);
  }

  @Override
  public String getStrategyName() { return "EXPONENTIAL_BACKOFF"; }
}

Default wiring in AppConfig: new ExponentialBackoffRetryStrategy(1000, 30000, 2.0) — starts at 1 s, doubles each attempt, caps at 30 s. maxRetries lives on the Task itself (default 3), so the strategy is stateless across tasks.

from strategy/retry/FixedIntervalRetryStrategy.java
public class FixedIntervalRetryStrategy implements RetryStrategy {

  private final long fixedDelayMs;

  public FixedIntervalRetryStrategy(long fixedDelayMs) {
    if (fixedDelayMs <= 0) {
      throw new IllegalArgumentException("fixedDelayMs must be positive");
    }
    this.fixedDelayMs = fixedDelayMs;
  }

  @Override
  public boolean shouldRetry(Task task, int attemptNumber, String errorMessage) {
    return attemptNumber <= task.getMaxRetries();
  }

  @Override
  public long getRetryDelayMillis(int attemptNumber) {
    return fixedDelayMs;   // constant, regardless of attempt
  }

  @Override
  public String getStrategyName() { return "FIXED_INTERVAL"; }
}

When to prefer fixed: transient errors with predictable recovery time (e.g., a database restart takes ~5 s regardless of how many retries you've done). Exponential can be excessive when the underlying fault clears at a known cadence.

Why jitter matters: 10 000 tasks all failing at t=0 with a deterministic backoff would retry simultaneously at t=1 s, t=2 s, t=4 s, ... — a thundering herd that would knock over the same downstream service that just failed. ±10 % spreads them across a 200 ms window at t=1 s, 400 ms at t=2 s, 800 ms at t=4 s. AWS SDK, gRPC, Kafka clients all use jittered exponential backoff for exactly this reason.

from strategy/assignment/RoundRobinAssignmentStrategy.java
public class RoundRobinAssignmentStrategy implements TaskAssignmentStrategy {

  private final AtomicInteger counter = new AtomicInteger(0);   // lock-free CAS

  @Override
  public Optional<Worker> assignTask(Task task, List<Worker> availableWorkers) {
    List<Worker> ready = availableWorkers.stream()
        .filter(Worker::isAvailable)
        .collect(Collectors.toList());

    if (ready.isEmpty()) return Optional.empty();

    int index = Math.abs(counter.getAndIncrement()) % ready.size();
    return Optional.of(ready.get(index));
  }

  @Override
  public String getStrategyName() { return "ROUND_ROBIN"; }
}

Thread-safety: AtomicInteger.getAndIncrement() is a single CAS operation — safe for concurrent dispatchers on multiple scheduler threads. Limitation: ignores current worker load — can overload a 2-slot worker just as easily as an 8-slot one. Best when the cluster is homogeneous (same capacity, same hardware).

from strategy/assignment/LeastLoadedAssignmentStrategy.java (verbatim)
public class LeastLoadedAssignmentStrategy implements TaskAssignmentStrategy {

  @Override
  public Optional<Worker> assignTask(Task task, List<Worker> availableWorkers) {
    return availableWorkers.stream()
        .filter(Worker::isAvailable)
        // 1. Sort by currentLoad ascending
        // 2. Break ties by registeredAt ascending (prefer older workers)
        .min(Comparator.comparingInt(Worker::getCurrentLoad)
                .thenComparing(Worker::getRegisteredAt));
  }

  @Override
  public String getStrategyName() { return "LEAST_LOADED"; }
}

Tie-breaker on registeredAt: when two workers have identical load, prefer the older one — it's already proven stable (survived heartbeats), while a freshly-registered worker might be about to fail its first tasks. Complexity: O(W log W) for the stream min; W is typically ≤ 100 in a scheduler tier so this is a rounding error even at 1 K TPS.

extension pattern — from LLD §13.3
public class AffinityAssignmentStrategy implements TaskAssignmentStrategy {

  @Override
  public Optional<Worker> assignTask(Task task, List<Worker> availableWorkers) {
    String requiredTag = task.getPayload().get("required_tag");

    return availableWorkers.stream()
        .filter(Worker::isAvailable)
        .filter(w -> requiredTag == null || w.hasTag(requiredTag))
        .min(Comparator.comparingInt(Worker::getCurrentLoad));
  }

  @Override
  public String getStrategyName() { return "AFFINITY"; }
}

// Wire in AppConfig — ZERO changes to SchedulerService or ExecutionService:
config.setAssignmentStrategy(new AffinityAssignmentStrategy());

Use case: GPU tasks require gpu-tagged workers; high-memory ML jobs need hi-mem workers. Worker tags live on Worker.tags (Set<String>); the strategy filters + falls back to least-loaded within the affinity subset. This is a textbook Open/Closed Principle extension — a whole new class of behavior with zero touches to existing code.

Interview point: production schedulers (Kubernetes scheduler, Nomad, YARN) combine all three via a scoring function: for each candidate worker, sum weighted scores from multiple predicates (fits? tagged? load percentile?). Our Strategy interface is deliberately narrow (assignTask → Optional<Worker>) so a ScoringAssignmentStrategy could compose the primitives without changing SchedulerService.

the transition method — from service/ExecutionService.java (paraphrased)
public void handleTaskFailure(TaskExecution execution, String error) {
  Worker worker = workerRepo.findById(execution.getWorkerId()).orElseThrow();
  worker.decrementLoad();                          // free the slot regardless

  Task task = taskRepo.findById(execution.getTaskId()).orElseThrow();
  int attemptNumber = execution.getAttemptNumber();

  if (retryStrategy.shouldRetry(task, attemptNumber, error)) {
    task.updateStatus(TaskStatus.RETRYING);        // will be re-picked next tick
    // In prod: schedule re-enqueue with retryStrategy.getRetryDelayMillis(attempt)
  } else {
    task.updateStatus(TaskStatus.FAILED);          // terminal — retries exhausted
  }
  taskRepo.save(task);
}

// cancelTask() guard — from service/TaskService.java
public void cancelTask(String taskId) {
  Task task = taskRepo.findById(taskId).orElseThrow(
      () -> new SchedulerException("Task not found: " + taskId));
  TaskStatus current = task.getStatus();
  if (current == TaskStatus.COMPLETED || current == TaskStatus.FAILED) {
    throw new SchedulerException("Cannot cancel task in terminal state: " + current);
  }
  task.updateStatus(TaskStatus.CANCELLED);
  taskRepo.save(task);
}
Why put isTerminal() on the enum: the check appears in at least 4 places — cancelTask (block cancel), Failover.reassignTasks (skip terminal tasks), DependencyResolver.getReadyTasks (COMPLETED unblocks), and MonitoringService.getFailureRate (denominator). Encoding it on the enum instead of scattering if (s == COMPLETED || s == FAILED || ...) across the codebase means adding a new terminal state (e.g., PERMANENTLY_LOST) is a one-line change.

Latency budget (typical dispatch tick): cron scan 0.1 ms (N ≤ 100) · getReadyTasks 1 ms (V+E ≤ 10 K) · queue drain 0.5 ms · getAvailableWorkers 0.5 ms (CHM read) · assignTask O(W log W) < 1 ms · executeTask handoff 0.1 ms = ~3 ms per tick per task. At 1 s tick cadence and 100-task batches, a single scheduler node dispatches ~30 K tasks/min. Work simulation (Step 5) is off the critical path — actual worker latency lives on the worker fleet, not the scheduler.
