Distributed Task Scheduler (Airflow / Celery / Temporal) — High-Level Design

Use case 17 · Canvas 1 of 3. One leader-elected scheduler owns a priority queue and dispatches tasks to a pool of ~1 000 workers; a DAG resolver (Kahn's algorithm) unblocks tasks whose upstreams have completed; a retry engine (exponential backoff + jitter) handles transient failures; a failover service reassigns tasks from dead workers. Correctness is defended by idempotency keys, terminal-state guards, and fencing tokens — at-least-once delivery + idempotent handler = effective exactly-once. A

Problem & requirements

background jobs at scale — Airflow / Celery / Temporal
functional
  • Submit tasks — one-time, delayed, cron (5-field), or DAG-dependent; fields: name, priority, payload, maxRetries, timeoutMillis, dependsOn[].
  • Priority scheduling — CRITICAL > HIGH > MEDIUM > LOW; FIFO tie-break by createdAt.
  • DAG dependencies — Kahn's topological sort; DFS three-colour cycle detection at submission time.
  • Worker pool management — register / deregister; 5 s heartbeat; load + capacity tracking; tag affinity ("gpu", "high-memory").
  • Assignment strategies — Round-Robin (homogeneous) or Least-Loaded (heterogeneous), pluggable via Strategy pattern.
  • Retry with backoff — min(1 s · 2^(n-1), 30 s) × jitter(0.9–1.1); after maxRetries → Dead-Letter Queue.
  • Cron + delayed scheduling — cron expression fires on tick(); delayed tasks wait for scheduledAt.
  • Leader election — Bully algorithm for scheduler coordinator (interview); Raft/etcd in production.
  • Worker failover — heartbeat > 30 s stale → mark DEAD → reset RUNNING tasks → reassign to healthy worker.
  • Task cancellation — allowed only in PENDING / QUEUED / ASSIGNED (not RUNNING or terminal).
  • Monitoring dashboard — task counts by status, worker utilisation, throughput, failure/retry rate, queue depth.
non-functional
  • Task durability — zero data loss: persist to Task Repo before ACK to client.
  • Exactly-once effect — idempotency key + terminal-state guard + fencing token (at-least-once + idempotent handler).
  • Availability 99.99 % — infrastructure service; downstream systems depend on it.
  • Throughput — 10 M tasks/day, ~116 TPS avg, ~1 160 TPS peak, ~5 800 TPS burst.
  • Scheduling latency p99 < 100 ms (queued → assigned).
  • Submit latency p99 < 50 ms (API to ACK).
  • Leader failover p99 < 5 s · worker failover p99 < 30 s (heartbeat timeout).
  • Retry correctness — exp backoff + jitter to break synchronised retry storms.
  • Horizontal scale — add workers with no restart; HPA on queue depth.
  • Retention — 30 days execution history (audit + debugging).
  • CAP — CP for task state / assignment / leader (correctness); AP for monitoring / logs (always visible).
Why this problem is hard: every large system needs background jobs (emails, ETL, ML training, payments). A single-machine cron has no priority, no dependencies, no retries, no observability, and dies with the box. A distributed scheduler must pick exactly one coordinator (else duplicate dispatch), preserve task ordering under priority (else starvation), handle DAG dependencies (else deadlocks), and never double-execute (else double-charge a customer). These are the exact staff-engineer distributed-systems primitives interviewers probe.

Why the numbers seem small but aren't: 116 TPS in isolation is trivial — but each task involves a persist (durable) → enqueue (priority) → dispatch (assignment) → execute (heartbeat) → record (audit) pipeline where every step must be exactly-once-effective. A double-executed payment task is a double-charge; a lost email task is an SLA breach. The scale of coordination is what makes it a staff-level problem, not raw QPS.
Peak vs burst is the interview trap: peak 1 160 TPS is a normal daily maximum; burst 5 800 TPS happens when a batch job submits 100 K tasks at once. The queue must absorb the burst (174 K entries = 174 MB — fits in RAM), the worker pool must NOT be provisioned for burst (that would be 8 700 workers idle 99 % of the time), and the retry engine must NOT synchronise (else the downstream service dies of a thundering herd on top of the burst).

API design

idempotent writes · JWT auth · rate-limited
EndpointPurposeResponse
POST /api/v1/tasksSubmit a one-time, delayed, or cron task. Header: Idempotency-Key. Body: {name, priority, payload, maxRetries, timeoutMillis, delayMillis, cronExpression?}.201 + {task_id, status: PENDING} · 409 on duplicate key

POST /api/v1/workersRegister a new worker in the pool. Body: {hostname, port, capacity, tags[]}. Auth: service token.201 + {worker_id, status: ACTIVE, current_load: 0}
PUT /api/v1/workers/{id}/heartbeatWorker liveness signal — every 5 s. Body: {current_load, cpu_usage_pct, memory_usage_pct}.200 + {heartbeat_recorded_at}
POST /api/v1/scheduler/dispatchManually trigger a scheduling cycle (test/ops override). Production runs on a fixed 1–5 s tick.200 + {dispatched_count}
POST /api/v1/task-groupsCreate a task group (parallel = true / false) then PUT /task-groups/{id}/tasks to add members.201 + {group_id}
GET /api/v1/monitoring/dashboardAggregate: task_status_counts, worker_utilisation, execution_metrics, queue_depth.200 + dashboard JSON

Idempotency contract: every write endpoint accepts Idempotency-Key. Duplicate keys within 24 h return the original response body (never re-execute). For tasks, the natural key is also enforced at the DB layer: UNIQUE INDEX (payload->>'idempotency_key') WHERE payload->>'idempotency_key' IS NOT NULL — belt-and-braces so even a Redis outage can't cause a duplicate task.

The golden rule: task state is CP — durable, ACID, single writer. A lost or double-executed task is a correctness bug that costs money (double-charge) or breaks pipelines (missed SLA). Metrics and logs are AP — always available, eventually consistent. A stale dashboard is fine; an unavailable dashboard during an incident is not.
F

Key design choices (deep-dived on canvas 3)

defend these in the interview
coordination

Bully vs Raft

Bully wins on simplicity — highest-priority alive node becomes leader in ~5 s. NOT partition-safe (split-brain risk). For production: Raft via etcd/Consul — majority-quorum prevents split-brain at the cost of more messages. → canvas 3 · leader election

queue

PriorityQueue over FIFO

CRITICAL tasks (payments) MUST preempt LOW (batch reports). FIFO would let a batch flood block critical writes. Comparator: priority DESC, createdAt ASC. O(log n) enqueue/dequeue. Starvation mitigated by aging (age > threshold → priority bump). → canvas 3 · priority queue

retry

Exp backoff + jitter

delay = min(1 s · 2^(n-1), 30 s) × jitter(0.9–1.1). Without jitter, 1 000 simultaneous failures retry synchronously → thundering herd → cascading failure. With ±10 % jitter, retries spread over a 200 ms window → downstream recovers gradually. → canvas 3 · retry storms

correctness

Effective exactly-once

True exactly-once is impossible (Two Generals + FLP). We layer three defences: (1) client idempotency key, (2) server terminal-state guard, (3) fencing token bumped on reassign. At-least-once + idempotent handler = user perceives exactly-once. → canvas 3 · exactly-once

DAG

Kahn's algorithm

Topological sort in O(V + E). At submit-time, DFS three-colouring rejects cycles (GRAY → GRAY = back edge = DependencyCycleException). At runtime, getReadyTasks(completedSet) promotes any task whose upstreams are all COMPLETED. Fail-fast beats deadlock. → canvas 3 · DAG resolution

failover

Heartbeat + reassignment

Workers send heartbeats every 5 s; failover scans every 10 s; stale > 30 s → DEAD → reassign RUNNING tasks. Total disruption ~30 s (bounded by heartbeat interval). Prod enhancement: SWIM/Serf gossip → O(log N) detection, no single point of detection. → canvas 3 · worker failover

Glossary — one-liners

Priority queuebinary-heap ordering CRITICAL > HIGH > MEDIUM > LOW; FIFO within lane; O(log n) enqueue/dequeue
Kahn's algorithmBFS topological sort — peel zero-in-degree nodes, decrement neighbours, repeat; O(V + E)
DFS three-colouringcycle detection — WHITE/GRAY/BLACK; a GRAY → GRAY back edge means a cycle exists
Bully algorithmleader election — highest-priority alive node wins; simple, O(n²) messages, not partition-safe
Raft consensusproduction alternative to Bully — majority-quorum + log replication; partition-safe
Fencing tokenmonotonically increasing epoch per assignment; stale writes with lower token are rejected
Idempotency keyclient UUID; server stores response for 24 h; duplicate requests return the original
Effective exactly-onceat-least-once delivery + idempotent handler = user perceives exactly-once
Exponential backoff + jittermin(initial · mult^(n-1), max) × rand(0.9, 1.1) — spreads retry storms
Dead-letter queueterminal-failure bucket after maxRetries; pages ops for manual review
Round-Robin assignmentcounter % workers.size() — even distribution over time, O(1)
Least-Loaded assignmentmin(currentLoad), tie-break by registeredAt — capacity-aware, O(n)
SWIM / gossip protocolfailure detection via random peer probes; O(log N) propagation; no single detector
State machinePENDING → QUEUED → ASSIGNED → RUNNING → COMPLETED / FAILED / TIMED_OUT / CANCELLED; guarded transitions
