Bully algorithm — every scheduler node has a numeric priority. The highest-priority ALIVE node becomes the leader. It's what LeaderElectionService.java implements.

// From LeaderElectionService.electLeader()
List<SchedulerNode> alive = allNodes.stream()
    .filter(n -> n.isAlive(ALIVE_TIMEOUT))
    .toList();

SchedulerNode leader = alive.stream()
    .max(Comparator.comparingInt(SchedulerNode::getPriority)
                   .thenComparing(SchedulerNode::getNodeId))
    .orElseThrow();

// Each node self-checks: am I the highest? If yes, claim leadership.
// If a higher-priority node comes back, it "bullies" the current leader out.
  • Election time: O(N) messages. ~seconds on 10 nodes.
  • Split-brain risk: HIGH on partition — both sides may elect their own leader. Requires fencing tokens (see § B) to be safe.
  • Complexity: LOW. ~150 lines of code. Easy to test.
  • Ops burden: LOW. No external cluster. Uses existing DB (DynamoDB) for heartbeats.
When Bully wins: small clusters (3–7 schedulers) where you already trust the DB for coordination and want zero external dependencies. Airflow's HA scheduler uses a similar pattern with a Postgres row lock.

Raft consensus — a majority quorum protocol. Nodes vote for a leader in numbered terms; a candidate wins only if it collects votes from more than N/2 nodes.

// Simplified Raft leader-election state machine
FOLLOWER  ──(election timeout)──►  CANDIDATE
CANDIDATE ──(RequestVote to all)──► collects votes
CANDIDATE ──(majority YES)──►     LEADER  (term = term + 1)
CANDIDATE ──(higher-term seen)──► FOLLOWER
LEADER    ──(heartbeat every 50 ms)──► followers
LEADER    ──(quorum unreachable)──►   step down

// Log replication:
//   Every leader command is appended to a log entry.
//   Leader replicates entries to a majority BEFORE applying.
//   A follower can only vote for a candidate whose log is at least as up-to-date.
  • Election time: 150–500 ms typical (randomised election timeout avoids duel-vote).
  • Split-brain risk: NONE — a leader without quorum immediately steps down. Only ONE side of a partition can have a leader.
  • Complexity: HIGH. Log replication, snapshotting, membership changes are non-trivial. Use a proven library — hashicorp/raft, etcd-io/raft, MicroRaft.
  • Ops burden: MEDIUM. Need an odd number of nodes (3 or 5). Rolling restarts must respect quorum.
When Raft wins: when you need correct-by-construction single-leader guarantees and can afford 3 or 5 dedicated coordinator nodes. It's what powers etcd, Consul, CockroachDB, and Temporal's history service.

ZooKeeper is an external CP coordination store (itself built on the ZAB protocol, close cousin of Paxos/Raft). Leader election is a well-known recipe using ephemeral sequential znodes.

// ZooKeeper leader-election recipe
1. Every candidate creates an EPHEMERAL_SEQUENTIAL child under /scheduler/leader/
     e.g. /scheduler/leader/n_0000000012
2. Candidate lists all children, sorted by sequence number.
3. If MY znode is the lowest sequence, I am the leader.
4. Otherwise: watch the znode immediately below mine.
     When it disappears (session death), re-check step 3.

// Ephemeral = auto-deleted when the client's session dies.
// Sequential = ZK assigns strictly-increasing monotonic sequences.
// Watching only the predecessor avoids the "herd effect" on failover.
  • Election time: ~100–300 ms after session death (tick-based detection).
  • Split-brain risk: NONE on ZK's side — a partitioned ZK follower will refuse writes.
  • Complexity: MEDIUM. The client recipe is small; but you inherit ZooKeeper's operational surface (ensembles, JVM tuning, log compaction).
  • Ops burden: HIGH. You now run a stateful CP cluster (3 or 5 ZK nodes) in addition to your scheduler.
When ZooKeeper wins: when you already have a ZK ensemble (Kafka, Hadoop, HBase shops) and want a battle-tested recipe. Modern alternatives — etcd and Consul — offer the same primitives with a smaller footprint.

Single-master = one scheduler node, no HA. Simpler than any consensus protocol; ships in a day.

// One process. No election. If it crashes, an operator restarts it.
public class Scheduler {
  public static void main(String[] args) {
    while (true) {
      List<Task> ready = engine.tick();
      dispatch(ready);
      sleep(1000);
    }
  }
}
  • Election time: N/A — no election. Recovery = human intervention + process restart (~minutes).
  • Split-brain risk: NONE by construction — there is only ever one.
  • Complexity: TRIVIAL. Zero coordination code.
  • Ops burden: LOW day-to-day, HIGH on incident. No automatic failover means SLA lives and dies with one node.
Only viable when: workload is small (< 100 tasks/min), 30-minute recovery is tolerable, and you can run a standby manually. This is what Celery Beat ships out of the box — a single point of failure for cron scheduling.

Exactly-once semantics — the 4 mechanisms that add up

no double-execution, ever
Foundational fact: true exactly-once delivery is impossible in a distributed system. If the sender times out mid-write, it cannot distinguish "delivered but ACK lost" from "not delivered." What we build instead is at-least-once delivery + idempotent processing — the observed effect is exactly-once.
Idempotency key
Fencing token
Terminal-state guard
At-least-once + idempotent

Idempotency key — a client-generated UUID (or a stable natural key like {taskId}-{dagRunId}-attempt-{n}) that flows end-to-end through every hop.

// 1) Client / scheduler creates the key
String key = task.getId() + "-" + dagRunId + "-attempt-" + attemptNumber;

// 2) Enqueue to SQS FIFO with the key as MessageDeduplicationId
sqs.sendMessage(SendMessageRequest.builder()
    .queueUrl(queueUrl)
    .messageBody(payload)
    .messageDeduplicationId(key)     // SQS dedup window = 5 min
    .messageGroupId(dagRunId)
    .build());

// 3) DB stores UNIQUE(idempotency_key)
INSERT INTO task_executions (idempotency_key, task_id, status, ...)
  VALUES (?, ?, 'RUNNING', ...)
  ON CONFLICT (idempotency_key) DO NOTHING
  RETURNING *;
// If 0 rows returned → duplicate; short-circuit and reuse the prior execution.
  • Retry-safe: retries reuse the same key → same execution row → no duplicate side effects.
  • Attempt suffix matters: if the key were just taskId-dagRunId, SQS FIFO's 5-minute dedup would reject legitimate retries. Include attempt-{n}.
  • Downstream: the same key flows into external services (Stripe, PagerDuty) as their Idempotency-Key header — belt-and-braces across the whole call chain.

Fencing token — a monotonic epoch counter that increments on every leader election. Every dispatched command carries the epoch under which it was issued. Workers reject any command whose epoch is older than what they've already seen.

// Leader claim — DynamoDB atomic counter
UpdateItem:
  PK = "LEADER#scheduler",  SK = "LOCK"
  UpdateExpression: SET epoch = epoch + 1, nodeId = :me, leaseTTL = :now + 30s
  ConditionExpression: "attribute_not_exists(PK) OR leaseTTL < :now"
Returns: { epoch: 6, nodeId: "scheduler-2" }

// Every message emitted by the leader carries the epoch
{ "taskId": "T-42", "dagRunId": "R-9", "epoch": 6, ... }

// Worker validates before executing
long myEpoch = getKnownMaxEpoch();  // cached, refreshed periodically
if (msg.epoch < myEpoch) {
  log.warn("stale leader command, epoch {} < {}, dropping", msg.epoch, myEpoch);
  sqs.deleteMessage(msg);   // don't execute — just drain the stale msg
  return;
}
Why this is essential: the Bully algorithm can produce a brief split-brain during a partition. Without fencing, both leaders enqueue the same cron trigger → double-execution. With fencing, the older leader's messages are dropped harmlessly at the worker.

Terminal-state guard — COMPLETED, FAILED, CANCELLED, and TIMED_OUT are absorbing states. Once a task is in one of them, no further transition is allowed. This is enforced by the state-machine transition table, not by "hope."

// TaskStatus.java
public boolean isTerminal() {
  return this == COMPLETED || this == FAILED
      || this == CANCELLED || this == TIMED_OUT;
}

// TaskService.updateStatus() — reject any transition from a terminal state
public void updateStatus(Task task, TaskStatus target) {
  if (task.getStatus().isTerminal()) {
    throw new IllegalStateTransition(
      "cannot transition " + task.getStatus() + " → " + target);
  }
  // Same enforcement at the DB layer:
  // UPDATE tasks SET status = ? WHERE id = ? AND status NOT IN ('COMPLETED','FAILED',…)
  // If 0 rows updated, the task is already terminal — swallow the update.
}
  • Guards against replay: a delayed message that would re-run a COMPLETED task is rejected at both the app and DB layers.
  • Guards against crash-recovery: a worker that crashed AFTER writing COMPLETED but BEFORE deleting the SQS message → SQS redelivers → next worker sees COMPLETED → no-op.
  • Cancellation is not always available: we explicitly refuse cancel() once the task is already COMPLETED.

The formula:

EXACTLY-ONCE EFFECT = AT-LEAST-ONCE DELIVERY + IDEMPOTENT PROCESSING

Each layer catches what the others miss. The customer observes each task running once, even though messages may be delivered multiple times.

CAP split — different subsystems, different guarantees

the key interview insight

A distributed task scheduler is not one CAP problem. Task correctness is CP; observability is AP. Knowing which is which is what separates a passing answer from a staff-level answer.

SubsystemChoicePACELCWhy
Scheduler leader / task queueCPPC / ECSingle-writer via leader election. Two leaders = duplicate cron fires. Refuse to enqueue rather than double-fire.
Task repository (state machine)CPPC / ECPostgres primary (or DynamoDB conditional write). QUEUED → RUNNING must be a CAS. Isolation via the DB, not via hope.
DAG dependency stateCPPC / ECTransform must NOT start until Extract is truly COMPLETED. A stale read = premature execution = garbage data.
Task priority queueCPPC / ECHIGH-priority task must overtake LOW. Ordering is an invariant, not a hint.
Worker heartbeatAPPA / ELGossip-style updates every 10 s; 30 s ALIVE_TIMEOUT tolerates 2–3 missed beats. Delayed failure detection is an acceptable cost of eventual consistency.
Execution audit logAPPA / ELAppend-only, idempotent. Missing the last 5 s of logs is acceptable — recover from workers on reconnect.
Metrics / dashboardAPPA / ELRedis cache with 5 s TTL. Best-effort. 100 dashboard clients polling for strong reads would waste RCU for zero operational benefit.
Auto-scaler input (queue depth)APPA / EL60-second CloudWatch metric is fine — scaling decisions are not urgent.
The boundary matters: CP path (task state, leader lease, DAG deps) uses DynamoDB conditional writes and strongly-consistent reads. AP path (heartbeats, metrics, logs) reads from Redis or eventually-consistent DDB. Never cross the paths — do NOT use the AP cache to drive a CP decision.

DynamoDB throttled—everything, with retries (5 ms → 50 ms)

Design principle — fail narrow, not wide
  • DDB throttling should not stop SQS processing.
  • Scheduler down should not stop already-dispatched tasks.
  • Worker crash should not stop the leader from scheduling other work.
  • DLQ pile-up on one task type should not delay unrelated task types.
  • Every failure mode has an explicit "what continues" answer — if you can't answer it, the design is wide-brittle.

DAG resolution — Kahn's topological sort + cycle detection

O(V + E), safe and standard

Every task can declare upstream dependencies. Before any task can be dispatched, we must (1) verify the DAG has no cycles and (2) produce a valid execution order. Kahn's algorithm does both in one pass.

Example DAG

ETL pipeline: Extract feeds Transform and Validate; both feed Load; Load triggers Notify. Note the diamond in the middle.

Kahn's algorithm — step by step
// Step 1: build indegree map
indeg = { Extract:0, Transform:1, Validate:1, Load:2, Notify:1 }

// Step 2: enqueue all indeg == 0 nodes (roots)
queue = [ Extract ]
output = [ ]

// Step 3: drain the queue
while queue not empty:
  n = queue.pop()
  output.append(n)
  for m in successors(n):
    indeg[m] -= 1
    if indeg[m] == 0:
      queue.push(m)

// Step 4: check termination
if len(output) < total_nodes:
  raise CycleDetected      // leftover indeg > 0
return output

Trace on our DAG:

  1. Pop Extract. Decrement Transform → 0, Validate → 0. Queue: [Transform, Validate].
  2. Pop Transform. Decrement Load → 1. Queue: [Validate].
  3. Pop Validate. Decrement Load → 0. Queue: [Load].
  4. Pop Load. Decrement Notify → 0. Queue: [Notify].
  5. Pop Notify. Queue empty. Output = [Extract, Transform, Validate, Load, Notify] — length 5 == node count. No cycle.
Cycle detection — DFS with 3-colour marks

Kahn's algorithm detects cycles by termination check (unprocessed nodes = a cycle). An alternative is DFS with WHITE / GRAY / BLACK — better when you want to point at the offending edge for a user error message.

// WHITE = unvisited, GRAY = on current DFS stack, BLACK = fully explored
color = { every node: WHITE }
def dfs(n):
  color[n] = GRAY
  for m in successors(n):
    if color[m] == GRAY:
      raise CycleDetected(back_edge = n → m)   // back-edge into stack
    if color[m] == WHITE:
      dfs(m)
  color[n] = BLACK

for n in all_nodes:
  if color[n] == WHITE:
    dfs(n)

Key rule: encountering a GRAY node during traversal ⇒ a back-edge ⇒ a cycle. The path from that GRAY node back down the recursion stack is the actual cycle to report.

Complexity + practical notes
  • Time: O(V + E) — every node and every edge is visited once.
  • Space: O(V) for the indegree map + queue.
  • Caching: for CRON DAGs that run daily, cache the topological order and re-validate only when the DAG definition changes. This is what Airflow does with DAG-parse caching.
  • Dynamic dependencies: if tasks can add dependencies at runtime (rare), re-run Kahn's each tick. O(V + E) is cheap.
  • Multiple valid orders: Kahn's produces one topological order out of many valid ones. If the queue is a min-heap by priority, you get "prioritised topological order" — useful.

Retry & backoff — the formula walkthrough

exponential + jitter + cap + DLQ
Pure exponential backoff
// From ExponentialBackoffRetryStrategy.java
delay = base * 2^attempt

attempt = 1 → 1000 ms
attempt = 2 → 2000 ms
attempt = 3 → 4000 ms
attempt = 4 → 8000 ms
attempt = 5 → 16000 ms
...
// grows unboundedly — will exceed the SLA on attempt ~10

Problem: unbounded growth, plus synchronised retries — if a downstream outage fails 10 K tasks at the same instant, they all retry at exactly T+1s, T+3s, T+7s, … a thundering herd that keeps the downstream service on its knees.

Full-jitter recipe (AWS builder's library)
// Full jitter: pick uniformly from [0, base * 2^attempt]
delay = random(0, base * 2^attempt)

attempt = 1 → uniform(0, 1000)
attempt = 2 → uniform(0, 2000)
attempt = 3 → uniform(0, 4000)
attempt = 4 → uniform(0, 8000)
...
// Spreads retries evenly. Downstream sees ~constant load.

Our implementation uses ±10 % jitter around the exponential base — a milder variant that keeps some ordering guarantee. Full-jitter is stronger but sacrifices predictability. Both are correct answers; know both.

Cap on max delay
// Without a cap, delay grows unboundedly
delay = min(base * 2^attempt, maxDelayMs)

maxDelayMs = 30_000        // 30 seconds
attempt = 10 → min(1024 s, 30 s) = 30 s   // capped
  • Prevents pathological cases where a task waits an hour between retries.
  • Cap should be smaller than your SLA (5 min for a task = 30 s max delay).
  • Combine with a max-attempts count — otherwise a broken task retries forever at the cap.
Dead-letter queue after N attempts
// SQS redrive policy
{
  "deadLetterTargetArn": "arn:aws:sqs:...:tasks-dlq",
  "maxReceiveCount": 3      // after 3 failed receives → DLQ
}

// Application-level
if (attemptNumber > task.getMaxRetries()) {
  task.updateStatus(FAILED);        // terminal
  dlq.publish(task, lastError);     // alarm on DLQ depth > 0
  pageOnCall(task, lastError);      // human eyes
}

DLQ is where poison pills end up — messages that will fail no matter how many times you retry them. Always alarm on DLQ depth > 0 for > 5 min.

When to give up — the DLQ contract
  • Retry budget per task: maxRetries = 3 by default; override per task type.
  • Retry budget per queue: SQS maxReceiveCount = 3 — after 3 failed receives, message → DLQ.
  • Alarm on: DLQ.depth > 0 for > 5 min; page on-call.
  • Runbook: inspect DLQ payload → categorise (bug · bad input · downstream outage) → fix or drop.
  • Never: auto-replay DLQ back into the main queue without human triage — that's how poison pills flood you a second time.
Thundering-herd mitigation, in one line: delay = min(random(0, base × 2^attempt), maxDelay). Randomises the retry moment (spreads herd), grows with attempts (backs off from persistent failures), caps at a bounded worst-case (respects the SLA), and combined with maxRetries + DLQ keeps the queue from growing forever.

Bottlenecks & mitigations

the 8 things that will kill you
1 · Single leader = throughput ceiling

Symptom: as tasks/sec grows, the single leader can't parse cron entries, resolve dependencies, and dispatch fast enough. Airflow hits this ceiling around 1 000 tasks/min.

Mitigation: shard by task-group. Partition the DAG namespace across N leaders (each owning a hash of groupId). Leader election still runs — but each of the N leaders is authoritative only for its slice. Combine with consistent hashing so re-balancing on failover is minimal.

2 · Task queue depth grows unboundedly under burst

Symptom: a burst of 500 K DAG submissions floods SQS in 30 seconds. Workers can only drain at 3 000/sec cluster-wide. Queue depth explodes; client polling starves.

Mitigation: burst absorption + back-pressure. SQS holds the burst (14-day retention). Auto-scale workers on queue-depth signal. If depth > threshold for > 5 min, return 429 Too Many Requests to submission API — clients back off. Priority topics ensure critical tasks still flow.

3 · DAG topological sort cost on every tick

Symptom: a DAG with 10 000 tasks is re-topo-sorted on every scheduler tick (1 s). O(V + E) is cheap once, expensive at 1 Hz × 10 K nodes.

Mitigation: cache the indegree map. Store the initial topological order on DAG-submit. On completion, decrement successors' indegree in O(fan-out). Only recompute if the DAG definition itself changes (rare). This turns the tick from O(V+E) into O(fan-out per completion).

4 · Worker heartbeat storm

Symptom: 10 000 workers all heartbeat at T=0, T=10, T=20, … → DynamoDB write spike every 10 s → throttling. Same on failover — every worker registers within a 1-second window.

Mitigation: randomised heartbeat intervals. Instead of exactly 10 s, use 10 s ± random(0, 3 s). Spreads writes uniformly over 13 s. Same jitter applied on worker startup smooths the registration burst.

5 · Retry storm on downstream outage

Symptom: a downstream microservice (say, the transform HTTP API) goes down. Every task calling it fails. All retries pile up on the same broken endpoint. When it comes back, it's crushed by the retry backlog.

Mitigation: circuit breaker + backoff. Track error-rate per downstream. If > 50 % for a rolling window, open the circuit — fail-fast without calling. Half-open probes gradually restore. Combined with exponential backoff, the retry rate stays bounded.

6 · Cron fire-time contention

Symptom: 10 000 DAGs all fire at 0 0 * * * (midnight UTC). At T=0 the scheduler tries to enqueue 10 K root tasks in the same second → DynamoDB partition hot → throttling.

Mitigation: jittered fire times. When a DAG is defined with 0 0 * * *, internally add a random offset in [0, 60 s] per DAG (stored once, stable across runs). Same UX ("fires around midnight"), but the actual fire is spread over a minute.

7 · Failover split-brain

Symptom: a network partition isolates the current leader. The other side re-elects. Both leaders think they're in charge → duplicate cron fires + double execution.

Mitigation: fencing tokens + lease renewal. Every leader claim increments a monotonic epoch. Workers reject messages from stale epochs. Even if two leaders briefly coexist, only one produces effective work.

8 · Execution history growth

Symptom: every task run records ~1 KB of history. At 1 M runs/day = 1 GB/day = ~365 GB/year in DynamoDB. Cost balloons; query performance degrades.

Mitigation: 30-day hot retention + S3 archive. DynamoDB TTL removes rows after 30 days. A CDC stream to Kinesis Firehose lands full history in S3 as Parquet, partitioned by day. Historical queries hit Athena (cheap). Hot dashboard hits DDB (fast). Best of both.

Rule of thumb — measure before you mitigate: every mitigation above adds complexity. In an interview, spell out the metric that would trigger each mitigation (e.g. "shard when a single leader exceeds 800 dispatch/s p95 for 5 min"). Otherwise you're premature-optimising and the interviewer will call it out.

Queue ordering Priority queue (min-heap by TaskPriority) FIFO HIGH tasks must overtake LOW even if enqueued later. FIFO buries urgent work behind bulk backfills.
Leader election Bully + fencing tokens Raft · ZooKeeper Bully is cheapest for small clusters; fencing tokens close the split-brain gap. Raft is correct-by-construction but adds a coordinator layer. Migrate at 10× scale.
Delivery guarantee At-least-once + idempotent = effective exactly-once true exactly-once True exactly-once delivery is impossible in a distributed system (FLP). At-least-once + idempotent processor is the standard workaround.
Queue durability Durable (SQS · Service Bus) in-memory queue In-memory loses tasks on crash. Durable queue is the boundary between "trust the scheduler" and "trust the platform".
Worker assignment LeastLoaded RoundRobin RoundRobin ignores heterogeneous worker capacity — a slow worker gets the same load as a fast one, becomes the bottleneck. LeastLoaded balances by current load.
Retry backoff Exponential + jitter fixed interval Fixed interval creates thundering herd on shared downstream outages. Exponential + jitter spreads retries.
Retry execution Async re-enqueue synchronous retry in worker Sync retry ties up a worker slot for minutes. Async re-enqueue frees the slot immediately; another worker (or same, later) picks it up.
External coordination DynamoDB atomic counter ZooKeeper · etcd · Consul Already using DDB for task state; no need for a second stateful cluster. ZK / etcd / Consul only if you already have them.
State persistence model Snapshot state (mutable rows) event sourcing Event sourcing gives perfect replay (Temporal's model) but adds complexity. Snapshot state + audit log is simpler and covers the interview bar.
DAG lifecycle Static definition + dynamic runs fully dynamic dependencies Static DAG lets us pre-validate cycles at submit time and cache topo order. Dynamic-only is powerful but rarely needed.
Worker dispatch model Worker pull (poll SQS) scheduler push (RPC) Pull scales trivially — add a worker, it starts polling. Push requires the scheduler to track every worker's address and load.
Tenancy Multi-tenant with per-tenant quotas single-tenant per cluster Single-tenant burns fleet capacity. Multi-tenant + quotas per tenant (max queue depth, max concurrent workers) gives isolation without over-provisioning.

35-minute interview walkthrough

the answer, timed
0 – 5 min · clarify scope & priorities
  • "Airflow-style DAGs, Celery-style task queue, or Temporal-style workflows? I'll assume Airflow-like: DAGs of tasks with dependencies, cron + one-time triggers, retries."
  • "How big — small team (1 K tasks/day) or platform-scale (1 M tasks/day)? I'll design for 1 M tasks/day = ~12 tasks/sec peak."
  • "Exactly-once required? Yes → I'll add idempotency keys and fencing tokens."
  • "Multi-tenant?" Assume yes → per-tenant quotas and priority.
5 – 10 min · capacity + core APIs
  • Numbers: 1 M tasks/day / 86 400 s ≈ 12/s avg, 5× burst ≈ 60/s. 10 KB task payload + 1 KB history = ~11 MB/s ingest = trivial.
  • API surface: submitDAG, submitTask, cancelTask, getStatus, listRuns, describeDAG.
  • SLA: submit → dispatched < 2 s p99; task-completed → dependents unblocked < 1 s p99.
  • Storage: DDB for task state (hot), S3 for history (cold, 30 d TTL DDB → S3).
10 – 20 min · draw architecture · submit + execute flows
  • Client → API Gateway → SchedulerService (composition-root of TaskService, WorkerService, ExecutionService, SchedulerEngine).
  • Scheduler is HA via Bully leader election — one leader owns cron parsing + dependency resolution.
  • Leader pushes to SQS FIFO (idempotencyKey = MessageDeduplicationId). Workers pull.
  • Workers claim via DynamoDB conditional write (QUEUED → RUNNING). Execute. Write COMPLETED. Publish TaskCompleted event → scheduler unblocks dependents.
20 – 25 min · exactly-once & retry deep dive
  • Exactly-once = at-least-once (SQS) + idempotent processor (DDB CAS + terminal-state guard + downstream Idempotency-Key).
  • Fencing tokens close the split-brain gap.
  • Retry = exponential backoff with ±10 % jitter, capped at 30 s, DLQ after 3 attempts.
  • Poison pills alert on-call — do not retry forever.
25 – 30 min · DAG resolution & leader election
  • DAG validation on submit: Kahn's topological sort — O(V+E). Reject cycles synchronously with the offending back-edge.
  • On task completion, decrement indegree of successors — O(fan-out). No full re-sort each tick.
  • Leader election: Bully by priority + tie-break by nodeId. Fencing tokens for split-brain.
  • Lease-based leadership: 30 s TTL, renewed every 10 s. 20 s grace covers GC pauses.
30 – 35 min · bottlenecks & Q&A
  • Bottlenecks + fixes: (1) leader ceiling → shard by group. (2) queue depth → back-pressure + auto-scale. (3) heartbeat storm → jittered intervals. (4) cron thundering herd → jittered fire times. (5) retry storm → circuit breaker. (6) history growth → 30 d + S3.
  • "What would you do at 10× scale?" → migrate leader election to Raft (or delegate to etcd); event-source the state (Temporal-style).
  • "Where's the single point of failure?" → the elected leader for ~30 s during failover. New enqueues pause; running work continues.

30-second pitch: "A leader-elected scheduler (Bully + fencing) parses cron and resolves DAG dependencies (Kahn's O(V+E)). Ready tasks are enqueued to SQS FIFO with an idempotency key. Workers pull, claim via DynamoDB conditional write (CAS on QUEUED → RUNNING), execute, and mark COMPLETED. Retries use exponential backoff with jitter, capped, and a DLQ after 3 attempts. Task state is CP (correctness); heartbeats and metrics are AP (best-effort). Exactly-once effect = at-least-once delivery + idempotent processing at every layer."
Interview red flags to avoid:
• "I'll guarantee exactly-once delivery." (impossible — say "exactly-once effect via idempotency")
• "The scheduler is a single node." (no failover story)
• "Retry indefinitely." (poison pill risk — always DLQ after N)
• "Use in-memory queue." (loses tasks on crash)
• "Poll DynamoDB every second for completed tasks." (event-driven scales; polling doesn't)

Glossary — one-liners

Bully algorithmLeader election where the highest-priority alive node self-elects.
RaftConsensus protocol; a majority quorum elects a leader per term and replicates a log.
Fencing tokenMonotonic epoch counter incremented on every election; workers reject stale-epoch commands.
Idempotency keyStable identifier that lets a receiver detect and deduplicate retries end-to-end.
Terminal stateAn absorbing state in the task lifecycle (COMPLETED, FAILED, CANCELLED, TIMED_OUT) — no further transitions.
At-least-once deliveryEvery message is delivered at least once; duplicates are possible and the consumer must handle them.
Exactly-once effectObserved outcome = one execution, achieved by at-least-once delivery + idempotent processing.
Kahn's algorithmTopological sort in O(V+E) using an indegree map and a queue of zero-indegree nodes.
Back-edgeA DFS edge from a GRAY node back into the current stack — proof of a cycle.
Full jitterRetry-delay formula that picks uniformly from [0, base × 2^attempt]; kills thundering herd.
DLQDead-letter queue — where messages go after N failed processing attempts; alarms on depth > 0.
CAS (Compare-And-Swap)Atomic conditional write; DynamoDB's ConditionExpression gives us CAS across regions.
LeaseA time-bounded lock that auto-expires without a renewal — safe under crashes.
ALIVE_TIMEOUTThreshold beyond which a stale heartbeat means the node is presumed dead (30 s in our design).
PACELCExtension of CAP: if partition → C or A; else → Latency or Consistency.
Split-brainTwo nodes each believing they are the leader; produces duplicate work; prevented by quorum or fencing.
Poison pillA message that will never be processable no matter how many times you retry — sends to DLQ.
