A

Problem & requirements

clarify first
functional
  • Topics + partitions — create a topic with N partitions and RF replicas. Partition count is the max parallelism.
  • Produce — send with optional key (routes to a partition), optional explicit partition, and ackMode (0/1/all).
  • Consume — poll from committed offset for (group, topic, partition); does NOT auto-advance offset.
  • Commit offset — explicit; drives at-most-once vs at-least-once semantics.
  • Consumer groups — subscribe / unsubscribe; range rebalance on membership change.
  • Retention — time-based (delete > retention.ms) OR log compaction (latest value per key).
  • Cluster — register / deregister brokers; elect controller (lowest ID); handle failures.
  • Lag & metrics — per-topic throughput, per-group lag = latestOffset − committedOffset.
non-functional
  • Throughput 1 M+ msg/s per cluster, horizontally scalable.
  • Latency p99 < 10 ms (acks=1), < 50 ms (acks=all).
  • Durability zero loss with acks=all + min.insync.replicas ≥ 2 + RF ≥ 3.
  • Availability 99.99% — survive a single broker without data loss.
  • Ordering strict within a partition (monotonic offset); no global order.
  • Scalability linear — add partitions for throughput, brokers for storage/compute.
  • Retention configurable per-topic (ms, bytes, or compaction).
  • Lag monitoring real-time, sub-second granularity — the #1 ops metric.

Why sequential I/O is the whole point: commit log = append-only ⇒ pure sequential writes. Sequential HDD ≈ 600 MB/s, random HDD ≈ 100 KB/s. That's a 6000× advantage. Combined with page cache + sendfile() zero-copy, one broker can shove ~600 MB/s at hardware limits without JVM heap pressure.
Rule of thumb — partition count: partitions = max(target_throughput / per_partition_throughput, target_throughput / per_consumer_throughput). Per-partition ≈ 10 MB/s. Err on more — you cannot easily reduce partitions after creation (would break key→partition hash).

Data model

7 core entities
Message (in-memory + on-disk record)
Message
  id         String   // UUID
  key        String   // nullable → RR partition
  value      String   // payload
  headers    Map<S,S> // correlation / trace ids
  topic      String
  partition  int      // set by router
  offset     long     // set by CommitLog.append
  timestamp  Instant
  producerId String

Built via Message.Builder — enforces required (topic, value), defaults optional. offset and partition start at −1 and are stamped broker-side.

Partition + ISR
Partition
  topicName, partitionId
  leaderId          String
  replicaIds        List<String>
  inSyncReplicaIds  List<String>   // ISR
  addToIsr / removeFromIsr / isLeader

CommitLog                            // 1 per partition
  List<Message> log
  AtomicLong currentOffset            // high watermark
  append(msg) → offset                // synchronized O(1)
  read(fromOffset, max) → List        // bounds-checked
  truncateBefore(offset)              // retention
Topic + retention
Topic
  name              String  // unique
  partitionCount    int     // hard to change
  replicationFactor int     // RF, typ. 3
  retentionMs       long    // default 7d
  config            Map     // overrides

RetentionPolicy
  retentionMs, retentionBytes
  cleanupPolicy: DELETE | COMPACT | COMPACT_DELETE
ConsumerGroup + Offset
ConsumerGroup
  groupId               String
  subscribedTopics      Set<String>
  members               Map<consumerId, ConsumerInstance>
  assignments           Map<consumerId, List<PartitionAssignment>>

Offset                                       // per (group,topic,part)
  groupId, topicName, partitionId
  committedOffset  long   // −1 = start from beginning
  lastCommitTime   Instant
  commit(newOffset)

Composite key groupId-topic-partition. In Kafka the value lives inside the compacted __consumer_offsets topic.

The offset is the API: committed offset = "I've processed everything below this". Lag = latestOffset − committedOffset. Move the offset back = replay. Move it forward = skip. That's the entire consumer contract.
F

Key design choices (deep-dived on canvas 3)

defend these
core data structure

Append-only commit log

O(1) append, O(1) seek by offset, sequential I/O (~600 MB/s). NOT deleted on consumption ⇒ replay + multi-consumer for free. → canvas 3 · Commit Log

partitioning

Hash on key ▸ round-robin

Same key → same partition → per-key ordering (userId → user activity ordered). Null key → RR for max throughput (metrics). → canvas 2 · LLD

durability

ISR + acks=all + min.isr=2

Zero loss with RF=3. acks=1 loses data on leader crash before replication. acks=0 = fire-and-forget. Configurable per producer. → canvas 3

consumer coord.

Range rebalance

One partition → one consumer within a group. Sort + divide + remainder-first. Kafka default; prod uses CooperativeSticky for incremental.

delivery

At-least-once (default)

Commit AFTER processing → duplicates possible → consumer must be idempotent. Exactly-once = idempotent producer + dedup on consumer.

retention

Time-based OR compaction

Time-based (delete > 7 d) for events / logs. Compaction (latest per key) for changelogs, CDC, materialized views. Strategy pattern — swap at runtime.
