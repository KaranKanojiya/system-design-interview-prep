The CommitLog — verbatim

the single most important class
the code (append + read, from CommitLog.java)
public class CommitLog {
  private final String topicName;
  private final int partitionId;
  private final List<Message> log;                // append-only
  private final AtomicLong currentOffset;         // next offset

  public synchronized long append(Message msg) {
    long assigned = currentOffset.getAndIncrement();
    msg.setOffset(assigned);
    log.add(msg);
    return assigned;                              // O(1)
  }

  public synchronized List<Message> read(
          long fromOffset, int maxMessages) {
    if (fromOffset < 0 || fromOffset >= log.size()
        || maxMessages <= 0) return emptyList();
    int start = (int) fromOffset;
    int end   = Math.min(start + maxMessages, log.size());
    return new ArrayList<>(log.subList(start, end));
  }

  public synchronized void truncateBefore(long offset) {
    log.removeIf(m -> m.getOffset() < offset);         // retention
  }
}
why this shape
  • Append-only ⇒ pure sequential I/O. Sequential HDD ~600 MB/s vs random ~100 KB/s = 6000×.
  • AtomicLong offset ⇒ every message gets a strictly monotonic 64-bit id, no coordination beyond synchronized on the log.
  • Bounds-checked read — no exception on past-tail reads; consumers poll an empty list and back off.
  • subList = O(1) seek + O(k) copy. Production: sparse index maps offset → segment file byte position (~4 B per 4 KB batch).
  • truncateBefore here uses removeIf (O(n)); production deletes whole segment files (O(1) per segment).
  • The log is the database of record — nothing external stores the messages themselves. Only metadata (KRaft) and offsets (__consumer_offsets compacted topic) live outside the log.
  • Zero-copy consume in prod — sendfile() shovels bytes from page cache → NIC without user-space copy or JVM heap allocation.
Complexity summary: append O(1) · read(fromOffset, k) O(k) · getLatestOffset O(1) · getEarliestOffset O(1) · truncateBefore O(n) in-memory / O(segments) on-disk.

Partition routing cascade & strategies

Strategy pattern × 3
code (verbatim)
public class HashPartitioningStrategy
    implements PartitioningStrategy {

  public int assignPartition(String key, int count) {
    if (key == null) return 0;
    return Math.abs(key.hashCode()) % count;
  }
}
semantics
  • Same key → same partition, always. This is the whole reason for keys.
  • All events for userId=alice land in one partition ⇒ per-user ordering.
  • Uses Java hashCode; Kafka uses Murmur2 for better distribution.
  • Failure mode: hot key (viral user, one product) ⇒ hot partition. Salt the key or pick a compound key.
  • Cannot change partition count after creation without breaking the mapping.
code (verbatim)
public class RoundRobinPartitioningStrategy
    implements PartitioningStrategy {

  private final AtomicInteger counter = new AtomicInteger(0);

  public int assignPartition(String key, int count) {
    return Math.abs(counter.getAndIncrement() % count);
  }
}
semantics
  • Even distribution, key IGNORED (even if present).
  • Max throughput — all partitions equally loaded.
  • NO ordering — two events for the same entity may land on different partitions.
  • Use for metrics collection, log aggregation, load-testing producers. Anywhere ordering ≺ throughput.
code (from MessageRouter.routeToPartition)
// Strategy 1 — explicit partition wins
if (record.getPartition() >= 0)
    return record.getPartition();

// Strategy 2 — key-based hash
if (record.getKey() != null)
    return Math.abs(record.getKey().hashCode()) % partitionCount;

// Strategy 3 — round-robin fallback
return Math.abs(roundRobinCounter.getAndIncrement()) % partitionCount;
why a cascade
  • Explicit ▸ key ▸ RR — most-specific first, most-general last.
  • Producers rarely set explicit partition — reserved for tests, replay, and rack-aware placement.
  • Key handling here duplicates HashPartitioningStrategy — this is Kafka's DefaultPartitioner logic, kept inside the router so plain ProducerRecord routing works without swapping strategies.
  • Round-robin uses its own AtomicInteger counter — no shared state with the standalone RoundRobinPartitioningStrategy.

Delivery strategies — retries & exactly-once

DeliveryStrategy
code (verbatim)
private static final int MAX_RETRIES = 3;
private static final double FAILURE_RATE = 0.05;

public boolean deliver(Message msg, String consumerId) {
  for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
    boolean acked = ThreadLocalRandom.current().nextDouble() >= FAILURE_RATE;
    if (acked) return true;                      // success
    // no ack → retry; the consumer may see duplicates
  }
  return false;                                    // all attempts failed
}
semantics
  • Default guarantee. Commit AFTER processing.
  • Retry until acked or MAX_RETRIES exhausted. Duplicates on retry are the consumer's problem.
  • Consumer must be idempotent — dedup by message.id or database unique constraint.
  • Common pattern: consumer writes to a table with UNIQUE(msg_id) — duplicate insert fails silently.
code (verbatim)
private final Set<String> deliveredIds =
    ConcurrentHashMap.newKeySet();

public boolean deliver(Message msg, String consumerId) {
  String id = msg.getId();
  if (deliveredIds.contains(id)) {
    // DUPLICATE — silently skip (idempotent)
    return true;
  }
  deliveredIds.add(id);
  // first delivery — process it
  return true;
}
semantics
  • Idempotent consumer — dedup by message.id in a Set.
  • In production the Set is Redis (SETNX + TTL) or a DB with a unique constraint — the JVM Set doesn't survive restarts.
  • Combined with Kafka's idempotent producer (producerId + seq number for broker-side dedup) ⇒ end-to-end exactly-once.
  • Kafka's full EOS also adds transactions for atomic read-process-write across topics.

Storage strategies — retention vs compaction

StorageStrategy
TimeBasedRetentionStrategy (verbatim)
public boolean shouldRetain(Message msg, long retentionMs) {
  long ageMs = Instant.now().toEpochMilli()
             - msg.getTimestamp().toEpochMilli();
  return ageMs <= retentionMs;
}

Delete-based. Default retentionMs = 604 800 000 (7 d). Prod deletes whole segment files, not individual messages.

LogCompactionStrategy (essence)
public List<Message> compact(List<Message> msgs) {
  List<Message> nullKey    = new ArrayList<>();
  Map<String, Message> latest = new LinkedHashMap<>();
  for (Message m : msgs) {
    if (m.getKey() == null) nullKey.add(m);
    else {
      Message existing = latest.get(m.getKey());
      if (existing == null || m.getOffset() > existing.getOffset())
        latest.put(m.getKey(), m);
    }
  }
  // null-key messages ALWAYS survive
  return concat(nullKey, latest.values());
}

Latest-per-key. Offsets are preserved, not renumbered. Tombstone = message with value=null — marks a key for deletion during compaction (retained for delete.retention.ms).

Which one? Time-based for event streams, logs, metrics (bounded by window). Compaction for changelogs, CDC, materialized views, KTables, and __consumer_offsets itself (bounded by unique key count). Combine as cleanup.policy=compact,delete to compact THEN drop old segments.

Request sequences (call chains)

produce · consume · commit · subscribe
produce (POST /topics/{t}/messages)
Controller.produce
  → MessageQueueService.send
    → ProducerService.send(record, ackMode)
       1. topicRepository.findByName → partitionCount
       2. resolvePartition(record)          // explicit ▸ hash ▸ RR
       3. partitionManager.getPartition     // CommitLog
       4. new Message.Builder(topic, val)
             .key(k).partition(p).headers(h).build()
       5. commitLog.append(msg)             // synchronized · O(1)
                                            // assigns monotonic offset
       6. replicationEngine.replicate(msg, partition, ackMode)
       7. metricsService.recordProduce(topic, msg)
       8. return offset
consume (GET /topics/{t}/messages)
Controller.poll
  → MessageQueueService.poll
    → ConsumerService.poll(group, topic, part, max)
       1. coordinator.getCommittedOffset(g, t, p) → committedOffset
       2. partitionManager.getPartition(t, p)     → CommitLog
       3. commitLog.read(committedOffset, max)   // O(1) seek + O(k) copy
       4. map Message → ConsumerRecord           // immutable snapshot
       5. metricsService.recordConsume(topic, ...)
       6. return List<ConsumerRecord>            // offset NOT advanced
commit (POST /topics/{t}/commit)
Controller.commit
  → MessageQueueService.commit
    → ConsumerService.commit(g, t, p, offset)
       → coordinator.commitOffset(g, t, p, offset)
         // committedOffsets["g-t-p"] = offset
         // next poll starts here → at-least-once
subscribe + rebalance
Controller.subscribe
  → MessageQueueService.subscribe
    → ConsumerService.subscribe(g, cId, topic, partitionCount)
       1. if group absent → coordinator.createGroup(g)
       2. group.subscribe(topic)
       3. new ConsumerInstance(cId, g, "localhost")
       4. coordinator.joinGroup(g, consumer)
       5. coordinator.rebalance(g, partitionCount)   // range assign
          // sort consumerIds; perConsumer = N/M;
          // first (N%M) consumers get one extra partition
          // group.setAssignment(cId, List<PartitionAssignment>)
