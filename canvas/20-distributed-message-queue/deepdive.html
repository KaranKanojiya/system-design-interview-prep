Scaling strategy — three orthogonal axes

throughput · storage · consumption
add partitions

throughput ↑

More partitions ⇒ more parallel producers & consumers. Topic 6 → 12 = 2× throughput. Caveat: you cannot easily shrink partition count — hash(key)%N mapping would break. Err high at creation.

add brokers

storage & compute ↑

Reassignment via kafka-reassign-partitions.sh or Cruise Control. 3 → 6 brokers = 2× disk + 2× network. Controller moves partition leaderships during the shuffle.

add consumers

consumption rate ↑

Max consumers = partition count. More consumers than partitions ⇒ some sit idle. Consumer-group rebalance is automatic. To increase parallelism further, first add partitions.

B

ISR + acks + min.insync.replicas — the zero-loss recipe

the star of the interview
acks=0 (fire & forget)

~0.5 ms

LOWEST durability. Producer returns immediately. Message may be lost if leader crashes before disk flush. No retry possible (producer never knew there was a problem). Use: high-volume metrics / logs.

acks=1 (leader only)

~2–5 ms

MEDIUM. Durable on leader's disk. Lost if leader crashes between write and follower fetch. Kafka's historical default. Good balance for user-activity streams.

acks=all (all ISR)

~5–20 ms (~50 ms cross-rack)

HIGHEST. Leader waits for every ISR replica to write. With RF=3 & min.insync.replicas=2: zero loss if ≥ 2 brokers alive. Rejects (NotEnoughReplicasException) if ISR too small — CP behavior.

The zero-loss recipe (verbatim from any Staff+ interview): acks=all · replication.factor=3 · min.insync.replicas=2 · unclean.leader.election.enable=false. That's it. Any subset weakens the guarantee. Ask about at least two of those in an interview — most candidates only name acks=all.
ISR maintenance — how a replica falls out
Partition orders-2  (RF=3)

  Broker-1 (LEADER):  [0 .. 20]
  Broker-2 (ISR):     [0 .. 20]   // caught up
  Broker-3 (ISR):     [0 .. 8]    // 2 s behind → still ISR

// Broker-3 falls > 10 s behind (replica.lag.time.max.ms):

  Broker-3 (OUT):     [0 .. 8]    // REMOVED from ISR
  ISR = [B1, B2]

// Broker-3 recovers → fetches from leader → catches up → re-added.
min.insync.replicas — the safety net
acks=all · min.insync.replicas=2 · RF=3

Scenario 1 — all 3 alive
  ISR = [B1, B2, B3]  → 3 >= 2 → WRITE OK

Scenario 2 — one replica down
  ISR = [B1, B2]      → 2 >= 2 → WRITE OK

Scenario 3 — two replicas down
  ISR = [B1]          → 1 < 2 → WRITE REJECTED
                                 NotEnoughReplicasException
                                 producer retries or gives up

// This is CP behavior — availability sacrificed to guarantee durability.

Exactly-once semantics (EOS) — the interview trap

idempotent producer + transactions
layer 1 — idempotent producer (broker dedup)
Producer stamps every record with:
  producerId   (assigned by broker)
  sequenceNum  (per (producer, partition))

Broker keeps per-partition:
  Map<producerId, lastSequenceNum>

On write:
  if seq == lastSeq + 1  → accept
  if seq <= lastSeq       → DUPLICATE, silently drop
  if seq >  lastSeq + 1  → OutOfOrderSequenceException

// This prevents duplicates from producer retries.
// Kafka config: enable.idempotence=true (default since 3.0).
layer 2 — transactions (atomic read-process-write)
1. producer.beginTransaction()
2. consumer.poll() → messages
3. process(messages) → results
4. producer.send(outputTopic, results)         // buffered
5. producer.sendOffsetsToTransaction(
       offsets, groupId)                       // commit offsets in same txn
6. producer.commitTransaction()                // atomic flush

// Steps 4–5 are atomic — either both visible or neither.
// Consumer isolation.level=read_committed skips aborted txns.
// Crash during commit → txn coordinator times out → aborts → replay from committed offset.
What our code does: ExactlyOnceDeliveryStrategy models only the consumer-side idempotent dedup (a Set of processed message IDs) — the second layer. Full Kafka EOS also needs idempotent producers on the write side and (for stream processing) transactions to atomically commit output-topic writes with input-topic offsets. Our code is a teaching simplification.

Consumer group rebalancing — Range vs Sticky vs Cooperative

stop-the-world vs incremental
algorithm (verbatim from ConsumerGroupCoordinator)
consumerIds.sort(String::compareTo);
int M = consumerIds.size();
int perConsumer = partitionCount / M;
int remainder   = partitionCount % M;
// first `remainder` consumers get 1 extra partition

Example — 7 partitions, 3 consumers: A→[0,1,2], B→[3,4], C→[5,6].

character
  • Simple + deterministic. Easy to reason about.
  • High partition movement on any change — nearly all partitions reassigned. Consumer must rebuild any in-memory state.
  • Skew on multi-topic subs — same consumer index gets partition 0 across all topics; that consumer becomes hot.
  • Fine for single-topic, low-membership-churn workloads.

RoundRobinAssignor: flatten all (topic, partition) pairs across all subscribed topics; deal them round-robin to consumers.

  • Better than Range for multi-topic subscriptions — evens skew.
  • Still full reshuffle on membership change.

StickyAssignor: optimise for two goals — even load AND minimise movement from the previous assignment.

  • Only moves what it must.
  • Still stop-the-world — all consumers pause during the rebalance protocol.

CooperativeStickyAssignor — Kafka's production default since 2.4.

  • Incremental rebalance: only partitions that need to move are revoked; the rest keep flowing.
  • Two rebalance rounds instead of one — first revoke, then reassign — but no full stop-the-world pause.
  • Static membership (group.instance.id) further reduces spurious rebalances on rolling restarts.

Bottlenecks & solutions

click a card to open

Hot partition (the classic)

Symptom: one partition sees 10× the traffic of the others — one broker's CPU pegs at 100 % while others idle. Consumer lag on that partition grows unbounded.

Cause: key skew. Viral user, best-selling product, one big tenant. Hash partitioning is deterministic: same key → same partition → all traffic for that key on one broker.

Fixes:

  • Salt the key — for hot keys append a random suffix (userId + "-" + rand(0,10)) so writes spread; consumer must know to fan-in on read.
  • Custom partitioner — sub-partition hot keys explicitly (routing table for the top-N).
  • Composite key — (userId, sessionId) instead of userId. Trades per-user ordering for per-session ordering + spread.
  • Accept the skew — if per-key ordering is non-negotiable (e.g., account balance events), scale up that broker (bigger disk + NIC) and cap the number of hot partitions per broker.

Consumer lag runaway

Symptom: lag = latestOffset − committedOffset keeps growing. Alert.

Diagnose: is producer rate up (traffic spike) or consumer rate down (GC, downstream DB slow)? Compare produce & consume MB/s per topic. If lag on one partition only → hot partition (above).

Fixes, in order:

  • Scale consumers up to partition count (free — no rebuild).
  • Beyond that, add partitions (requires producer restart to see the new topology and re-hash keys).
  • Reduce max.poll.records if processing is CPU-bound and blocking heartbeats.
  • Move downstream I/O off the consumer thread — async / batch writes to the DB.

Rebalance storm

Symptom: consumers repeatedly join / leave / are evicted; every rebalance pauses the whole group for seconds; lag oscillates.

Cause: long GC pauses miss the session timeout · slow processing exceeds max.poll.interval.ms · rolling restarts without stable IDs.

Fixes:

  • Static membership — set group.instance.id. Restart within the session timeout is a no-op.
  • CooperativeStickyAssignor — incremental rebalance eliminates the stop-the-world pause.
  • Tune session.timeout.ms up (30–60 s), heartbeat.interval.ms down (~ session/3).
  • Increase max.poll.interval.ms if per-batch processing is slow.

Data loss on leader failure (acks=1)

Timeline: T1 producer sends → T2 leader writes + acks (=1) → T3 leader crashes BEFORE follower replicates → T4 controller elects follower as new leader → message M is gone.

Fix: the zero-loss recipe (section B). acks=all + min.insync.replicas=2 + RF=3 + unclean.leader.election.enable=false. Trade ~5–20 ms of latency for zero loss.

Unclean leader election

Scenario: ISR = ∅ (all in-sync replicas dead). An out-of-sync replica has messages up to offset 900; the (now-dead) leader had up to 1000.

Option A — unclean.leader.election=false (default since 1.0): partition OFFLINE until an ISR replica recovers. Zero loss. CP behavior.

Option B — unclean.leader.election=true: the out-of-sync replica becomes leader; offsets 901–1000 are lost forever. Partition available immediately. AP behavior.

Choose CP for financial data, AP for metrics / logs. This is CAP in action.

Controller failure / split brain

Impact: no new topic creation, no leader elections; existing traffic continues on last-known leaders.

Detection & recovery: ZK ephemeral znode expires OR KRaft Raft leader heartbeat lost → new controller elected (lowest brokerId in our code; Raft leader in KRaft). Typically < 5 s.

Split brain prevention: KRaft's Raft quorum (2f+1 controllers, needs majority) or ZK's ephemeral znode make double-election impossible — only one controller can hold the lock at a time.

Retention runaway — disk fills up

Symptom: broker disk at 100 % → new writes fail. Cascading: producer buffer fills → producer crashes.

Fixes:

  • Two knobs, not one: retention.ms AND retention.bytes. Whichever hits first triggers cleanup.
  • Per-topic overrides — noisy topics get shorter retention.
  • Tiered storage (Kafka 3.6+): hot on local NVMe (7 d), cold on S3 (30 d+). Consumer transparently reads either tier.
  • Alert at 70 %, add brokers and reassign before 90 %.

Zombie fencing (producer / consumer restarts)

Producer zombie: old producer instance keeps sending after a new one starts → duplicates or out-of-order. Fix: transactional producer with transactional.id — the second producer.init() fences the first (broker rejects its writes).

Consumer zombie: old consumer holds a partition assignment after the coordinator moved it. Fix: generation ID — every rebalance bumps a generation counter; commits from an old generation are rejected. Automatic in Kafka.

Interview walkthrough — timing strip

30–45 min answer
phase-by-phase
  • P1 · Opening (1 min) — "I'll design a Kafka-style queue: append-only commit log per partition; producers append at O(1) with configurable ack modes; consumers pull by offset; consumer groups share partitions for parallel load-balanced consumption."
  • P2 · Requirements (3 min) — FR: produce, consume, commit, subscribe, retention, cluster mgmt. NFR: 1M+ msg/s, p99 < 10 ms, zero-loss with acks=all, per-partition ordering, linear scaling.
  • P3 · API (2 min) — POST /topics, POST /topics/{t}/messages, GET /topics/{t}/messages, POST /commit, POST /subscribe.
  • P4 · Data model (3 min) — Message (id, key, value, headers, topic, partition, offset, ts), Topic (partitionCount, RF, retentionMs), Partition (leader, replicas, ISR), ConsumerGroup, Offset, BrokerNode.
  • P5 · High-level arch (8 min) — commit log per partition · MessageRouter cascade · ReplicationEngine with acks · ConsumerGroupCoordinator (join / leave / rebalance / offsets) · retention cleaner · controller / KRaft.
  • P6 · Deep dives (12 min) — pick 2–3 of: ISR + acks + min.isr (zero-loss recipe), hot partition fixes, EOS (idempotent producer + transactions), cooperative rebalance, log compaction vs retention, unclean leader election (CAP).
  • P7 · Scaling (5 min) — three axes (partitions / brokers / consumers) · lag alerts · tiered storage · KRaft over ZK.
  • P8 · Follow-ups (5 min) — cloud mapping (MSK / Event Hubs / Pub/Sub) · monitoring (lag is #1) · schema evolution (Confluent Registry) · MirrorMaker for multi-DC.
green flags vs red flags

Green:

  • You say "commit log" not "message broker". You know why the append-only shape wins.
  • You describe the zero-loss recipe as 4 knobs: acks=all · RF=3 · min.isr=2 · unclean.leader.election=false.
  • You separate idempotent producer from transactions when discussing EOS.
  • You mention consumer lag as the #1 operational metric.
  • You mention CooperativeSticky over Range rebalance and static membership.
  • You call out hot partition without being asked.

Red:

  • "Kafka is exactly-once by default" — no, at-least-once is default. EOS needs specific config.
  • "Just add partitions" — you cannot easily shrink; producers need restart to see new topology.
  • Confusing consumer groups with consumers — same groupId shares partitions; different groupId reads independently.
  • Suggesting global ordering — Kafka only guarantees per-partition order.
  • Ignoring controller failover behavior.
  • "Store offsets in Redis" — __consumer_offsets already handles it, durably.
