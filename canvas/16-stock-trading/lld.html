The match — LimitOrderStrategy.matchAgainstAsks

verbatim · price-time priority · partial fills
from strategy/order/LimitOrderStrategy.java
// WALK-THROUGH (Buy Limit $105 for 200 shares):
//   Ask side: $103×80 · $104.50×100 · $106×50
//   Step 1: Match 80 @ $103 → Trade. Remaining = 120.
//   Step 2: Match 100 @ $104.50 → Trade. Remaining = 20.
//   Step 3: $106 > $105 limit → STOP. Remaining 20 rests as bid at $105.

private void matchAgainstAsks(Order buyOrder, OrderBook book, List<Trade> trades) {
  double priceLimit = buyOrder.getPrice();      // buyer's maximum acceptable price

  while (buyOrder.getRemainingQuantity() > 0 && book.hasAsks()) {
    PriceLevel bestAsk = book.getBestAsk();     // O(log N) — TreeMap firstEntry()
    if (bestAsk == null || bestAsk.isEmpty()) break;

    // PRICE CHECK: only match if ask price is at or below buyer's limit
    if (bestAsk.getPrice() > priceLimit) {
      break;                                    // no more matchable asks — remainder rests
    }

    Order sellOrder = bestAsk.peekFirst();      // FIFO — earliest seller at this price
    if (sellOrder == null) break;

    int    fillQty   = Math.min(buyOrder.getRemainingQuantity(),
                                sellOrder.getRemainingQuantity());
    double fillPrice = sellOrder.getPrice();    // execute at PASSIVE (maker) order's price

    Trade trade = new Trade(
        buyOrder.getOrderId(),  sellOrder.getOrderId(),
        buyOrder.getUserId(),   sellOrder.getUserId(),
        buyOrder.getSymbol(),   fillPrice, fillQty
    );
    trades.add(trade);

    buyOrder.fill(fillQty, trade);              // updates status → PARTIALLY_FILLED or FILLED
    sellOrder.fill(fillQty, trade);
    bestAsk.updateQuantityAfterFill(fillQty);

    if (sellOrder.isFilled()) {
      bestAsk.removeFirst();                    // FIFO pop — next order at this level moves up
    }
    if (bestAsk.isEmpty()) {
      book.removeBestAsk();                     // TreeMap.pollFirstEntry — level gone
    }
  }
}

// After matching:
//   if (buyOrder.getRemainingQuantity() > 0 && buyOrder.isActive()) {
//     book.addOrder(buyOrder);   ← unfilled remainder rests in bids at $105
//   }
Why fillPrice = sellOrder.getPrice() (the passive order's price): the resting sell order was there first — the buyer is the "aggressor" who crossed the spread. Exchange convention: maker gets their price, taker pays it. This also incentivises makers (rebate) and disincentivises takers (fee) — the "maker-taker" fee model. Selling at $103 (the resting price) instead of $105 (buyer's limit) is a $2 discount to the buyer — that's price improvement, and Reg NMS requires it if the venue can do better than NBBO.

strategy/order/LimitOrderStrategy.java
public List<Trade> execute(Order order, OrderBook book) {
  List<Trade> trades = new ArrayList<>();
  if (order.getSide() == OrderSide.BUY) {
    matchAgainstAsks(order, book, trades);        // match at ask ≤ limit
    if (order.getRemainingQuantity() > 0 && order.isActive()) {
      book.addOrder(order);                       // unfilled → rest as bid
    }
  } else {
    matchAgainstBids(order, book, trades);        // match at bid ≥ limit
    if (order.getRemainingQuantity() > 0 && order.isActive()) {
      book.addOrder(order);                       // unfilled → rest as ask
    }
  }
  return trades;
}

Rules: Buy Limit $105 only matches asks ≤ $105 · Sell Limit $95 only matches bids ≥ $95. Unfilled quantity rests in the book (provides liquidity) until matched, cancelled, or day's end. Most retail orders are limit.

strategy/order/MarketOrderStrategy.java
public List<Trade> execute(Order order, OrderBook book) {
  List<Trade> trades = new ArrayList<>();
  if (order.getSide() == OrderSide.BUY) {
    // priceLimit = Double.MAX_VALUE → no price check, sweep asks
    matchAgainstAsks(order, book, trades, Double.MAX_VALUE);
  } else {
    matchAgainstBids(order, book, trades, 0.0);   // sweep bids down to 0
  }
  return trades;    // never rests — unfilled market orders cancel
}

Slippage risk: a market buy for 1000 shares in a thin book fills 100 @ $100, then 200 @ $105, then 300 @ $110, then 400 @ $120 — avg $114. That's walking the book. Smart clients check depth first; naive clients pay the spread. Never rests in the book.

stop-loss + stop-limit — triggered promotion

if (order.getType() == OrderType.STOP_LOSS) {

// LIFECYCLE:
// 1. User places STOP_LOSS at trigger=$95 (currently trading at $100).
// 2. Order does NOT enter the book yet — held in a "pending trigger" store.
// 3. Trigger monitor watches trades.SYMBOL. On any trade at price ≤ $95:
//      trigger monitor emits new MARKET order → engine matches it.
// 4. Result: stop-loss "kicks in" and sells at whatever the market offers.

// STOP_LIMIT (better protection): trigger=$95, limit=$94. If price hits $95,
//   place LIMIT sell at $94 → won't fill below $94 (protects from flash crash).

Why stops don't sit in the book: a resting sell at $95 would show as an ask level and be matched by any buy that crosses it. But a stop-loss says "only after the price falls to $95" — it's a conditional order. So it lives in a separate trigger store; the engine sees it only after promotion.

Matching algorithm — price-time vs pro-rata

how ties at same price are broken
Price-time priority (default)
Pro-rata (options / futures)
mixed / weighted
rule: best price wins; at same price, earliest order fills first
// This is what our LinkedList inside PriceLevel implements — insertion order:
LinkedList<Order> orders;
orders.addLast(order);        ← new order goes to the back
Order first = orders.peekFirst(); ← oldest fills first

// SCENARIO — three resting bids at $100:
//   A: 100 shares @ 09:15:01
//   B:  50 shares @ 09:15:02
//   C: 200 shares @ 09:15:03
// Incoming sell market for 200 shares:
//   fill 100 from A (A fully filled, removed from queue)
//   fill  50 from B (B fully filled)
//   fill  50 from C (C partially filled — remaining 150 stays at head)

Universal at NYSE, NASDAQ, LSE, NSE (India). Rewards liquidity providers for showing up early — the first bid at $100 gets priority forever until it's filled or cancelled. Modifying an order (change qty or price) loses time priority — that's why platforms let you cancel + re-place separately.

rule: incoming volume divided proportionally across all orders at best price
// SCENARIO — three resting bids at $100:
//   A: 100 shares (25 % of level)
//   B: 200 shares (50 % of level)
//   C: 100 shares (25 % of level)
// Total at level = 400. Incoming sell market for 100 shares.
//
// Pro-rata: each gets its % share:
//   A: 100 × 25% = 25 shares filled  (75 remaining)
//   B: 100 × 50% = 50 shares filled  (150 remaining)
//   C: 100 × 25% = 25 shares filled  (75 remaining)

Used by: CME futures (crude, gold), some interest-rate products, part of Eurex. Why: for large institutional books, time priority creates a "race to be first" that rewards latency arms-race spending. Pro-rata neutralises that — it's about size, not speed. Downside: gaming — traders inflate their order size to grab more of the fill.

rule: first M % time-priority, rest pro-rata

Some exchanges combine both: the first-in order at each price gets top-of-book priority (typical: 40 %) but the rest of the level is distributed pro-rata. This preserves the incentive to show up early while diluting the latency-race intensity.

NYSE Options uses a hybrid: customer > public customer > firm proprietary priority classes, then time within class. NSE India uses strict price-time. Bitcoin exchanges (Binance, Coinbase) use strict price-time.

Order state machine — guarded transitions

from model/Order.java
the transitions (verbatim)
public void markOpen() {
  if (status != OrderStatus.PENDING_RISK) {
    throw new IllegalStateException(
        "Cannot open order in state " + status + ". Order: " + orderId);
  }
  this.status = OrderStatus.OPEN;
  this.updatedAt = Instant.now();
}

public void fill(int qty, Trade trade) {
  // Guard: only OPEN or PARTIALLY_FILLED orders can be filled
  if (status != OrderStatus.OPEN && status != OrderStatus.PARTIALLY_FILLED) {
    throw new IllegalStateException(
        "Cannot fill order in state " + status + ". Order: " + orderId);
  }
  if (qty <= 0 || qty > getRemainingQuantity()) {
    throw new IllegalArgumentException(
        "Invalid fill qty " + qty + " for remaining " + getRemainingQuantity());
  }
  this.filledQuantity += qty;
  this.trades.add(trade);
  this.updatedAt = Instant.now();

  // Transition based on whether fully filled
  if (filledQuantity >= quantity) {
    this.status = OrderStatus.FILLED;
  } else {
    this.status = OrderStatus.PARTIALLY_FILLED;
  }
}

public void cancel() {
  // Can cancel from OPEN or PARTIALLY_FILLED (cancels REMAINDER only)
  if (status != OrderStatus.OPEN && status != OrderStatus.PARTIALLY_FILLED) {
    throw new IllegalStateException(
        "Cannot cancel order in state " + status + ". Order: " + orderId);
  }
  this.status = OrderStatus.CANCELLED;
  this.updatedAt = Instant.now();
}

public void reject() {
  if (status != OrderStatus.PENDING_RISK) {
    throw new IllegalStateException(
        "Cannot reject order in state " + status + ". Order: " + orderId);
  }
  this.status = OrderStatus.REJECTED;
  this.updatedAt = Instant.now();
}
Why encode transitions in the model, not the service: the service can (and will) be called concurrently by the matching engine, cancel API, admin console, and reconciliation jobs. If guards live in the service, a rogue caller can just order.setStatus(FILLED). In the model there is no setter — only guarded transitions. An IllegalStateException is your last line of defence against a bug that would corrupt an order's audit trail.
success path
PENDING_RISK
  ↓ markOpen()           // risk passed
OPEN
  ↓ fill(qty, trade)     // first match
PARTIALLY_FILLED         // rests in book
  ↓ fill(qty, trade)     // last match
FILLED                   // terminal — settlement next
failure / cancel paths
PENDING_RISK
  ↓ reject()             // margin fail / halt
REJECTED                 // terminal

OPEN / PARTIALLY_FILLED
  ↓ cancel()             // user cancels remainder
CANCELLED                // terminal

// IllegalStateException on any other transition

Latency budget (typical happy path): Validate + persist (Aurora sync insert) 3 ms · Risk checks (3 × Redis reads) 2 ms · Block margin (DDB CAS) 3 ms · Kafka publish (acks=all) 2 ms · Engine dequeue + match (in-memory) < 1 ms · Trade Kafka publish 1 ms · Position update (DDB CAS) async — off critical path. ACK to client: ~11 ms end-to-end. Matching engine itself: < 1 ms (in-memory, no network). Everything above ~5 ms is I/O — the algorithm is a rounding error.
