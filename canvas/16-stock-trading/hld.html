Stock Trading Platform (NASDAQ · NYSE · Robinhood) — High-Level Design

Use case 16 · Canvas 1 of 3. Two planes, one design: the order plane (CP — every order must persist, no double-fills, correctness is regulatory) and the market-data plane (AP — a 50 ms stale price is fine for display, matching still reads the real book). At the heart sits a single-threaded matching engine per symbol whose in-memory TreeMap order book matches with price-time priority. Click a component, then step both flows.

A

Problem & requirements

orders CP · market-data AP
functional
  • Place order — market, limit, stop-loss, stop-limit. Fields: symbol · side · type · qty · price · validity.
  • Cancel / modify — cancel resting orders; modify = cancel + re-place (loses time priority).
  • Matching engine — price-time priority: best price wins; at same price, earliest order wins (FIFO).
  • Order book — bids (desc price) / asks (asc price) per symbol; publish top 5–20 depth levels.
  • Pre-trade risk — margin check · position limit · circuit-breaker · rate limit. Reject BEFORE the book.
  • Real-time market data — LTP, best bid/ask, volume, OHLCV via WebSocket to 500 K concurrent clients.
  • Portfolio & P&L — positions, avg cost, realized (FIFO or AvgCost) + unrealized (mark-to-market).
  • Settlement (T+1) — end-of-day netting; move cash + shares between clearing accounts.
  • Audit trail — every order & state change immutably logged (SEC Rule 613 · SEBI · WORM S3).
non-functional
  • Order latency p99 < 10 ms (API → ACK) · matching latency p99 < 1 ms per match.
  • Tick-to-client p99 < 50 ms · burst 1 M msg/sec (NBBO consolidation).
  • Throughput 50 M orders/day (~2 K OPS avg) · 22 K OPS peak · 110 K OPS burst at open.
  • Availability 99.999 % during market hours (~2 sec/day) — regulators watch this.
  • Durability zero data loss for orders — Kafka acks=all, WAL to disk, replay from log on crash.
  • Consistency strong (CP) for orders + trades (single-writer per symbol) · AP for market data.
  • No double-fills, no phantom trades — deterministic single-threaded matching per symbol.
  • Recoverability < 30 s failover — replay from Kafka offset rebuilds order book.
  • Regulatory SEC Rule 613 (CAT), SIP consolidation, best-execution (Reg NMS / NBBO).

Why the numbers look small but are scary: 22 K OPS is trivial in isolation — but each order needs durable persistence + risk check + deterministic match + trade persistence + notification, all under 10 ms p99. If risk-check p99 spikes to 20 ms you serialize the whole fleet; if the matching engine leader hangs you lose the exchange. The design is dominated by tail latency and correctness — not raw throughput.
The market-open (9:30 AM) problem: 50× spike + hot symbols (top 100 tickers see 80 % of the volume) + everyone reading the same order book. Mitigations: partition by symbol (one engine thread per ticker), Kafka partition = symbol (ordered delivery), Redis snapshot of L2 book for display so risk checks don't hit the engine, circuit breakers that halt trading if price band breached.

Data model — write path (CP) vs read path (AP)

right store per access pattern
write path (Aurora PG · DynamoDB)
Order                       // Aurora PG, sharded by symbol
  order_id (PK)             // "ORD-20260426-000001"
  user_id, account_id
  symbol, side, order_type  // enums
  price, trigger_price      // nullable for MARKET
  quantity, filled_quantity
  status                    // state machine enum
  idempotency_key (UNIQUE)  // dedup writes
  placed_at, accepted_at    // TIMESTAMP(6) μs precision
  filled_at, cancelled_at

Trade                       // Aurora PG, immutable
  trade_id (PK)             // "TRD-20260426-000001"
  buy_order_id, sell_order_id (FK)
  symbol, price, quantity
  traded_at                 // TIMESTAMP(6)
  settlement_date           // T+1
  settlement_status         // PENDING/SETTLED/FAILED

Position                    // DynamoDB
  (user_id, symbol, product) // composite PK
  quantity, avg_cost
  realized_pnl
  version                   // optimistic lock (CAS)

Account                     // DynamoDB
  account_id (PK)
  balance, blocked_margin
  used_margin, version
  // invariant: balance + blocked + used = total
read path (Redis · in-memory · Timestream)
Redis md:{symbol}           // JSON blob, 500 ms TTL
  ltp, open, high, low
  best_bid, best_ask
  volume, upper_circuit
  updated_at

Redis book:{symbol}:l2      // top 20 levels each side
  bids: [{price, qty, orders}, ...]
  asks: [{price, qty, orders}, ...]
  // refreshed every 100 ms from engine

OrderBook (JVM heap)        // matching engine ONLY
  bids: TreeMap<Double, PriceLevel>
        // Comparator.reverseOrder()
  asks: TreeMap<Double, PriceLevel>
        // natural order (asc)
  PriceLevel: LinkedList<Order>
        // FIFO — time priority
  orderIndex: Map<String, Loc>
        // O(log N) cancel

Timestream ohlcv_1m         // TS-series
  (symbol, ts) → o, h, l, c, v
  // 5 aggregations: 1m, 5m, 15m, 1h, 1D

S3 audit/                    // WORM append-only
  yyyy/mm/dd/hh/orders.ndjson
  yyyy/mm/dd/hh/trades.ndjson
  // 7-year retention (SEC Rule 613)
The golden rule: cache for display, read the live book for matching. Redis md:{symbol} being 300 ms stale is fine for a watchlist tick — but the matching engine ALWAYS matches against its in-memory OrderBook, never against Redis. If Redis lags, users see a stale LTP briefly; nobody gets a bad fill because the engine's book is the source of truth.
F

Key design choices (deep-dived on canvas 3)

defend these
matching

Single-threaded per symbol

One thread per ticker. Zero locks, deterministic, replayable from Kafka. Different symbols parallelize across cores. LMAX Disruptor pattern. → canvas 3 · matching architecture

correctness

Price-time priority (FIFO at price)

Best price wins; at same price, earliest order fills first. TreeMap (bids desc / asks asc) + LinkedList queue per level. Universal rule at NASDAQ / NYSE. → canvas 3 · correctness

CAP split

Orders CP · Market data AP

Orders + trades = CP (single-writer, Kafka acks=all, Aurora sync repl). Market data = AP (Redis TTL 500 ms, dropped-tick OK). Boundary at the trader's screen. → canvas 3 · CAP

pre-trade

Risk before the book

Chain of responsibility: MarginCheck → PositionLimit → CircuitBreaker. Reads Redis (sub-ms). Fail-fast. NEVER let a rejectable order into the engine. → canvas 3 · risk checks

partitioning

Kafka partition = symbol

All RELIANCE orders → one Kafka partition → ONE engine thread. Ordered delivery per symbol. Add new engine node = give it a partition. Hot symbol on its own beefy box. → canvas 3 · sharding

recovery

Kafka replay = the WAL

Engine crashes → new leader replays orders.{symbol} from last committed offset → same trades. Same input, same output. In-memory book rebuilds in seconds. → canvas 3 · leader-follower

Glossary — one-liners

Order bookper-symbol pair of sorted collections: bids desc + asks asc, each price level = FIFO queue
Price-time prioritymatch best price first; at same price, earliest order fills first (universal exchange rule)
Spreadbest ask − best bid; narrow = liquid, wide = illiquid
LTPLast Traded Price — most recent execution price
NBBONational Best Bid & Offer — Reg NMS requires fills at NBBO or better across US venues
Circuit breakerprice band (typically ±20 %) — order rejected if outside; market-wide halt on index moves
Market vs limit orderMARKET = fill at any price · LIMIT = fill only at price-or-better; unfilled limits REST in book
Partial fillonly some of the quantity matched; remainder either rests (limit) or cancels (market)
T+1 settlementtrade today, cash + shares change hands next business day (US & India 2023)
SIPSecurities Information Processor — consolidates quotes across all US venues into NBBO
FIX 4.4Financial Information eXchange — the tag-value protocol used by institutional order routing
SEC Rule 613 (CAT)Consolidated Audit Trail — every order & state change must be reported for 7 years
