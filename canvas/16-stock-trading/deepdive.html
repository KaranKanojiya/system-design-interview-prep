Matching engine architecture — how to run it fast & correct

the concurrency question

decision matrix
one thread per symbol · zero locks · deterministic

Why single-threaded? A matching engine must process orders in strict arrival order — Order A before Order B at the same price ⇒ A fills first (time priority). Multi-threaded matching on the same order book needs locks; locks are:

  • Slow. 50–200 ns per acquire — dominates the 1 μs match budget.
  • Non-deterministic. Thread scheduling varies across restarts. Replay from Kafka can't produce the same trades.
  • Bug-prone. A partial fill across two price levels must be atomic → nested locks → deadlock risk.

Single-threaded is FASTER than multi-threaded here: zero lock contention, zero cache-line bouncing (shared mutable state kills L1), predictable p99, easier correctness. LMAX Exchange processes 6 M orders/sec on ONE thread. CPU is never the bottleneck; network I/O is (handled separately).

// Zone 1: Ingress ring (multi-producer, one consumer per shard)
Kafka orders.RELIANCE ──► RingBuffer ──► RELIANCE-thread
Kafka orders.TCS      ──► RingBuffer ──► TCS-thread
Kafka orders.INFY     ──► RingBuffer ──► INFY-thread

// Zone 2: Match (single-threaded — 100 ns loop)
while (true) {
  Order o = ringBuffer.take();       // lock-free — no mutex
  OrderBook book = orderBooks.get(o.symbol);
  List<Trade> trades = strategy.execute(o, book);
  publishTrades(trades);              // async, batched
}

// Zone 3: Publish (separate thread — never blocks match loop)
horizontal scale via symbol partitioning

One thread per symbol is fine for 5 K symbols on a beefy 96-core box — but for 50 K symbols, or for redundancy, you shard symbols across engine instances:

// Kafka topic: orders.{symbol} — partitionKey = symbol
// One partition per hot symbol, many symbols per partition for cold tail.

Engine Instance 1: consumes partition for {AAPL, MSFT, ...}
Engine Instance 2: consumes partition for {GOOG, AMZN, ...}
Engine Instance 3: consumes partition for {small-caps ...}

Consistent hashing on symbol → engine. Add capacity = add engines.
Rebalance = drain partition, transfer order book snapshot, reassign.

Hot-symbol problem: if RELIANCE takes 80 % of the day's volume, one engine gets hammered. Mitigation: dedicated engine for top-N hot symbols, shared engine for the tail. Rebalance based on daily observed volume, not name-hash.

Why NOT shard by user: the same order book has BOTH a user's buy and someone else's sell — they must meet in the same engine. Partitioning by user would split the book across engines, requiring cross-partition matching (⇒ locks ⇒ we're back to square one). Symbol is the natural sharding axis for order books.

how the exchange survives a crash

Each engine instance is a leader for its symbol shard, with 2 follower replicas. Followers consume the same Kafka partition + tail the leader's trade output — they hold a warm order book.

// Normal operation:
Leader RELIANCE:      consumes orders.RELIANCE @ offset 1_234_567 → matches
Follower A RELIANCE:  consumes orders.RELIANCE @ offset 1_234_567 (silent tail)
Follower B RELIANCE:  consumes orders.RELIANCE @ offset 1_234_567 (silent tail)

// Leader crashes:
1. Kafka consumer-group heartbeat timeout (2 s) → rebalance triggers.
2. Follower A promoted to leader (ZooKeeper / Raft election).
3. New leader continues from its last committed offset — same input → same output.
4. Optional: reject in-flight order acks for 5 s, ask clients to re-submit with same idempotency-key.

RTO ≈ 5 s · RPO = 0 (Kafka is the source of truth).

The genius of Kafka-as-WAL: the engine's in-memory order book is derived state. The orders topic is the write-ahead log. Replay it end-to-end and you get bit-identical trades. No snapshotting needed for correctness (snapshots are just a speed optimisation).

Interview point: "Why isn't this a Paxos / Raft consensus problem?" — because there's ONE writer (the leader), not a multi-leader system. The 2 followers are silent — they only speak up if the leader dies. This is primary-backup replication, simpler and faster than consensus.
the LMAX Disruptor pattern (mechanical sympathy)

LMAX Exchange (UK) published the Disruptor pattern in 2011 — a lock-free ring buffer designed for the JVM. The design lessons:

  • Sequential memory access. Ring buffer entries live in a contiguous array — CPU prefetcher works perfectly.
  • Cache-line padding. Producer sequence + consumer sequence padded to 64 B so they don't share a cache line (false sharing kills performance).
  • Single writer. Only ONE thread writes to the ring at each stage — no CAS retry loops.
  • Batching consumers. A consumer takes N items at once (up to available), amortising per-item overhead.
  • Bounded ring. Fixed-size (power of 2) → cheap modulo via bit-and.

Result: 6 M orders/sec on a single JVM, p99 < 100 μs. Same design used by Coinbase, Chronicle, Aeron, Kaltura. In our code, the MatchingEngine is the sequential consumer — in prod, the ring buffer sits in front of it as the input queue.

What NOT to say: "We'd use ConcurrentHashMap for the order book." That's what we did in the JVM demo — because it's small, single-JVM, and needs no concurrency. In prod, the order book is inside the single-writer thread — plain HashMap is faster because no lock overhead. Concurrency primitives are a code smell in the hot path.

Correctness — the invariants regulators check

match at the right price, in the right order
Price-time priority
Wash-trade prevention
Self-trade prevention
Audit determinism
the universal rule: best price first, then earliest order

Two invariants the engine must maintain across every match:

  • Price priority. Buy Limit $105 → matches ask $103 BEFORE ask $105 (better price for buyer). Sell Limit $95 → matches bid $97 BEFORE bid $95.
  • Time priority. At the same price, the earliest resting order fills first. FIFO queue at each PriceLevel.

How we enforce:

// bids: highest price first (Comparator.reverseOrder)
// asks: lowest price first (natural order)
// getBestBid()/getBestAsk() = TreeMap.firstEntry() — O(log N) but usually O(1)-ish (cached root)

PriceLevel bestAsk = book.getBestAsk();
if (bestAsk.getPrice() > buyOrder.getPrice()) break;   // price priority

Order sellOrder = bestAsk.peekFirst();   // time priority — FIFO head

What could break priority: a modify operation that keeps the same order_id. Solution: modify = cancel + re-place — always assign a new timestamp. Every major exchange does this.

preventing manipulation trades that inflate volume

Wash trading: the same trader buys and sells the same security at the same time, creating fake volume to attract other traders. Illegal under SEC Rule 15c3-5, punishable by fines & delisting.

// Pre-trade check in the engine — right before creating a Trade:
if (buyOrder.getUserId().equals(sellOrder.getUserId())) {
  // OPTIONS:
  //  a) REJECT_INCOMING: cancel the incoming order, keep the resting one.
  //  b) REJECT_RESTING: cancel the resting order, incoming rests instead.
  //  c) CANCEL_BOTH: both orders cancelled.
  //  d) CANCEL_SMALLER_QTY: cancel the smaller of the two.
  // NASDAQ default: CANCEL_NEWEST (option a).
  return skipMatch(sellOrder);   // continue with next resting order
}

Beyond same-user: also flag trades between related accounts (family, algorithmic bot cluster, subsidiary firm). This is done in post-trade surveillance, not in the engine — false positives are common and blocking real trades is worse than a delayed flag.

Regulator context: FINRA's OATS + CAT + SEBI's SMART surveillance systems consume the trade feed and flag suspicious patterns (wash + spoofing + layering). Exchanges are required to prevent obvious wash trades in the engine.

STP — same-firm self-trade prevention

Self-Trade Prevention (STP) is a specific NASDAQ / CBOE / EEX rule that goes beyond wash. Traders can opt-in to have the exchange cancel one side automatically when their firm's orders would cross.

STP tag values (NASDAQ):
  N = None (no STP)
  B = Cancel both orders
  O = Cancel resting (Older)
  N = Cancel newest (incoming)
  D = Decrement — reduce both by min(qty) instead of canceling

Example:
  User X has resting sell at $100 for 500 shares (STP=D).
  User X submits buy at $100 for 200 shares.
  Engine sees same firm ID + same STP tag → decrement:
    resting sell: 500 - 200 = 300 shares remains
    incoming buy: 200 - 200 = 0 → cancelled
  No trade created, no wash issue.

Why the exchange, not the client, enforces STP: a fast algo might place orders faster than it can reason about its own book. The exchange has the atomic view. STP is a value-add feature the venue offers to algo shops.

every trade must be reproducible from the log

SEC Rule 613 (CAT — Consolidated Audit Trail) requires every order event (place / modify / cancel / route / execute) to be logged with microsecond timestamps and reported daily to FINRA. Similar rules: SEBI (India), FCA (UK), ESMA (EU MiFID II).

How we support this without slowing the match:

  1. Kafka topic orders.{symbol} is the primary audit trail — every order write is recorded with acks=all.
  2. Trade events published to trades.{symbol} with buyer/seller order_ids, price, qty, μs timestamp.
  3. S3 Object-Lock (WORM) — 7-year immutable archive, Athena SQL for surveillance.
  4. Deterministic engine — replay of the orders topic produces identical trades → any auditor can independently reconstruct.
Interview mic-drop: "The engine is a pure function of the orders log. Given the same partition and same code version, you can crash it, replay from offset 0, and get bit-identical trades. That's audit determinism — the strongest possible correctness guarantee. It's also how we hot-swap engine versions without downtime."

Order book data structure — the choice under the hood

TreeMap · red-black tree · why not others
what we chose
TreeMap<Double, PriceLevel> bids;
  // Comparator.reverseOrder() → highest first
TreeMap<Double, PriceLevel> asks;
  // natural order → lowest first

// TreeMap = red-black tree (self-balancing BST):
//   put/get/remove   → O(log N)
//   firstEntry (best) → O(log N), often cached
//   headMap/tailMap  → O(log N) — for range queries

PriceLevel {
  double price;
  LinkedList<Order> orders;   // FIFO
  int totalQuantity;          // O(1) depth
}

In prod (LMAX / Nasdaq), a hand-rolled red-black tree or a skip list with cache-friendly memory layout — 2–3× faster than the JVM's boxed TreeMap<Double, ...>.

why not others
StructureOps complexityWhy not
HashMapput/get O(1)NO ordering — best-bid query is O(N) scan
PriorityQueue (heap)peek O(1) · remove-arb O(N)can't remove arbitrary order for cancel without O(N) scan
Sorted arrayget O(1) · insert O(N)N is 100–500 price levels — insert cost is real; shift-heavy
Skip listO(log N) all opsGreat alt; simpler than RB-tree; used by some HFT firms
B-treeO(log N) with high fanoutCache-friendly for larger N; over-engineered for ~500 price levels
Why LinkedList (not ArrayList) inside PriceLevel: orders are added at the tail and matched from the head — pure queue semantics. LinkedList: O(1) addLast + O(1) removeFirst. ArrayList: O(1) add but O(N) removeFirst (shifts every element). N per level is small (~10) but this happens on every match — savings compound.
cancel-order optimisation
Map<String, OrderLocationIndex> orderIndex;
  // orderId → (side, price) 

// Without this: cancel scans ALL PriceLevels on both sides → O(P × K)
// With this: O(log N) TreeMap lookup + O(K) PriceLevel scan
//   where P = # price levels (100s), K = orders at that price (10s)

public boolean removeOrder(String orderId) {
  OrderLocationIndex loc = orderIndex.get(orderId);
  if (loc == null) return false;
  PriceLevel level = (loc.side == BUY ? bids : asks).get(loc.price);
  boolean removed = level.removeOrder(orderId);
  if (level.isEmpty()) side.remove(loc.price);
  return removed;
}

execution order matters

The RiskService runs checks in order and fails fast:

  1. Circuit breaker — pure comparison, ~50 ns, cheapest.
  2. Margin — 1 Redis read, ~1 ms.
  3. Position limit — 1 Redis read + aggregation, ~2 ms.

If margin fails, position-limit isn't checked → saves work. In prod, some checks call the clearing house — expensive; do them LAST.

the kill-switch (regulatory must-have)

Under SEC Rule 15c3-5, every broker-dealer must have a "kill switch" — a manual override to halt all activity when things go wrong. Ours:

  • Per-symbol halt: Redis flag halt:{symbol} — Circuit-breaker check sees it → reject.
  • Per-user halt: for suspicious activity — flip flag, existing orders can cancel but new ones reject.
  • Global kill: Kafka consumer groups paused, all new orders → HTTP 503 "market halted".

Knight Capital, 2012: lost $460 M in 45 minutes because a buggy algo placed millions of orders and there was no kill switch. Result: SEC Rule 15c3-5. Every design must have this.

35-minute interview walkthrough

the answer, timed
phase 1 · clarify (2–3 min)
  • "Retail broker (routes to exchange) or full exchange (runs matching engine)? I'll design as an exchange to show the full engine."
  • "Order types — market, limit, stop-loss, stop-limit, iceberg? I'll cover the first four."
  • "Latency target — HFT (sub-μs) or retail (sub-10 ms)? Retail — I'll use JVM with LMAX Disruptor, not FPGA."
  • "Regulator — SEC (US) or SEBI (India)? I'll cover Reg NMS + Rule 613 (CAT) + SEBI SMART."
  • "Settlement — T+0 (instant) or T+1? T+1 batch (US & India 2023 standard)."
phase 2 · draw architecture (5–7 min)
  • Three latency zones: ingress (< 10 ms) · matching (< 1 ms) · post-trade (async).
  • Client → API Gateway → Order Service → Risk chain → Kafka orders.{symbol}.
  • Matching engine (single-thread per symbol) → in-memory order book → trades.{symbol}.
  • Post-trade: Trade Service → Aurora + DDB · Market Data Service → Redis + Timestream · WebSocket Hub.
  • Call out the CAP split — orders CP, market data AP.
phase 3 · matching engine deep dive (8–10 min · the STAR)
  • Draw the order book: bids desc + asks asc, FIFO at each price level.
  • Walk through matchAgainstAsks — while remaining > 0 and price ≤ limit, fill.
  • Explain single-thread per symbol — no locks, deterministic, LMAX 6 M/s single thread.
  • Sharding by symbol via Kafka partition — one thread per partition.
  • Recovery = Kafka replay → same input, same output.
phase 4 · correctness (5–7 min)
  • Price-time priority invariant — how TreeMap + LinkedList enforce.
  • Modify = cancel + re-place (loses time priority).
  • Self-trade prevention (STP tag) — engine cancels rather than creates wash trade.
  • Reg NMS + NBBO — Reg NMS Rule 611 requires best-execution across venues.
  • Audit determinism — replay produces bit-identical trades.
phase 5 · scale & failure (5–7 min)
  • Market-open burst → Redis Cluster + pre-warmed JIT + queue-mode risk.
  • Hot-symbol engine → dedicated node for top-N tickers.
  • Leader crash → follower promoted, replays from Kafka offset (5 s RTO).
  • Kill switch (SEC Rule 15c3-5) — per-symbol · per-user · global.
  • Circuit breakers on price bands · trading halts published to Redis flag.
phase 6 · what would you do differently (2–3 min)
  • "At 10× scale I'd move the engine to a custom lock-free ring (LMAX / Aeron) — the JVM Disruptor pattern."
  • "For HFT-adjacent tenants I'd add FPGA-accelerated NICs and colocate near the primary matching venue."
  • "I'd add IEX-style speed-bump (350 μs delay) if I want to attract retail flow against latency arbitrage."
30-second pitch: "Microservices behind API Gateway. Split into CP order plane (Order Service → Risk chain → Kafka → matching engine → Trade Service → Aurora / DDB) and AP market-data plane (Market Data Service → Redis + WebSocket Hub → 500 K clients). The matching engine is single-threaded per symbol — Kafka partition = symbol = engine thread. In-memory TreeMap order book matches with price-time priority. Recovery = Kafka replay. 22 K OPS peak, 110 K burst, p99 < 10 ms end-to-end, < 1 ms engine match."
Interview red flags to avoid:
• "Multi-threaded matching with locks." (contention · non-determinism · deadlock risk — LMAX proved single-thread wins)
• "Match against Redis LTP." (Redis lags — engine must own its in-memory book)
• "Shard by user." (both sides of the trade would sit on different engines — impossible)
• "Return the ACK before persisting the order." (durability violation — an ACK'd order that vanishes is a lawsuit)
• "Use SQS." (no ordered delivery per symbol · no replay · fan-out is manual)
• "Skip pre-trade risk to save latency." (Knight Capital lost $460 M in 45 min this way)
