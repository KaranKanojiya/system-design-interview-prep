A

Problem & requirements

clarify first
functional
  • 1:1 and group chat (up to 256 members) in real time.
  • Online/offline presence + last-seen; read receipts (sent / delivered / read ticks).
  • Paginated message history; media sharing (image/video/file) via object storage.
  • Offline delivery — queue messages, deliver on reconnect + push notification.
non-functional
  • Latency < 200 ms delivery for online users (same region).
  • Ordering — guaranteed per-conversation; durability — zero loss after ACK.
  • Availability 99.99%; scale 500M concurrent WebSocket connections.
  • Delivery at-least-once (clients dedup by messageId); presence is eventually consistent.

E

Data model

right store per shape
message — Cassandra (write-heavy)
conversation_id UUID    // partition key
sequence_number BIGINT  // clustering, DESC
message_id      UUID
sender_id       UUID
content         TEXT
type            TEXT     // TEXT/IMAGE/VIDEO/FILE
media_url       TEXT
created_at      TIMESTAMP

PK (conversation_id) + clustering sequence_number DESC → all messages for a chat co-located and sorted. TTL for 30-day server retention.

status & membership + Redis keys
message_status (Cassandra)
  message_id UUID, user_id UUID
  status TEXT   // SENT/DELIVERED/READ

conversation_member (PostgreSQL)
  conversation_id, user_id, role
  last_read_message_id   // read pos

Redis: conn:{userId}→serverId (TTL)
       presence:{userId} (TTL 60s)
       seq:{conversationId} (INCR)
       offline:{userId} (LIST, 30d)

Per-conversation read position (last_read_message_id) batches read receipts — one update marks all earlier messages READ.

F

Key design choices (deep-dived on canvas 3)

defend these
connection layer

WebSocket + Redis registry

Persistent bidirectional channel; a registry (userId→serverId) lets any router reach any user — beats sticky sessions for failover & even load. → canvas 2 · LLD

fan-out

Fan-out on write

Push to recipients immediately; batch per connection server for groups. Max group 256 bounds the cost — read fan-out only for broadcast channels.

ordering

Kafka partition = convId

Per-conversation ordering via partition + Redis sequence number; client reorders as defense in depth. No global order needed. → canvas 3

storage

Cassandra + PostgreSQL

Cassandra for write-heavy time-series messages; PostgreSQL (CP) for relational user/group metadata.

delivery guarantee

At-least-once + dedup

Exactly-once is too costly; persist-before-ACK gives durability, clients dedup by messageId. → canvas 3

presence

Heartbeat + TTL (AP)

30s heartbeat refreshes a 60s Redis TTL; stale “online” for a few seconds is harmless. Availability > strict consistency.

Glossary — one-liners

terms used above
WebSocketpersistent bidirectional TCP channel — server can push without the client polling
Connection registryRedis map userId→serverId so any node can find which server holds a user's socket
Stateful vs statelessConnection Gateway pins a socket (stateful); Message Service keeps none (stateless)
Fan-out on writepush a new message to every recipient at send time (vs pull on read)
Sequence numbermonotonic per-conversation counter (Redis INCR) giving gap-free ordering
Heartbeat / TTLperiodic ping refreshes a short-lived Redis key; expiry ⇒ user offline
At-least-oncea message may arrive twice but never zero times; client dedups by messageId
Tickssingle = SENT, double = DELIVERED, blue = READ (per-member in groups)
QUORUMa majority of Cassandra replicas must ack a write for durability
Thundering herda burst of simultaneous fan-out RPCs — avoided by batching/staggering
