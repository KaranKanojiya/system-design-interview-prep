B

Message ordering & routing — the core algorithm

Conversation.nextSequence + MessageService.sendMessage
the send path (grounded)
// MessageService.sendMessage(...)
Conversation conv = convRepo.findById(id)
    .orElseThrow(ConversationNotFound::new);
if (!conv.isMember(senderId))
    throw new UnauthorizedException(...);

// server-side, gap-free order per conversation
long seq = conv.nextSequence();   // AtomicLong ++

Message m = new Message.Builder()
    .messageId(uuid8()).conversationId(id)
    .senderId(senderId).content(content)
    .type(type).status(SENT)
    .sequenceNumber(seq);
for (String mid : conv.getMemberIds())
    if (!mid.equals(senderId)) m.addRecipient(mid);

msgRepo.save(m.build());
// route by conversation type
if (conv.getType() == ONE_TO_ONE)
    router.routeToUser(m, conv.getOtherMember(senderId), name);
else
    router.routeToGroup(m, conv, name);

The sequence number is assigned server-side under an AtomicLong, so two concurrent senders in one conversation can never collide or leave a gap.

worked example — three sends, one offline
// conv seqCounter starts at 0
alice→bob "Hey"      nextSequence() = 1
  bob online?  YES → deliverMessage, mark DELIVERED
bob→alice "yo"       nextSequence() = 2
  alice online? YES → deliverMessage, mark DELIVERED

// group grp-7 = {alice,bob,carol}, carol offline
alice→grp "standup?" nextSequence() = 1
  routeToGroup fan-out (skip sender):
    bob   online → deliver, DELIVERED
    carol OFFLINE→ offlineQueues[carol].add(m)
                   [PUSH → carol]
...carol reconnects → deliverOfflineMessages(carol)
    drains queue → deliver, mark DELIVERED

One deliveryStatus map entry per recipient means a group message can be DELIVERED to bob while still queued for carol — the per-recipient truth that drives the tick marks.

Why per-conversation sequence numbers? A monotonic AtomicLong on the Conversation gives every message a unique, gap-free, total order within that thread — the client can reorder out-of-order arrivals and detect gaps to re-request. Wall-clock timestamps suffer clock skew and sub-ms collisions across servers; random UUIDs give no ordering and no efficient range scan. Sequence also powers cursor pagination: findByConversationId(id, limit, beforeSequence) walks backward from a cursor. The trade-off — one counter per conversation is a write-serialization point — is exactly the ordering problem canvas 3 revisits at scale.
C

Delivery routing (Strategy pattern)

online vs offline, without if/else sprawl

routeToUser when registry.isOnline(recipient) is true. the real-time path

  • Look up the recipient's ConnectionHandler in the router's connections map.
  • msg.markAsDelivered(recipientId) — flips overall status and the per-recipient entry to DELIVERED.
  • handler.deliverMessage(msg, senderName) pushes it down the (simulated) WebSocket immediately.

routeToUser when the recipient is not online. store-and-forward

  • offlineQueues.computeIfAbsent(recipient, k → new ArrayList<>()).add(msg) — one FIFO list per user.
  • Logs a [PUSH → user] line (a real system fires an APNs/FCM push here).
  • On reconnect, ChatService.userConnects → router.deliverOfflineMessages(user) drains the queue in order and marks each DELIVERED.

routeToGroup — the same per-recipient decision, applied to every member. fan-out

  • Iterate group.getMemberIds(), skip the sender, call routeToUser for each.
  • Each recipient independently takes the online or offline branch — a message can be live for some, queued for others.
  • Because GroupChat extends Conversation, no special storage path — same repository, same sequence counter.

Not in the repo, but the seams make them drop-in:

  • Redis-backed ConnectionRegistry: swap the in-memory map so any WS server can locate a user's edge node — the multi-server routing story.
  • Kafka / Redis Pub-Sub router: replace the in-process connections map with a message bus so delivery survives a server crash and scales fan-out horizontally.
  • Durable offline queue: back offlineQueues with Redis / a durable store so queued messages survive restarts.

The pattern: MessageRouter picks a delivery behaviour from the recipient's presence, never branching on message type in the caller — MessageService just calls routeToUser / routeToGroup. Adding a new delivery mode (push-only, email digest) is a new branch/strategy inside the router with zero changes to the services above it.
D

Data model detail

Message · Conversation / GroupChat
Message — per-recipient delivery tracking
messageId      String   // 8-char UUID
conversationId String   // owning thread
senderId       String
content        String
type           MessageType   // TEXT/IMAGE/VIDEO/FILE/SYSTEM
status         MessageStatus // overall (min)
sequenceNumber long          // order KEY
createdAt      LocalDateTime
deliveryStatus Map<String,MessageStatus>
               // recipientId → SENT/DELIVERED/READ

deliveryStatus is a ConcurrentHashMap so many delivery threads update it safely. MessageStatus is ordered SENDING → SENT → DELIVERED → READ (each carries a tick symbol); markAsRead / markAsDelivered flip both the per-user entry and the overall status.

Conversation & GroupChat — ordering + members
conversationId String
type           ConversationType // ONE_TO_ONE|GROUP
name           String
memberIds      List<String>  // CopyOnWriteArrayList
sequenceCounter AtomicLong    // nextSequence()

// GroupChat extends Conversation
maxMembers   int = 256
adminIds     Set<String>   // ConcurrentSkipListSet
description  String        // addMember() caps at 256

Membership uses a CopyOnWriteArrayList — cheap concurrent reads (the common case: fan-out iterates members) with copy-on-write on the rarer join/leave. Storage is uniform: a GroupChat is-a Conversation, so both live in the one ConversationRepository.

Two status views, on purpose: Message.status is the coarse overall state shown as a single tick, while deliveryStatus[user] is the fine-grained per-recipient truth — that split is what lets a group message show delivered-to-Bob while still queued-for-Carol, and it is what a read receipt updates. Canvas 3 shows how this maps onto a Cassandra table partitioned by conversation_id, clustered by sequence_number.

Request handling sequence

which class does what, in order

POST /messages  →  send a 1:1 message (recipient online)

ChatController.handleSendDirectMessage(alice, bob, text)
  └─ ChatService.sendDirectMessage(alice, bob, text, TEXT)
       1  convRepo.findOneToOne(alice, bob)
            empty? → new Conversation(ONE_TO_ONE) + addMember×2 + save
       2  MessageService.sendMessage(alice, convId, text, TEXT)
            a  convRepo.findById → isMember(alice)?  else Unauthorized
            b  seq = conv.nextSequence()            // AtomicLong ++
            c  Message.Builder … addRecipient(bob) … build()
            d  msgRepo.save(message)
            e  conv.type == ONE_TO_ONE →
                 router.routeToUser(msg, bob, "Alice")
                   registry.isOnline(bob)? YES
                   msg.markAsDelivered(bob)          // ✓✓
                   handler[bob].deliverMessage(msg)  // [WS → bob]
  └─ [RESPONSE] message SENT

Offline path  →  queue, then drain on reconnect

// send while carol is offline
router.routeToUser(msg, carol, name)
   registry.isOnline(carol)? NO
   offlineQueues[carol].add(msg)     // FIFO list
   println("[PUSH → carol] new message")

// later: carol connects
ChatController.handleConnect(carol)
  └─ ChatService.userConnects(carol)
       1  presenceService.heartbeat(carol, "server-1")  // → ONLINE
       2  userRepo.updateStatus(carol, ONLINE)
       3  router.deliverOfflineMessages(carol)
            queued = offlineQueues.remove(carol)
            for m in queued:
               m.markAsDelivered(carol)      // ✓✓
               handler[carol].deliverMessage(m)

The queue is drained in insertion order, preserving the per-conversation sequence the client will reassemble.

PUT /messages/{id}/read  →  read receipt

ChatController.handleReadReceipt(msgId, bob)
  └─ ChatService.markAsRead(msgId, bob)
       └─ MessageService.markAsRead(msgId, bob)
            1  msgRepo.findById(msgId)  // else not-found
            2  msgRepo.updateDeliveryStatus(msgId, bob, READ)
                  → message.markAsRead(bob)      // ✓✓ blue
            3  new ReadReceipt(msgId, bob, READ)
            4  return receipt   // sender notified via handler (Observer)
  └─ [RESPONSE] read receipt recorded

Presence changes follow the same shape: PresenceService flips status, then pushes deliverPresenceUpdate to each online contact through their ConnectionHandler — the Observer fan-out.

F

Design patterns used

GoF-categorized
Creational
  • Builder — Message.Builder. Readable construction of a 9-field entity with an incremental addRecipient; build() assembles the immutable-ish Message.
  • Factory — AppConfig wires the entire object graph in its constructor + createController() (composition root).
Behavioral
  • Mediator — ChatService is the hub; sub-services never call each other, cutting N×(N−1) coupling to N.
  • Strategy — MessageRouter chooses online vs offline delivery from presence, no branching leaking upward.
  • Observer — presence updates & read receipts push to contacts via ConnectionHandler; adding a channel needs no service change.
Architectural (not GoF)
  • Repository — Message / Conversation / User contracts over in-memory maps; swap in Cassandra / Postgres with no service change.
  • Dependency Injection — constructor injection everywhere, wired by hand in AppConfig (Spring @Configuration in production).
Why they cluster: Mediator keeps the service graph a star instead of a mesh; Strategy + Repository keep delivery and storage swappable (Open-Closed); Observer decouples who-gets-notified from who-changed. Builder plus the concurrency primitives — AtomicLong sequence, ConcurrentHashMap stores, CopyOnWriteArrayList members, ConcurrentSkipListSet admins — keep the write paths lock-light. → scaling, ordering & the multi-server follow-up on canvas 3
