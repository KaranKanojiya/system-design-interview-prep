A

Scaling strategy

stateful gateway · what to shard
connection tier (stateful)

Shard by connection count

Each connection server holds ~50K WebSockets (Java/Netty). At 200M concurrent connections (~40% of 500M DAU) that is ~4,000 servers — provision 8–10K for headroom. Scale horizontally; the Redis connection registry lets any server route to any user.

message tier (stateless)

Auto-scale freely

Validate → assign seq_num → persist is stateless, so any instance serves any message. Scale behind the LB against the ~460K msg/s average (~1.4M peak). No session affinity needed.

Kafka / consumers

Add partitions & workers

One partition consumed by exactly one worker in the delivery-workers group. Add workers up to N = partition count to scale delivery in parallel — no duplicate delivery.

message sharding — how to partition Cassandra & Kafka

Hash on conversation_id ← chosen

Both Cassandra and Kafka partition by conversation_id. All messages for one conversation land on the same node / Kafka partition, which is exactly what preserves per-conversation ordering and co-locates a wide row for pagination.

partition = hash(conversation_id) % N   // same convo → same partition
Cassandra PK (conversation_id, seq_num)     // wide row, ORDER BY seq_num DESC
verdict
  • Ordering for free — Kafka guarantees FIFO within a partition, so messages arrive in seq_num order.
  • Even spread across conversations; a wide row per chat = efficient reverse-chronological reads.
  • Watch the hot group: one partition caps a single conversation at ~10K msg/s — fine for any human chat.

Time / range-based partitioning

Bucket messages by time window (e.g. one partition per day) or by contiguous key ranges. Tempting for a time-series workload, but the newest bucket takes all the write traffic.

2026-07-30 → shard 1
2026-07-31 → shard 2   // today's shard is a write hot spot
verdict — avoid as the primary key
  • Hot partition: today's bucket absorbs every write while yesterday's idles.
  • Breaks per-conversation ordering — a conversation's messages scatter across time buckets.
  • Time bucketing is fine only as a secondary lever for TTL/archival, not the shard key.

Consistent hashing (the ring)

Nodes and conversation_id keys map onto a hash ring; adding or removing a node only remaps the keys in that node's arc. This is how Cassandra partitions natively — hashing on conversation_id rides on top of it.

// only ~1/N keys move when a node joins/leaves
node = firstNodeClockwise( hash(conversation_id) )
verdict
  • Elastic: add nodes for growth with minimal reshuffling — no full-keyspace remap.
  • Virtual nodes smooth uneven arcs and speed rebalancing.
  • Same technique shards the Redis cluster (presence, registry, queues) across nodes.
PostgreSQL stays small. Users, groups, membership, contacts and blocks fit a single primary + read replicas — millions of rows, not billions. Route heavy relational queries (group admin, mutual contacts) to replicas so they never compete with membership writes on the fan-out path.

Caching deep-dive

Redis is on every message's path
write-through — presence & connection registry
on heartbeat (every 30s):
  SETEX presence:{userId} 60 ONLINE        // TTL = 2× heartbeat
  SET   connection:{userId} server-N EX 120

on message send → GET presence:{userId}
  ├─ ONLINE → GET connection:{userId} → forward to server-N → WebSocket
  └─ null   → user OFFLINE → RPUSH offline-queue:{userId}

Redis is the primary store for presence — no DB behind it. TTL is automatic offline detection: miss two heartbeats and the key evaporates. Both keys are ~100% hit rate because every write goes to Redis first.

cache-aside — recent messages & group members
open conversation → GET recent-msgs:{conversationId}
  ├─ HIT  → return last 50            // ~sub-ms
  └─ MISS → SELECT … LIMIT 50 (Cassandra) → SETEX 1800

group send → SMEMBERS group-members:{groupId}   // O(N) in-memory fan-out

Recent messages: append-on-write (push new message, trim to 50) instead of full invalidation → 80–90% hit rate as users cycle 3–5 active chats. Group set refreshed hourly from PostgreSQL; 95%+ hit rate.

local L1 cache

Caffeine for profiles

Sender display-name / avatar is rendered on every message. Profiles change rarely, so each connection server keeps an in-process Caffeine cache — no Redis round-trip per render. 5-min staleness is invisible.

Caffeine.newBuilder()
  .maximumSize(10_000)
  .expireAfterWrite(5, MINUTES)
  .build();   // LRU, per-server
what NOT to cache

Skip the volatile

Some data hurts if cached:

  • Delivery status — must be real-time accurate; query Cassandra directly.
  • Conversation list — reorders on every message → near-zero hit rate.
  • Typing indicators — ephemeral, fire-and-forget over WebSocket.
  • Media — that is the CDN's job, not app cache.
offline queue

Redis List, drained on connect

Offline users' messages buffer in a bounded list; on reconnect the client sends its last seq_num and the queue is drained + backfilled from Cassandra.

RPUSH offline-queue:{userId} {msg}
LTRIM offline-queue:{userId} 0 999   // cap at 1000
// on connect:
LRANGE …0 -1 → DEL → deliver in order
Graceful degradation if Redis fails: a replica promotes in <1s. During failover, presence checks default to OFFLINE (safe — messages queue, never lost), the registry falls back to broadcasting to all connection servers (expensive but correct), and group membership falls back to PostgreSQL. Degrade, don't fail. → full cache layering on canvas 1 · HLD

Bottlenecks & solutions

click a card to open

Stateful connection servers — the core hard part

Impact: WebSockets are long-lived and pinned to one server. Sticky sessions mean if a server dies, all its users drop and there is no record of where they were. Naive round-robin can't route a reply to the right socket.

Fix: keep the gateway stateful but externalize the mapping — a Redis connection registry (connection:{userId} → server-N) so any server routes to any user. L4 LB preserves the TCP upgrade; connection draining sends reconnect signals on deploy. This is the ConnectionRegistry / InMemoryConnectionRegistry abstraction in the codebase.

Single Kafka partition for a hot group

Impact: partitioning by conversation_id caps one conversation at a single partition's throughput (~10K msg/s). A broadcast channel with millions of subscribers would saturate it.

Fix: for human groups (≤256 members, rarely >100 msg/s) one partition is plenty. For broadcast scale, keep one partition for ordering then fan out to multiple worker partitions for delivery; workers process sequentially by seq_num so order is preserved.

Presence fan-out storm

Impact: notifying every contact when a user comes online is 500M × ~500 contacts ≈ 250B notifications/day just for presence. It does not scale.

Fix: pull presence on demand when the app opens; only push updates for conversations currently open; subscribe to presence:{userId} via Redis pub/sub only for visible chats. Presence is AP with a 60s TTL, so eventual is fine.

Split-brain — two servers think the user is connected

Impact: a network blip leaves server-1 believing user-A is still connected while user-A reconnects to server-2. The registry could route to a dead socket.

Fix: registry uses overwrite semantics (SET connection:{userId} server-2 wins). Server-1's send to its dead WebSocket fails and it self-cleans. Prevention: heartbeat eviction after 2 missed intervals, connection versioning, and Redis pub/sub to notify the old server. At-least-once + client dedup by messageId absorbs any double delivery.

Message loss vs duplication

Impact: retries at the network / Kafka / server layers can deliver a message twice; a naive fire-and-forget could lose one entirely. A lost message is catastrophic.

Fix: persist to Cassandra before the SENT ack (message is safe even if Kafka dies), then at-least-once delivery with a client-generated messageId (UUID). Cassandra upserts by primary key (idempotent), clients dedup by messageId → "effectively once" without distributed transactions.

Out-of-order delivery

Impact: clock skew and network delays mean wall-clock timestamps can't order messages; #5 may arrive before #4.

Fix: never order by timestamp. Server assigns a monotonic seq_num per conversation (Redis INCR / Kafka offset), Kafka partition-by-conversation_id guarantees FIFO, and the client renders sorted by seq_num, buffering a gap until it fills.

Kafka cluster unavailable

Impact: if the whole cluster is down (rare — RF 3 + ISR handles broker loss), the delivery pipeline stalls.

Fix: a broker failure fails the partition leader over automatically. For a full outage, buffer messages in a bounded in-memory queue on the connection server and retry — a temporary AP choice; the message is already durable in Cassandra, so this only delays delivery.

CAP & consistency — mixed, per feature

the key interview insight
the choice

P is mandatory in any distributed system, so the real decision is A vs C during a partition. The mature answer: a chat system does not have one CAP choice — each feature picks its own based on tolerance for staleness vs unavailability.

  • Presence / read receipts: AP — 30s stale online or a 5s-late receipt is harmless; blocking is worse.
  • Message delivery: AP, at-least-once — a duplicate is annoying and filtered; a lost message is unacceptable.
  • Message ordering: CP-like — delay delivery rather than deliver out of order.
  • Group membership: CP — a user who left must immediately stop receiving messages (privacy/legal).
where CP actually bites — group leave
on user leaves group:
  1. PostgreSQL DELETE group_members   // source of truth
  2. Redis SREM group-members:{gid} u  // SYNCHRONOUS
  3. return success                    // only after step 2

// during partition: FAIL the op rather than risk
// delivering to someone who left.

Cache invalidation here is synchronous and mandatory — never return success before the SREM. An async window would let a removed user still receive messages, which is a privacy violation. This is why membership lives in PostgreSQL (ACID), not just a cache.

How we simulate exactly-once: at-least-once delivery + client-side dedup by messageId = "effectively once". The client generates the UUID before sending, so retries at any layer are safe; Cassandra upserts on the same primary key are a no-op. Ordering never uses wall clocks — only server-assigned seq_num.

phase-by-phase
  • P1 Clarify (2–3): 1:1 + groups (≤256), presence, read receipts, media, offline delivery; mention E2E but don't design it; scale = 500M DAU.
  • P2 Estimate (2–3): 500M × 80 msg = 40B/day → ~460K/s, ~1.4M peak; 200M concurrent conns / 50K per server → ~4K servers; ~4 TB/day text, media on CDN.
  • P3 API (2–3): WebSocket events (SEND_MESSAGE, NEW_MESSAGE, DELIVERY_ACK, PRESENCE_UPDATE) + REST for history / media upload.
  • P4 Architecture (5–7 · CORE): draw the stateful connection gateway vs stateless message service split; Redis registry bridges them; Kafka → router → Cassandra / PostgreSQL / S3.
  • P5 Message flow (5–7 · MOST ASKED): Alice→Bob 10 steps — persist before SENT ack, Kafka publish, registry lookup, online vs offline (queue + push). Then group fan-out (batch by server).
…and finish strong
  • P6 Ordering (3–4): timestamps skew → server seq_num + Kafka partition-by-conversation_id FIFO; client buffers gaps.
  • P7 Presence (2–3): 30s heartbeat, 60s TTL, auto-offline on expiry; avoid the fan-out storm with pull-on-demand + pub/sub for visible chats.
  • P8 DB & storage (3): Cassandra for messages (PK conversation_id, seq_num DESC), PostgreSQL for users/groups, S3 + CDN + pre-signed URLs for media.
  • P9 Trade-offs & CAP (2–3): at-least-once + dedup; mixed CAP per feature; memory-vs-connections (Erlang 2M vs Java 50K); fan-out on write vs read.
  • If only 25 min: do P1–6 + P9; one-line presence and DB.
Green flags: separate stateful connection layer from stateless processing · Redis registry for WS routing · Kafka partition by conversation_id · client-generated messageId for dedup · heartbeat + TTL presence · pre-signed media URLs. Red flags: HTTP polling · ignoring WebSocket statefulness · one DB for everything · global message ordering · eager presence fan-out · skipping offline delivery.
