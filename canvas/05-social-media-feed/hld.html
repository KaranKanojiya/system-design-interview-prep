A

Problem & requirements

clarify first

Build a Twitter/X-like feed: users post short tweets, follow others, and see a personalized home timeline aggregating everyone they follow. The core challenge: deliver a ranked feed to 300M users in <500 ms when a single celebrity post must reach 50M timelines.

functional
  • Post a tweet (≤280 chars + optional media) → unique tweet_id (Snowflake); fan-out to followers.
  • Home timeline — aggregated & ranked feed of followees, cursor-paginated, near real-time.
  • User timeline (reverse-chrono), follow / unfollow, like / retweet.
  • Trending topics (by velocity, not volume; per region/window) and full-text search.
non-functional
  • Feed latency < 500 ms p99; poster sees own tweet < 1 s; fan-out lag < 5 s.
  • Availability 99.99% — global, always-on (→ AP system).
  • Consistency eventual — a 5–10 s stale feed is acceptable.
  • Scale 300M MAU · 500M tweets/day · 100K tweets/s peak · 600:1 read-heavy · no tweet loss.

GET /api/search?q=…&type=recentfull-text tweet / hashtag search200 + results[] + next_cursor

Cursor-based pagination (not offset) keeps feed reads O(1) and stable as new tweets arrive — the cursor is the last tweet_id.

E

Data model

polyglot: Cassandra + Redis + Postgres
tweets — Cassandra (durable store)
tweet_id      BIGINT      // Snowflake, time-sortable
user_id       BIGINT
content       TEXT        // ≤ 280 chars
media_urls    LIST<TEXT>  // CDN links only
like_count    COUNTER
retweet_count COUNTER
hashtags      SET<TEXT>
is_deleted    BOOLEAN     // soft delete
created_at    TIMESTAMP
PRIMARY KEY (user_id, tweet_id)
CLUSTERING ORDER BY (tweet_id DESC)

Partition by user_id → a user's tweets co-located; clustering DESC → newest first (user timeline & celebrity pull). Follow / like / retweet live in sibling Cassandra tables.

timeline:{user_id} — Redis sorted set (hot read)
Type   : Sorted Set (ZSET)
Member : tweet_id
Score  : tweet_timestamp (or rank score)

ZADD     timeline:u_892 1713436200 "t_174928"
ZREVRANGE timeline:u_892 0 19   // newest 20

Max size : ~800 entries / user
TTL      : 7 days (old entries age out)

Pre-computed feed for normal-user tweets — populated by the Fan-Out Service, read in ~1–2 ms. Users live in Postgres (profiles, counts, is_celebrity); trending uses per-window ZSETs.

F

Key design choices (deep-dived on canvas 3)

defend these
fan-out strategy

Hybrid push / pull

Normal users → fan-out on write (fast reads); celebrities → fan-out on read (no 50M-write storm). Merged at read time. → canvas 2 · LLD

storage

Polyglot

Cassandra for write-heavy tweets, Redis for hot timelines, Postgres for small relational user/graph data. Right tool per access pattern.

consistency

AP · eventual

A feed must never fail; a 5–10 s stale timeline is fine. Optimize the 600:1 read path. → canvas 3

Also on the deep-dive: the celebrity problem & dynamic reclassification · thundering herd on a viral celebrity tweet (singleflight + local cache) · trending by velocity · tweet-deletion & unfollow via lazy read-time filtering. → canvas 3 · Deep-dive & Trade-offs

Glossary — one-liners

terms used above
Fan-out on writepush a new tweet into every follower's timeline cache at post time
Fan-out on readskip the push; pull the author's tweets when a follower loads their feed
Hybrid fan-outwrite-path for normal users, read-path for celebrities, merged at read time
Celebrity problemone high-follower post triggers tens of millions of timeline writes
Snowflake ID64-bit time-sortable unique ID (timestamp + machine + sequence)
Sorted set (ZSET)Redis structure ordering members by score — used for timelines & trending
Timeline cachethe pre-computed home feed for a user, stored as a Redis ZSET
Social graphthe follower/following adjacency lists that drive fan-out
Cursor paginationpage by last-seen id (stable, O(1)) instead of numeric offset
Trending velocityrank hashtags by spike vs baseline, not raw volume
Thundering herdmillions stampede one hot key when a celebrity tweets
AP (CAP)favour Availability + Partition-tolerance over strong Consistency
