A

Scaling strategy

what to shard & how
app / feed tier

Stateless → horizontal

Feed & Tweet services hold no session state, so any instance serves any request. Auto-scale behind the LB on CPU / p99. At ~35K feed reads/s (3B/day) that is dozens of instances round-robined; the merge+rank work is CPU-bound and parallelisable.

fan-out workers

Scale on Kafka lag

The fan-out consumer group (~32 instances over 128 partitions) auto-scales on consumer lag — the critical metric. Sustained load is ~1.16M timeline writes/s (100B/day), so workers scale out when a burst of tweets pushes lag past 60 s.

read replicas

Redis replicas absorb reads

The celebrity-tweet key is read by millions at once — a master + read replicas spreads those reads so the master only takes writes. Cassandra runs RF=3 so any of three replicas serves a tweet read; PostgreSQL user store gets read replicas for profile lookups.

sharding — every tier partitions differently, pick a tier

Timeline cache — shard on userId

Each home timeline is a Redis Sorted Set timeline:{userId} capped at 200 items. Consistent-hash the userId across the ~40–80 shard cluster so any Feed-service instance and any fan-out worker land on the same shard for a given user.

shard = consistentHash(userId)   // ~1 TB / 25 GB ≈ 40 shards
ZADD timeline:{userId} {ts} {tweetId}
verdict ← chosen
  • Even spread: user IDs are effectively random keys → no hot shard from the timeline itself.
  • 200-item cap keeps every shard's per-user footprint at ~10 KB — memory is predictable.
  • Elastic: consistent hashing means adding a shard remaps only ~1/N keys, not the whole cluster.

Tweet store — partition on user_id

Cassandra table tweets_by_user partitions by user_id, clustered by created_at DESC. One partition read returns all of a user's recent tweets — exactly what fan-out-on-read (celebrity pull) needs. Masterless, RF=3, linear scale-out.

PRIMARY KEY ((user_id), created_at, tweet_id)
  WITH CLUSTERING ORDER BY (created_at DESC)
verdict
  • Time-series friendly: wide rows, newest-first, append-only — natural for tweets.
  • Celebrity partition is huge: a 90M-follower account's row is enormous → we read only the recent slice (LIMIT) and TTL old tweets at 90 days.
  • Consistent hashing across nodes; no leader, no failover election.

Fan-out topic — partition on poster userId

tweet.published has 128 partitions keyed by the poster's userId, so all of one user's tweets stay ordered and no two workers fan out the same tweet at once. A worker reads one message and writes to many follower timelines.

// partition = hash(posterUserId) % 128
// NOT follower id — one tweet → millions of followers
verdict
  • Ordering per poster preserved; consumer groups let trending, search & notifications read the same stream independently.
  • Replay from offset recovers a stalled pipeline — no lost tweets.
  • Partitioning by follower would be impossible: a single tweet spans millions of follower keys.
Celebrity split saves the write budget: normal-user tweets fan out on write; celebrity (≥10K followers) tweets skip fan-out and are pulled at read time — this is what keeps the ~1.16M writes/s from becoming 50M writes on a single celebrity tweet. → full fan-out design on canvas 1 · HLD
B

Caching deep-dive

<200 ms feed lives here
read path — feed generation
GET /feed?userId=user-42
  1. ZREVRANGEBYSCORE timeline:{user}   // pushed tweets, ~2 ms
  2. SMEMBERS celebrity-followees:{user} // who to pull
  3. per celeb: ZREVRANGEBYSCORE celebrity-tweets:{id}
  4. hydrate: GET tweet:{id}  (90% Redis hit)
  5. merge + dedup + rank → return top N

Cache hit path is all Redis: ~12 ms p99. The timeline cache is THE core cache — one Sorted Set per user, populated by fan-out-on-write for normal posters; celebrity tweets are merged in from a shared per-celebrity key.

write path — populate on publish
POST /tweets
  normal poster  → Kafka → fan-out worker
                   ZADD timeline:{follower} …  // write-through
  celebrity      → ZADD celebrity-tweets:{id}
                   SET tweet:{id} (content)   // pre-warm, no fan-out
  own timeline   → ZADD timeline:{author}  // sync: read-your-writes

Author's own timeline is written synchronously so they see their tweet instantly; follower fan-out is async. Celebrity keys are pre-warmed before the Kafka event fires, so followers never cold-miss a viral tweet.

thundering herd — the big one

Shared celebrity key

@taylorswift tweets → 5M followers open feeds in 60 s. Without a cache that's 5M Cassandra reads of one tweet. Instead, one Redis Sorted Set per celebrity serves every follower — 5M cheap Redis reads, ~0 Cassandra reads.

ZREVRANGEBYSCORE
  celebrity-tweets:{celebId}
  +inf -inf LIMIT 0 10   // max 20 items kept
cache stampede

Singleflight mutex

If a celebrity key is missing, 5M simultaneous misses would stampede Cassandra. First reader grabs a lock, loads once, backfills; the rest wait 50 ms and re-read. Read replicas spread the 5M reads across the cluster.

SETNX lock:celebrity-tweets:{id} 1 EX 5
  ok  → load Cassandra, ZADD, del lock
  !ok → sleep 50ms, re-read cache
cold start / warming

Rebuild from Cassandra

A dormant user's timeline:{userId} has expired. Cold start pulls recent tweets for every followee, merges, ranks, writes back the top 200. On deploy / Redis failover we pre-warm DAU timelines so this stays off the hot path.

SMEMBERS following:{userId}
per followee: SELECT … tweets_by_user
merge → rank → ZADD top 200
  // 500 ms–2 s cold · <50 ms warm
two-tier profile cache

User profiles change rarely, so a per-instance Caffeine L1 (1-min TTL, 10K entries) fronts Redis L2 (5-min TTL) fronts PostgreSQL. L1 is sub-ms with no network hop; staleness of a minute is invisible for a name/bio.

L1 Caffeine (1 min) → L2 Redis (5 min) → Postgres
  hit L1 → <1 ms · hit L2 → ~1 ms · miss → ~5 ms
trending — precompute, don't compute per request

A background job runs ZUNIONSTORE across time windows (recent hours weighted more) every 1–5 min and caches the top-10 as one key. Requests do a single GET trending:top10 (~0.1 ms) instead of a 5 ms union each — at 100K req/s that's the difference between possible and not.

GET trending:top10   // 0.1 ms, refreshed by job
Multi-layer: CDN edge (media images) → Caffeine L1 (profiles) → Redis L2 (timelines · celebrity tweets · social graph · trending) → Cassandra / PostgreSQL. Total Redis footprint ≈ 2 TB across ~80 shards. → full cache map on canvas 2 · LLD
C

Bottlenecks & solutions

click a card to open

Celebrity fan-out explosion

Impact: pushing one celebrity tweet to 50M follower timelines is 50M Redis writes — ~50 s of fan-out at 1M ops/s, and it starves normal users' fan-out behind it. This is why pure fan-out-on-write breaks.

Fix: hybrid model — accounts ≥10K followers skip fan-out entirely; their tweets live in one shared celebrity-tweets:{id} key and are pulled + merged at read time. Zero follower writes per celebrity tweet.

Thundering herd on a viral tweet

Impact: millions of followers request the same celebrity tweet within seconds; naive reads hammer one Cassandra partition / one Redis key and melt it.

Fix: one shared Redis key serves all followers; pre-warm the key at post time (before Kafka fires); Redis read replicas distribute the read load; singleflight mutex (SETNX lock … EX 5) prevents stampede on a miss.

Fan-out lag (workers fall behind)

Impact: a burst of tweets pushes Kafka consumer lag past 60 s — followers stop seeing new tweets promptly, hurting the "feed feels live" experience.

Fix: fan-out lag is the headline alert; workers auto-scale on consumer lag; Kafka's 128 partitions absorb the burst durably; a "surprise viral" normal user is dynamically promoted to the celebrity (pull) tier so their pending fan-out stops amplifying.

Cold-start feed (dormant user)

Impact: a user returns after 30 days; their timeline:{userId} was evicted, so the first feed load must rebuild from scratch — 500 ms–2 s if they follow many accounts.

Fix: cache warming pre-loads DAU timelines on deploy / after Redis failover; on a live miss, rebuild pulls recent tweets per followee, ranks, and writes back top 200 so all subsequent reads are <50 ms.

Read fan-out on the pull path

Impact: if a user follows 500 celebrities, naive pull is 500 store reads per feed request — at 3B reads/day that dwarfs the write cost.

Fix: a per-user celebrity-followees:{userId} Set returns only the celebrity subset (usually a handful), so we pull from a small set; each pull hits the shared celebrity cache, not Cassandra; pulls run in parallel and merge with the pre-computed timeline.

Duplicate delivery (at-least-once Kafka)

Impact: a fan-out worker crashes between the ZADD and the offset commit; the message is redelivered and the tweet could land twice in a timeline.

Fix: Redis ZADD is idempotent for the same member — re-adding a tweetId just updates its score, so no duplicate. The pull path dedups at merge time with a LinkedHashMap keyed by tweetId.

Store / partition failure

Impact: a Kafka broker, a Redis shard, or a Cassandra node drops mid-traffic.

Fix: graceful degradation — Kafka down → feed still serves via the pull path; timeline cache lost → rebuild from Cassandra; Cassandra partition → serve stale content from the Redis tweet cache; social-graph Redis down → pause fan-out with backoff, keep serving cached timelines. The feed never shows an error page.

Hot / oversized Cassandra partition

Impact: a celebrity's tweets_by_user partition grows unbounded; full-partition scans get slow.

Fix: only ever read the recent slice with created_at > ? + LIMIT; TTL tweets at ~90 days (USING TTL) so old data auto-expires; the celebrity cache absorbs nearly all reads so the partition is rarely touched directly.

D

CAP & consistency — why AP

pick two; P is not optional
the choice

P is mandatory across data centres, so the real decision is A vs C during a partition. A tweet appearing 5–10 s late is invisible; a feed that fails to load is lost engagement and lost ad revenue. So the feed is AP — serve slightly-stale rather than error.

  • AP: during a partition, serve the cached timeline rather than time out.
  • Strong consistency for 500M users would make every tweet write wait on a cross-DC quorum — seconds, not milliseconds.
  • Two followers legitimately see different feeds for a few seconds — by design, per-user eventual consistency.
strong-consistency islands

Not everything tolerates staleness. Two places lean CP:

  • Follow / unfollow graph: written synchronously (Redis MULTI dual-write). A stale graph means the next fan-out is wrong — sending tweets to someone who unfollowed, or missing someone who just followed.
  • Read-your-own-writes: the author's own timeline is written synchronously before the async fan-out, so a poster always sees their tweet immediately.
MULTI
  SADD followers:{B} {A}
  SADD following:{A} {B}   // atomic, strong
EXEC
Tweet deletion is eventual + safe: soft-delete flag set immediately in Cassandra, async ZREM from timelines via Kafka, and every feed read checks isDeleted() as a read-time safety net — so a deleted tweet is filtered out even before the ZREM lands.

Tweet creation (own view)Strong · read-your-writesSync write to author's own timeline before fan-out

…and finish strong
  • P6 Ranking (2–3): engagement score = likes·1 + RT·2 + replies·1.5, times a time-decay; re-score top 200 every 5–10 min as the ZSET score.
  • P7 Trending (2–3): ZINCRBY per hashtag per window; score on velocity not volume; spam filter + count unique users.
