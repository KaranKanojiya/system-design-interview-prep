B

Hybrid fan-out — the core algorithm

HybridFanoutStrategy + FeedService
the decision (verbatim)
// HybridFanoutStrategy.fanout(...)
boolean isCeleb = poster.isCelebrity();
// isCelebrity() = followerCount >= 10_000

if (isCeleb) {
  // PULL — do nothing now
  readStrategy.fanout(tweet, poster,
      followerIds, timelineCache);
} else {
  // PUSH — write to every follower cache
  writeStrategy.fanout(tweet, poster,
      followerIds, timelineCache);
}

FanoutOnWriteStrategy loops followerIds and calls timelineCache.addToTimeline(...) once per follower. FanoutOnReadStrategy is a deliberate no-op.

worked example — one celebrity, one normal
// @elon posts (50,000,000 followers)
isCelebrity() = true  → READ
   writes to timeline caches = 0
   → 50,000,000 writes AVOIDED
   tweet pulled at read time (max 3/celeb)

// @alice posts (350 followers)
isCelebrity() = false → WRITE
   for each of 350 followerIds:
     cache.addToTimeline(id, FeedItem)
   → 350 cache writes, feed pre-built

// @alice's feed read (follows elon+taylor)
push cache  → [bob, carol tweets]
pull celebs → elon(3) + taylor(3) = 6
merge → dedup → drop deleted → rank

The asymmetry is the whole point: celebrities pay zero write cost; the merge work is deferred to the (far rarer, per-user) read.

Why hybrid? Pure fan-out-on-write gives O(1) reads but pushing Elon's tweet to 50M timelines is a write storm; pure fan-out-on-read is cheap to write but every feed read must pull from every followee. The hybrid splits on User.CELEBRITY_THRESHOLD = 10_000: normal users push (the common case, instant feeds), celebrities are pulled at read time and merged in. A user can cross the threshold mid-session — updateUserType() flips NORMAL→CELEBRITY on the follower increment, so the next tweet fans out the other way.
C

Fan-out & ranking strategies (two Strategy axes)

swap behaviour, not the service

FanoutOnWriteStrategy — push at post time to every follower's timeline cache. name() = "Fan-out on Write (Push)"

  • Writes: O(followers) — one addToTimeline per follower.
  • Reads: O(1) — the feed is already materialised in the cache.
  • Best for: normal users (< 10K followers); wasteful and dangerous for celebrities.

FanoutOnReadStrategy — a no-op at write time; the tweet is pulled from the poster's store at read time. name() = "Fan-out on Read (Pull)"

  • Writes: O(1) — tweet stored once, nothing pushed.
  • Reads: O(celebrities followed) — FeedService pulls the latest few tweets per celebrity.
  • Best for: celebrities (≥ 10K followers) where push would be prohibitive.

HybridFanoutStrategy — composes both leaves, delegating on poster.isCelebrity(). the wired default in AppConfig

  • Composite: holds a write leaf + a read leaf + a celebrityThreshold; callers see one fanout().
  • Normal → push, celebrity → pull: best of both; the merge happens in FeedService.
  • Tunable: the threshold is the ops knob (10K today) trading write cost against read cost.

The second Strategy axis — FeedRanker orders the merged feed, independent of how items arrived.

  • EngagementRanker (wired): freshness × (likes·1 + retweets·2 + replies·1.5 + 1), freshness = 1/(1+hoursAge·0.1) — the "For You" feed.
  • ChronologicalRanker: 1000/(1+secondsAgo·0.01) — pure recency, the "Latest" tab.
  • Drop-in: a future MlRanker is a new class + one line in AppConfig, no FeedService change.

The pattern: FanoutService holds a single FanoutStrategy and FeedService holds a single FeedRanker — neither branches on type, they just call strategy.fanout(...) / ranker.rank(...). Adding a new distribution scheme or ranker is a new class + one line in AppConfig, with zero changes to the services (Open-Closed Principle).
D

Data model detail

Tweet · User · FeedItem · TrendingTopic
Tweet — immutable, Builder-built
tweetId     String   // UUID prefix (8 chars)
userId      String
content     String   // ≤ 280, required
mediaUrls   List<String>   // unmodifiable
hashtags    List<String>   // auto-extracted #\w+
likeCount   AtomicInteger
retweetCount AtomicInteger
replyCount  AtomicInteger
createdAt   LocalDateTime
deleted     volatile boolean  // soft delete

Built via Tweet.Builder — build() validates id/user/content and the 280-char cap, and hashtags are extracted once at construction. Counters are atomic; deleted is volatile for cross-thread visibility.

User — drives the fan-out decision
userId        String
username      String
displayName   String
followerCount int            // synchronized ++/--
followingCount int
userType      UserType       // NORMAL | CELEBRITY | VERIFIED
createdAt     LocalDateTime

isCelebrity() = followerCount >= 10_000

incrementFollowers() is synchronized and calls updateUserType(), which flips NORMAL↔CELEBRITY the moment the count crosses CELEBRITY_THRESHOLD. This is the value the hybrid strategy branches on.

FeedItem — merge unit
tweet   Tweet
score   double            // set by the ranker
source  FeedSource        // FANOUT_WRITE | FANOUT_READ | MERGED
addedAt LocalDateTime

compareTo: higher score first

Wraps a Tweet with a mutable score and a source tag. source records whether the item was pushed or pulled — invaluable for debugging feed latency (too many FANOUT_READ = too many celebrity follows).

TrendingTopic + Follow
// TrendingTopic (Comparable)
hashtag String
count   long
score   double      // count-weighted

// Follow — social-graph edge
followerId String   // who follows
followeeId String   // who is followed
createdAt  LocalDateTime  // equals/hashCode on the pair

TrendingRepository keys a ConcurrentHashMap<String,AtomicLong> by lowercased hashtag; getTopTrending(k) sorts by count. Follow uses value equality on (follower, followee) so the graph stays deduplicated.

Two stores on the read path, on purpose: the TimelineCacheRepository holds pre-built FeedItems pushed for normal users (fast), while TweetRepository keeps the source-of-truth tweets pulled for celebrities. FeedService merges the two and dedups by tweetId so a tweet that arrived via both paths appears once. In production the cache is a Redis Sorted Set and tweets live in Cassandra.
E

Request handling sequence

which class does what, in order

POST /api/tweets  →  post & fan-out

FeedController.handlePostTweet(userId, content)
  └─ TweetService.postTweet(userId, content, mediaUrls)
       1  userRepo.findById(userId)        // UserNotFoundException
       2  Tweet.Builder().tweetId(UUID).userId(..)
              .content(..).mediaUrls(..).build()  // validates, extracts #tags
       3  tweetRepo.save(tweet)
       4  fanoutService.processTweet(tweet):
            poster = userRepo.findById(tweet.userId)
            followerIds = followRepo.getFollowerIds(userId)
            strategy.fanout(tweet, poster, followerIds, cache)
              poster.isCelebrity()? READ (no-op) : WRITE (push each)
            return followerIds.size()
       5  trendingService.recordTweet(tweet)   // HashtagExtractor → incrementHashtag
  └─ return Tweet

Fan-out and trending both hang off the post, but only the strategy decides push vs. pull. In production steps 4–5 become Kafka consumers (Observer) so the poster's request returns immediately.

GET /api/feed  →  generate feed (the read path)

FeedController.handleGetFeed(userId, limit)
  └─ FeedService.generateFeed(userId, limit)
       1  timelineCache.getTimeline(userId, 200)     // pushed items
       2  followRepo.getFolloweeIds(userId)
            → filter userRepo.findById(id).isCelebrity()
       3  for each celeb: tweetRepo.findByUserId(id, 3)  // PULL, FANOUT_READ
       4  merged = pushed + pulled
       5  dedup by tweetId (HashSet)
       6  drop item.tweet.isDeleted()
       7  ranker.rank(active)          // EngagementRanker: score desc
       8  return top `limit`
  └─ printFeed(feed)

Steps 1 and 3 are the two halves of the hybrid model reunited: pre-computed pushes for the many normal followees, live pulls for the few celebrities. Ranking runs over the merged, deduped, non-deleted set.

F

Design patterns used

GoF-categorized
Behavioral
  • Strategy ×2 — FanoutStrategy (push/pull/hybrid) and FeedRanker (chrono/engagement). Two independent axes swapped without touching services.
  • Mediator — FeedService orchestrates cache lookup → celebrity pull → merge → dedup → rank → trim so no caller coordinates the pipeline.
  • Observer (conceptual) — post fires fan-out + trending; in production a Kafka topic with independent consumer groups.
Structural
  • Composite — HybridFanoutStrategy IS-A FanoutStrategy but HAS-A write leaf + read leaf, delegating on celebrity status. The caller sees one fanout().
  • Repository — five interfaces (Tweet / User / Follow / TimelineCache / Trending) over InMemory… impls; swap to Redis / Cassandra with no service change.
Creational
  • Builder — Tweet.Builder. Required + optional + derived (hashtags) fields; build() validates the 280-char cap and yields an immutable Tweet.
  • Factory / Composition root — AppConfig news-up and wires the entire graph in one place (Spring @Configuration in production).
Why they cluster: Strategy + Composite + Repository together deliver the Open-Closed Principle — a new fan-out scheme, a new ranker, or a new storage backend is an addition, never an edit. The Mediator keeps the feed pipeline in one readable place, and the Builder + atomic counters keep Tweet immutable and thread-safe. → scaling trade-offs (Redis sorted sets, Kafka fan-out, the celebrity problem at 150M) on canvas 3

Glossary — one-liners

terms used above
Fan-out on writepush a tweet to every follower's timeline cache at post time — fast reads, costly writes
Fan-out on readstore the tweet once, pull it into followers' feeds at read time — cheap writes, costly reads
Hybrid fan-outpush for normal users, pull for celebrities — the production answer to the celebrity problem
Celebrity problema user with millions of followers can't be pushed to in real time; route them to pull
Timeline cacheper-user store of pre-computed FeedItems filled by fan-out-on-write
Strategy patterninterchangeable algorithms behind one interface, chosen at runtime (fan-out, ranker)
Composite patternan object that is a strategy but delegates to child strategies (HybridFanoutStrategy)
Mediator patternone class (FeedService) coordinates a multi-step pipeline so callers don't have to
Engagement scorefreshness × (likes·1 + retweets·2 + replies·1.5 + 1) — the "For You" ordering
Soft deleteset a volatile deleted flag; the tweet is filtered out of feeds, not physically removed
