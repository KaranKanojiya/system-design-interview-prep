The engine — TimeSeriesStore.query + downsample

verbatim · TreeMap.subMap · O(log n + k)
from engine/TimeSeriesStore.java
// The core data structure — metricName → (epochSecond → points in that second)
private final Map<String, TreeMap<Long, List<MetricPoint>>> store = new ConcurrentHashMap<>();

// ── STORE — O(log S) where S = distinct seconds for that metric ──
public void store(MetricPoint point) {
  store.computeIfAbsent(point.getName(), k -> new TreeMap<>())
       .computeIfAbsent(point.getTimestamp().getEpochSecond(),
                        k -> Collections.synchronizedList(new ArrayList<>()))
       .add(point);
}

// ── RANGE QUERY — the whole reason for TreeMap ──
// subMap is inclusive-exclusive; +1 to include the 'to' second.
// Returns a VIEW — no tree copy. O(log S + K) where K = points in range.
public List<MetricPoint> query(String metricName, Instant from, Instant to) {
  TreeMap<Long, List<MetricPoint>> timeBuckets = store.get(metricName);
  if (timeBuckets == null) return List.of();

  return timeBuckets.subMap(from.getEpochSecond(), to.getEpochSecond() + 1)
      .values().stream()
      .flatMap(List::stream)
      .collect(Collectors.toList());
}

// ── DOWNSAMPLE — raw → 1-min → 5-min → 1-hr ──
// Group by bucket key, average, one representative point per bucket.
public List<MetricPoint> downsample(String metricName, Duration bucketSize) {
  TreeMap<Long, List<MetricPoint>> timeBuckets = store.get(metricName);
  if (timeBuckets == null) return List.of();

  long bucketSeconds = bucketSize.toSeconds();
  Map<Long, List<MetricPoint>> downsampledBuckets = new TreeMap<>();

  for (List<MetricPoint> points : timeBuckets.values()) {
    for (MetricPoint point : points) {
      // bucket-align — 12:37:42 with 60 s bucket → 12:37:00
      long bucketKey = (point.getTimestamp().getEpochSecond() / bucketSeconds)
                       * bucketSeconds;
      downsampledBuckets.computeIfAbsent(bucketKey, k -> new ArrayList<>())
                        .add(point);
    }
  }

  List<MetricPoint> result = new ArrayList<>();
  for (Map.Entry<Long, List<MetricPoint>> entry : downsampledBuckets.entrySet()) {
    double avgValue = entry.getValue().stream()
        .mapToDouble(MetricPoint::getValue).average().orElse(0.0);
    result.add(new MetricPoint(
        metricName, avgValue,
        Instant.ofEpochSecond(entry.getKey()),
        entry.getValue().getFirst().getMetricType(),
        entry.getValue().getFirst().getTags()));
  }
  return result;
}
Why TreeMap.subMap beats HashMap: HashMap point lookup is O(1) but range query = iterate ALL keys + filter = O(n). For time-series data, range queries dominate (every dashboard query is [from, to]). TreeMap gives O(log n) seek to from, then O(k) sequential iteration — exactly the access pattern we have. On top of this in prod, add: (1) Gorilla compression (delta-of-delta on timestamps + XOR on values = 10-20× shrink), (2) LSM-tree on disk for durability, (3) columnar chunks — same shape, orders-of-magnitude scale.

// Deterministic hash → same traceId always gets the same decision → 
// no cross-service coordination needed. O(1).
@Override
public boolean shouldSample(TraceContext context) {
  if (context == null || context.getTraceId() == null) return false;
  int hash   = Math.abs(context.getTraceId().hashCode());  // guards Integer.MIN_VALUE
  int bucket = hash % 100;
  return bucket < (int) (sampleRate * 100);               // 0.1 → bucket < 10
}

// Operation-agnostic — head-based decision is fixed at the trace root
@Override
public boolean shouldSample(TraceContext context, String operationName) {
  return shouldSample(context);
}

Baseline for all traffic. Dropped at the entry point, so downstream services don't waste CPU on unsampled traces. Blind: may drop a rare error trace at the same rate as normal ones — mitigate by layering tail-based on top.

from strategy/sampling/TailBasedSamplingStrategy.java
// Phase 1 — collect all spans (return true always, buffer everything)
@Override
public boolean shouldSample(TraceContext context) {
  return true;
}

// Phase 2 — post-collection decision, once collector has full trace
@Override
public boolean shouldSample(TraceContext context, String operationName) {
  if (context == null) return false;

  // Errors are ALWAYS interesting — 100 % retention
  String errorFlag = context.getBaggageItem("error");
  if ("true".equalsIgnoreCase(errorFlag)) return true;

  // Slow traces (> latencyThresholdMs) also kept — the debug tail
  String latencyStr = context.getBaggageItem("latency_ms");
  if (latencyStr != null) {
    try {
      long latencyMs = Long.parseLong(latencyStr);
      if (latencyMs > latencyThresholdMs) return true;
    } catch (NumberFormatException e) { // malformed → drop }
  }
  return false;
}

Never loses errors or slow traces. Requires all spans for a trace to reach the SAME collector instance — partition Kafka by traceId. Memory heavy: buffer all spans for the assembly window (typically 30 s).

from strategy/sampling/RateLimitedSamplingStrategy.java
// Predictable cost ceiling. Lock-free CAS on AtomicInteger + AtomicLong.
// Benign race on window reset can only OVER-sample, never under.

private final AtomicInteger counter = new AtomicInteger();
private final AtomicLong windowStart = new AtomicLong();
private final int maxPerSecond;

@Override
public boolean shouldSample(TraceContext context) {
  long now = System.currentTimeMillis() / 1000;
  long window = windowStart.get();

  if (now != window) {                       // new epoch second
    if (windowStart.compareAndSet(window, now)) {
      counter.set(0);                        // reset — winner sets
    }
  }
  int count = counter.incrementAndGet();
  return count <= maxPerSecond;
}

Safety valve. Combines with head + tail: if head 10 % + tail-all-errors still produces > 1 000 traces/s during a spike, rate limit at 1 000 to prevent cost explosion (DDoS scenario). First N traces per second may be health checks — accepted trade-off.

Prod recipe: layer all three — head 10 % baseline → tail keep 100 % errors + slow → rate 1 K/s ceiling. Result: bounded cost, no lost errors, ~2-5 % of original volume retained.

Retention tiers — raw → 1-min → 5-min → 1-hr → archive

1 000× shrink per year
Raw · 1 h
1-min avg · 24 h
5-min avg · 7 d
1-hr avg · 1 yr
Cold archive · 2 yr+
Raw resolution — hot tier
  • Retention: 1 hour · volume: 3 600 pts/hr per series
  • Storage: SSD / NVMe · compression: Gorilla (10-20×)
  • Use case: real-time debugging — an on-call needs the exact spike shape at 15 s resolution
  • Query cost: highest — full-resolution scan. Cache at Query Engine (30 s TTL).
1-min rollup · downsample(name, Duration.ofMinutes(1))
Raw: 3 600 pts/hour
  ↓ downsample bucket = (epochSec / 60) · 60
  ↓ avg per bucket
1-min avg: 60 pts/hour (60× shrink)
  • Retention: 24 hours · volume: 1 440 pts/day per series
  • Use case: yesterday's incident retro — resolution good enough to see the p99 spike
  • Query router: range > 1 h → hit this tier instead of raw
5-min rollup
  • Retention: 7 days · volume: 12 pts/hour · 288 pts/day
  • Use case: weekly SLO reports · trend analysis · capacity planning inputs
  • Query router: range > 24 h → this tier · 12× shrink vs 1-min
1-hr rollup · downsample(name, Duration.ofHours(1))
  • Retention: 1 year · volume: 24 pts/day · 8 760 pts/year
  • Use case: capacity planning · year-over-year seasonality · Black Friday sizing
  • Total shrink: raw 3 600 pts/hr → 1 pt/hr = 3 600× shrink per year
Cold archive — S3 Glacier / GCS Archive / Azure Archive Blob
  • Retention: 2+ years · volume: 1-hr avg + compressed columnar (Parquet)
  • Storage cost: pennies/GB — $0.004/GB-mo vs $0.023/GB-mo for hot S3
  • Retrieval latency: minutes (Glacier) — NOT for interactive queries
  • Use case: compliance (SOX / GDPR) · post-incident forensic replay · audit trail
Automatic resolution router: the Query Engine picks the right tier by time range — range < 1 h ? raw : range < 24 h ? 1-min : range < 7 d ? 5-min : range < 1 y ? 1-hr : archive. Dashboard authors don't know this exists — they write rate(http_requests_total[5m]) and the engine picks the cheapest tier that satisfies the resolution.

Alert state machine — PENDING → FIRING → ACKNOWLEDGED → RESOLVED

from model/AlertStatus.java + service/AlertService.java
the evaluation loop (verbatim)
public void evaluateRules() {
  Instant now         = Instant.now();
  Instant windowStart = now.minusSeconds(60);         // last 60 s of data

  for (AlertRule rule : rules) {
    if (!rule.isEnabled()) continue;

    // 1. Query metric data DIRECTLY from TSDB — the CP contract, NO cache
    List<MetricPoint> points = metricService.query(
        rule.getMetricName(), windowStart, now);

    // 2. Delegate to Strategy — Threshold or Anomaly
    boolean shouldAlert = alertingStrategy.shouldAlert(rule, points);

    if (shouldAlert && !firingRules.containsKey(rule.getId())) {
      // 3a. NEW alert — transition OK → FIRING
      double currentValue = points.isEmpty() ? 0.0
          : points.get(points.size() - 1).getValue();

      Alert alert = new Alert(rule, currentValue,
          "Rule '" + rule.getName() + "' triggered: "
              + rule.getCondition() + " " + rule.getThreshold()
              + " (current=" + currentValue + ")");

      alertRepo.save(alert);
      firingRules.put(rule.getId(), alert.getId());   // DEDUP — no double-page

      System.out.println("[ALERT] FIRING — rule '" + rule.getName() + "'");

    } else if (!shouldAlert && firingRules.containsKey(rule.getId())) {
      // 3b. Condition cleared — resolve existing
      String alertId = firingRules.remove(rule.getId());
      resolveAlert(alertId);                          // alert.resolve() stamps resolvedAt
    }
  }
}
Why firingRules is essential: without it, every 60 s evaluation cycle that sees a firing condition would create a NEW Alert and re-notify — 60 pages/hour for a single ongoing outage. With it, the FIRST breach creates the Alert and adds to the dedup map; subsequent evaluations see it's already firing and skip. Only the resolution transition (breach clears) is announced.
state transitions (enum AlertStatus)

  ↓ new Alert(rule, value, msg)
FIRING             // evaluateRules detects breach
  ↓ alert.acknowledge()
ACKNOWLEDGED       // operator saw it, still investigating
  ↓ alert.resolve()
RESOLVED           // stamps resolvedAt = Instant.now()

Latency budget (happy path ingest): HTTP receive 1 ms · MetricPoint.of + tags 0.1 ms · timeSeriesStore.store 0.5 ms (two computeIfAbsents + list append) · repo write (only first time) 0.5 ms · 202 return 0.5 ms = < 3 ms end-to-end. That's why we can absorb 100 M points/s across a scaled ingestor fleet — the hot path is O(log n) TreeMap insert, nothing else.
