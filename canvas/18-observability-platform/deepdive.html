The reality: big shops run BOTH. Prometheus pulls metrics from services (self-healing on target churn), while OTLP pushes traces and logs (matches the request-response lifecycle). Our platform accepts both — the OTel Collector is the funnel that unifies them.

Prometheus scrape — pull model
# prometheus.yml — service discovery + scrape interval
scrape_configs:
  - job_name: 'k8s-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:                # which pods to scrape
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
    scrape_interval: 15s
    metrics_path: /metrics

# On the application side — expose /metrics via client library
# Prometheus GET /metrics every 15 s → returns text exposition format:
#
#   # HELP http_requests_total Number of HTTP requests
#   # TYPE http_requests_total counter
#   http_requests_total{method="POST",status="200"} 1027
#   http_requests_total{method="POST",status="500"} 3

Wins: service-discovery-driven — no config change when pods rescheduled · up{} for free · Prometheus is the source of truth for what's alive · target can't overwhelm Prometheus (Prometheus paces itself).

Loses: can't scrape past NAT / firewall · misses short-lived jobs (use Pushgateway workaround) · no partial-second precision · scrape lag (up to 15 s stale).

OTLP push — application initiates
// Instrumented app — OpenTelemetry SDK, gRPC or HTTP push
OpenTelemetrySdk otel = OpenTelemetrySdk.builder()
    .setTracerProvider(SdkTracerProvider.builder()
        .addSpanProcessor(BatchSpanProcessor.builder(
            OtlpGrpcSpanExporter.builder()
                .setEndpoint("http://otel-collector:4317")
                .build())
            .setMaxExportBatchSize(512)     // batch — amortize network
            .setScheduleDelay(5, SECONDS)   // flush every 5 s or on full
            .build())
        .build())
    .build();

// Emit a span — non-blocking, queued for batch export
Span span = tracer.spanBuilder("checkout")
    .setAttribute("user_id", userId)
    .startSpan();
try (Scope scope = span.makeCurrent()) {
  processCheckout();
} finally { span.end(); }

Wins: works across firewalls (outbound only) · sub-second granularity · natural fit for request-response spans and log streams · vendor-neutral (OTLP is standard).

Loses: back-pressure only via retry / drop (Kafka buffer + collector queue essential) · silent when the app is down (need external liveness) · SDK adds ~1-3 % CPU overhead on instrumented services.

AspectAgent (Datadog agent, otel-collector-agent DaemonSet)Agentless (SDK sends direct to backend)

Buffering during outageYes — local disk buffer, resends when backend recoversApp must retry / drop — no local buffer
BatchingCross-service batching (multiple apps → 1 agent → 1 batch)Per-app batching only

Our pick: DaemonSet OTel Collector (agent per K8s node). Pod → localhost collector → central collector fleet → Kafka. Local buffer for outage tolerance, cross-pod batching, and metadata enrichment happen at the agent — the app SDK stays cheap.

picking push vs pull, per signal type
  • Long-running service metrics (K8s deployments, cron pods) → Prometheus pull. Free up{}, service-discovery-driven, right cadence (15 s).
  • Batch jobs / serverless / Lambda → OTLP push. Prometheus can't scrape a dead job.
  • Traces (spans) → OTLP push. Span lifecycle is inherently push (start / end at real times).
  • Logs → OTLP push or agent tail (Fluentbit / Vector) reading files.
  • Custom business metrics with high cardinality → OTLP push through the sampling pipeline — Prometheus pull would break cardinality limits.

side by side
Gorilla compression (Facebook, 2015) — the 10-20× shrink
// Timestamp encoding — delta-of-delta
// Metrics have STABLE cadence (15 s scrape). Deltas are near-constant → deltas of deltas are near-zero → variable-length encoding fits most in 1-7 bits.

t0 = 1_700_000_000
t1 = 1_700_000_015  → Δ=15
t2 = 1_700_000_030  → Δ=15  → ΔΔ=0  (encode "same delta" = 1 bit)
t3 = 1_700_000_046  → Δ=16  → ΔΔ=1  (encode ΔΔ in 7 bits)

// Value encoding — XOR with previous
// Consecutive metric values are close (CPU 32.1 %, then 32.3 %) → XOR has many trailing zeros → encode leading + trailing zeros + meaningful bits.

v0 = 32.1  → store full 64-bit float
v1 = 32.3  → XOR(v0, v1) = 0x00...0000abc  → "5 leading zero bytes + 12 bits" ≈ 20 bits total

// Result: 16 bytes/point raw → 1.37 bytes/point avg. 10-12× shrink.
// Combined with block-level Zstd on cold blocks → 20× shrink.

In our engine: TimeSeriesStore uses in-memory TreeMap<Long, List<MetricPoint>> (uncompressed for O(1) modification). In prod (VictoriaMetrics / InfluxDB), the hot bucket is uncompressed; blocks > 2 hr old get compacted to Gorilla-compressed columnar chunks on disk.

Parquet + object storage — the trace long-tail
Trace store layout (Grafana Tempo / Jaeger with S3 backend):

s3://traces-bucket/
├── year=2026/month=08/day=31/hour=14/
│   ├── block-abc123.parquet          # 1-hour blocks, columnar
│   ├── block-abc123.index            # traceId → block-offset bloom filter
│   └── ...

Column groups in the Parquet block:
  traceId (STRING)                    # dictionary encoded — repeats hugely
  spanId (STRING)                     # dictionary encoded
  parentSpanId (STRING, nullable)
  serviceName (STRING)                # dictionary encoded — ~500 unique
  operationName (STRING)              # dictionary encoded — ~10K unique
  startTime (INT64)                   # delta-of-delta
  durationMs (INT32)                  # RLE + bit-packing
  status (INT8)                       # RLE — mostly OK
  tags (MAP<STRING,STRING>)           # optional (heavy — often dropped for cost)

Why Parquet not TSDB: traces are WRITE-once, READ-rare. 99 % of traces are read 0 times. Row-based storage wastes disk; columnar allows column-level projection (return only traceId, serviceName, durationMs for a service map — never touch tags column). Bloom filter on traceId in each block: query "get trace X" hits ~1 block, not the whole day.

Retention tiers: 24 h hot (SSD) · 7 d warm (S3 Standard) · 30 d cold (S3 Glacier IR) · then delete. Errors + long tail (kept via tail-sampling) retained 30 d always.

Inverted index (Elasticsearch / OpenSearch / Loki)
// Inverted index — the "which docs contain this word" lookup
// Same idea as a book index at the back.

Documents:
  doc1: "user 42 login failed"
  doc2: "user 17 login ok"
  doc3: "payment 42 failed"

Inverted index:
  "user"     → [doc1, doc2]
  "42"       → [doc1, doc3]
  "login"    → [doc1, doc2]
  "failed"   → [doc1, doc3]
  "payment"  → [doc3]
  "ok"       → [doc2]

Query: "user AND failed"
  → intersect(user_postings, failed_postings)
  → {doc1, doc2} ∩ {doc1, doc3}  = {doc1}   ← O(smaller-list)

Loki alternative (lighter weight): index ONLY on labels (service, level, env, host), leave message body unindexed → LogQL scans block bodies with a full-text grep. Cheaper storage (no inverted index for body), slower for full-text queries. Good when queries mostly filter by service/level and use free-text only for the last mile.

Retention: 24 h hot (fast full-text) · 3 d warm (cheaper storage class) · 7 d cold (compressed, slow) · delete. Errors kept longer via routing rule.

Correlation glue: every signal carries traceId + spanId. A dashboard error spike ⇒ click ⇒ query trace store by traceId ⇒ click ⇒ query log store by traceId. Three stores, one lookup pattern — that's what turns "logs" into "observability".

CAP split — AP ingest, CP alerting

from docs/tradeoffs/CAP_THEOREM.md
SubsystemChoiceWhyFailure mode
Metric / trace / log ingestionAP — availability + partition toleranceNever block application producers. Applications must not slow down because observability is unhappy.During partition: keep buffering to Kafka, may temporarily lose durability guarantees. Eventual consistency once reconnected.
Kafka event busAP (with ISR)acks=1 per-partition — availability-first. Replication factor 3 gives durability; ISR shrink allowed during partition.May lose < 1 s of un-replicated writes on broker failure. Producers keep publishing.
TSDB reads (dashboards)AP with staleness boundDashboards can return "last known good" during partition — a 30 s stale dashboard is fine.Query proxy caches last successful query per panel (30 s TTL).
Alert rule evaluatorCP — consistency + partition toleranceAn alert firing at 12:00 must query fresh data — a cached "CPU 40 %" would MISS a spike to 95 %. Alert rules tableCP — strong consistencyA newly-created rule must be visible on the next 60 s eval cycle across all nodes. Postgres with row-level replication.Rule create returns 503 during partition to primary. Rule reads may go to replica (may miss latest for a few seconds).
Notification dedupCP — Redis SETNXPrevent double-page: SETNX alert:{ruleId}:{timestamp} with 5 min TTL — only ONE notification per alert-window across ALL nodes.During Redis partition: prefer double-page over silent miss (fail-open on notification).
Service mapAPEventually consistent — service edges derived from trace assembly. A newly-deployed edge may take 60 s to appear.Missing edges shown as "recently added" hint. Never a hard error.
Aggregation cache (5 min p99)AP — Redis with TTLDashboard aggregates cached; a 5 min stale p99 chart is fine (dashboards are exploratory).Cache miss on Redis partition → recompute from TSDB.
The split is the interview soundbite: "We are AP for ingestion (never block the app) and CP for alerting (never lie to on-call). Everything else lives on the spectrum — dashboards cache aggressively, alert rules replicate strongly, service map is best-effort. Trying to be CP everywhere would make the platform itself the outage; trying to be AP everywhere would miss real incidents."

Cardinality management — the label explosion trap

why user_id is a career-ending tag
the explosion
// Two metrics look identical to a developer. 
// One will bankrupt your cluster.

// SAFE — bounded cardinality:
http_requests_total{
  service="checkout",     // ~500 services
  method="POST",          // ~10 methods
  status="200",           // ~30 status codes
  endpoint="/api/orders"  // ~200 endpoints
}
// = 500 × 10 × 30 × 200 = 30 M unique series
// large but bounded — grows with deployment

// TOXIC — unbounded cardinality:
http_requests_total{
  ...,
  user_id="u_193847",     // 200 M users
  request_id="uuid",      // infinite
  trace_id="uuid"         // infinite
}
// = 30 M × 200 M × ∞ × ∞ = HEAT DEATH
// TSDB memory grows with unique tag combos. 
// Per-series overhead: ~3 KB.  200M × 3KB = 600 GB 
// per hour PER METRIC. Cluster crashes.
the fix — hard cap at ingest
// At the OTel Collector: cardinality-limiter processor

processors:
  cardinalitylimit:
    max_cardinality_per_metric: 10000
    action_on_exceed: drop        # or "aggregate_into_bucket"
    drop_labels_regex: ".*_id$"   # drop trace_id, user_id, request_id
    high_cardinality_labels:
      - request_id: drop
      - user_id: hash_to_bucket   # 200M → 100 buckets
      - session_id: drop

// Backend also enforces — belt-and-suspenders
// VictoriaMetrics: -search.maxUniqueTimeseries=10000
// Prometheus: sample_limit + label_limit per scrape target

// Escalation path:
// 1. Metric exceeds cap → drop labels, emit warning metric
// 2. Metric persistently exceeds → email metric owner
// 3. Repeated → auto-quarantine metric name
The rule of thumb: a label is safe if its cardinality grows with deployment size (service count, region count, host count) — not with traffic (user_id, request_id, timestamp). "Would this label value have existed yesterday?" — if no, don't tag it. Use it in a trace instead — traces are meant for high-cardinality per-request context; metrics are for aggregate rates.

Query performance — LSM tree · block index · downsampling router

how p99 stays < 1 s at 1 M series
LSM tree layout (VictoriaMetrics / InfluxDB IOx)
MEMORY (hot writes):
  ├── active bucket (last 2 hr uncompressed)
  ├── flushed to WAL (append-only durability)

DISK — L0 (recent, 2-24 hr):
  ├── block-{start}-{end}.chunk       # Gorilla-compressed
  ├── block-{start}-{end}.index       # tag → posting list
  ├── block-{start}-{end}.bloom       # label existence

DISK — L1 (24 hr - 7 d, compacted):
  ├── merged blocks, 1-hr downsampled

OBJECT STORE — L2 (> 7 d):
  ├── S3 / GCS / Blob — cheap, 5-min downsampled

Query 'rate(http_requests_total[5m])' from 12:00 to 13:00:
  1. Parse selector → tag posting list intersection
  2. Bloom filter each L0 block → keep candidates only
  3. subMap scan candidate blocks → collect points
  4. Apply rate() → return series
  Total: ~50-200 ms for typical dashboard panel
downsampling router — cheapest tier that fits
// PromQL router pseudo-code
Duration range = to.minus(from);
Duration step  = query.step ?? (range / 300);
                     // aim for ~300 points per chart

if (step <= 30s)  return queryRaw(name, from, to);       // L0 raw
if (step <= 5m)   return query1MinRollup(name, from, to);// L0 downsampled
if (step <= 1h)   return query5MinRollup(name, from, to);// L1
if (step <= 1d)   return query1HrRollup(name, from, to); // L1
                  return queryArchive(name, from, to);   // L2 (S3)

// Result — same query, different tier by range:
//   last 1 hr chart  → raw (60 pts, 10 ms)
//   last 24 hr chart → 5-min (288 pts, 30 ms)
//   last 30 d chart  → 1-hr (720 pts, 100 ms)
//   last 1 yr chart  → 1-hr (8760 pts, 500 ms)
Alert queries are the exception — they intentionally hit raw / L0 (no cache). A 60 s alert eval window of rate(errors[1m]) > 100 must see the true 12:34:00 - 12:35:00 slice, not a 5-min bucket that may have started at 12:32. This is the CP boundary from Section C — AlertService.evaluateRules in the LLD calls metricService.query directly, never the cache.

I

35-minute interview walkthrough

the answer, timed
phase 1 · clarify (2–3 min)
  • "Scale — mid (Shopify) or hyperscaler (Netflix)? I'll assume 100 M metrics/s · 1 B spans/day · 1 TB logs/day."
  • "Multi-tenant or single? Single tenant simplifies isolation; I'll assume single."
  • "3 pillars in scope — metrics, traces, logs? Alerting too? Yes."
  • "Query p99 target? < 1 s for dashboards, < 60 s alert eval latency."
phase 2 · draw architecture (5–7 min)
  • 3-col: instrumented apps · OTel Collector · Kafka as unifying bus.
  • 3 processor lanes → 3 stores: TSDB · Trace Store · Log Store. Correlation via traceId.
  • Split CAP: ingest = AP (never block apps); alert eval = CP (fresh TSDB).
  • Query Engine + Grafana on the read path; Alert Manager on the eval + notify path.
phase 3 · storage deep dive (8–10 min)
  • TSDB: Gorilla compression = delta-of-delta timestamps + XOR values → 10-20× shrink.
  • TreeMap bucketed by epochSec — subMap is O(log n) range seek. Show it on the board.
  • Traces: Parquet on S3, dictionary-encoded columns, bloom index on traceId. Write once, read rarely.
  • Logs: inverted index (ES) OR label-only (Loki) — trade-off is search flexibility vs cost.
  • Downsampling router: cheapest tier that satisfies the query resolution.
phase 4 · cardinality & sampling (5–7 min)
  • Cardinality trap: user_id as a tag ⇒ 200 M series ⇒ cluster OOM. Hard cap 10 K at collector.
  • Sampling layers: head 10 % (hash % 100) + tail 100 % errors + rate 1 K/s ceiling.
  • Tail-based needs Kafka partition by traceId so all spans hit the same collector.
  • "Would this label have existed yesterday?" — if no, don't tag it, put it in a trace.
phase 5 · alerting & scale (5–7 min)
  • Alert eval 60 s cadence · reads directly from TSDB, no cache (CP).
  • firingRules in-process map + Redis SETNX across nodes = dedup, no double-page.
  • Strategy pattern — Threshold for infra (CPU > 80 %), Anomaly (k · σ) for app metrics.
  • Kafka lag > 5 s ⇒ auto-scale consumers · back-pressure signal ⇒ drop low-priority DEBUG.
phase 6 · trade-offs defended (3–5 min)
  • Why Kafka not Kinesis — replay tooling, at-scale ecosystem, self-hosted flexibility.
  • Why tiered retention — 30 d raw costs 30× with 0 % more insight.
  • Why build not buy — break-even ~$200-400K/yr; below that, Datadog / New Relic win.
  • Why AP ingest + CP alert — the two SLAs have opposite priorities; force-fitting one hurts both.
30-second pitch: "Three pillars — metrics, traces, logs — unified by a shared traceId for correlation. Push and pull ingest through an OTel Collector fleet into Kafka partitioned by traceId. Three lanes fan out to purpose-built stores: Gorilla-compressed TSDB for metrics, Parquet columnar on S3 for traces, inverted-index or label-only for logs. Alert Manager evaluates rules every 60 s against fresh TSDB reads — that's the CP boundary — with Redis SETNX dedup on notify. Cardinality hard-capped at 10 K series per metric to prevent one bad label crashing the cluster. Layered sampling (head 10 % + tail-all-errors + rate 1 K/s) delivers bounded cost with zero missed errors."
Interview red flags to avoid:
• "Store everything raw forever." (no tiering = 30× cost)
• "Add user_id as a metric label." (cardinality bomb)
• "Cache alert query results for 30 s." (silent alert misses — CP violation)
• "Trust Prometheus pull for everything." (misses batch jobs, serverless)
• "Sample traces at fixed 1 %." (drops real errors 99 % of the time)
• "Log everything at DEBUG in prod." (Kafka lag, log pipeline collapse)
• "Use the same TSDB for metrics and traces." (wrong access pattern, wastes storage)
