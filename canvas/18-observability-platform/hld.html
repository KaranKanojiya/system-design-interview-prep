A

Problem & requirements

3 pillars · split CAP
functional
  • Metrics — ingest COUNTER · GAUGE · HISTOGRAM · TIMER with tag labels; query by name + range; aggregate sum/avg/percentile/rate.
  • Traces — start trace, create child spans, propagate context traceparent: 00-{traceId}-{spanId}-01, assemble span tree.
  • Logs — structured JSON with optional traceId + spanId; search by service, level, time, and trace.
  • Sampling — head-based (hash %) · tail-based (keep errors + slow) · rate-limited (cost ceiling).
  • Downsampling — raw → 1-min → 5-min → 1-hour tiers, 1 000× compression over a year.
  • Alerts — declarative rules (metric · condition · threshold · duration · severity); threshold + anomaly (mean ± k·σ).
  • Service map — auto-derived from trace parent-child edges; per-edge request/error/latency stats.
  • Dashboards — RED (Rate · Errors · Duration) for services · USE (Utilisation · Saturation · Errors) for resources.
  • Cardinality management — tag drop-list, hash-bucket high-card labels, hard cap per metric.
non-functional
  • Ingestion 100 M metric points/s · 1 B spans/day · 1 TB log/day; never block producers.
  • Query p99 < 500 ms for 1-hour dashboard windows (cached · pre-aggregated).
  • Alert eval latency < 60 s from ingest to fire; direct TSDB query (no cache).
  • Data freshness < 5 s ingest-to-dashboard.
  • Compression 100× via downsampling; 10-70× column compression on-disk.
  • Cardinality cap reject metrics > 10 K unique label combos.
  • Sampling accuracy head-based ± 2 % of rate; tail-based captures 100 % of errors.
  • Availability 99.9 % ingest (AP · buffered) · 99.99 % alert eval (CP · dedicated path).
  • Meta-monitoring deadman switch + external Pingdom — who watches the watcher?
The split-CAP insight: ingest is AP — a partition must never block a production service that's trying to emit metrics (Kafka absorbs, we backfill). Alerting is CP — a stale cached read that misses a real spike is worse than a brief alert outage (query TSDB directly, meta-alert if unreachable). Same platform, two consistency stances at the boundary.

Cardinality is the #1 cost driver: a metric with 5 tags × 100 values each = 100⁵ = 10 B time series. One rogue tag (user_id, request_id) added at the SDK can 10⁶× the storage bill. Mitigation: drop at ingest · hash-bucket (user_id → user_bucket = hash % 100) · hard cap per metric (429 + on-call the metric owner).
Why 100 M points/s isn't scary: Kafka absorbs bursts (72 h buffer). Consumers scale horizontally by partition. TSDB writes are batch-appended (10-70× compression). The real bottleneck is query fan-out (a p99 over 1 hour = 3 600 buckets × 5 M series = infeasible without downsampling), not ingest.

Data model — 3 pillars, one traceId

correlation is the glue
write path (in-memory · TSDB · Trace · Log)
MetricPoint                // atomic unit — immutable
  name                      // "http.request.duration_ms"
  value        double
  timestamp    Instant      // Instant.now() at ingest
  metricType   COUNTER|GAUGE|HISTOGRAM|TIMER
  tags         Map<String,String>   // Map.copyOf

Span                        // one op in a distributed trace
  traceId      String       // shared across all spans
  spanId       String       // unique
  parentSpanId String       // null == root
  operationName, serviceName
  startTime, endTime, duration
  status       OK|ERROR|TIMEOUT|CANCELLED
  tags         Map<String,String>
  logs         List<SpanLog>

LogEntry                    // structured JSON log
  timestamp    Instant
  level        TRACE|DEBUG|INFO|WARN|ERROR|FATAL
  message      String
  serviceName  String
  traceId, spanId (nullable — the cross-pillar link)
  attributes   Map<String,String>

AlertRule                   // declarative — PostgreSQL row
  metricName, condition (>/<), threshold
  durationSeconds (must hold this long)
  severity     WARNING | CRITICAL | PAGE
  enabled      boolean
read path (TreeMap · index · cache)
TimeSeriesStore             // engine class
  Map<String,               // metricName
      TreeMap<Long,         // epochSecond bucket
        List<MetricPoint>>>
  query(name, from, to) →
    subMap(from.epochSec,
           to.epochSec + 1)  // O(log n + k)

TraceContext                // W3C propagation carrier
  traceparent: 00-{traceId}
               -{spanId}-01 // HTTP header
  baggage      Map<String,String>   // tail-sample hints

Downsampling tiers
  raw           1 h retention (real-time debug)
  1-min avg    24 h retention (this week)
  5-min avg     7 d retention (weekly trends)
  1-hr avg      1 y retention (capacity plan)

Redis cache keys
  q:{hash}     30 s TTL   // query results
  svcmap       5 m TTL    // topology
  meta:names   10 m TTL   // autocomplete
  alert:notify:{id} 60 s   // SETNX dedup
The correlation contract: the SDK sets MDC.put("traceId", ctx.getTraceId()) when a request enters, and the log encoder emits it as a JSON field. Result: a log line, a span, and a metric emitted during the same request all carry the same traceId — and the dashboard's "click metric anomaly → open trace → click span → correlated logs" flow just works.

Key design choices (deep-dived on canvas 3)

defend these
CAP

Ingest AP · Alert CP

Kafka absorbs ingest bursts; producers never block. AlertService queries TSDB direct (no cache, meta-alert if down). Same platform, two consistency stances at the boundary. → canvas 3 · CAP

sampling

Layer 3 strategies

Head-based 10 % baseline + tail-based 100 % of errors/slow + rate-limited 1 K/s ceiling. Bounded cost, no lost errors. → canvas 3 · sampling

storage

Bucketed TreeMap · O(log n)

TreeMap.subMap(from, to+1) is O(log n + k) for range queries. Downsampling raw → 1-min → 5-min → 1-hr = 1 000× shrink per year. → canvas 2 · TSDB

cardinality

Cap at ingest, not query

10 K unique combos / metric hard cap. Drop-list for user_id · hash-bucket high-card labels. Cost control is a WRITE-path problem — you can't fix it at read time. → canvas 3 · cardinality

alerting

Threshold + anomaly (Strategy)

Static threshold for infra metrics · anomaly (mean ± k·σ) for app metrics with natural variation. Swap via setAlertingStrategy. Runbook required per rule. → canvas 3 · alert fatigue

correlation

traceId is the glue

Metric · span · log all carry the same traceId. Dashboard drilldown: metric anomaly → trace waterfall → correlated logs. Without correlation, 3 pillars are 3 dashboards. → canvas 2 · sequence
