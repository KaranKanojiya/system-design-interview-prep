worked examples
// 300M requests/month → per second
300M ÷ 2.5M = 120/sec

// 10B requests/day → per second
10B ÷ 100K = 100K/sec

// 1000 req/sec → per month
1000 × 2.5M = 2.5B/month

Full ladder: month ÷30 day ÷24 hour ÷60 min ÷60 sec.

M

Interview math tips

how to sound structured
  • Round aggressively — 86,400 → 100K. Speed > precision.
  • Use powers of 10 — "about 30M seconds in a year," don't multiply 365×24×3600.
  • State assumptions first — "100M users, 10% DAU, 5 actions each."
  • Formula first, then plug in — you look structured.
  • Convert to per-second early — capacity planning works in QPS.
  • Multiply storage by 3 — replication factor; always mention it.
  • Peak = 3× average — simple default for peak traffic.
  • Cap it at ~3 minutes — get the order of magnitude and move on.

terms used above
QPS / RPSqueries (requests) per second — the unit all capacity planning uses
DAU / MAUdaily / monthly active users — the traffic driver you assume first
Throughputhow much work per unit time a component handles (req/s, MB/s)
Latencytime for one operation to complete (ns / µs / ms)
Bandwidthdata moved per second = QPS × payload size
Back-of-envelopea fast, rounded estimate to get the order of magnitude
Order of magnitudethe power-of-10 bucket (1K vs 1M vs 1B) — what actually matters
Replication factorcopies of each record for durability (usually ×3)
Shardingsplitting data across nodes when it exceeds one machine
Hot / cold datafrequently vs rarely accessed — the 80/20 cache rule
p50 / p99median / 99th-percentile latency — tail latency is what users feel
