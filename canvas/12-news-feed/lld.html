B

Algorithmic ranking — the core formula

AlgorithmicRankingStrategy
the code (verbatim, from computeScore)
private double computeScore(FeedItem it, User viewer) {
  double aff   = computeAffinityScore(
                    viewer.getUserId(),
                    it.getPost().getAuthorId());
  double rec   = computeRecencyDecay(
                    it.getPost().getCreatedAt());
  double eng   = computeEngagementBoost(it.getPost());
  double ctype = it.getPost().getContentType()
                                .getWeight();
  return aff * rec * eng * ctype;
}

// affinity: 1.0 + interactions*0.1, capped 2.0
Math.min(1.0 + n * 0.1, 2.0)

// recency: exp(-0.05 * hoursAge)
Math.exp(-0.05 * hoursAge)

// engagement: log-compressed (comments×2, shares×3)
1.0 + Math.log(1 + likes + com*2 + sh*3) / 10.0

Constants: RECENCY_DECAY_CONSTANT 0.05, AFFINITY_PER_INTERACTION 0.1, MAX_AFFINITY 2.0, ENGAGEMENT_LOG_DIVISOR 10.0. ContentType weights TEXT 1.0 · IMAGE 1.3 · VIDEO 1.5 · LINK 1.1 · POLL 1.4.

worked example — best friend vs viral stranger
// P1: best friend, 2 h old, 50 likes, 10 com, 5 sh, VIDEO
aff = min(1.0 + 5*0.1, 2.0)        = 1.5
rec = exp(-0.05 * 2)               = 0.905
eng = 1 + log(1 + 50 + 20 + 15)/10 = 1.445
ctype = VIDEO                      = 1.5
score = 1.5 * 0.905 * 1.445 * 1.5  = 2.94

// P2: stranger, 1 h old, 500 likes, 50 com, 20 sh, VIDEO
aff = 1.0 (no history)             = 1.0
rec = exp(-0.05 * 1)               = 0.951
eng = 1 + log(1 + 500+100+60)/10   = 1.649
ctype = VIDEO                      = 1.5
score = 1.0 * 0.951 * 1.649 * 1.5  = 2.35

// P1 > P2. AFFINITY DOMINATES.

This is why your best-friend's mundane video ranks above a stranger's viral one. Even though P2 has 10× the engagement and is newer, the 1.5× affinity multiplier flips the ranking.

Why log on engagement and exp on recency? Log compression on engagement stops a 1 M-like post from permanently owning the feed (5 → 50 likes matters more than 100 K → 1 M). Exponential decay on recency drops off fast: a 24-hour-old post scores 0.30, a 72-hour-old one 0.03 — effectively invisible. Affinity is additive (0.1 per interaction, capped 2.0) so it doesn't explode. Each factor has its own shape and its own reason.

Fan-out strategies (Strategy + Composite)

swap the distribution, not the service

FanoutOnWriteStrategy — O(N) writes on publish, O(1) on read

public void distribute(Post post, User author,
                       List<String> followerIds,
                       TimelineCache cache) {
  for (String followerId : followerIds) {
    cache.addToTimeline(followerId,
                         post.getPostId(),
                         post.getCreatedAt());
  }
}
  • Great for: normal users (100–1 000 followers). Bounded write cost.
  • Kills: celebrities — 10 M followers × 10 posts/day = 100 M cache writes/day from one user.
  • In production: the for-loop is a Kafka consumer that pipelines 1 000 ZADDs per round-trip against Redis Cluster.

FanoutOnReadStrategy — O(1) publish, O(C) read (C = celebrities followed)

public void distribute(Post post, User author,
                       List<String> followerIds,
                       TimelineCache cache) {
  // NO-OP — celebrity's post stays in author's
  // user timeline. Pulled at read by FeedService.
}
  • Great for: celebrities — post is instant, no write amplification.
  • Cost: each feed request must query C celebrity timelines. Cache with a per-node local L1 (Caffeine, 10 s TTL) to survive the thundering herd.

HybridFanoutStrategy — Strategy + Composite. the production answer

public void distribute(Post post, User author,
                       List<String> followerIds,
                       TimelineCache cache) {
  if (author.isCelebrity()) {   // followerCount > 10_000
    readPathCount.incrementAndGet();
    readStrategy.distribute(post, author,
                             followerIds, cache);
  } else {
    writePathCount.incrementAndGet();
    writeStrategy.distribute(post, author,
                              followerIds, cache);
  }
}
  • A single if-statement is the entire hybrid design. From FanoutService's side, it's just one strategy — the routing is invisible.
  • Composite pattern: it wraps both concrete strategies and delegates. Owned by AppConfig, which wires new HybridFanoutStrategy(writeStrategy, readStrategy).
  • Tracks writePathCount / readPathCount AtomicInts — surfaced in FeedStatsDisplay.

Two Strategy axes power the whole system:

FanoutStrategy      →  Write · Read · Hybrid (composite)
RankingStrategy     →  Algorithmic · Chronological
  • Anti-pattern: a god UglyFeedService with if (isCelebrity) hardcoded in publishPost and a growing switch(rankMode) in getFeed. Adding an algorithm = editing service code (violates OCP).
  • Clean: services depend only on the two interfaces. Adding a new fan-out mode = new class + one line in AppConfig. Zero service edits. A/B testing per user cohort becomes trivial.

Timeline cache — the sorted-set analogue

InMemoryTimelineCache
the guts (Java stand-in for Redis ZSET)
Map<String, TreeMap<LocalDateTime, String>> timelines;
// per-user TreeMap, sorted reverseOrder (newest first)

// WRITE (fan-out on write):
timeline = computeIfAbsent(userId,
    k -> new TreeMap<>(Collections.reverseOrder()));
synchronized(timeline) {
  timeline.put(timestamp, postId);
  while (timeline.size() > MAX_TIMELINE_SIZE) {  // 1000
    timeline.pollLastEntry();  // evict oldest — O(1)
  }
}

// READ (cursor):
NavigableMap<LocalDateTime, String> afterCursor =
  timeline.tailMap(cursor.getLastTimestamp(), false);
// tailMap of a reverse-ordered TreeMap = older posts. O(log N).
Redis mapping
// Java (in-memory)         Redis (production)
addToTimeline          →  ZADD timeline:{u} score post
pollLastEntry (cap 1K) →  ZREMRANGEBYRANK timeline:{u} 0 -1001
getTimeline(u, limit)  →  ZREVRANGEBYSCORE +inf -inf
                             LIMIT 0 20
tailMap(cursorTs)      →  ZREVRANGEBYSCORE (cursorScore -inf
                             LIMIT 0 20
removeFromTimeline     →  ZREM timeline:{u} postId

// TTL (production):
                           EXPIRE timeline:{u} 604800   // 7d

The in-memory TreeMap is not a toy — it's an O(log N) sorted structure with the same ops as a Redis ZSET (with an O(1) tail evict via pollLastEntry).

Timestamp collisions: if two posts hit the same LocalDateTime, the code appends plusNanos(1) in a loop to avoid overwriting the map entry. Redis avoids this natively because ZSET members are unique — score ties are broken by member string. In prod, score = ranking_score, member = post_id.

Request handling sequence

which class does what, in order

POST /posts  →  publish (write path)

FeedController.handleCreatePost(userId, content, contentType, mediaUrl)
  └─ PostService.createPost(...)
       1  userRepository.findById(userId)                // or UserNotFound
       2  Post.Builder()
             .postId(UUID.randomUUID()...substring(0,8))
             .authorId(userId).authorName(name)
             .content(content).contentType(type)
             .mediaUrl(url).createdAt(now).build()
       3  postRepository.save(post)                      // ConcurrentHashMap put
       4  author.incrementPostCount()                    // denormalised counter
       5  fanoutService.distribute(post, author)
            ├─ socialGraphService.getFollowers(authorId)
            ├─ HybridFanoutStrategy.distribute(...)
            │     ├─ if isCelebrity → FanoutOnReadStrategy  (no-op)
            │     └─ else          → FanoutOnWriteStrategy
            │                        for each: cache.addToTimeline(f, postId, ts)
            └─ notificationService.notifyNewPost(followerIds, post)
  └─ return Post   // 201 to client (~60 ms sync)

GET /feed/{userId}  →  read the feed

FeedController.handleGetFeed(userId, cursor)
  └─ FeedService.getFeed(userId, cursor)   // «Facade»
       1  timelineService.getTimeline(userId, cursor)
             └─ timelineCache.getTimeline(...) → postIds
             └─ postRepository.findByIds(postIds)      // hydrate
           wrap each Post → FeedItem(TIMELINE_CACHE)
       2  socialGraphService.getFollowing(userId)
           for each followedId:
             user = userRepository.findById(followedId)
             if (user.isCelebrity()):                    // >10_000
               postRepository.findRecentByAuthorId(id, 10)
               wrap each Post → FeedItem(PULLED_ON_READ)
       3  de-dupe by postId (HashSet)
       4  rankingService.rank(items, viewer)
             └─ AlgorithmicRankingStrategy.rank(...)
                  for each item: setScore(computeScore(item, viewer))
                  ranked.sort(null)                        // FeedItem: Comparable DESC
                  setPosition(i+1)
       5  applyPagination(ranked, cursor)
             ├─ if firstPage: subList(0, pageSize)
             └─ else: skip until lastPostId, then take pageSize
  └─ return List<FeedItem>   // 200 to client

POST /posts/{id}/likes  →  like & feed the ranker

FeedController.handleLike(userId, postId)
  └─ EngagementService.likePost(userId, postId)
       1  if engagementRepository.hasLiked(u, p): return  // idempotent
       2  engagementRepository.saveLike(new Like(u, p))
       3  post.incrementLikes()                             // AtomicInteger
       4  algorithmicRanking.recordInteraction(u, post.getAuthorId())
          // affinityScore for (u → author) grows by +0.1, cap 2.0
          // → the ranker will boost author's future posts for u
       5  notificationService.notifyLike(post.getAuthorId(), u.name)

Step 4 is the loop that closes ranking: every engagement trains the affinity map used on the next feed read. Shares are the same shape (strongest signal), comments too.

F

Design patterns used

GoF-categorised
Behavioral
  • Strategy × 2 — FanoutStrategy (Write / Read / Hybrid) and RankingStrategy (Algorithmic / Chronological). Two independent axes; both injected in AppConfig.
  • Iterator — FeedCursor (lastPostId + lastTimestamp + pageSize) drives cursor-based infinite scroll.
  • Observer (conceptual) — NotificationService observes post/like/comment events fired by services.
Structural
  • Composite — HybridFanoutStrategy composes both write & read strategies behind one interface.
  • Facade — FeedService.getFeed hides 5 collaborators (TimelineService, SocialGraphService, RankingService, PostRepository, UserRepository) behind one call.
  • Repository — 4 interfaces (User / Post / Follow / Engagement) → InMemory impls. Swap to Cassandra / PG for prod.
Creational
  • Builder — Post.Builder for the multi-field immutable Post (id, content, type, media, timestamp).
  • Factory — AppConfig is the composition root; the one place new appears. Replace with Spring @Configuration / Guice in production.
Why they cluster: Strategy × 2 + Composite + Facade + Repository together enforce the Open-Closed Principle across every dimension the system varies on — fan-out mode, ranking algorithm, storage backend. New content-type weights, a new "ForYou" ranker, a Cassandra repository — all are additions, never edits to service code. → CAP / consistency deep-dive on canvas 3
