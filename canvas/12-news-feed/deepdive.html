A

Scaling strategy

what to shard & how
app tier

Stateless → horizontal

Post / Feed / Engagement / Ranking / SocialGraph all stateless. Auto-scale by CPU + p99. Feed peak ~175 K/s ÷ ~1 K rps/instance → ~200 Feed pods.

timeline cache

Redis Cluster · 40 shards

Hash-slot sharding on timeline:{user_id}. 500 M DAU × 40 KB ≈ 20 TB → ~40 masters × 512 GB (+ replicas → 80 nodes). Add nodes with MIGRATE: only 1/N keys move.

fan-out workers

Kafka consumer group · 32 → 256

Auto-scale on Kafka lag. Lag > 100 K → +8 workers. Emergency at 500 K → +32. Cooldown 10 min. Max = 4× partitions.

database sharding — pick a partition strategy

Hash on user_id (posts table)

Cassandra's default. Partition key user_id co-locates all of a user's posts on one node — enables the O(1) celebrity pull (ZREVRANGE user_timeline:{celeb} 0 4).

CREATE TABLE posts (
  post_id BIGINT, user_id BIGINT, ...,
  PRIMARY KEY (user_id, post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);
verdict — chosen for posts
  • Even load — 1 B random user_ids hash uniformly.
  • Free ordering within a partition (clustering on post_id DESC).
  • Hot partition on celebrities: Elon's row gets slammed by the pull path. Fix with L1 Caffeine + read replicas.

Range on post_id (Snowflake time-sortable)

Post IDs are Snowflake → monotonically increasing. Range-based means all new posts hit the newest shard.

shard 1: post_id 0..2^62
shard 2: post_id 2^62..2^63
// today's writes → only shard 2. hot!
verdict — avoid
  • Hot write shard: Snowflake is time-sortable → today's 6 K writes/s all land on one shard.
  • Good for range scans, which the feed never needs — the read pattern is point look-ups by user_id or post_id.
  • Interview red flag: "range partitioning on time-sortable keys = hot shard."

Consistent hashing ← the Redis / Cassandra default

Ring of virtual nodes. Add or lose a node → only ~1/N keys move (not the whole keyspace). Redis Cluster uses 16 384 hash slots; Cassandra uses vnodes. Same idea both places.

slot = CRC16("timeline:user_123") % 16384
node = slotOwner(slot)
// re-shard: MIGRATE moves slots, keys keep their homes.
verdict
  • Elastic: add capacity for a spike without a rehash storm.
  • Virtual nodes smooth out uneven arcs.
  • Same technique used by the Redis cluster and Cassandra partitioner — one mental model.
Fan-out auto-scaling in practice: monitor aggregate_lag = produced − consumed. Lag > 100 K for 2 min → +8 workers. Lag < 10 K for 10 min → −4 workers. Emergency at 500 K → +32 & page. During a major event (election night, ~170 K posts/s = 10× baseline), workers scale 64 → 256 in 2–3 min; feed becomes 30–60 s stale during the ramp — users see the "N new posts" banner and move on.

Fan-out deep-dive — the star of the interview

push · pull · hybrid — with the math
Push (Fan-out on Write)

Great for normals

  • Publish: O(N followers) — Redis pipeline of ZADD.
  • Read: O(1) — single ZREVRANGEBYSCORE.
  • Bounded for a user with 300 followers (~1–2 ms pipelined).
Pull (Fan-out on Read)

Great for celebs

  • Publish: O(1) — post lands only in author's user timeline.
  • Read: O(C) — for each celeb followed, pull latest 5.
  • Reader-side cost, but bounded (~5–20 celebs / user).
Hybrid ← chosen

Best of both

  • if (author.isCelebrity()) pull else push.
  • 99.99% of users → push. 0.01% → pull.
  • Adds ~5–15 ms to reads; eliminates ~2.5 T writes/day.
The math that kills pure push: Celebrity with 50 M followers posts. Redis pipeline @ 100 K ZADD/s ⇒ 50 M / 100 K = 500 s ≈ 8 min of fan-out per post. Times 10 posts/day = 83 min/day of fan-out from one user — during which workers back up and everyone else's feed goes stale. Across ~100 K celebrities × 5 posts/day × 5 M avg followers = 2.5 trillion writes/day just for celebrities. Hybrid deletes all of them.
read-path timing (hybrid)
Feed read: viewer opens app
  ├─ 1–2 ms   ZREVRANGEBYSCORE timeline:{u}  (500 IDs)
  ├─ 5–15 ms  parallel pull ~12 celebrities
  ├─ 10–20 ms rank 560 candidates
  ├─ 1–2 ms   diversity injection
  ├─ 15–30 ms hydrate 20 posts (batch, parallel)
  └─ 2–5 ms   serialise + return
Total server:  ~35–75 ms
+ network:    ~20–40 ms RTT
p99 < 200 ms budget: met with room to spare.
write-path timing
Publish: sync path (in code)
  ├─ 5–15 ms  Cassandra QUORUM write (posts + posts_by_id)
  ├─ 1–2 ms   HSET post:{id} cache
  ├─ 1–2 ms   Kafka publish
  └─ 2–5 ms   serialise + return
Total sync:   ~9–24 ms  (client sees 201 in ~60 ms with RTT)

Async fan-out (Kafka consumer)
  ├─ hybrid: celebrity? YES → skip. NO → follower-list pipeline
  ├─ 300 followers: ~1–2 ms pipelined ZADD
  └─ 10 M followers via push would take ~100 s — skipped

Caching & feature store — where 200 ms lives

L1 · L2 · feature
L1 · local (Caffeine)

Celeb timelines & hot posts

Per Feed Service node: 10 K entries, 10 s TTL. 10 M concurrent celeb reads → ~600 Redis reads after coalescing across 100 nodes.

Caffeine.newBuilder()
  .maximumSize(10_000)
  .expireAfterWrite(10, SECONDS)
  .refreshAfterWrite(5, SECONDS);
L2 · timeline & post cache (Redis)

ZSET + Hash

Timeline: sorted set per user, cap 500, 7 d TTL. Post content: post:{id} Hash, 24 h TTL — hot hydration.
Cache-aside on read; write-through on publish.

ZADD timeline:{u} score post_id
ZREMRANGEBYRANK timeline:{u} 0 -501
EXPIRE timeline:{u} 604800
HSET post:{id} content author ... EX 86400
Feature store (Redis)

Pre-computed ranker inputs

Score 560 candidates in <20 ms only if features are already there. Hashes:

user_features:{u}       // daily
affinity:{viewer}:{author}   // 30d TTL
post_features:{p}       // updated on engagement
Cache warming: after a Redis shard restart, first requests trigger a rebuild — pull last ~20 posts from each followed user, rank, populate timeline:{u}. First page is 200–500 ms instead of ~2 ms — one-time cost, transparent to the user. On new-user signup: cold-start pulls latest from onboarding follows + trending fillers so the feed isn't empty.

Bottlenecks & solutions

click a card to open

Celebrity fan-out (the classic)

Impact: pure push to 50 M followers = 500 s of ZADD, saturates Kafka workers, delays everyone else's fan-out.

Fix: HybridFanoutStrategy — skip fan-out when author.isCelebrity(). Post lives in author's user timeline; FeedService pulls it at read time. 2.5 T daily writes eliminated. In our code: User.CELEBRITY_THRESHOLD = 10_000, ~1 M in production.

Thundering herd on a celebrity post

Impact: celeb posts → 10 M followers refresh in 60 s → 10 M reads target the same celebrity user_timeline key.

Fix (layered): (1) L1 Caffeine on each Feed Service node (10 s TTL) → 10 M requests coalesce to ~600 Redis reads across 100 nodes; (2) singleflight — same-key concurrent misses share one downstream call; (3) Redis read replicas for hot celeb keys; (4) preemptive cache warming when the celebrity posts.

Fan-out queue depth during major events

Impact: election night — post rate 10× (17 K/s → 170 K/s). Kafka lag balloons; feeds go stale.

Fix: auto-scale on lag — 64 → 256 workers in 2–3 min. Feed is 30–60 s stale during the ramp; the "N new posts available" banner absorbs the perceived UX cost. Scale-down with 10-min cooldown to avoid oscillation.

Hot Redis shard (celebrity timeline or viral post)

Impact: one shard saturated while others idle. Feed p99 spikes.

Fix: Redis Cluster distributes reads across replicas natively for celeb timelines; L1 Caffeine absorbs the top ~10 K hot posts with a 5–10 s TTL. For truly viral posts, key-replicate the entry across shards.

Cache stampede on TTL expiry

Impact: when timeline:{u} or post:{id} expires under load, thousands of misses race to the DB.

Fix: singleflight lock — SET lock:{key} NX EX 5. First request rebuilds and populates; the rest sleep 50 ms and re-GET. TTL jitter (±10%) prevents synchronised expiry across the fleet.

Concurrent likes on a viral post (lost updates)

Impact: 1 000 users like the same post in 1 s. Naive read-modify-write loses updates.

Fix: two-layer counter. Redis INCR post_likes:{id} (atomic, sub-ms, single-threaded → serialised) for the display count that feeds the ranker, plus a Cassandra counter for durability. Dedup with SADD post_likers:{id}. In code: Post.likeCount is AtomicInteger; engagementRepository.hasLiked is the idempotency check.

Deep-scroll fallback (page 26+)

Impact: timeline cache holds only 500 entries. Page 26 exhausts it.

Fix: fall back to Cassandra range query on posts partitioned by follower's following list, ordered by created_at DESC. Latency jumps ~2 ms → ~50–100 ms — acceptable because <0.1% of feed requests reach page 26. Optionally maintain a compressed archive_timeline:{u} ZSET (posts 501–2000) for power users.

Redis Cluster node loss

Impact: a master fails → ~1/N of timelines vanish; the replica must promote.

Fix: Redis Cluster promotes replica in <30 s. Feed degrades gracefully: L1 Caffeine serves what it has; complete cache miss falls back to fan-out-on-read against Cassandra (~200–500 ms — slower but functional). Cache warming rebuilds organically as new posts fan out.

CAP & consistency — AP feed, CP social graph

the exception matters
the choice

P is mandatory. Between A and C for the feed: A wins. At 175 K feed reads/s, 1 s of errors = 175 K failed impressions and directly hits ad revenue. A 5–10 s stale feed is invisible to users.

  • AP for feed / timeline / counts — eventually consistent.
  • PACELC → PA/EL: partition → A; else → L. Fast reads always.
  • Read-your-writes for the poster: client-side optimistic render — 201 response is inserted at the top locally until the server copy arrives via fan-out.
the CP exception — social graph

Follow / unfollow must be strongly consistent. A stale follower list means fan-out includes an ex-follower ("why am I seeing their posts?") or misses a fresh follower.

// atomic follow
BEGIN
  INSERT INTO following (a, b);
  INSERT INTO followers (b, a);
COMMIT
MULTI
  SADD followers:b a
  SADD following:a b
EXEC

Postgres source of truth + synchronous Redis Set update. No Kafka on the follow path.

Post creationStrong (write-ack)0 sAuthor must see their post immediately (optimistic UI)

Post deletion is soft: flip is_deleted=true in Cassandra; the post lingers in 300+ follower timelines and ages out naturally. Trying to eagerly ZREM from every follower's cache is infeasible at 50 M followers. Filter is_deleted during hydration in FeedService step 5. Same idea for unfollow: lazy filter at read time — no cache scan.

Cursor pagination + real-time push

why offset breaks · WebSocket banner
why NOT offset
// Page 1: LIMIT 20 OFFSET 0    → A B C D ... T
// User reads. 3 new posts (X Y Z) arrive above.
// Page 2: LIMIT 20 OFFSET 20  → R S T U V W ...
// PROBLEM: R S T were already on page 1. DUPLICATES.

Offset shifts under real-time inserts. At 500 M posts/day this breaks constantly.

cursor: stable
// cursor = {score}_{post_id}  (ties broken by post_id)
Page 1  → next_cursor = "5.42_post_724..."
Page 2  → ZREVRANGEBYSCORE timeline:{u}
             (5.42 -inf LIMIT 0 20
// New posts get HIGHER scores → appear ABOVE cursor
// Old posts stay in position relative to cursor
// No duplicates. No misses within a page.

In our code: FeedCursor = {lastPostId, lastTimestamp, pageSize=20}. InMemoryTimelineCache.tailMap(cursorTs, false) is the O(log N) skip.

gap detection

"N new posts available"

When serving page 2+, count posts with score > page-1-max-score. If >0 → gap_detected=true, new_posts_count=N. Client renders a banner instead of jumping.

WebSocket

Push notification, not content

Message = ~100 B: {type:"NEW_POSTS", count:3}. Content is fetched on the next feed request. 100 M concurrent connections across ~1 000 WS gateway nodes (100 K per node).

SSE / long-poll fallback

For hostile networks

Corporate firewalls or old browsers can't hold WebSockets. GET /feed/stream (Server-Sent Events) is one-way, HTTP-friendly. Long-polling as last resort.

Banner vs auto-inject: Facebook / LinkedIn use the banner — user controls when to refresh; no scroll jumps. Twitter historically auto-injects — great for a live event stream, bad for casual reading. Choose banner by default.

  • P2 Estimate (3–4): 500 M posts/day → 6 K W/s (peak 17 K), 5 B feed reads → 60 K R/s (peak 175 K), 100:1 read heavy, 20 TB timeline cache.

  • P4 Architecture (4–5 · CORE): Client → API GW → LB → Post/Feed → Kafka → Fan-out workers → Redis Timeline Cache + Cassandra + PG + Push. Draw first, narrate write + read.
  • P5 Fan-out (10–12 · STAR): compare push / pull / hybrid; deliver the celebrity math (50 M × 100 K/s = 500 s); back-pressure & auto-scaling; the celebrity thundering herd + L1 Caffeine fix.
…and finish strong

  • P7 Pagination + WS (3–4): why offset breaks; cursor = {score}_{post_id}; gap detection + banner; WebSocket sends the notification, not the content.

Green flags: you drive scoping · deliver the celebrity math without prompting · state AP + CP-exception explicitly · walk through the ranking formula with a worked example · address gap detection unasked · name-drop thundering herd + singleflight.
