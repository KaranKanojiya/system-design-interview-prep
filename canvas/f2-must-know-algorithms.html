B

Hashing & partitioning

where does this key live?
consistent hashing — mechanism

Place both nodes and keys on a ring of hash values (0 … 2³²−1). A key is owned by the first node found walking clockwise. Add or remove a node and only the keys in that one arc move.

# naive: rebalances almost everything
partition = hash(key) % N   # N changes → ~100% remap

# consistent hashing: only ~1/N keys move
owner = first_node_clockwise( hash(key) )

Virtual nodes: give each physical node 100–200 points on the ring so load is even and rebalancing is smooth.

Used in: P07 distributed cache (consistent hash + vnodes), P19 API gateway load balancing (same key → same backend), P01 URL shortener (which shard stores the mapping).

rendezvous (highest-random-weight) hashing — mechanism

No ring. For a key, score every node with hash(key, node) and pick the highest. Removing a node only re-homes that node's keys (each moves to its next-highest scorer); no vnode bookkeeping needed.

owner = argmaxnode  hash(key, node)   # pick the max-scoring node
Consistent vs rendezvous: both move only ~1/N keys on change. Consistent hashing scales to huge node counts cheaply (lookup via the ring); rendezvous is simpler and gives perfectly even load for a small, mostly-static node set. Used in: cache/shard placement, CDN edge selection.

Consensus & coordination

agreeing without a boss
leader election (Raft)

What: elect one leader per term via majority vote, using randomized election timeouts to avoid split votes.

  • Follower times out → becomes candidate, votes for itself, requests votes.
  • Wins on a majority → sends heartbeats to stay leader.
  • Split vote → new random timeouts, retry next term.

Why/when: exactly one node must own writes/decisions.

Used in: P17 task scheduler (Bully election), P19 service discovery (Consul/Raft).
quorum — W + R > N

What: a write needs W acks, a read needs R responses; if W+R>N the two sets must overlap on a fresh replica.

// N=3, W=2, R=2  →  4 > 3
write {A,B}   read {B,C}
overlap = {B} // sees latest

Why/when: tune the W/R split for read- vs write-heavy loads; W+R≤N = fast but may read stale (AP).

Used in: P07 distributed cache (tunable consistency).
gossip / SWIM

What: every T seconds each node syncs state with a random peer; knowledge spreads exponentially.

round k → ~2^k nodes know
all N nodes in O(log N) rounds
1000 nodes, T=1s → ~10 s

Why/when: decentralized membership & failure detection with no central registry; SWIM adds indirect PINGs to avoid false positives.

Used in: Cassandra/Consul membership; P18 observability, P19 backend health.
Quorum ≠ consensus: quorum guarantees read/write overlap; consensus (Raft/Paxos) guarantees all nodes agree on a single ordered log. Reach for consensus when you need a leader or a replicated log; reach for quorum when you just need to not read stale data.

E

Caching eviction — LRU vs LFU

bounded memory
least recently used

What: evict the entry untouched for the longest time. Implemented with a hash map + doubly-linked list → O(1) get/put; every access moves the key to the front.

Why/when: access is bursty and recency predicts the next hit (a key hot now is likely hot in a second). The safe default.

Weakness: a one-off scan of many keys can flush genuinely popular entries.

least frequently used

What: evict the entry with the lowest access count (with tie-breaking / aging so old spikes decay).

Why/when: long-run popularity matters more than recency — a stable hot set that shouldn't be evicted by a burst of cold traffic.

Weakness: new-but-good entries start at count 1 and can be evicted before they prove themselves; needs aging to adapt.

Used in: P07 distributed cache exposes both as pluggable EvictionStrategy (LRU / LFU / TTL).
F

Rate limiting

throttle the firehose
token bucket

What: tokens refill at a fixed rate up to a cap; each request spends one; empty bucket → reject.

Why/when: you want a steady average rate but should allow short bursts (up to the bucket size). The most common API limiter.

tokens = min(cap, tokens + rate*Δt)
if tokens >= 1: tokens -= 1  # allow
else: reject
leaky bucket

What: requests enter a queue and drain (leak) at a constant rate; overflow → reject.

Why/when: you need a smooth, constant output rate downstream (no bursts) — e.g. protecting a fragile backend.

sliding window

What: count requests in a rolling time window (log of timestamps, or a weighted counter across two fixed windows).

Why/when: you need an accurate rolling limit without the boundary spike that fixed windows allow (2× burst at the edge).

Used in: P02 rate limiter ships all five (token bucket, leaky bucket, fixed window, sliding-window log, sliding-window counter); P19 API gateway applies per-client limits at the edge. Rule of thumb: token bucket for APIs (bursts OK), leaky bucket to smooth downstream, sliding window when accuracy at the boundary matters.
G

Ordering & IDs

time without a clock
Lamport timestamps

What: one integer per node; bump on each event, and on receive set C = max(C, T) + 1.

Why/when: a cheap total order for events with no synced wall clock. a → b ⟹ C(a) < C(b).

Catch: the converse is false — C(a)<C(b) does not imply causality. Can't detect concurrency.
vector clocks

What: a vector of counters, one slot per node; merge = element-wise max on receive.

Why/when: detect concurrency — if neither vector dominates the other, the two writes conflict and need resolution.

Used in: P14 real-time collaboration, P04 chat ordering, Dynamo-style conflict detection.
Snowflake IDs

What: 64-bit ID = timestamp | machine-id | sequence.

| 41b time | 10b node | 12b seq |

Why/when: globally unique, roughly time-sortable IDs across many servers with no coordination and no DB round-trip.

Used in: P01 URL shortener (distributed ID gen), P04/P16 event & order IDs.
H

Geo & anti-entropy

space & repair
geohash / quadtree

What: geohash interleaves lat/long bits into one sortable string — shared prefix ≈ nearby. Quadtree recursively splits space into 4 quadrants, denser where there are more points.

Why/when: "find everything near me" and spatial range queries — turn 2-D proximity into a 1-D index lookup or a tree descent.

Used in: P08 ride sharing (match nearby drivers ↔ riders).
Merkle trees

What: a tree of hashes; each parent hashes its children, so the root fingerprints all the data.

        root=h(AB+CD)
       /           \
   h(A+B)        h(C+D)
   /   \          /   \
 [A]   [B]      [C]   [D]

Why/when: anti-entropy — compare roots between replicas; if they differ, drill down in O(log N) to find and sync only the divergent ranges.

Used in: Cassandra/DynamoDB replica repair; P15 file storage (content verification & dedup).
