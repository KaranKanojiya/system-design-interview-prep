A

Problem & requirements

clarify first
functional
  • Assign the nearest free spot by vehicle type (Motorcycle / Car / Bus-Truck); deny entry if that type is full.
  • Issue a ticket on entry (ticket ID, vehicle, spot, entry time); free the spot on exit.
  • Calculate fee by duration × per-hour rate (rounded up); take payment (cash / card) at exit before the barrier opens.
  • Show real-time availability per floor & per type on display boards and via API.
non-functional
  • Thread safety — two gates must never double-book the same spot (the core NFR).
  • Latency — ticket issuance < 100 ms so the gate opens quickly.
  • Data integrity — ACID for payment; money must not be lost or double-charged.
  • Availability 99.9%; availability display refresh < 1 s. Consistency > availability → CP.
B

Back-of-envelope estimation

single lot · 850 spots
Total spots850
Floors5
Vehicles / day~2,000
Peak entry~5 / min
Write QPS (entry+exit)<1 / s
Avail reads~5 / s
Avg stay3 hrs
Storage / 5 yr<500 MB
Derivation: 850 spots (5 floors × 170) · 2,000 vehicles/day ÷ 86,400 s ≈ 0.02 writes/s, peak 5/min ≈ 0.08/s — trivial load. Display boards poll every 1 s → a handful of read/s. Storage = ~2,000 tickets/day × 365 ≈ 730K rows/yr × ~300 B ≈ 220 MB/yr → <500 MB over 5 yr, so one PostgreSQL node is plenty — the interest is correctness under concurrency, not scale. → full math on canvas 3 & F3 · Estimation

E

Data model

relational · ACID
parking_spot (hot lookup)
spot_id     VARCHAR(20) // PK e.g. S-2-045
floor       INT         // 1–5
spot_number INT
spot_type   ENUM        // MOTORCYCLE/CAR/LARGE
is_occupied BOOLEAN     // default false
vehicle_id  VARCHAR(20) // FK, nullable

Partial index on (spot_type, floor, spot_number) WHERE is_occupied=false makes nearest-spot lookup instant. The row lock lives here.

parking_ticket + payment
ticket_id  VARCHAR(30) // PK, date-based
vehicle_id VARCHAR(20) // FK
spot_id    VARCHAR(20) // FK
entry_time TIMESTAMP
exit_time  TIMESTAMP   // null until exit
amount     DECIMAL(8,2)
is_paid    BOOLEAN
// payment: id, ticket_id (UNIQUE),
//   amount, method, status, timestamp

One payment per ticket (UNIQUE FK). Entry + exit each run inside a single ACID transaction. Ticket IDs are date-based → human-readable & time-sortable.

F

Key design choices (deep-dived on canvas 3)

defend these
concurrency

Pessimistic lock

SELECT … FOR UPDATE serialises the assign-spot transaction — simplest correct fix for double-booking at low contention. Optimistic/CAS if throughput ever demands it. → canvas 3

storage

PostgreSQL (RDBMS)

Relational entities, ACID for payments, foreign keys, row locking. NoSQL adds nothing at 850 spots — CP over AP.

extensibility

Strategy ×3

Spot assignment, pricing, and payment each vary on an independent axis — swap without touching the others. The OOP heart of this problem. → canvas 2 · LLD

Glossary — one-liners

terms used above
Double-bookingtwo gates assign the same spot to two vehicles — the race this system must prevent
SELECT … FOR UPDATEtakes an exclusive row lock so a second transaction blocks until the first commits
Pessimistic lockinglock the row before acting; assumes conflicts happen
ACIDAtomic-Consistent-Isolated-Durable transactions — required for payment
Strategy patternswap an algorithm (spot choice, pricing) behind an interface at runtime
CP (CAP)favour Consistency + Partition-tolerance — a stale/duplicate spot is unacceptable
FacadeParking Service hides orchestration behind one park / unpark call
Observerdisplay boards subscribe to spot-change events and refresh
ALPRAutomatic License-Plate Recognition — the entry camera
Idempotency keytags a payment so a retry never charges twice
