B

Spot assignment + the polymorphic fit check — the core algorithm

ParkingStrategy + canFitVehicle()
the code (verbatim)
// NearestFirstStrategy — scan floors 1→N
public Optional<ParkingSpot> findSpot(
        ParkingLot lot, Vehicle vehicle) {
  for (ParkingFloor floor : lot.getFloors()) {
    List<ParkingSpot> available =
        floor.getAvailableSpots(vehicle);
    if (!available.isEmpty())
      return Optional.of(available.getFirst());
  }
  return Optional.empty();  // lot full
}

// the polymorphic hook — one per subclass
// HandicappedSpot:
public boolean canFitVehicle(Vehicle v) {
  return v.getVehicleType() == CAR
      && v.isHandicapped();
}

floor.getAvailableSpots(vehicle) iterates every spot type and calls spot.canFitVehicle(vehicle) — a virtual dispatch that lands on the right subclass rule.

worked example — park a handicapped Car, then a Bus
// canFitVehicle rules (Template Method)
CompactSpot     → CAR | MOTORCYCLE
LargeSpot       → true   (any vehicle)
MotorcycleSpot  → MOTORCYCLE only
HandicappedSpot → CAR && isHandicapped

// 1) handicapped Car, NearestFirst
floor 1 spots scanned →
  MotorcycleSpot.canFit(car) = false
  CompactSpot.canFit(car)    = true  ■
  HandicappedSpot.canFit(car)= true
→ first fit wins: F1-C001

// 2) Bus (needsMultipleSpots = true)
  CompactSpot.canFit(bus)    = false
  LargeSpot.canFit(bus)      = true  ■
→ F1-L001

The service never branches on vehicle or spot type — it just asks each spot canFitVehicle(v) and lets polymorphism decide. Adding an EVSpot is one new subclass, zero edits.

Why a Strategy for assignment? NearestFirst optimises the driver's walk (fill floor 1 first); CompactFloor instead picks the most-full floor that still fits (min by getAvailableCount()) to keep whole floors empty for events or to power down unused levels. Same findSpot(lot, vehicle) signature, opposite goal — and ParkingService.setParkingStrategy(...) swaps them at runtime.
C

The three Strategy families

swap the algorithm, not the service

ParkingStrategy — Optional<ParkingSpot> findSpot(lot, vehicle). default = NearestFirstStrategy

  • NearestFirst: scan floors 1→N, return the first compatible spot — shortest walk from the gate.
  • CompactFloor: pick the most-full floor that still fits (min by available count) — concentrates cars, frees whole floors.
  • Cost: O(F × S) worst case, short-circuits on first fit.

PricingStrategy — double calculateFee(ticket). default = HourlyPricingStrategy

  • Hourly: ceil(hours) × rate per vehicle type — Motorcycle $1, Car $2, Bus $5; minimum 1 hour.
  • FlatRate: fixed per-day regardless of duration — Motorcycle $10, Car $20, Bus $50.
  • Both read ticket.getVehicle().getVehicleType() from an EnumMap of rates.

PaymentProcessor — Payment processPayment(ticketId, amount, method). held in an EnumMap by method

  • Cash: always succeeds — the kiosk baseline.
  • CreditCard: ~95% success rate to simulate declines; a failed Payment makes the service throw PaymentFailedException (spot stays occupied).
  • Each processor declares supportedMethod(); the service looks up the right one at exit.

Not in the repo, but the interfaces make them drop-in — implement the interface, register in AppConfig:

  • DynamicPricingStrategy: surge on occupancy — higher rates as the lot fills.
  • ReservationStrategy: honour pre-booked spots (uses the RESERVED SpotStatus already modelled).
  • MobilePaymentProcessor: Apple/Google Pay — a new PaymentMethod enum value + one processor.

The pattern: ParkingService holds one field per strategy family and never branches on type — it calls strategy.findSpot(...), pricing.calculateFee(...), processor.processPayment(...). Three separate small interfaces (not one fat one) is Interface Segregation; adding a new algorithm is a new class + one line in AppConfig with zero service edits (Open-Closed).
D

Data model detail

ParkingTicket · ParkingSpot · enums
ParkingTicket — the entry↔exit record
ticketId    String        // KEY (repo map key)
vehicle     Vehicle       // final
spot        ParkingSpot   // final
entryTime   LocalDateTime // final
exitTime    LocalDateTime // set at exit
amount      double        // set on payment
isPaid      boolean

Built via the inner Builder (vehicle + spot required). calculateHours() = ceil(entry→exit), min 1; markAsPaid(amount) flips isPaid. Stored in a ConcurrentHashMap<String,ParkingTicket> keyed by ticketId.

ParkingSpot — state carried per spot
spotId        String   // final, e.g. F1-C001
floorNumber   int      // final
spotNumber    int      // final
spotType      SpotType // final
status        SpotStatus // volatile
currentVehicle Vehicle // null when free

Abstract; concrete subtype fixes spotType + canFitVehicle(). park()/vacate() are synchronized (per-spot lock) and return boolean so a losing thread in a race simply gets false.

the enums that carry behaviour
enum VehicleType { MOTORCYCLE, CAR, BUS }
      // each maps to a default SpotType
enum SpotType { MOTORCYCLE_SPOT, COMPACT,
                LARGE, HANDICAPPED }
enum SpotStatus { AVAILABLE, OCCUPIED,
                  RESERVED, OUT_OF_ORDER }
      // canTransitionTo() guards the State m/c
enum PaymentMethod { CASH, CREDIT_CARD, DEBIT_CARD }
enum PaymentStatus { PENDING, COMPLETED,
                     FAILED, REFUNDED }
Payment — the transaction record
paymentId  String
ticketId   String
amount     double
method     PaymentMethod
status     PaymentStatus
timestamp  LocalDateTime

Produced by a PaymentProcessor. isSuccessful() gates the exit — only a COMPLETED payment lets the service vacate() the spot and mark the ticket paid; a FAILED one throws PaymentFailedException.

Enums with behaviour, not flags: VehicleType carries its default SpotType, and SpotStatus.canTransitionTo() encodes the legal state machine (AVAILABLE→OCCUPIED→AVAILABLE, ANY→OUT_OF_ORDER). Putting the rule in the enum kills the if-else chains interviewers hate and keeps the model Open-Closed.
E

Request handling sequence

which class does what, in order

Entry  →  park a vehicle

Controller.handleEntry(type, plate)
  1  createVehicle(type, plate)          // Factory Method → Car/Moto/Bus
  └─ Service.parkVehicle(vehicle)
       2  lot.isFull()? → ParkingFullException
       3  parkingStrategy.findSpot(lot, vehicle)   // Optional
            empty? → SpotNotAvailableException
       4  spot.park(vehicle)              // synchronized; false = lost race
            false? → SpotNotAvailableException
       5  new ParkingTicket.Builder()
              .vehicle(v).spot(spot)
              .entryTime(v.getEntryTime()).build()
       6  ticketRepo.save(ticket)         // map.put(ticketId, ticket)
  └─ return ParkingTicket

Step 3 delegates the whole assignment policy to the injected strategy; step 4's synchronized spot lock is what makes "two cars, one spot" safe — the loser simply retries via a different spot.

Exit  →  unpark, price & pay

Controller.handleExit(ticketId, method)
  └─ Service.unparkVehicle(ticketId, method)
       1  ticketRepo.findById(ticketId)
            empty? → InvalidTicketException
       2  pricingStrategy.calculateFee(ticket)     // hours × rate
       3  processor = paymentProcessors.get(method)
            null? → PaymentFailedException
       4  payment = processor.processPayment(id, fee, method)
       5  payment.isSuccessful()?
            yes → ticket.getSpot().vacate()   // synchronized
                  ticket.markAsPaid(fee)
            no  → PaymentFailedException       // spot stays occupied
  └─ return Payment

Pricing and payment are separate strategies looked up by PaymentMethod — the service coordinates the five subsystems but delegates every decision. The spot is only freed after a successful charge.

F

Design patterns used

GoF-categorized
Creational
  • Singleton — ParkingLot (double-checked locking). One physical lot; two instances = two availability counts.
  • Builder — ParkingTicket.Builder. Readable construction; build() enforces vehicle + spot.
  • Factory Method — Controller.createVehicle() + AppConfig spot helpers map an enum to the right subclass.
Behavioral
  • Strategy ×3 — ParkingStrategy, PricingStrategy, PaymentProcessor. Independently swappable algorithms.
  • Template Method — ParkingSpot.park() fixes the skeleton; abstract canFitVehicle() is the varying hook.
  • State — SpotStatus.canTransitionTo() guards AVAILABLE↔OCCUPIED / OUT_OF_ORDER.
  • Observer (style) — DisplayBoard reflects availability off the lot after each park/unpark.
Structural / Architectural
  • Facade — ParkingService hides 5+ subsystems behind parkVehicle / unparkVehicle.
  • Repository — TicketRepository / SpotRepository → in-memory today, JDBC tomorrow, no service change.
  • Dependency Injection — constructor injection everywhere, wired by hand in AppConfig.
Why Parking Lot is THE classic: it exercises inheritance (Vehicle / ParkingSpot), polymorphism (canFitVehicle), and every SOLID letter at once — Strategy + Repository + DI deliver Open-Closed and Dependency Inversion, Template Method + LSP make subtypes substitutable, and three small interfaces give Interface Segregation. → concurrency & scale trade-offs on canvas 3
