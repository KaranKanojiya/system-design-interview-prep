Scaling strategy

what to lock & when to shard
service tier

Facade, one lot

ParkingService orchestrates entry/exit for a single physical lot. Real throughput ceiling is the gate hardware (~1 car / 3–5 s per gate), not the JVM — so vertical scale on one node is plenty for one lot.

availability reads

Off the write path

AvailabilityService serves counts from in-memory state; the multi-lot central dashboard reads a Redis aggregate / read-replica so heavy “where's a spot?” queries never contend with park/vacate.

natural shard

Partition by lot

Each lot is independent — no cross-lot coordination to park a car. Sharding by lotId is a free partition boundary: 50 lots = 50 CP islands + one AP dashboard.

concurrency granularity — pick a locking strategy (the ladder you climb in the interview)

Coarse lock on ParkingService

One synchronized method serializes every park/unpark. The find-then-park sequence is atomic because only one thread is ever inside — trivially correct.

public synchronized ParkingTicket parkVehicle(Vehicle v) {
  ParkingSpot spot = parkingStrategy.findSpot(v, lot.getFloors())
      .orElseThrow(() -> new ParkingFullException());
  spot.park(v);            // only one thread here
  return ticketService.issueTicket(v, spot);
}
verdict — start here
  • Simplest — no race conditions, easy to reason about. Ideal interview opener / demo.
  • Whole lot is locked per operation: Gate 2 waits while Gate 1 parks → throughput ceiling at peak.
  • Fine for a single-entrance, low-traffic lot.

Fine-grained lock per ParkingSpot ← chosen for a real lot

Each spot owns its lock. park() is an atomic check-and-set; the strategy walks spots and stops at the first that accepts. Cars on different floors never block each other.

public synchronized boolean park(Vehicle v) {  // lock THIS spot
  if (this.vehicle != null) return false;   // taken → try next
  if (!canFitVehicle(v)) return false;
  this.vehicle = v; return true;
}
verdict
  • Higher throughput — parallelism scales with the number of gates / free spots.
  • Two cars racing for the same spot: first wins, second gets false and the strategy retries the next spot.
  • Retry loop for “spot taken, try next”; risk of livelock only under extreme contention.

Optimistic CAS on status

Hold status in an AtomicReference<SpotStatus>. A single compare-and-swap flips AVAILABLE → OCCUPIED; only the winner mutates the spot. No blocking, no monitor.

boolean parked = status.compareAndSet(
    SpotStatus.AVAILABLE, SpotStatus.OCCUPIED);
if (parked) this.vehicle = v;
return parked;   // lock-free, nanosecond scale
verdict
  • Maximum throughput, non-blocking — good for a very high-traffic lot with many gates.
  • CAS retry loop under high contention on the same spot; correctness is harder to reason about.
  • Often over-engineering for a lot bounded by physical gate speed.

Database SELECT … FOR UPDATE

When the lot runs multiple app instances, JVM locks no longer coordinate. Push the lock into Postgres: row-level lock on the chosen spot, plus a partial UNIQUE index as a hard backstop against double-booking.

BEGIN;
  SELECT * FROM parking_spot
   WHERE status='AVAILABLE' AND spot_type='COMPACT'
   ORDER BY floor_number, spot_number LIMIT 1
   FOR UPDATE;                       // row lock
  UPDATE parking_spot SET status='OCCUPIED' …;
COMMIT;
verdict — production
  • Survives restarts and works across many app instances — the DB is the source of truth.
  • Extra latency (a DB round-trip) and you must handle deadlocks.
  • Same TicketRepository / SpotRepository interface — swapping in-memory → Postgres is one class.
Don't reach for a distributed lock (Redis SETNX) on a single lot: every thread is in one JVM, so synchronized / AtomicReference is faster (ns vs ms), simpler, and dependency-free. Redis locks earn their keep only across multiple instances.

Caching deep-dive

the state IS the cache
core insight — no cache-aside for one lot
// 5,000-spot mega-lot ≈ 500 KB of heap
Floor.spots : List<ParkingSpot>   // source of truth
  ├─ park(v)  → status = OCCUPIED  // immediate, atomic
  └─ vacate() → status = AVAILABLE // no TTL, no stale copy

There is no cache-invalidation problem because there is no separate cache — the in-memory structure is both store and cache. Availability is a live stream().filter(isAvailable).count(), not a snapshot.

ticket & pricing — HashMap, not Redis
// InMemoryTicketRepository
Map<String,ParkingTicket> active
    = new ConcurrentHashMap<>();  // ~500–2000 live, ~400 KB

// HourlyPricingStrategy — rates cached at construction
Map<SpotType,BigDecimal> rates = Map.copyOf(cfg); // immutable

Tickets are written once on entry, read once on exit — a textbook HashMap by ticketId. Pricing rules change quarterly, so they're loaded once at startup (AppConfig) and swapped atomically on reload.

display board — push

Observer refresh

On every park/vacate, ParkingService notifies observers so the LED board re-renders in real time — no polling latency on the happy path.

parkVehicle()
  └─ spot.park(v)
       └─ notifyObservers()
            → DisplayBoard.update(lot)
              // Floor 1: Cars 8/50 …
display board — fallback

5-second poll

A missed Observer event would leave a stale board. A heartbeat poll re-reads live state every 5 s, so the board always self-heals. Push for latency, poll for resilience.

while (true) {
  board.update(lot);   // fresh in-mem read
  Thread.sleep(5_000);
}
when caching DOES matter

Multi-lot Redis

Only when the interviewer says “50 lots across a city”: each lot stays in-memory, but a Redis aggregate holds per-lot counts with a 30 s TTL for the mobile app / dashboard.

SET lot:A:available 41
  // TTL 30s, eventual
// fed by a Kafka/SNS event
// on every park/vacate
Layer map: single lot → JVM heap only (strong). Multi-lot → local heap (strong) + Redis aggregate (30 s TTL, eventual) + HTTP cache headers (~10 s) + CDN/push for the mobile app. Spend zero interview time on Redis for one lot — spend it all on thread-safe spot assignment. → full layering on canvas 1 · HLD

Bottlenecks & solutions

click a card to open

Double-booking race (the core problem)

Impact: two cars at two gates both call findSpot(), both get spot #42 as AVAILABLE, both call park() → one spot, two vehicles, data corruption.

Fix: make check-and-set atomic — synchronized park() per spot (or CAS on status). The loser sees false and the strategy assigns the next free spot. In multi-instance production, a partial UNIQUE (spot_id) WHERE status='OCCUPIED' index is the hard backstop.

Coarse lock throughput ceiling

Impact: a single synchronized on ParkingService serializes the whole lot — Gate 2 blocks while Gate 1 parks, capping peak-hour throughput.

Fix: drop to per-spot locking so parallelism scales with free spots and gates; a 500-spot lot can service 500 concurrent tryPark() calls on distinct spots. Reserve CAS for the highest-contention lots.

Deadlock when a bus needs 3 spots

Impact: locking multiple spots for a Bus (consecutive large spots) in arbitrary order can create a circular wait between two threads.

Fix: a single-spot design has no circular dependency. When multiple locks are unavoidable, acquire them in a fixed global order (by spot ID) so no cycle can form.

Display board misses an event

Impact: a dropped Observer notification leaves the LED board showing a stale count — a driver circles a “free” floor that's full.

Fix: hybrid push + poll — Observer for real-time updates, plus a 5-second heartbeat poll that re-reads live in-memory state and catches any missed event.

Crash mid-parking

Impact: the app crashes after findSpot() but before issueTicket() — in the in-memory demo the spot may be marked occupied with no ticket, a leaked reservation.

Fix: make the DB the source of truth — park + issue-ticket in one transaction, so a crash rolls back and the spot reverts to AVAILABLE. On restart, reload spot state from the DB (or re-sync from sensors).

Payment / gate hardware slowness

Impact: a slow Stripe call or a stuck barrier at exit holds the driver — and if it also held the spot lock, it would stall the whole exit lane.

Fix: keep PaymentProcessor behind a Strategy interface with timeouts/retries; don't hold a spot lock across the external call — compute fee, charge, then vacate(). The real throughput bound is the physical gate (~1 car / 3–5 s), not software.

Multi-lot dashboard staleness

Impact: across 50 lots, a central dashboard that tried to be strongly consistent would need cross-lot coordination on every park — killing availability for a number that doesn't need to be exact.

Fix: accept eventual consistency at the dashboard — Redis aggregate with a 30 s TTL, fed by per-lot park/vacate events over Kafka/SNS. Each lot stays CP for its own spots; the aggregate is AP. Stale “42 vs 41” is fine.

CAP & consistency — why CP

one spot, one car
the choice

A single lot on a local DB has no network partitions — gate controllers, sensors, terminals and boards share a LAN. So CAP's real lesson here is the A-vs-C tradeoff, and consistency wins: you can never double-book a spot. A 1–2 s wait at the gate is acceptable; a collision is not.

  • CP: two cars, one spot → one parks, the other waits ~1 s, never both.
  • Gate-sensor fault → stay closed rather than admit an untracked car (revenue & safety).
  • The real challenge is concurrency, not partitions — locks, not quorums.
where it becomes distributed (50 lots)
// each lot = an independent CP island
Lot A (local DB, CP)  Lot B (CP)  Lot C (CP)
        └──────── events ─────────┘
              ▼
Central dashboard (AP)  // Redis, read replicas
  "Lot A: 42  Lot B: 15"  // stale ≤30s = fine

Lots don't coordinate to park a car, so lotId is a natural partition boundary. The dashboard and mobile app go AP (stale counts OK); a cross-lot reservation flips back to CP because a promised spot must be guaranteed.

Read-your-own-state: because a single lot's in-memory structure is the source of truth and every mutation is atomic, a park is visible immediately — no propagation lag, no read-repair. Consistency is a lock, not a replication setting.

phase-by-phase
  • P1 Clarify (2–3): vehicle types (car/motorcycle/bus), floors & spots, pricing model, payment methods, display board, multiple gates, reservations vs walk-in.
  • P2 Core entities (5–7 · START HERE): abstract Vehicle and abstract ParkingSpot (Compact/Large/Motorcycle/Handicapped); canFitVehicle() as a Template Method — say why abstract class over interface (shared state).
  • P3 Floor + Lot (3–4): ParkingFloor holds spots + board; ParkingLot Singleton (one physical lot) — note DI is often preferred but Singleton maps to reality here.
  • P4 Strategies (5–7 · PATTERN MASTERY): ParkingStrategy, PricingStrategy, PaymentProcessor — “Strategy in three places because each axis varies independently.”
…and finish strong
  • P5 Facade (3–4): ParkingService.parkVehicle / unparkVehicle orchestrates find → park → ticket → notify; one entry point for gate, panel, or app.
  • P6 Ticketing flow (3–4): entry (scan → find spot → park() → ticket → gate) and exit (ticket → fee → pay → vacate() → gate).
  • P7 Concurrency (2–3 · unprompted wins): synchronized park() — two cars, same spot, first wins, strategy retries; follow-up: ReentrantLock.tryLock() or optimistic version field on a DB.
  • P8 SOLID (2–3 · if time): one concrete example each — OCP: add EVChargingSpot with zero edits; DIP: service depends on strategy interfaces.
Green flags: clean abstract hierarchies · Strategy with “each axis varies independently” · explain abstract-class-vs-interface · raise thread safety unprompted · Template Method for canFitVehicle() · Observer for the board. Red flags: one giant ParkingLot class · switch(vehicleType) instead of polymorphism · hardcoded pricing · ignoring concurrency · everything public · schema before classes.
