The saga — OrderSagaOrchestrator.execute

verbatim · 3 steps · compensate reverse
from saga/OrderSagaOrchestrator.java
public SagaResult execute(Order order) {
  SagaResult.Builder resultBuilder = new SagaResult.Builder();
  List<OrderItem> reservedItems = new ArrayList<>();
  Payment payment = null;

  // ─── Step 1 · RESERVE_INVENTORY ───
  SagaStepRecord inventoryStep = new SagaStepRecord("RESERVE_INVENTORY");
  order.addSagaStep(inventoryStep);
  try {
    for (OrderItem item : order.getItems()) {
      inventoryService.reserve(item.getProductId(), item.getQuantity());
      reservedItems.add(item);          // track what to release on failure
    }
    inventoryStep.markCompleted();
    order.confirmInventory();            // state → INVENTORY_RESERVED
    resultBuilder.addCompletedStep("RESERVE_INVENTORY");
  } catch (InsufficientStockException e) {
    inventoryStep.markFailed();
    compensateInventory(reservedItems, order);   // release any partial reservations
    return resultBuilder.success(false).failedStep("RESERVE_INVENTORY")
        .message("Inventory reservation failed: " + e.getMessage()).build();
  }

  // ─── Step 2 · PROCESS_PAYMENT ───
  SagaStepRecord paymentStep = new SagaStepRecord("PROCESS_PAYMENT");
  order.addSagaStep(paymentStep);
  try {
    payment = paymentService.processPayment(order, paymentStrategy);
    if (payment.getStatus() == PaymentStatus.FAILED) {
      throw new PaymentFailedException("Payment declined for order " + order.getOrderId());
    }
    paymentStep.markCompleted();
    order.confirmPayment();              // state → PAYMENT_CONFIRMED
    resultBuilder.addCompletedStep("PROCESS_PAYMENT");
  } catch (PaymentFailedException e) {
    paymentStep.markFailed();
    compensateInventory(reservedItems, order);         // release Step 1
    notificationService.notifyPaymentFailed(order);
    return resultBuilder.success(false).failedStep("PROCESS_PAYMENT")
        .message("Payment failed: " + e.getMessage()).build();
  }

  // ─── Step 3 · CREATE_SHIPMENT ───
  SagaStepRecord shippingStep = new SagaStepRecord("CREATE_SHIPMENT");
  order.addSagaStep(shippingStep);
  try {
    Shipment shipment = shippingService.createShipment(order);
    shippingStep.markCompleted();
    order.ship(shipment.getTrackingNumber());  // state → SHIPPED
    resultBuilder.addCompletedStep("CREATE_SHIPMENT");

    // ─── Success path: confirm reservations + notify ───
    for (OrderItem item : order.getItems()) {
      inventoryService.confirmReservation(item.getProductId(), item.getQuantity());
    }
    notificationService.notifyOrderConfirmed(order);
    notificationService.notifyOrderShipped(order, shipment);
    return resultBuilder.success(true).build();

  } catch (ECommerceException e) {                     // Step 3 failed → compensate BOTH prior steps
    shippingStep.markFailed();
    if (payment != null) {
      paymentService.refundPayment(payment.getPaymentId());
      resultBuilder.addCompensatedStep("PROCESS_PAYMENT");
    }
    compensateInventory(reservedItems, order);
    resultBuilder.addCompensatedStep("RESERVE_INVENTORY");
    return resultBuilder.success(false).failedStep("CREATE_SHIPMENT")
        .message("Shipment creation failed: " + e.getMessage()).build();
  }
}

private void compensateInventory(List<OrderItem> reservedItems, Order order) {
  order.getSagaSteps().stream()
      .filter(s -> s.getStepName().equals("RESERVE_INVENTORY"))
      .findFirst()
      .ifPresent(s -> {
        s.markCompensating();
        for (OrderItem item : reservedItems) {
          inventoryService.releaseReservation(item.getProductId(), item.getQuantity());
        }
        s.markCompensated();
      });
}
Why reverse-order compensation matters: Step 3 fails → we must undo Step 2 (refund payment) BEFORE undoing Step 1 (release inventory). If we released inventory first and refund failed halfway, we'd have a paid order with released stock — the customer's money is charged but no one is committed to shipping. Reverse order plus idempotent compensations (release ×2 = release ×1, refund an already-refunded payment is a no-op) makes the whole thing crash-safe.

from service/PaymentService.java
public Payment processPayment(Order order, PaymentStrategy paymentStrategy) {
  // ─── Idempotency guard — the exactly-once effect ───
  Optional<Payment> existing = paymentRepository.findByOrderId(order.getOrderId());
  if (existing.isPresent() && existing.get().getStatus() == PaymentStatus.COMPLETED) {
    return existing.get();          // short-circuit — never re-charge
  }

  // Delegate to injected strategy — HTTPS call to Stripe / UPI / wallet
  Payment payment = paymentStrategy.processPayment(order.getTotalAmount(), order.getOrderId());
  paymentRepository.save(payment);
  return payment;
}

Why this alone is enough: in prod, orderId is used as the Stripe Idempotency-Key — Stripe stores the response for 24 h. Our DB check catches the case where the retry happens AFTER Stripe already returned but before we saved. Together: at-least-once retry + idempotent gateway + local dedup = exactly-once effect. The customer is never double-charged.

from strategy/payment/CreditCardPaymentStrategy.java
private static final double SUCCESS_RATE = 0.95;   // demo only

public Payment processPayment(double amount, String orderId) {
  // In prod: HTTPS POST to https://api.stripe.com/v1/charges
  //         with header "Idempotency-Key: {orderId}"
  //         Retry on 5xx / 429 with exponential backoff.
  boolean success = ThreadLocalRandom.current().nextDouble() < SUCCESS_RATE;

  return new Payment.Builder(UUID.randomUUID().toString(), orderId, amount, PaymentMethod.CREDIT_CARD)
      .status(success ? PaymentStatus.COMPLETED : PaymentStatus.FAILED)
      .transactionId(success ? "ch_" + UUID.randomUUID() : null)
      .build();
}

Rate 95 % simulates real card decline rates. In prod: Stripe / Adyen / Braintree — all use idempotency keys the same way. Latency dominates checkout p99 (500–1 500 ms).

from strategy/payment/WalletPaymentStrategy.java
private static final double SUCCESS_RATE = 0.99;

public Payment processPayment(double amount, String orderId) {
  // PayPal / Amazon Pay / UPI — the customer already OAuth'd,
  // so the "does the card work" uncertainty is gone.
  boolean success = ThreadLocalRandom.current().nextDouble() < SUCCESS_RATE;
  return new Payment.Builder(UUID.randomUUID().toString(), orderId, amount, PaymentMethod.WALLET)
      .status(success ? PaymentStatus.COMPLETED : PaymentStatus.FAILED)
      .transactionId(success ? "wallet_" + UUID.randomUUID() : null)
      .build();
}

Higher success rate — customer's balance already verified. Preferred for repeat customers.

from strategy/payment/CODPaymentStrategy.java
public Payment processPayment(double amount, String orderId) {
  // No money moves at checkout — collect at delivery.
  // Payment stays PENDING; state advances on delivery confirmation.
  return new Payment.Builder(UUID.randomUUID().toString(), orderId, amount, PaymentMethod.COD)
      .status(PaymentStatus.PENDING)
      .build();
}

Interview twist: COD breaks the "payment before ship" invariant. Handled by treating PENDING as a saga success at Step 2 (order ships anyway); a delivery-side flow later marks Payment COMPLETED. Adds a whole new failure mode: undelivered COD → auto-refund is a no-op, but inventory was consumed.

Order state machine — guarded transitions

from model/Order.java
the transition guard (verbatim)
public void confirmInventory() {
  guardTransition("confirmInventory", status, Set.of(OrderStatus.CREATED));
  transitionTo(OrderStatus.INVENTORY_RESERVED);
}

public void confirmPayment() {
  guardTransition("confirmPayment", status,
      Set.of(OrderStatus.INVENTORY_RESERVED, OrderStatus.PAYMENT_PENDING));
  transitionTo(OrderStatus.PAYMENT_CONFIRMED);
}

public void ship(String trackingNumber) {
  guardTransition("ship", status, Set.of(OrderStatus.PAYMENT_CONFIRMED));
  this.trackingNumber = trackingNumber;
  transitionTo(OrderStatus.SHIPPED);
}

public void deliver() {
  guardTransition("deliver", status, Set.of(OrderStatus.SHIPPED));
  transitionTo(OrderStatus.DELIVERED);
}

public void cancel() {
  guardTransition("cancel", status,
      Set.of(OrderStatus.CREATED, OrderStatus.INVENTORY_RESERVED, OrderStatus.PAYMENT_PENDING));
  transitionTo(OrderStatus.CANCELLED);
}

public void refund() {
  guardTransition("refund", status,
      Set.of(OrderStatus.PAYMENT_CONFIRMED, OrderStatus.SHIPPED, OrderStatus.DELIVERED));
  transitionTo(OrderStatus.REFUNDED);
}

private void guardTransition(String action, OrderStatus current, Set<OrderStatus> allowed) {
  if (!allowed.contains(current)) {
    throw new InvalidOrderStateException(
        String.format("Cannot %s: order %s is in %s (allowed: %s)",
            action, orderId, current, allowed));
  }
}
Why encode transitions in the model, not the service: the service can (and will) be called concurrently by admin tools, webhooks, and background jobs. If the guard lives in the service, a rogue caller can just order.setStatus(SHIPPED) directly. In the model, there is no setter — only guarded transitions. An InvalidOrderStateException is your last line of defense against a bug that would corrupt an order.
