2PC (Two-Phase Commit) is the "obvious" answer if you learned distributed transactions from a database textbook. It works like this:

Phase 1 — PREPARE:
  TM asks each participant: "Can you commit?" Each writes to durable log, replies YES/NO.
  Participants hold LOCKS on their data during this wait.

Phase 2 — COMMIT:
  If ALL said YES → TM sends COMMIT. Everyone commits, releases locks.
  If ANY said NO → TM sends ROLLBACK.
  If TM CRASHES between phases → participants stuck holding locks (the "in-doubt" state).

Why we don't:

  • Lock hold-time. Payment gateway takes 500–1 500 ms. During that time, the inventory row is locked — nobody else can buy that SKU. 35 K orders/sec × 1 sec = 35 K locks. This is the death of throughput.
  • Cross-vendor. Stripe doesn't support XA. Neither does Kafka. Neither does DynamoDB. Modern infrastructure is federated — 2PC assumes a homogeneous world we don't live in.
  • In-doubt state. If the TM crashes after PREPARE but before COMMIT, participants can't unilaterally proceed. Manual DBA intervention. Not compatible with SRE culture.
Interview red flag: "I'd use a distributed transaction across all four services." Correct answer: 2PC doesn't scale and doesn't work with 3rd-party gateways. Use Saga.

Saga (orchestration) is what our code implements — see OrderSagaOrchestrator.execute().

  • Local transactions. Each step is a normal ACID transaction on its own DB (inventory reserve = DDB conditional write; payment = Stripe API + Postgres row).
  • Central coordinator. One orchestrator drives the sequence and knows what to do on failure. In prod: AWS Step Functions or Temporal — same shape, durable state machine, resumes on crash.
  • Compensation is code. Written explicitly per step (release inventory / refund payment / cancel shipment). Not "the DB rolls back for you."
  • Requires idempotency. If the orchestrator crashes mid-saga, restart replays steps — each must be safe to call twice.

Saga (choreography) replaces the orchestrator with an event chain — each service publishes on completion, the next reacts.

OrderService  ─► order.created         → Kafka
InventoryService reacts:
  reserve stock. On success ─► inventory.reserved → Kafka
                On failure ─► order.failed
PaymentService reacts to inventory.reserved:
  charge. On success ─► payment.completed → Kafka
         On failure ─► order.failed
             → InventoryService reacts (release stock)
ShippingService reacts to payment.completed:
  create shipment. On success ─► order.shipped
                   On failure ─► order.failed
             → PaymentService reacts (refund)
             → InventoryService reacts (release)

Pros: no central bottleneck, services truly independent, easy to add a new consumer for analytics.

Cons: nobody knows the whole flow at debug time. A stuck order = grep across N services. Timeout logic scattered. Cyclic-dependency risk on compensations. Blast radius: a poison-pill event keeps triggering handlers forever.

When choreography wins: for POST-order fan-out — notifications, analytics, search indexing. Those consumers are truly independent and their failure doesn't affect the customer. We use it for that in the HLD (Kafka → Notification / Analytics / SearchIndexer).

The decision tree:

Is this a distributed transaction (≥ 2 services or DBs need atomic outcome)?
├─ NO → single-DB ACID. You're done.
└─ YES ─► Are ALL participants under your control (same DB engine, XA-capable)?
          ├─ YES → maybe 2PC — but only if throughput is low and lock hold-time is small.
          └─ NO ─► Is there a single "workflow owner" (like an order)?
                   ├─ YES → Saga orchestration. Central log, easy debug. ← checkout
                   └─ NO  → Saga choreography. Events + correlationId. ← post-order fan-out

Idempotency — the exactly-once effect

never double-charge, ever
why "exactly-once" is a myth
the 3-layer stack we use
code walk
failure scenarios

Exactly-once delivery is impossible over a network. If the sender times out mid-write, it can't tell: did the receiver get it and the ACK got lost, or did the message get lost? Both cases look identical.

What we build instead: at-least-once delivery + idempotent handler = exactly-once effect (as observed by the customer). Retry as many times as you want; only the first call has effect.

Cost of getting this wrong: a duplicate POST /charge that both succeed = customer charged twice for one order. Chargeback + support ticket + trust damage. This is the single most important guarantee in an e-commerce system.

Three cooperating layers, each catching what the other misses:

ClientGenerates a UUID Idempotency-Key per checkout attempt. Retries reuse the same key. Persist locally so a page-refresh reuses too.Mobile / web app
API Gateway / OrderServiceStores (idempotency_key → response) in Redis (24 h TTL). Duplicate key = return stored response, don't execute.Redis + Postgres UNIQUE(idempotency_key)
PaymentServiceBefore calling gateway, paymentRepository.findByOrderId(orderId) — if COMPLETED, return existing.Postgres UNIQUE(order_id) on Payment
Gateway (Stripe/UPI)Stores response for 24 h keyed by Idempotency-Key header. A retry within 24 h returns identical response.Stripe infrastructure
 
// 1) Client sends
POST /checkout
Idempotency-Key: 8f2b1a-...   // UUID v4, persist locally

// 2) Gateway checks Redis
if (redis.exists("idem:" + key)) return redis.get("idem:" + key); // short-circuit

// 3) OrderService creates order with UNIQUE constraint
INSERT INTO orders (idempotency_key, ...)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING *;
// If 0 rows returned → duplicate; fetch the existing order.

// 4) PaymentService — Java (verbatim from PaymentService.java)
Optional<Payment> existing = paymentRepository.findByOrderId(order.getOrderId());
if (existing.isPresent() && existing.get().getStatus() == COMPLETED) {
  return existing.get();     // never re-charge — even if step 3 above missed it
}

// 5) Stripe HTTPS call
POST https://api.stripe.com/v1/charges
Idempotency-Key: order-{orderId}   // stable natural key
// Stripe: if we already returned a response for this key in the last 24h, return the same one.

not one CAP for the whole system
SubsystemChoicePACELCWhy

The boundary matters: browse plane (AP — cache-heavy) → checkout plane (CP — DB-authoritative). Crossing at "Place Order" button is the design's most important line. Before that, everything is optimised for latency + hit rate. After that, everything is optimised for correctness — no cache reads on the write path.

Flash sale — Redis DECR gate

100 K QPS on 1 SKU without a Postgres row lock
the problem

At sale start: 50 K users click "Buy" on a single SKU within 1 second. Without a gate:

  • 50 K concurrent Postgres SELECT FOR UPDATE on the same row.
  • Lock queue backs up. p99 goes from 50 ms → 30 s → timeout cascade.
  • Overselling risk if you switch to optimistic w/o care.
  • Fleet health goes red. One SKU takes down all checkouts.
the solution

Put a Redis DECR counter in front of the DB. Redis is single-threaded per shard → DECR is atomic. Turn 100 K QPS into ≤ 100 QPS of actual DB writes.

// Pre-warm at sale start
SET flash:sku-42:stock 1000     // 1000 units available

// Every checkout attempt
result = DECR flash:sku-42:stock
if (result < 0) {
  return 503 "Sold out";        // CDN caches "sold out" for 60 s
}
// Only 1000 requests get past this gate.
// Now enter the normal saga — 1000 rows on Postgres is trivial.
what if Redis crashes mid-sale?
  • Redis Cluster + AOF — hardware failure = <100 ms failover to replica.
  • Reset from DB — background job re-syncs counter from Postgres reserved_stock.
  • Circuit breaker on the DECR path — if Redis unreachable, immediately return 503 "sold out" (better to say sold out than to oversell).
why this is CP-safe
  • DECR is atomic. Only one client sees the value that crossed 0.
  • False negatives OK. DECR gate might undercount slightly during a Redis network blip → customer sees "sold out" a few seconds early. Refund-free.
  • False positives NOT OK. DECR is the gate; the DB conditional write is the belt-and-braces. Both fail together → we refuse the sale.

Queue-based checkout — surviving 35 K QPS

degrade to 202 + poll under spike

When observed QPS exceeds a per-instance safety threshold (e.g. > 3 000/instance), API Gateway flips a config flag → checkout switches from sync HTTP to SQS FIFO:

Client sends POST /checkout
   ↓
Gateway (flag = "queue mode")
   ↓ enqueue message to SQS FIFO (MessageGroupId = userId)
   ↓ return 202 Accepted + { orderId, pollUrl: "/orders/{id}" }
   ↓
Client polls GET /orders/{id} every 1 s
                     until status ≠ PROCESSING

Meanwhile:
Saga worker fleet drains SQS at controlled rate (~3 K/s cluster-wide)
  ↓ pulls message → SagaOrchestrator.execute(order)
  ↓ writes final state to Order DB
  ↓ Gateway serves poll from Order DB (Redis-cached)
why FIFO
  • Per-user ordering guaranteed via MessageGroupId — no cross-order interleaving for one customer.
  • Dedup window 5 min — client retries with same idempotency key don't create duplicate work.
  • Max 300 msg/sec per group — a viral customer can't DoS the queue.
what the customer sees
  • Progress bar: "Your order is being processed... position 1 234 in queue."
  • Mobile push when done: "Order confirmed!"
  • Poll fallback: web UI polls every 1 s; retries with backoff on 429.
The Amazon lesson: during the 2018 Prime Day outage, checkout API was down for 60 minutes because sync capacity was saturated. Queue mode = the same fleet survives 10× spike, just slower per-user. Slow > broken.

35-minute interview walkthrough

the answer, timed
phase 1 · clarify (2–3 min)
  • "How big — mid-scale (Shopify) or Amazon-scale? I'll assume 200 M DAU · 100 M orders/day."
  • "Do we support flash sales / Black Friday? Yes → I'll add Redis DECR + queue mode."
  • "Consistency model — do we ever allow oversell? No → CP checkout with saga."
phase 2 · draw architecture (5–7 min)
  • Client → CDN + API Gateway → microservices behind ALB.
  • Split into browse (AP: PG + ES + Redis + CDN) and checkout (CP: Saga → Inventory → Payment → Shipping).
  • Kafka as event backbone; SNS/SQS for notifications; S3 + CloudFront for images.
phase 3 · saga deep dive (8–10 min)
  • Write out the 3 steps + compensation matrix on the board.
  • Show reserve/confirm/release protocol on inventory.
  • Explain 3-layer idempotency (client · DB UNIQUE · Stripe key).
  • Draw the compensate-in-reverse-order argument.
phase 4 · scale & failure (5–7 min)
  • Redis DECR gate for flash sales — 100 K QPS → 100 QPS at DB.
  • Queue-mode checkout under spike (SQS FIFO + 202 + poll).
  • Circuit breakers between services; per-service bulkheads.
  • Auto-scale Kafka consumers on lag.
phase 5 · trade-offs defended (5–8 min)
  • Why Saga not 2PC (lock hold-time · no XA on Stripe).
  • Why orchestration not choreography (debug-ability · blast radius).
  • Why DynamoDB for inventory + Postgres for orders (right store per access pattern).
  • Why AP browse + CP checkout (right consistency per subsystem).
phase 6 · what would you do differently (2–3 min)
  • "At 5× current scale I'd move to Temporal for saga durability."
  • "I'd add CDC to move product catalog to a global multi-region store."
  • "I'd move notifications to a separate ML-based priority queue for A/B testing."
30-second pitch: "Microservices behind an API Gateway. Split into AP browse (CDN + Redis + Postgres + ES) and CP checkout. Checkout runs a Saga with 3 local transactions — reserve inventory, charge payment, create shipment — and reverse-order compensation on failure. 3-layer idempotency (client UUID + Postgres UNIQUE + Stripe Idempotency-Key) makes every write effectively exactly-once. At Black Friday scale, we gate hot SKUs with Redis DECR and switch checkout to SQS FIFO queue mode when QPS > 3K/instance."
Interview red flags to avoid:
• "I'd use 2PC across all services." (doesn't scale · no Stripe XA)
• "Decrement stock directly from checkout." (thundering herd on hot SKUs)
• "One DB for everything." (misses the AP/CP split)
• "Retry the payment on failure." (double-charge if no idempotency)
• "Compensate stock first, then refund." (payment stuck if refund fails)
