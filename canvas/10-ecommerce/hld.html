A

Problem & requirements

browse vs checkout — different CAP
functional
  • Catalog browse / search — 500 M SKUs, keyword + category filters; p99 < 200 ms.
  • Cart — add / remove / update; price snapshot at add time; persistent across sessions.
  • Checkout — validate stock, compute totals, charge payment, create shipment; saga with compensation.
  • Order lifecycle — CREATED → INVENTORY_RESERVED → PAYMENT_CONFIRMED → SHIPPED → DELIVERED state machine; also CANCELLED / REFUNDED.
  • Payment — idempotent charge (Stripe/UPI); refunds on cancellation; retry on gateway 5xx.
  • Inventory — never oversell. Reserve → confirm (on paid) OR release (on failed / TTL expiry).
  • Shipping — create shipment record, hand off to carrier, track status.
  • Notification — order confirmed / shipped / delivered / cancelled → email + push (async).
  • Graceful degradation — under spike, checkout switches from sync HTTP to queued SQS (return 202 + poll).
non-functional
  • Catalog latency p99 < 200 ms · search throughput 500 K QPS peak (CDN + ES).
  • Checkout latency p99 < 2 s (payment is the bottleneck).
  • Order throughput 3.5 K/s avg; 35 K/s Black Friday (10× spike).
  • Availability 99.99 % browse (AP) · 99.9 % checkout (CP — refuse if unsure).
  • Inventory strong consistency — a phantom oversell costs money + trust.
  • Payment exactly-once effect via idempotency key (never double-charge).
  • Read : write ≈ 1 000 : 1 for catalog — optimise the read path aggressively.
  • Cart AP — stale merge better than empty cart.
  • Recovery compensation must be idempotent (release ×2 == release ×1).

Why the checkout number is small but scary: 3.5 K orders/s is trivial in isolation — but each order is a 3-service distributed transaction (inventory → payment → shipping) with strong-consistency requirements. If any step hangs at 500 ms you serialize the whole tree; if payment is down you must compensate reversed. That's why the saga (not 2PC) exists.
The 35 K/s Black Friday problem: 10× spike + hot SKUs (top 100 products get 80 % of orders) → one Postgres row lock destroys the fleet. Mitigations: Redis DECR gate in front of the DB, queue-based checkout (HTTP 202 + SQS FIFO), circuit breaker on the sold-out product returning 503 with a 60 s CDN cache.

API design

idempotent writes · cacheable reads
EndpointPurposeResponse
GET /products?q=&category=Search / browse (cacheable, CDN 30 s)200 + {items[], nextCursor}
GET /products/{id}Product detail (Redis 5 min)200 + product JSON
POST /cartAdd item (with price snapshot)200 + cart JSON
POST /checkoutSaga trigger. Header: Idempotency-Key. Body: {cartId, paymentMethod, shippingAddress}201 + Order (sync) OR 202 + pollUrl (queue mode)
GET /orders/{id}Order status (state machine)200 + {status, items, payment, shipment}
POST /orders/{id}/cancelCancel (state-machine guarded)200 or 409 (invalid state)
POST /webhooks/paymentStripe webhook — payment confirmed / failed200 (idempotent by event.id)
POST /admin/inventory/reserveDirect reserve (admin / internal)200 or 409 (InsufficientStock)

Idempotency contract: every write endpoint accepts Idempotency-Key. Duplicate keys within 24 h return the original response (never re-execute). Payment endpoint additionally uses orderId as a natural key — paymentRepository.findByOrderId short-circuits if COMPLETED.

E

Data model — writes (CP) vs reads (AP)

right store per access pattern
write path (Postgres · DynamoDB)
Order                       // Postgres (Aurora, sharded userId)
  order_id (PK, snowflake)
  user_id
  status                    // state machine enum
  total_amount, currency
  idempotency_key (UNIQUE)  // dedup writes
  created_at, updated_at

OrderItem                   // PG, FK order_id
  order_id, product_id, quantity
  price_snapshot            // at add-to-cart time

Payment                     // PG, same shard as Order
  payment_id, order_id (INDEX)
  amount, method, status
  transaction_id            // Stripe charge_id
  idempotency_key (UNIQUE)

Inventory                   // DynamoDB
  product_id (PK)
  total_stock, reserved_stock
  version                   // optimistic lock

SagaStepRecord              // PG audit trail
  order_id, step_name
  status                    // PENDING/COMPLETED/FAILED/COMPENSATED
  attempted_at, completed_at
read path (Redis · ES · CDN)
Redis cart:{userId}         // hash
  product_id → {qty, price_snapshot}
  TTL 7 days                // abandoned-cart recovery

Redis product:{sku}         // JSON blob
  TTL 5 min                 // invalidate on price change
  jitter ±20 %              // avoid stampede

Elasticsearch products      // denorm search index
  keyword, category[], price
  attributes (color/size/brand)
  is_prime, avg_rating

Redis flash:{sku}:stock     // atomic DECR gate
  int counter               // pre-warmed at sale start
  DECR returns -1 → 503

CDN cache                   // CloudFront/Fastly
  images: 30 d              // content-hashed URLs
  API JSON: 30 s            // GET /products/{id}
The golden rule: cache for display, read DB for decisions. A stale product price shown to a browser is fine (they'll see the real price at checkout); a stale inventory count that lets you oversell is a nightmare. Checkout ALWAYS reads inventory + price from the DB, never the cache.
F

Key design choices (deep-dived on canvas 3)

defend these
consistency

Saga (orchestration)

3 steps · compensate reverse. Beats 2PC (no distributed lock) and choreography (central visibility). Central log = one place to debug a stuck order. → canvas 3 · Saga vs 2PC

correctness

Idempotency at every write

Client sends Idempotency-Key. Stripe dedups for 24 h. Retry on network glitch is safe — never a double-charge. → canvas 3 · idempotency

CAP split

AP browse · CP checkout

Catalog / cart / search are AP (stale OK). Inventory / payment / orders are CP (refuse if unsure). Boundary crossed at the checkout button. → canvas 3 · CAP

hot-key

Redis DECR for flash sales

100 K QPS burst on 1 SKU → Redis DECR flash:{sku} gate turns it into 100 QPS at the DB. Losers get 503 & a "sold out" CDN cache. → canvas 3 · flash sale

spike

Queue-based checkout mode

When QPS > 3 000/instance, gateway switches from sync HTTP to SQS FIFO + return 202 + pollUrl. Saga workers drain at controlled rate. → canvas 3 · queue mode

state

Order state machine

CREATED → INVENTORY_RESERVED → PAYMENT_CONFIRMED → SHIPPED → DELIVERED. Every transition guarded — cancel/refund fails cleanly on wrong state. → canvas 2 · Order LLD

Glossary — one-liners

Saga (orchestration)central orchestrator runs local transactions with matching compensations; no distributed lock
Compensationthe "undo" for a completed step — must be idempotent (release ×2 == release ×1)
Idempotency keyclient-generated UUID; server stores response for 24 h and returns it on retry
Exactly-once effectat-least-once delivery + idempotent handler = user perceives exactly-once
CQRSseparate write model (Postgres · CP) from read model (ES + Redis · AP)
Transactional outboxwrite DB row + outbox row in one TX; poller pushes to Kafka — no dual-write inconsistency
Reserve / confirm / release3-phase stock protocol — reserve at cart-add / confirm at paid / release on failure or TTL
Flash sale (Redis DECR)atomic pre-DB gate — turns hot-SKU QPS from millions to hundreds
Queue-based checkoutunder spike, HTTP 202 + SQS FIFO — saga workers drain at DB-safe rate
Circuit breaker (sold-out)when stock = 0, return 503 immediately + CDN cache "sold out" 60 s → offload from origin
Debezium CDCreads Postgres WAL → publishes row changes to Kafka → ES / Redis updaters
State machineOrder transitions are guarded; illegal transition throws InvalidOrderStateException
