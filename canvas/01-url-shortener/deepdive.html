A

Scaling strategy

what to shard & how
app tier

Stateless → horizontal

No session affinity, so any instance serves any request. Auto-scale behind the LB (~1K req/s each → ~12–15 at 12K peak reads/s). Round-robin is enough for stateless nodes.

read replicas

Off the hot path

Redirects hit cache, not replicas. Add replicas for the stats/analytics queries so heavy aggregations never compete with the redirect path.

cache tier

Redis Cluster

Consistent-hash the short_code across Redis nodes so any app server finds the same entry. Cluster mode lets the cache grow past one node's RAM.

database sharding — pick a partition strategy

Hash-based partitioning

Route each row by hash(short_code) % N. Because short codes are random Base62 keys, the hash spreads writes and reads evenly across shards — no hot partition.

shard = hash(short_code) % N   // even spread, random keys
verdict
  • Even load — the natural fit for a key-value lookup by short_code.
  • Resharding pain: changing N remaps almost every key → use consistent hashing to avoid it.
  • No range scans — but a URL shortener never needs them.

Range-based partitioning

Assign contiguous key ranges to shards (e.g. a* → shard 1, b* → shard 2). Simple to reason about and supports range scans.

a000000–azzzzzz → shard 1
b000000–bzzzzzz → shard 2   // sequential keys pile up
verdict — avoid here
  • Hot partitions: if codes are handed out sequentially, all fresh writes hit the same shard.
  • Good only when you need ordered scans — a URL shortener does point lookups, so this buys nothing.
  • The interview red flag: "range-based causes hot partitions."

Consistent hashing ← chosen at scale

Nodes and keys map onto a hash ring. Adding or removing a node only remaps the keys in that node's arc — not the whole keyspace. This is how Cassandra / DynamoDB partition natively.

// ring: only ~1/N keys move when a node joins/leaves
node = firstNodeClockwise( hash(short_code) )
verdict
  • Elastic: add capacity for traffic spikes with minimal reshuffling.
  • Virtual nodes smooth out uneven arcs and speed rebalancing.
  • Same technique shards the Redis cache tier and can give the LB cache-affinity.
Key generation at scale: a distributed counter with ZooKeeper-assigned ranges, or a KGS that pre-allocates disjoint key pools per server — so short-code minting never becomes the write bottleneck.
B

Caching deep-dive

5 ms vs 50 ms lives here
cache-aside — read path (redirect)
GET url:{shortCode} from Redis
  ├─ HIT  → 302 redirect                // ~2–5 ms
  └─ MISS → query Cassandra
             ├─ FOUND     → SETEX cache (TTL) → 302
             └─ NOT_FOUND → cache tombstone   → 404

Only hot data is cached; the first access to any code is a miss that self-heals. Negative tombstones (1–5 min) stop bad codes hammering the DB.

write path — write-through on create
POST /shorten
  1. write mapping → Cassandra (durable)
  2. write-through → Redis           // no guaranteed first miss

DELETE → remove from Cassandra + Redis (+ purge CDN)

Creators typically click their own link immediately, so write-through avoids a cold miss. Delete actively invalidates every layer; TTL is the safety net.

hot-key problem

Local Caffeine L1

A viral URL can concentrate millions of hits on one Redis key. Put an in-process Caffeine cache on each app server for the top ~10K codes — sub-ms, no network hop, absorbs the spike before Redis.

Caffeine.newBuilder()
  .maximumSize(10_000)
  .expireAfterWrite(5, MINUTES)
  .refreshAfterWrite(3, MINUTES);
cache stampede

Singleflight lock

When a hot key's TTL expires, 1,000 concurrent misses would stampede the DB. First request grabs a lock, fetches once, backfills; the rest wait and re-read.

// only one DB call per expiry
ok = redis.set("lock:"+code, "1", NX, EX 5)
  ok  → load DB, SETEX, del lock
  !ok → sleep 50ms, re-GET cache
cache warming

Preload top 1,000

On startup / after deploy / after a Redis restart, bulk-load the top URLs by click_count so the first requests don't cold-miss.

SELECT short_code, original_url
FROM urls ORDER BY click_count DESC
LIMIT 1000;   // MSET into Redis
Multi-layer: Browser (302 + Cache-Control) → CDN edge → Caffeine L1 → Redis L2 → Cassandra. Each layer catches a tier of traffic; the DB is the last resort. → full layering on canvas 1 · HLD
C

Bottlenecks & solutions

click a card to open

Single load balancer — SPOF

Impact: one LB means one point of failure and one throughput ceiling — if it dies, every redirect and create fails.

Fix: active-passive (or active-active) LB pair with health checks and DNS failover; L7 LB (ALB / Nginx / HAProxy / Envoy) doing TLS termination and routing.

Database write bottleneck

Impact: a single-leader SQL primary caps write throughput as URL creation scales into thousands of TPS across regions.

Fix: masterless Cassandra / DynamoDB — any node accepts writes, linear horizontal scaling via consistent hashing, no leader election or failover. Postgres is fine below ~10M URLs.

Hot key (viral URL)

Impact: a single trending code sends millions of requests at one Redis shard, saturating it while other shards idle.

Fix: per-node Caffeine L1 cache (top ~10K, 5-min TTL) absorbs the spike with zero network hop; CDN edge caches the 302 for viral traffic; optionally key-replicate the hot entry across shards.

KGS failure

Impact: if the Key Generation Service is a single instance, its outage stops all new-URL creation.

Fix: run multiple KGS instances, each holding a disjoint in-memory key batch; a crash simply discards its unused batch (3.5T codes total, so no scarcity) and no duplicates are ever issued.

Cache stampede (thundering herd)

Impact: when a popular key expires, a burst of simultaneous misses fires identical queries at the DB and can overload it.

Fix: singleflight / mutex (Redis SET key val NX EX 5) so only one request repopulates; stale-while-revalidate and TTL jitter as complements.

Database node / region failure

Impact: a node or an entire datacenter drops offline mid-traffic.

Fix: AP design — replication factor ≥ 3 with QUORUM writes and ONE reads; masterless nodes keep serving, and multi-region replication (Cassandra / DynamoDB global tables) survives a DC loss. Reconcile conflicts with last-write-wins / CRDT counters after the partition heals.

Slow analytics on the hot path

Impact: writing a click row synchronously on every redirect adds latency and couples the redirect to the analytics store.

Fix: fire-and-forget a click event to Kafka (partition by short_code); a consumer batches into a columnar store (ClickHouse / Druid). Redirect returns the 302 immediately; Kafka replay recovers if the pipeline fails.

D

CAP & consistency — why AP

pick two; P is not optional
the choice

P is mandatory in any distributed deployment, so the real decision is A vs C during a partition. Redirects are ~100:1 reads and must always work — a link that fails to resolve is useless. A brand-new URL taking 1–2 s to propagate is fine.

  • AP: during a partition, serve possibly-stale data rather than error.
  • PACELC → PA/EL: partition → Availability; else → Latency. Fast reads always.
  • Worst case for a just-created URL: a rare 404 that resolves on retry.
tunable consistency (Cassandra levels)
// W + R > N gives read-your-writes overlap
create alias → QUORUM write   // leaning CP where it matters
redirect     → ONE read      // fast, AP behavior
custom alias → IF NOT EXISTS   // LWT / conditional write

Per-key linearizability for alias uniqueness (Cassandra IF NOT EXISTS, DynamoDB attribute_not_exists, Redis SETNX) — the one place duplicates are unacceptable — without giving up system-wide availability.

Read-your-own-writes: if a creator needs to hit their link instantly, use sticky routing to the writing node, write-through the local cache, or sync-replicate to one extra replica before ack.
