B

Base62 encoding — the core algorithm

Base62EncodingStrategy
the code (verbatim)
public String encode(String input) {
  long number = Long.parseLong(input);
  StringBuilder enc = new StringBuilder();
  // decimal → base62
  while (number > 0) {
    int r = (int)(number % 62);
    enc.append(BASE62_CHARS.charAt(r));
    number /= 62;
  }
  // pad to length 7, then flip
  while (enc.length() < 7) enc.append('0');
  return enc.reverse().toString()
            .substring(0, 7);
}

BASE62_CHARS = "0123456789a…zA…Z" — index 0-61.

worked example — encode the first id
// counter starts at 100_000
nextId() = 100001

100001 % 62 = 57 → 'V'   100001 / 62 = 1612
  1612 % 62 = 0  → '0'     1612 / 62 =   26
    26 % 62 = 26 → 'q'       26 / 62 =    0  ■ stop

append order → "V0q"
pad to 7     → "V0q0000"
reverse      → "0000q0V"
final code   → "0000q0V"

Padding is appended before the reverse, so the zeros land as a prefix. Once the counter climbs past ~3.5B the code fills all 7 chars naturally.

Why Base62? The 62-char alphabet [0-9a-zA-Z] is URL-safe (no + / = escaping like Base64) and case-sensitive, so 7 chars give 62⁷ ≈ 3.5 trillion codes — far denser than Base10 (10⁷ = 10M) or hex (16⁷ ≈ 268M). Encoding a monotonic counter guarantees zero collisions without a lookup. The trade-off — a globally unique counter is a point of contention — is exactly the distributed-ID problem canvas 3 tackles.
C

Code-generation strategies (Strategy pattern)

swap the algorithm, not the service

Base62EncodingStrategy — encodes the service's AtomicLong counter value. name() = "Base62" · the default in AppConfig

  • Collisions: none — sequential ids are unique by construction.
  • Predictability: sequential → a client can enumerate neighbouring codes.
  • Cost: O(log₆₂ n) — a handful of divisions. Best general-purpose choice.

Md5EncodingStrategy — MD5(url) then first 7 hex chars. name() = "MD5"

  • Deterministic: same URL → same code, so it doubles as deduplication.
  • Collisions: only 16⁷ ≈ 268M codes from 7 hex chars → mandatory retry; the service appends "#" + attempt to the input on each retry.
  • Cost: O(n) over the URL bytes to hash. Best for content-addressed links.

RandomEncodingStrategy — 7 chars from [0-9a-zA-Z] via SecureRandom, input ignored. name() = "Random"

  • Unpredictable: non-enumerable → good when you don't want users guessing links.
  • No counter: nothing to coordinate → naturally distributed-friendly.
  • Collisions: low over 62⁷ but non-zero → check-and-retry required.

Not implemented in the repo, but the interfaces make them drop-in — implement EncodingStrategy and register in AppConfig:

  • KGS (Key Generation Service): pre-generates random unique codes offline into a table; the service just claims the next unused key. No runtime hashing, no collisions, not guessable — the canvas-1 HLD choice.
  • Snowflake: 64-bit id = timestamp + machine-id + sequence, then Base62 it. Distributed, coordination-free, roughly time-sortable — the answer to Base62's single-counter bottleneck.

The pattern: UrlShortenerService holds a single EncodingStrategy field and never branches on algorithm type — it just calls strategy.encode(input). Adding Sha256EncodingStrategy is a new class + one line in AppConfig, with zero changes to the service, controller, or repository (Open-Closed Principle).

Data model detail

Url + ClickEvent
Url — url_mapping (hot lookup)
id          String   // UUID
shortCode   String   // KEY — the lookup index
originalUrl String
createdAt   LocalDateTime
expiresAt   LocalDateTime  // nullable → TTL
clickCount  long           // synchronized ++
customAlias String   // nullable
userId      String   // nullable

Immutable except clickCount. In the MVP the ConcurrentHashMap key is shortCode — that map key is the unique index. In a SQL store: UNIQUE(short_code) + a secondary index on expires_at for a TTL sweep.

ClickEvent — click_events (append-only)
shortCode  String
timestamp  LocalDateTime
ipAddress  String
userAgent  String

Fully immutable (all-args constructor, all fields final). Held in a Collections.synchronizedList in AnalyticsService; getClickCount is a stream-filter over that list. In production this is an append-only stream keyed / partitioned by short_code, indexed on (short_code, timestamp) for time-series queries.

Two counters, on purpose: Url.clickCount is a denormalized total incremented on the redirect hot path (fast read for stats); the ClickEvent list is the detailed audit trail queried off-path. Canvas 1 shows why the detailed events flow through Kafka rather than blocking the redirect.

Request handling sequence

which class does what, in order

POST /api/shorten  →  create a short URL

Controller.handleShortenRequest(request)
  └─ Service.shortenUrl(request)
       1  validateUrl(originalUrl)          // regex → InvalidUrlException
       2  customAlias present?
            yes → shortCode = alias
                  existsByShortCode(alias)? → DuplicateAliasException
            no  → generateUniqueCode():
                    counter.incrementAndGet() → strategy.encode(id)
                    existsByShortCode(code)? retry (max 3)
       3  Url.builder().id(UUID).shortCode(code)
              .originalUrl(..).createdAt(now)
              .expiresAt(now + 365d).build()
       4  repository.save(url)              // map.put(shortCode, url)
       5  return UrlShortenResponse(baseUrl + "/" + code, ...)
  └─ [201 Created]

GET /{shortCode}  →  redirect

Controller.handleRedirect(shortCode)
  └─ Service.redirect(shortCode)
       1  repository.findByShortCode(code)  // Optional
            empty? → UrlNotFoundException   // 404
       2  url.isExpired()? → UrlExpiredException  // 410 Gone
       3  url.incrementClickCount()         // synchronized
       4  return url.getOriginalUrl()
  └─ analyticsService.recordClick(code, ip, userAgent)  // off to the side
  └─ [302 Redirect] Location: originalUrl

Note the click is recorded by the controller after the service returns — the service's redirect() stays focused on resolution, and analytics never blocks the returned URL.

F

Design patterns used

GoF-categorized
Creational
  • Builder — Url.builder(). Readable construction of an 8-field entity; build() enforces required fields.
  • Factory — AppConfig static factory methods centralise all wiring (composition root).
  • Singleton (conceptual) — one shared AtomicLong counter is the single source of truth for the next id.
Behavioral
  • Strategy — EncodingStrategy + Base62 / Md5 / Random. The centrepiece: swap the algorithm without touching the service.
  • Template-style workflow — shortenUrl() fixes the skeleton validate → generate → build → save; the varying step (encode) is the injected strategy.
Architectural (not GoF)
  • Repository — UrlRepository → InMemoryUrlRepository. Decouples business logic from storage; swap in JPA / Cassandra with no service change.
  • Dependency Injection — constructor injection everywhere, wired by hand in AppConfig (Spring @Configuration in production).
Why they cluster: Strategy + Repository + DI together deliver the Open-Closed Principle — new encodings and new storage backends are additions, never edits. Builder keeps the entity immutable and thread-safe; the Singleton counter and ConcurrentHashMap keep the write path lock-light. → trade-offs & the distributed-ID follow-up on canvas 3
