A

Problem & requirements

clarify first
functional
  • Rider requests a ride (pickup + dropoff) → system returns a fare estimate and matches the nearest available driver by ETA.
  • Drivers stream GPS every 3–5 s; system keeps a real-time spatial index of all online drivers.
  • Driver accept/reject within a 15 s timeout; cascade to the next best driver on timeout.
  • Ride lifecycle state machine (REQUESTED → MATCHED → EN_ROUTE → ARRIVED → IN_PROGRESS → COMPLETED / CANCELLED).
  • Dynamic surge pricing per zone, fare calc, payment (charge rider, pay driver), push notifications.
non-functional
  • Matching latency < 30 s (request → matched); geo range query < 50 ms.
  • Ride-state consistency strong / linearizable — two riders must never get the same driver (→ CP).
  • Location freshness < 5 s; stale positions are tolerable (→ AP for location).
  • Availability 99.99% · GPS throughput ~200K updates/s sustained · notifications < 2 s.
  • Durability — zero ride/payment data loss (financial + legal audit).

Derivation: 500K drivers × (1 ping / 3 s) ≈ 167K updates/s × ~200 B ≈ 33 MB/s ≈ 2.8 TB/day raw (before compaction). 20M rides ÷ 86,400 s ≈ 230/s avg, ~1K/s peak · 20M × 2 KB ≈ 40 GB/day of ride records. At ~10K WebSocket connections/server the GPS firehose alone needs ~50 servers. → full math on canvas 3 & the estimation cheatsheet

E

Data model

relational core + Redis hot layer
rides (source of truth · CP)
ride_id            UUID  // PK
rider_id           UUID  // FK
driver_id          UUID  // NULL until matched
status             ENUM  // REQUESTED…COMPLETED/CANCELLED
pickup/dropoff     lat,lng,address
fare_cents         INT
surge_multiplier   DECIMAL(3,2)
estimated_fare_cents INT
version            INT   // optimistic lock
requested_at / matched_at / completed_at  TS

Index (driver_id, status) & (status, requested_at). State transitions guard on status + version to block double-booking.

driver last-location (Redis GeoSet · AP)
// hot spatial layer — not queried from SQL
GEOADD drivers <lng> <lat> "driver:{id}"
GEOSEARCH drivers FROMLONLAT <lng> <lat>
         BYRADIUS 5 km ASC COUNT 5

driver:{id}:active  EX 30   // TTL → auto-offline

// cold history → time-series / NoSQL
driver_locations(driver_id, lat, lng,
   heading, speed, ts)  // partitioned by day

Redis holds only the last known position; the raw stream lands in Kafka → time-series store for 30-day analytics.

Other tables: riders / drivers (profile, rating, status), payments (auth/capture, platform fee, driver payout), surge_zones (H3 cell, multiplier, supply/demand). → full schema on canvas 2 · LLD

F

Key design choices (deep-dived on canvas 3)

defend these
spatial index

Redis GeoSet / QuadTree → H3

GEOSEARCH gives O(log N + K) nearest-driver queries under 50 ms. QuadTree/GeoHash explain the theory; Uber uses H3 hexagons for uniform zones. → canvas 3 · Deep-dive

consistency per component

CP ride-state · AP location

Ride assignment & payments are strongly consistent (optimistic lock → no double-booking); location & surge are AP — 3–5 s staleness is fine. → canvas 2 · LLD

matching

Rank by ETA, cascade on timeout

Offer the lowest-ETA driver (not the closest), 15 s timeout, cascade to the next. Balances rider wait against driver utilization. → canvas 3

Glossary — one-liners

terms used above
Redis GeoSetsorted set with GEOADD/GEOSEARCH for radius queries in O(log N + K)
QuadTreerecursively splits 2D space into 4 quadrants for spatial range queries
GeoHash / H3encode a point into a grid cell (rectangles / Uber's hexagons) for indexing
Surge multiplierper-zone price factor from the supply/demand ratio, capped & TTL-cached
ETA rankingpick the lowest travel-time driver, not the shortest straight-line distance
CP vs APride state favours Consistency; location/surge favour Availability
Optimistic lockingUPDATE … WHERE version=? — 0 rows means someone else won → 409
Cascadeon reject/timeout, offer the ride to the next-best driver
WebSocketlong-lived connection for GPS streams & live-map pushes (no per-ping handshake)
At-least-onceconsumer commits only after delivery; dedup guards against duplicate pushes
