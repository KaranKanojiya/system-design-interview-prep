Core algorithms — Haversine & the QuadTree range query

Location · QuadTree
Haversine — great-circle distance (verbatim)
public static double distanceKm(Location from, Location to) {
  // 1 · degrees → radians
  double lat1 = Math.toRadians(from.lat);
  double lat2 = Math.toRadians(to.lat);
  double dLat = Math.toRadians(to.lat - from.lat);
  double dLng = Math.toRadians(to.lng - from.lng);
  // 2 · haversine of the central angle
  double a = Math.sin(dLat/2)*Math.sin(dLat/2)
    + Math.cos(lat1)*Math.cos(lat2)
    * Math.sin(dLng/2)*Math.sin(dLng/2);
  // 3 · central angle (atan2 = numerically stable)
  double c = 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1-a));
  return EARTH_RADIUS_KM * c;   // R = 6371
}

Every match, fare, ETA and surge-zone check funnels through this one method.

worked example — pickup → dropoff
A = (37.7749, -122.4194)   // SF pickup
B = (37.8049, -122.4094)   // dropoff

Δlat = 0.0300°   Δlng = 0.0100°
     → radians: dLat=5.24e-4, dLng=1.75e-4

a = sin²(dLat/2)               = 6.85e-8
  + cos(lat1)·cos(lat2)·sin²(dLng/2)
    ≈ 0.6241 · 7.62e-9       = 4.75e-9
  a ≈ 7.33e-8

c = 2·atan2(√a, √(1−a))        ≈ 5.41e-4 rad
d = 6371 · c                   ≈ 3.45 km

Flat Euclidean on the same points gives ≈0.032 "degrees" — meaningless. Haversine returns real kilometres because it accounts for longitude shrinking by cos(lat).

QuadTree.findNearby — prune, then filter
// 1 · box around the circle (fast, approximate)
BoundingBox box = BoundingBox.fromCenter(center, radiusKm);
List candidates = new ArrayList();
rangeQuery(root, box, candidates);

void rangeQuery(node, box, out) {
  // PRUNE — the whole reason QuadTree is fast
  if (!node.bounds.intersects(box)) return;
  if (node.isLeaf())
    for (p : node.points)
      if (box.contains(p)) out.add(p);
  else for (child : node.children)
    rangeQuery(child, box, out);       // recurse
}
// 2 · exact Haversine filter  3 · sort  4 · top-k
why two stages, and the cost
  • Stage 1 — box: intersects() lets the query skip entire quadrants that can't hold a result. Prunes most of the tree in O(√n).
  • Stage 2 — Haversine: a box is a square but the search area is a circle; the exact distance check drops the four corner points, then results sort by distance and truncate to maxResults.
  • Insert: a full leaf (>4 points) subdivide()s into NW/NE/SW/SE and redistributes — unless MAX_DEPTH=10 is reached, which caps recursion for co-located drivers (e.g. an airport queue).
  • Update: remove + re-insert, using a side HashMap<id,Location> for O(1) lookup — vital when 1M drivers ping every ~4 s.
The headline: a brute-force "distance to every driver" scan is O(n) — at 100K drivers × 1000 req/s that is 100M Haversine calls per second. The QuadTree turns each query into roughly O(√n + k) — a handful of intersecting leaves plus the k results — cutting the work by orders of magnitude. Production Uber replaces the QuadTree with H3 / Google S2 hex cells but the idea is identical: partition space, prune what's far away.

Pluggable strategies (Strategy ×2)

swap the algorithm, not the service

NearestDriverStrategy — ranks candidates by straight-line Haversine distance to the pickup. used by MatchingService · the AppConfig default

  • Rule: filter available + matching VehicleType, then min(distanceKm(driver, pickup)).
  • Pros: dead simple, predictable, cheap. Cons: ignores traffic — nearest ≠ fastest.

ETABasedStrategy — ranks by estimated arrival time instead of raw distance. drop-in alternative

  • Rule: ETA = (Haversine × 1.3) / (30 km/h × trafficFactor) × 60; pick the minimum.
  • Traffic: 0.5× speed at rush hour (7–9, 17–19), 1.2× late night (23–5), else 1.0×.
  • Pros: a farther driver on an open road beats a near one in gridlock. Cons: needs traffic data (simulated by time-of-day here).

StandardPricingStrategy — base + distance + time, per vehicle type, via an EnumMap rate table. ignores surge by design

  • Formula: base + dist·perKm + dur·perMin, floored at the base fare.
  • Rates: SEDAN 2.00/1.50/0.25 · SUV 3.50/2.00/0.35 · POOL 1.50/0.80/0.15 · LUXURY 5.00/3.00/0.50 · AUTO 1.00/0.50/0.10.

SurgePricingStrategy — a Decorator wrapping Standard; multiplies by the surge factor. the AppConfig default pricing

  • Rule: standardFare × min(surge, MAX_SURGE=3.0).
  • Surge source: SurgeService's per-zone demand/supply ratio (tiered, see §D).
  • Composable: Standard remains usable alone; decorators could stack (surge × promo × subscription).

The pattern: MatchingService holds one MatchingStrategy and PricingService holds one PricingStrategy; neither branches on a mode string. Switching Nearest→ETA or adding surge is a new class plus one line in AppConfig.createMatchingService(...) / createSurgePricingStrategy() — zero changes to the services (Open-Closed Principle).

Data model & the ride state machine

Ride · Location · SurgeZone
Ride — entity (Builder-built)
rideId      String   // UUID[0..8]
rider       Rider    // final
driver      Driver   // null until MATCHED
pickup      Location // final
dropoff     Location // final
status      RideStatus
requestTime Instant  // final
matchTime / startTime / endTime  Instant
estimatedFare / actualFare       double
surgeMultiplier                  double
distance    double   // km (Haversine)
route       List<Location>

Required fields (rider, pickup, dropoff) go in the Builder constructor; the rest are fluent setters with defaults. Mutable fields change only through guarded transition methods.

RideStatus — guarded state machine
REQUESTED ──matchDriver()──▶ MATCHED
MATCHED ──driverEnRoute()──▶ DRIVER_EN_ROUTE
DRIVER_EN_ROUTE ─startRide()─▶ IN_PROGRESS
IN_PROGRESS ─completeRide($)─▶ COMPLETED
   (any non-terminal) ─cancelRide()─▶ CANCELLED

COMPLETED / CANCELLED = terminal

Each method checks the current status and throws InvalidRideStateException on an illegal move — you can't complete a ride that never started, or cancel one already COMPLETED. completeRide(fare) also credits driver earnings and calls driver.markAvailable().

SurgeZone — tiered demand/supply
demand/supply ratio │ multiplier
────────────────────┼───────────
 supply ≥ demand     │ 1.00×  (none)
 ≤ 1.5               │ 1.25×
 ≤ 2.0               │ 1.50×
 ≤ 2.5               │ 2.00×
 ≤ 3.0               │ 2.50×
 > 3.0 or supply=0   │ 3.00×  (cap)

A zone is a circle: containsLocation() = distanceKm(center, p) ≤ radiusKm. SurgeService lays a 2 km grid over SF. The 3.0× cap is a deliberate PR guard.

Location & Vehicle
// Location — immutable, validated
lat  double   // [-90, 90]
lng  double   // [-180, 180]

// Vehicle.VehicleType (capacity)
SEDAN·4  SUV·6  POOL·3
LUXURY·4  AUTO_RICKSHAW·3

Driver carries volatile currentLocation and volatile isAvailable — read by matching threads, written by the location thread. The spatial index stores only (id, Location); MatchingService hydrates full Driver objects from the repository.

Two distances, two fares: the pre-ride estimate uses Haversine × 1.3 road factor at 30 km/h; the actual fare uses the ride's recorded distance and the real elapsed time between startTime and endTime. Keeping both on the Ride lets the app show a quote up front and reconcile at completion.
E

Request handling sequence

which class does what, in order

requestRide  →  find & match a driver

RideController.handleRequestRide(riderId, pickup, dropoff, type)
  └─ RideService.requestRide(...)
       1  riderRepository.findById(riderId)        // else RideException
       2  surgeService.getSurgeMultiplier(pickup)  // find zone → tier
       3  pricingService.estimateFare(pickup, dropoff, type, surge)
       4  new Ride.Builder(rider, pickup, dropoff)...build()  // REQUESTED
          rideRepository.save(ride)
       5  matchingService.findAndMatchDriver(request):
            a locationService.findNearbyDrivers(pickup, 5km, 10)  // QuadTree
            b hydrate Drivers from repo, filter isAvailable()
            c matchingStrategy.findBestDriver(...)
            d simulate accept; cascade to next (max 3) on timeout
               └─ none? → NoDriverAvailableException
       6  ride.matchDriver(driver)        // REQUESTED → MATCHED
       7  driver.markBusy()
       8  ride.driverEnRoute()            // MATCHED → DRIVER_EN_ROUTE
       9  notificationService.notifyRider / notifyDriver(...)
      10  rideRepository.save(ride)
  └─ return ride  (status DRIVER_EN_ROUTE)

Surge and fare are computed before matching so the rider sees a quote up front. If no driver survives the cascade, the rider is notified and the exception propagates.

completeRide  →  finish & charge

RideController.handleCompleteRide(rideId)
  └─ RideService.completeRide(rideId)
       1  rideRepository.findById(rideId)          // else RideException
       2  pricingService.calculateActualFare(ride) // real dist + elapsed time
       3  ride.completeRide(actualFare)            // IN_PROGRESS → COMPLETED
            └─ driver.addEarnings(fare); driver.markAvailable()
          rideRepository.save(ride)
       4  paymentService.processPayment(ride)      // PaymentFailedException → balance
       5  locationService.updateDriverLocation(driverId, dropoff)
       6  notificationService.notifyRider / notifyDriver(receipt)
  └─ return ride  (status COMPLETED)

Note ride.completeRide() is the single guarded transition that sets the fare, stamps endTime, and frees the driver atomically — the service never pokes ride fields directly.

cancelRide  →  release the driver

RideController.handleCancelRide(rideId)
  └─ RideService.cancelRide(rideId)
       1  rideRepository.findById(rideId)
       2  ride.cancelRide()               // throws if already COMPLETED/CANCELLED
            └─ endTime = now; if driver != null → driver.markAvailable()
          rideRepository.save(ride)
       3  notify rider (and driver if assigned)
       4  driver assigned? → locationService re-adds them as available
  └─ return ride  (status CANCELLED)

Cancellation is legal from any non-terminal state; the guard blocks only COMPLETED/CANCELLED. Production layers cancellation-fee rules on top (free before match, fee after).

F

Design patterns used

GoF-categorized
Creational
  • Builder — Ride.Builder. Readable construction of a 12-field entity; required fields in the constructor, optional ones fluent with defaults.
  • Factory — AppConfig static factories are the only new ConcreteClass() site (composition root).
  • Singleton (conceptual) — one QuadTree per LocationService is the shared spatial index all matching leans on.
Behavioral
  • Strategy ×2 — MatchingStrategy (Nearest / ETA) and PricingStrategy (Standard / Surge). The centrepiece: swap algorithms without touching services.
  • State — the Ride guarded state machine; transition methods enforce the legal REQUESTED→…→COMPLETED graph.
  • Observer — NotificationService reacts to ride state changes, keeping notification logic out of the business flow.
Structural (+ DDD)
  • Facade — RideService presents one API over 8+ collaborators.
  • Decorator — SurgePricingStrategy wraps StandardPricingStrategy and multiplies the result transparently.
  • Repository — Ride/Driver/RiderRepository hide the ConcurrentHashMap stores; swap to Postgres with no service change.
Why they cluster: Strategy + Repository + the SpatialIndex interface + AppConfig-driven DI together deliver the Open-Closed Principle — new matching/pricing algorithms and new storage or spatial backends are additions, never edits. Builder + the guarded State machine keep Ride consistent, and the Facade shields the controller from all of it. → scale, sharding & hot-zone trade-offs on canvas 3

Glossary — one-liners

terms used above
Haversinegreat-circle distance between two lat/lng points on a sphere
QuadTreerecursive 2-D partition; prunes far quadrants so nearby-search is ~O(√n + k)
BoundingBoxaxis-aligned rectangle; contains() / intersects() drive the pruning
Strategy patterninterchangeable algorithms behind one interface, chosen at wiring time
Decorator patternwrap an object to add behaviour (surge) while keeping its interface
Facadeone class (RideService) fronting many subsystems
State machineguarded transitions; illegal moves throw instead of corrupting state
Builder patternfluent construction of a many-field object with validation at build()
Repositoryinterface over storage so services never see the map/DB
Surge multipliertiered demand/supply price factor per zone, capped at 3.0×
Cascadeon driver timeout, offer the ride to the next-best candidate (max 3)
volatilevisibility keyword so a driver's location/availability is seen across threads
