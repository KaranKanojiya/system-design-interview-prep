A

Scaling strategy

what to shard & how
location tier

Write firehose

200K–500K drivers each streaming GPS every 3–5 s = ~50K–165K writes/s. Stateless Location Service instances behind the LB fan GPS into Redis GEO; GEOADD overwrites the driver's member, so the set never grows past N drivers.

matching tier

Read + compute

Only ~35 ride requests/s at peak, but each is a spatial query plus ETA ranking. Separate from Location Service so the write-heavy firehose and the read-heavy matcher scale on independent profiles.

ride-state tier

CP core, kept small

Ride Service owns the state machine and driver assignment in PostGIS with row locks. Low volume (a few writes per ride, not per second) so a single-leader RDBMS holds — replicas serve history/analytics off the hot path.

location sharding — pick a partition strategy for the GPS firehose

Cell-based ownership ← chosen for dispatch

Partition the map into geohash / H3 cells and assign each cell to exactly one owner node (consistent hashing, Uber's Ringpop). All requests in a cell serialize on that owner — no split-brain, no cross-node lock for assignment.

// each cell has exactly one owner node
owner = ring.node( geohash(lat, lng, 5) )   // ~5 km cell
verdict
  • Locality: nearby-driver queries and assignments stay on one node → cheap serialization.
  • Handoff: when a driver crosses a cell boundary, ownership is handed off (release → acquire) with no gap/overlap.
  • Hot cells: airports/stadiums concentrate load → over-provision + cache warming.

Hash on driver_id

Route each GPS write by hash(driver_id) % N. Spreads the 50K writes/s evenly and matches Kafka's driver_id partitioning for the location-update topic.

shard = hash(driver_id) % N   // even write spread
verdict
  • Even ingest: perfect for the write firehose and per-driver event ordering.
  • Scatter-gather reads: a "nearby drivers" query must fan out to every shard — a spatial query has no single driver_id.
  • Great for ingestion, wrong for proximity search.

Range-based (by lat or region)

Assign contiguous coordinate ranges to shards (e.g. all of downtown → shard 1). Simple to reason about and keeps a whole city on one node.

lat 37.70–37.80 → shard 1
lat 37.80–37.90 → shard 2   // dense cities pile up
verdict — careful
  • Hot partitions: downtown/airport ranges get orders of magnitude more traffic than suburbs.
  • Boundary queries still need neighbor shards (the same edge effect as geohash cells).
  • Only worth it when a region cleanly maps to one datacenter for latency.
Replicas off the hot path: point PostGIS read replicas at ride history and surge computation so heavy aggregations never compete with the row-locked assignment path. The Redis GEO cluster shards driver locations across nodes; each city fits in ~175 MB, so a 3-node cluster is plenty.

Caching deep-dive

sub-ms nearby queries live here
L1 → L2 → L3 hierarchy
L1  In-app buffer  // 5 GPS pts, batch upload 3–5 s
L2  Redis GEO      // GEOADD/GEOSEARCH, TTL 10 s, 100K ops/s
L3  PostGIS        // source of truth, polygon / geofence

Step 3 reads location from Redis GEO (stale OK). Step 4 reads availability from the DB (must be fresh). That split — cache location, never cache availability — is the whole trick.

geohash cache keys — the hit-rate trick
// BAD: every coordinate is a unique key → ~0% hits
nearby:37.7749:-122.4194:5km
// GOOD: geohash prefix → all riders in a ~5km cell share it
nearby:9q8yy:5   // 70–80% hit rate in dense areas

Precision-5 geohash ≈ 5 km cell = perfect for a 5 km radius query. On miss, query the target cell plus its 8 neighbors to catch drivers just across a boundary, then filter by exact Haversine distance.

TTL by data class

Extreme diversity

Every cache line has a different freshness budget. No cache at all for ride state or driver availability — stale there means double-booking.

driver GPS    → 10 s  // 2–3× update interval
nearby query  → 5 s   (+0–2 s jitter)
surge zone    → 30 s  // recomputed each cycle
ride state    → NONE  // DB is source of truth
available vs busy sets

No stale availability

Never cache a boolean flag. Keep two Redis GEO sets and move a driver atomically on assignment, so a BUSY driver never shows up in a search.

MULTI
  ZREM  drivers:available "D1"
  GEOADD drivers:busy lng lat "D1"
EXEC   // atomic move, no window
hot-spot thundering herd

Airport / stadium

500 requests/min on one cell. Layer four defenses so the DB sees ≤1 query per miss.

// 1 warm known hot spots every 3 s
// 2 TTL jitter 5–7 s (no sync expiry)
// 3 XFetch probabilistic early refresh
// 4 singleflight coalesces misses
Surge cache miss: return last known multiplier and trigger async recompute (never block a ride request 50–100 ms to compute surge), falling back to 1.0× only when nothing is cached. → full layering on canvas 1 · HLD
C

Bottlenecks & solutions

click a card to open

GPS write firehose overwhelms storage

Impact: 50K–165K location updates/s would flatten any single-leader SQL primary; synchronous writes queue up and drivers show 30 s behind on the map.

Fix: ingest into Redis GEO (100K+ ops/s per node, overwrite-in-place so no growth), shard by geohash cell, batch 3–5 GPS points per WebSocket/gRPC message, and mirror to Kafka (partitioned by driver_id) for analytics/history off the hot path.

Double-booking a driver

Impact: two riders request at once, both read driver D-017 as AVAILABLE, both get assigned — two riders wait for one car. A retry storm makes it cascade.

Fix: ride state is CP. Use optimistic locking — a single atomic UPDATE ... SET status='MATCHED' WHERE id=? AND status='AVAILABLE' AND version=?; rows_affected=0 means someone won first, so cascade to the next driver. Or SELECT ... FOR UPDATE / a Redis Lua CAS. Cell-based ownership serializes assignments locally to avoid cross-node coordination.

Stale availability from over-caching

Impact: caching an available/busy flag with even a 3 s TTL means a just-assigned driver still reads AVAILABLE — the classic route to a double booking that no lock catches.

Fix: never cache availability. Maintain drivers:available and drivers:busy GEO sets, move members atomically with MULTI/EXEC on each state change, and query only the available set. Availability transitions are event-driven off the ride state machine.

Hot spot / thundering herd

Impact: an airport arrivals surge or a stadium letting out sends hundreds of identical nearby-driver queries at one geohash cell; when its cache line expires they stampede PostGIS simultaneously.

Fix: cache warming for known hot spots (background job every 3 s), staggered TTL (5–7 s jitter), probabilistic early expiration (XFetch), and request coalescing (singleflight) so only one request per key hits the DB. For scheduled events, pre-warm surge and expand the search radius ahead of time.

Ghost drivers on the map

Impact: a driver whose app crashes or loses signal keeps appearing at their last position; riders get matched to a car that isn't moving.

Fix: heartbeat TTL — SET driver:{id}:heartbeat 1 EX 10 refreshed on every GPS update; the GEO location auto-expires ~10 s after the last update. Mark STALE at 30 s, OFFLINE at 2 min; if offline mid-ride >10 min, auto-cancel with no charge and offer re-match.

Nearest-by-distance picks the wrong driver

Impact: the closest driver by straight-line distance can be 8 min away through traffic while a driver 3 km down the highway is 3 min away. Riders wait longer than the "nearest" promised.

Fix: rank the K nearest candidates by ETA, not raw distance — Haversine straight-line as a first pass, then a routing API for road-network ETA in production. Send to the best ETA with a 15 s timeout and cascade to the next on decline/timeout.

Geohash boundary misses

Impact: a driver 1 m across a cell boundary has a different geohash prefix, so a single-cell query silently misses them — the nearest driver is invisible.

Fix: always query the target cell plus its 8 neighbors (9 cells total), then filter by exact Haversine distance. H3 hexagons reduce this to 6 equidistant neighbors with no corner artifacts — what Uber uses for zones.

Cross-region partition & split-brain

Impact: a partition between two regional Ride Services lets both independently assign a driver who crosses the boundary — the CP guarantee breaks if driver state is regional.

Fix: keep driver state in a single-leader DB (not per-region), route cross-region assignment through the leader, or shard drivers to exactly one region at a time with a handoff protocol at the boundary. During a partition, the CP side refuses new assignments ("high demand, try again") while in-progress rides continue.

D

CAP & consistency — a split system

CP ride state · AP location
the choice

P is mandatory, so each component picks A vs C on its own terms. Ride-sharing is neither pure CP nor pure AP — it's split. Assignment and payment are CP (double-booking / double-charging are unacceptable); location and surge are AP (a 3–5 s-old GPS fix is inherently approximate anyway, and unavailable location makes matching impossible).

  • CP (ride state): during a partition, refuse to assign rather than risk a double-book.
  • AP (location): serve slightly stale GPS and stay available — staleness (5 s ≈ 67 m at 30 mph) is fine.
  • In-progress rides continue through a partition; only new assignments pause.
PACELC — normal operation too
// if Partition: A or C  ·  Else: L or C
ride assignment → PC/EC   // row lock, ~15 ms, accept latency
location track  → PA/EL   // async to Redis GEO, ~1 ms write
surge pricing   → PA/EL   // precomputed, cached, bounded 60 s
payment         → PC/EC   // ACID, exactly-once

The principle: CP where correctness beats speed (assignment, payment), AP where freshness is already bounded by the real world (GPS interval, 30 s surge window). Location can't be CP anyway — 165K consensus rounds/s would swamp Raft.

How Uber does it: Ringpop consistent hashing makes each geofence cell owned by one node (CP dispatch, no distributed lock); Cassandra for location (AP, millions of writes/s); Redis for surge (AP, bounded staleness); MySQL+Vitess for payment (CP, ACID).

…and finish strong
