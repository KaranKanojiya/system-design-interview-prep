Choose gateway-only when:

  • You have < 20 services and internal calls are direct (no fan-out).
  • All internal traffic is on a trusted network (VPC + private subnets) — you're OK skipping mTLS.
  • Team size < 30 — the operational complexity of a mesh isn't worth it yet.
  • You need external API management (developer portal, quotas, billing) — Apigee / Kong shine here.

Choose mesh-only when:

  • Your ingress is a plain L4 load balancer (NLB) — you don't need JWT/OAuth/API-key features.
  • All clients are internal / mobile apps using long-lived mTLS certs (rare in practice).
  • Your team already runs Istio and doesn't want two vendors.

In practice this is uncommon — even mesh-heavy shops use a lightweight gateway for TLS termination and rate-limiting at the edge.

The standard architecture — use both:

  1. API Gateway at the edge handles ingress: JWT, rate-limit, WAF, DDoS protection, TLS termination, request-shape validation.
  2. Gateway forwards to the first internal hop's sidecar (or directly to service if that hop has no sidecar).
  3. All subsequent service-to-service calls go sidecar → sidecar with mTLS, circuit-breaking, and retries applied by the mesh.

This is what Netflix, Uber, Airbnb, LinkedIn all run. Gateway ≠ mesh; they're complementary.

Circuit breaker — the resilience keystone

stops cascading failure
why it exists

Without circuit breakers: backend B is slow (2 s per request). Callers wait full timeout (5 s), holding a thread each. At 100 RPS, threads pile up ⇒ caller pool exhausted ⇒ caller returns 503 ⇒ its callers also pile up ⇒ cascade until the entire mesh is on fire.

With circuit breakers: after 5 consecutive failures/timeouts, circuit trips OPEN. New requests fail-fast (< 1 μs) with 503 instead of waiting. Threads freed. Caller's caller gets a fast 503 and can degrade gracefully (cached response, alternative service).

the recovery dance (HALF_OPEN)

The tricky part. After 30 s in OPEN, we don't just flip back to CLOSED — the backend might still be broken. Instead we transition to HALF_OPEN and allow ONE test request.

  • If test succeeds → wait for SUCCESS_THRESHOLD (3) more successes → CLOSED.
  • If test fails → back to OPEN, another 30 s cooldown.

Thundering herd: if 1 000 callers all HALF_OPEN at the same moment, that's 1 000 test requests hitting the recovering backend simultaneously ⇒ they all fail ⇒ back to OPEN, worse than before. Mitigation: jitter the OPEN_DURATION (30 s ± 20 %) so not everyone probes at the same instant.

Advanced tuning: our code uses consecutive-count thresholds (5 fails in a row). Production circuit breakers (Hystrix, Resilience4j, Envoy) use error-rate percentage over a rolling window (e.g., open if >50 % of the last 100 requests failed AND at least 20 requests happened). More robust for sparse traffic and less prone to over-reaction on isolated blips.
Bulkhead pattern (companion): beyond CB, isolate resources per downstream — dedicated thread pool of size 20 per target service. If backend B slows down, only 20 threads are ever tied up on it — other services are unaffected. Combined with CB, blast radius stays contained.

Rate limiting algorithms — token bucket vs alternatives

interviews always ask
Token bucket (chosen)
Leaky bucket
Fixed window
Sliding window log
comparison

Bucket has N tokens. Refill at rate R per second (up to capacity). Each request consumes 1 token; deny if 0.

// On request for key = (client, route):
now = System.currentTimeMillis()
bucket.tokens = min(bucket.capacity,
                    bucket.tokens + (now - bucket.lastRefill) * bucket.rate / 1000)
bucket.lastRefill = now
if (bucket.tokens >= 1) {
  bucket.tokens--
  return ALLOW (remainingTokens = floor(bucket.tokens))
} else {
  retryAfterMs = (1 - bucket.tokens) / bucket.rate * 1000
  return DENY (429, Retry-After: retryAfterMs)
}

Pros: allows burst up to capacity; naturally smooth; O(1) memory per key.
Cons: a coordinated flood of bursts can still overwhelm downstream — must be paired with concurrency limits.

Bucket leaks at constant rate R. Incoming requests fill the bucket; if full, deny. Requests processed at rate R regardless of input.

// Equivalent formulation: FIFO queue with capacity N, drain at rate R
if (queue.size < capacity) {
  queue.offer(request)
  return ALLOW
} else {
  return DENY (429)
}

Pros: perfectly smooth downstream traffic — no bursts pass through.
Cons: latency increases as queue fills; poor UX for sporadic-burst traffic (mobile push, cron jobs).

Count requests in the current 1-second window. Reset counter at second boundary.

if (currentSecond != bucket.windowStart) {
  bucket.count = 0
  bucket.windowStart = currentSecond
}
bucket.count++
return bucket.count <= limit ? ALLOW : DENY

Pros: trivial O(1).
Cons: edge burst — a client can hit 2× limit by sending N requests at second 0.999 and another N at 1.001. Simple but leaky in practice.

Store timestamps of the last N requests. Deny if oldest > window-size ago.

bucket.timestamps.removeIf(t -> t < now - WINDOW_MS)
if (bucket.timestamps.size < limit) {
  bucket.timestamps.add(now)
  return ALLOW
}
return DENY (Retry-After: bucket.timestamps.get(0) + WINDOW_MS - now)

Pros: most accurate — no edge-burst; precise remaining-quota reporting.
Cons: O(limit) memory per key — expensive at millions of clients × routes. Use only for high-value endpoints (login, payment).

Distributed setup: in-memory works per-gateway-instance only. For global rate limits across the fleet, use Redis with a Lua script for atomic token-bucket ops. Cost: one Redis RTT (~0.5 ms) added to hot path. Alternative: soft local limit + eventually-consistent global counter for high-throughput / low-cost endpoints.

Zero-trust mTLS — cert rotation at 200 K/day

SPIFFE · SPIRE · SVIDs
what "zero trust" means

Traditional trust: "we're in the same VPC, so I'll accept HTTP without auth." Breaks the moment an attacker gets a foothold — lateral movement is trivial.

Zero-trust: every service pair authenticates via mutual TLS on EVERY connection. No network-based trust. Compromised pod A cannot make requests as pod B without pod B's cert.

Identity = SPIFFE ID: spiffe://cluster.local/ns/prod/sa/order-service. The mesh CA issues short-lived X.509 certs (SVIDs) with this URI in the SAN field. Auto-rotated every 24 h (or on cert refresh signal).

the rotation problem

At 50 000 pods × 1 rotation/day = 200 K cert issuances/day. Manual is impossible. Automated via SPIRE agents:

  1. Pod starts; SPIRE agent on the node attests it (validates via k8s ServiceAccount + node identity).
  2. Agent requests SVID from SPIRE server on behalf of pod.
  3. SPIRE server signs a short-lived cert (1 h TTL) with the pod's SPIFFE ID.
  4. Agent injects cert + private key into the pod's sidecar via SPIFFE Workload API.
  5. Sidecar hot-reloads cert every ~30 min; no downtime.

Failure mode: if SPIRE server is unreachable at rotation, sidecar uses last-known-good cert until it expires. Grace window (usually 2× rotation interval) buys time to recover.

Interview zinger: zero-trust with mTLS also solves internal replay attacks — even if an attacker records ciphertext, they can't replay it (session keys are unique per handshake) and can't forge new requests (no client cert). This is genuinely stronger than any network-perimeter model.

Canary deploys with automated rollback

1 000 deploys/day at Netflix
the flow
  1. Deploy v2 alongside v1; v2 registered with weight=0 (0 % traffic).
  2. Gradually shift weight: 0 → 1 → 5 → 25 → 50 → 100 over 30 min.
  3. At each step, SLO monitor compares v2 vs v1: error rate, p99 latency, saturation.
  4. If v2 within 2 % of v1 baseline → proceed to next step.
  5. If v2 worse by > anomaly threshold → automatic rollback: set v2 weight = 0, page on-call.
  6. If all steps pass → v1 weight = 0, then decommission v1 pods.
two ways to canary

1. Weighted (CanaryTrafficStrategy) — random 5 % of external users hit v2. Statistically representative; requires enough traffic to detect anomalies (usually > 1 000 RPS).

2. Header-based (HeaderBasedTrafficStrategy) — X-Canary: true or specific internal test accounts hit v2. Deterministic; great for QA / dogfooding; doesn't need traffic volume.

Best practice: combine both. Start header-based for internal validation, then weighted for real-user data, then full rollout.

Rollback within 60 s requires: (1) SLO computation on 30-s windows (not 5-min); (2) alert-to-traffic-shift automation (no human in the loop for red-alarm anomalies); (3) idempotent rollback API — the same "set v2 weight=0" call safe to retry.

CAP theorem — data plane AP · control plane CP

split answer again
The insight: the data plane (gateway request-handling, sidecar-to-sidecar proxying) MUST be highly available — a partition to the control plane must not stop traffic. So the data plane is AP. The control plane (route registration, policy config, cert issuance) must be strongly consistent — you don't want half the fleet on v1 config and half on v2. So control plane is CP.

Bottlenecks & mitigations

8 failure modes · defence against each
Control-plane outage (Istio Pilot down)

Symptom: can't push new routes / policies; new pods can't get certs.

Mitigation: data plane keeps operating on last-known-good config — that's WHY sidecars cache. Sidecar SVIDs valid for hours; xDS config valid indefinitely until push. Alert on control-plane down but don't panic — traffic keeps flowing. Multi-AZ control plane; automatic failover.

Certificate rotation storm

Symptom: at 3 AM, 50 K sidecars all try to rotate certs simultaneously → SPIRE server saturated → some rotations fail → some sidecars hit expiration → mTLS handshake failures spike.

Mitigation: jitter rotation windows (each pod rotates at random offset within 24 h). Cache cert-request results at SPIRE server. Scale SPIRE horizontally by k8s namespace.

Thundering herd on OPEN → HALF_OPEN

Symptom: 1 000 gateway threads all see OPEN_DURATION elapsed at t=30 s → all send probe → recovering backend crushed by 1 000 concurrent requests → all fail → back to OPEN.

Mitigation: jitter the OPEN_DURATION (30 s ± 20 %). Optionally: only ONE probe per cooldown (queue others in HALF_OPEN pending); rate-limit test requests per second.

Hot route in the routing table

Symptom: route table has 5 000 entries; the lookup for /api/users/* scans them all each request → CPU-bound at 10 K RPS.

Mitigation: trie / radix tree keyed by path segment for O(k) lookup where k = path depth (typically 3–5), not O(n). Envoy does this natively. Also: pre-compile globs to regex ONCE at registration, not per-request.

TLS handshake overhead

Symptom: new mTLS handshake = 2 RTTs + 4 cert-verify ops. At 10 K new connections/s, sidecar CPU pegged on handshake.

Mitigation: HTTP/2 with long-lived connections — one handshake amortized over thousands of requests. TLS session resumption. Cache parsed cert chains in memory.

Rate-limit inconsistency across gateway fleet

Symptom: local per-gateway limits mean a client can send 4× the intended rate by hitting different gateways.

Mitigation: Redis with Lua atomic INCR for global limits — one RTT (~0.5 ms) on hot path. For less critical routes: local limit at 1/N-th (N = gateway count) — cheap approximation. Use global limits only where correctness matters (payment, auth).

JWT validation cost

Symptom: RSA signature verify = ~0.5 ms per request → at 100 K RPS = 50 gateway cores just verifying JWTs.

Mitigation: cache verified JWT results by (tokenHash → AuthResult) for the token's TTL. Second request with same token = 0.01 ms cache hit. ~99 % hit rate for logged-in users. For DDoS spikes: rate-limit BEFORE auth so bad tokens don't consume CPU.

Stuck instances in registry

Symptom: instance crashed but registry still lists it as healthy for 10 s (heartbeat timeout) → LB routes requests to dead instance → 503s spike.

Mitigation: shorten heartbeat window (3 s instead of 10 s). Combine with active health probes (LB sends periodic /health checks and evicts on failure). Kill-switch API for ops to force-deregister an instance immediately.

Interview walkthrough — 8 phases

45-min structure · green & red flags
phase 1 — clarify (2 min)

Ask: external clients only, or internal too? # services and RPS? SLA target? On-prem or cloud-managed?

Green: "external RPS 100 K, internal 1 M, 200 services, GCP." Red: skipping straight to Envoy without knowing scale.
phase 2 — separate concerns (3 min)

Draw the two planes: N-S (gateway) vs E-W (mesh). Explain why one system can't do both — fan-out ratio.

Green: "gateway = ingress, mesh = internal, complementary". Red: "the gateway handles internal calls too" (breaks at scale).
phase 3 — gateway pipeline (5 min)

10 steps: route → auth → authz → rate-limit → CB → LB → forward → record → respond. Cheapest filters first, fail-fast.

Green: draw the pipeline; explain ordering. Red: "the gateway does auth" without saying WHEN in the pipeline.
phase 4 — mesh architecture (5 min)

Sidecar per pod (Envoy). Control plane (Istio/Consul) pushes config via xDS. mTLS via SPIRE. All apps unchanged.

Green: "sidecar intercepts via iptables; app code unaware". Red: "each service does its own mTLS" (defeats mesh point).
phase 5 — deep dives (15 min)

Pick 2–3: circuit breaker (3-state machine), token bucket (refill math), consistent hash LB (ring + vnodes), mTLS + SPIFFE, canary + auto-rollback.

Green: verbatim state-machine code, refill formula. Red: "we do circuit breaking" without state transitions.
phase 6 — CAP & failures (5 min)

Data plane AP (traffic must flow during CP blips). Control plane CP. 8 bottlenecks (thundering herd, cert storm, hot route, TLS handshake).

Green: "split answer — data plane AP for availability, control plane CP for correctness". Red: "the whole system is CP".
phase 7 — scale (5 min)

2–4 gateway instances × 50 K RPS = 100 K RPS. Mesh: 50 K pods × 1 sidecar each. Redis for global rate limits. Prometheus for metrics.

Green: quote per-instance numbers + headroom. Red: "we can scale to any RPS" without numbers.
phase 8 — extensions (5 min)

WAF at edge. Bot detection (Cloudflare). WebSocket / gRPC support. Multi-cluster mesh federation (across regions). API versioning strategy.

Green: name the extension AND the trade-off. Red: "we can add WebSocket easily" (not trivial in a mesh).
