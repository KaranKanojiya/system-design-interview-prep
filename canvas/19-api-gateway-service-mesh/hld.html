API Gateway & Service Mesh — High-Level Design

Use case 19 · Canvas 1 of 3. Two traffic planes, one design: North-South (external clients → API Gateway → services) and East-West (service ↔ service via sidecar mesh). Every request runs the pipeline: route → auth → rate-limit → circuit-breaker → load-balance → forward. Sidecars (Envoy-style) apply mTLS, retries, and observability transparently. A

Problem & requirements

why gateway ≠ mesh
functional
  • Routing — path (/api/users/**) + header + method → target service; glob wildcards; priority sort.
  • Authentication — JWT (decode + claim extraction) OR API key (trusted keystore lookup); pluggable via AuthStrategy.
  • Authorization — role-based per-route via metadata (required-role).
  • Rate limiting — token bucket per-client + per-route; return 429 with Retry-After.
  • Circuit breaker — CLOSED / OPEN / HALF_OPEN state machine per target service.
  • Load balancing — Round-Robin / Weighted / Consistent-Hash across healthy instances.
  • Service discovery — instance registration + heartbeat + stale eviction.
  • Service mesh (E-W) — sidecar per pod: mTLS enforcement, circuit-break, LB, retries.
  • Canary deploys — traffic split by weight (95/5) or header (X-Canary: true).
  • Observability — X-Trace-Id propagation, mesh headers, metrics per pipeline step.
non-functional
  • Gateway overhead < 1 ms p99 (excluding upstream latency).
  • Throughput 100 K RPS/instance; 2 M RPS at fleet level (Netflix-scale).
  • Availability 99.99 % (~52 min/yr downtime).
  • Route table updates propagate < 5 s (eventual consistency).
  • Circuit-breaker state transitions within 1 request of threshold.
  • Rate limiter accuracy within 1 % of configured rate.
  • mTLS validation < 0.1 ms (cached cert chains).
  • Health-check detection of failed instances < 10 s.
  • Canary rollback < 60 s of anomaly detection.
  • Zero-downtime deploys — rolling restart with graceful drain.

Why the mesh is bigger than the gateway: N-S traffic hits the gateway once; E-W fans out ~10× per external request (microservices call each other). At 100 K external RPS you already have ~1 M internal RPCs — every one of them wants auth, retry, and mTLS. That's why sidecars exist: it's infeasible to route 1 M RPS through a central gateway.

  successThreshold      // 3

  clientId
  routeId
  tokens                // current count

  refillRatePerSec
  lastRefillAt

RequestContext (per in-flight request)
  traceId
  route
  authResult            // principal, roles
  selectedInstance
  startedAt
Why 'small & hot' works: route table (1 000 routes × 1 KB = 1 MB), instances (5 000 × 500 B = 2.5 MB), rate buckets (100 K × 100 B = 10 MB), CB state (500 × 200 B = 100 KB). Total < 15 MB per gateway instance — trivially in-process. That's how you hit < 1 ms p99: zero cross-service calls on the hot path.
F

Key design choices (deep-dived on canvas 3)

defend these
separation

Gateway (N-S) vs mesh (E-W)

Central gateway for external ingress; per-pod sidecars for internal RPCs. Mesh scales linearly with fleet — no central bottleneck. → canvas 3 · gateway-vs-mesh

resilience

Circuit breaker

CLOSED → OPEN → HALF_OPEN state machine per target service. Stops cascading failures — one slow backend doesn't tie up threads. → canvas 3 · CB deep-dive

security

Zero-trust via mTLS

Every service pair authenticates via cert. Mesh CA auto-rotates daily. No implicit trust based on network location. → canvas 3 · zero-trust

balancing

Strategy-pattern load balancer

Round-Robin default, Weighted for canary, ConsistentHash for cache-affinity. Swap by config. → canvas 2 · LB tabs

deploys

Canary via traffic split

95/5 by weight OR header-based (X-Canary: true) for targeted testing. Rollback in 60 s. → canvas 3 · canary

observability

Trace ID propagation

Gateway generates X-Trace-Id; sidecars propagate. Every hop is a span in Jaeger. Debug a 20-hop request in one dashboard.

Glossary — one-liners

North-South (N-S)traffic between external clients and the cluster (ingress)
East-West (E-W)traffic between services inside the cluster (RPC fan-out)
Sidecara proxy container in the same pod as the service; intercepts all traffic
Service meshthe collection of sidecars + control plane managing E-W traffic uniformly
Circuit breaker3-state machine that fast-fails when a backend is unhealthy, preventing cascading failure
Token bucketrate-limit algorithm: bucket refills at rate R, each request consumes 1 token, deny when empty
mTLSmutual TLS — both sides present certs; enables zero-trust networking
Consistent hashLB scheme where the same key always routes to the same instance; adding nodes only shuffles 1/N of keys
xDSEnvoy's Discovery Service API — control plane pushes config to sidecars via gRPC stream
Canary deploysend small % of traffic to new version; rollback if error rate spikes
SPIFFE / SPIREstandard + runtime for issuing short-lived service identities (mTLS certs)
Trace ID propagationa request-level UUID passed through every hop so distributed calls can be reconstructed
