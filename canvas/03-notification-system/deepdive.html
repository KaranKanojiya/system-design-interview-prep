A

Scaling strategy

what to partition & how
API + service tier

Stateless → horizontal

The API gateway and NotificationService hold no session state, so any instance handles any request. Auto-scale behind the LB toward ~12K/s average and ~50K/s peak; the send call returns 202 Accepted and the real work is async on Kafka.

Kafka partitions

Key by userId

Each priority topic starts at ~10 partitions and scales to 100+. Partition key = userId so a user's events keep per-user order. Add partitions to raise parallelism; consumers rebalance automatically.

channel workers

Independent consumer groups

One consumer group per channel per priority (e.g. push-critical-cg). Scale SMS workers separately from push — SMS is 75× costlier and rate-limited, push is free and bursty. Autoscale on consumer lag.

data partitioning — pick a store & strategy

Notification logs → Cassandra

Write-heavy, append-only, time-series. Partition by userId + month with a timestamp clustering key so "get my notifications" is a single-partition read, newest first. Row-level TTL auto-expires after 90 days.

PRIMARY KEY ((user_id, yyyymm), created_at)
  // single-partition read, DESC clustering
  // TTL 90d → no manual cleanup
verdict
  • Linear write scaling — the natural fit for 1B writes/day.
  • Month in the key stops any one partition growing unbounded.
  • No joins / ad-hoc queries — but the feed only ever does a point-in-partition scan.

Priority topics ← separate queues

Four topics — notifications.high / medium / low plus dlq.notifications — so a marketing backlog can never block an OTP. Each topic has its own consumer groups and partition count.

notifications.high    // OTP, 2FA, payment
notifications.medium  // order / shipping
notifications.low     // marketing, digests
verdict
  • Isolation: critical drains first; low-priority is shed under backpressure.
  • acks=all, RF=3, min.insync.replicas=2 → survive 2 broker losses, no message loss.
  • Consumer replay from any offset recovers a corrupted batch — SQS cannot.

Preferences → PostgreSQL

~100M users × ~200 B ≈ a small relational dataset. A single primary (with read replicas) handles it, and ACID gives an opt-out that takes effect the instant it commits.

user → channels → preferences  // FKs, joins
opt-out = UPDATE ... COMMIT   // strongly consistent
verdict
  • Strong consistency where it legally matters (CAN-SPAM / GDPR).
  • Read replicas absorb the per-send preference lookups; the cache fronts most of them.
  • No sharding needed at this size — resist the urge to over-engineer.
Batch fan-out at scale: a 10M-user send is chunked into ~1,000-user segments, each enqueued as one Kafka message; a worker expands the chunk, runs the per-user preference gate, and emits individual sends — so one API call never blocks on 10M synchronous checks.
B

Caching deep-dive

compliance vs latency lives here
two-layer cache — read path
GET tmpl:{id}:{locale}  // on every send
  L1 Caffeine (~1µs) ─ miss →
  L2 Redis    (~1ms) ─ miss →
    Cassandra/Postgres (~5–50ms)
      → populate L2 → populate L1

Templates are read on every notification and change ~weekly → cache aggressively in both layers (~99% hit). Only hot, rarely-changing, staleness-tolerant data earns an L1 slot.

what each key looks like
tmpl:{id}:{locale}   L1+L2  no TTL, event-invalidate
pref:{userId}        L2     TTL 5 min + explicit DEL
tokens:{userId}      L2     TTL 24h, self-heal on 410
dedup:{hash}         L2     SET NX, TTL 24h
ratelimit:{u}:{ch}:{d} L2   INCR, TTL end-of-day

Preferences skip L1: with N instances you'd get N copies that go stale independently, and a stale opt-out is a violation. Redis is shared → one DEL invalidates everyone.

the big risk

Stale preferences

A user opts out at 10:00:00; a 5-min TTL could let a marketing email through at 10:00:02. Fix: the preference write does DB → Redis DEL → 200, so the next send cache-misses to fresh data. TTL is only the safety net.

// opt-out critical path
UPDATE prefs; COMMIT
Redis DEL pref:{userId}
// marketing sends: skip cache, read DB
cache stampede

Singleflight lock

A system-wide alert invalidates tmpl-maintenance-alert; 1,000 workers miss at once. First worker grabs a Redis lock, fetches once, backfills; the rest spin briefly then read the warm cache.

ok = redis.set("lock:tmpl:"+id, 1, NX, EX 5)
  ok  → load DB, populate, del lock
  !ok → short spin, re-GET cache
cache warming

Pre-load templates

Templates have no TTL, so a stampede only follows an explicit invalidation. On deploy, bulk-load all active templates into L1+L2 so the first sends after a rollout don't cold-miss.

SELECT id, locale, body
FROM templates WHERE active
// MSET into Redis + prime Caffeine
Redis is not always a cache: dedup keys (SET NX) and rate-limit counters (INCR) treat Redis as the source of truth, not a cache — that's why we chose Redis over Memcached. Delivery status is never cached: it changes rapidly (PENDING→SENT→DELIVERED→READ) and a stale value is a debugging nightmare. → full layering on canvas 1 · HLD
C

Bottlenecks & solutions

click a card to open

Single queue for all priorities

Impact: if OTP, order updates and marketing share one topic, a bulk marketing backlog sits in front of a login OTP — the user can't sign in while low-value mail drains.

Fix: separate notifications.high / medium / low topics, each with dedicated consumer groups. Critical drains first; under backpressure we stop accepting LOW batches while CRITICAL is always admitted.

Synchronous provider call in the request path

Impact: calling FCM/SES/Twilio inside the API request couples client latency to a flaky third party and caps throughput at provider speed.

Fix: return 202 Accepted immediately and hand off to Kafka. Channel workers call providers asynchronously; a crash mid-send just redelivers the Kafka message and dedup catches the duplicate.

External provider failure / throttling

Impact: FCM returns 429, SES rate-limits, or Twilio times out — naive retries amplify the overload and stall the whole worker group.

Fix: exponential backoff with jitter (1s→2s→4s→8s→16s, 5 tries) and a circuit breaker per provider that opens on 429 and backs off. Permanent errors (invalid token, hard bounce) skip retries and go straight to the DLQ.

Thundering herd after a partition heals

Impact: when a partition heals, a flood of queued notifications hits the workers and downstream providers at once.

Fix: consumer-level token-bucket rate limiting per channel, bounded concurrency via max.poll.records, priority draining (OTP first, marketing waits), and per-provider circuit breakers with exponential backoff.

Duplicate sends (at-least-once)

Impact: Kafka commits offsets after a successful provider call, so a worker crash mid-send redelivers the message — the user could get two OTPs.

Fix: idempotency key = hash(userId+templateId+channel+timeWindow), checked with Redis SET NX (24h TTL) before enqueue and before send. For payment SMS, also store a sent-flag in the DB as a second check.

Stale preference → compliance violation

Impact: a user opts out but a cached preference lets a marketing message through — a CAN-SPAM / GDPR breach, not just an annoyance.

Fix: the one CP exception — explicit cache invalidation on opt-out (DB → Redis DEL), a 5-min TTL safety net, and for legally-sensitive marketing sends skip the cache entirely and read PostgreSQL directly. Fail-closed: if the preference service is down, do NOT send.

DLQ full / silent message loss

Impact: after max retries, messages pile into the Dead Letter Queue; if it fills or is ignored, failed notifications vanish undetected.

Fix: fail-closed on a full DLQ — alert and stop processing rather than drop. Page on-call whenever dlq_depth > 0; a reviewer retries transient errors after an hour and marks permanent ones FAILED.

CAP & consistency — why AP (with one CP exception)

pick two; P is not optional
the choice

P is mandatory in any distributed deployment, so the real decision is A vs C during a partition. For delivery we pick A: a duplicate notification is annoying, a missing one is unacceptable — a lost OTP means the user can't log in, a lost order confirmation triggers a duplicate order.

  • AP for delivery: during a partition keep sending; reconcile duplicates with idempotency keys.
  • Fail-open for dedup cache, rate limiter and template cache — degrade, never stop delivery.
  • Fail-closed for opt-out enforcement and a full DLQ — never send to an opted-out user, never silently drop.
delivery semantics & idempotency
// at-least-once + dedup (our default)
key = hash(userId+templateId+channel+window)
Redis SET NX key EX 24h
  exists → skip   // duplicate
  new    → send   // retry keeps same key
// payment/billing → upgrade to exactly-once

Exactly-once everywhere is impossible — external providers (FCM/SES/Twilio) have no transactional "uncommit." We approximate it only where duplication is harmful (payments) with an idempotency key plus a DB sent-flag; everywhere else at-least-once is cheaper and safer.

Ordering: global ordering is not required (push and email for one event may arrive in any order). Per-user ordering is nice-to-have for the in-app feed, achieved with Kafka partition key = userId. Causal ordering ("order confirmed" after "order placed") uses sequence numbers where it matters.
