A

Problem & requirements

clarify first
functional
  • Multi-channel send — push (FCM/APNs), email (SES/SendGrid), SMS (Twilio), in-app; one or many channels per request.
  • Preferences — opt-in/out per channel, quiet hours (no non-critical 10 PM–8 AM), per-channel frequency caps.
  • Templates with {{variable}} substitution & localization; priority CRITICAL/HIGH/MEDIUM/LOW.
  • Scheduled delivery, retry w/ backoff, delivery tracking, batch (segment) send, idempotent dedup.
non-functional
  • Delivery guarantee at-least-once — a missed OTP is unacceptable; a duplicate is tolerable (→ AP system).
  • Latency CRITICAL < 1 s end-to-end · HIGH < 5 s · MEDIUM/LOW < 30 s.
  • Throughput 50K/s at peak · availability 99.9%.
  • Dedup via idempotency key (24 h TTL); global ordering not required; horizontal scaling everywhere.

E

Data model

Cassandra + PostgreSQL
notification (Cassandra — write-heavy, TTL)
id              UUID  // PK
user_id         VARCHAR(64)
template_id     VARCHAR(128)
channel         VARCHAR(16)  // PUSH/EMAIL/SMS/IN_APP
priority        VARCHAR(16)  // CRITICAL…LOW
status          VARCHAR(16)  // PENDING→SENT→…
data_json       TEXT         // template vars
idempotency_key VARCHAR(128)
scheduled_at    TIMESTAMP
retry_count     INT
created_at      TIMESTAMP

Partition key (user_id, day_bucket); 30-day TTL auto-cleanup. delivery_log (notification_id, attempt, provider, status) is a sibling append-only table.

user_preference (PostgreSQL — strong consistency)
user_id           VARCHAR(64)  // PK
channel           VARCHAR(16)  // PK
enabled           BOOLEAN
quiet_hours_start TIME         // e.g. 22:00
quiet_hours_end   TIME         // e.g. 08:00
frequency_cap     INT          // max/day
updated_at        TIMESTAMP

Relational so an opt-out is immediate (ACID). notification_template (subject/body templates, variables, locale, active) also lives here — both cached in Redis.

F

Key design choices (deep-dived on canvas 3)

defend these
queue

Kafka · priority topics

Separate topics per priority so a 10M-message marketing batch never starves an OTP; groups scale independently. Beats a single topic with headers, and RabbitMQ/SQS at this throughput. → canvas 2 · LLD

delivery guarantee

At-least-once · AP

A missed OTP is unacceptable; a duplicate is tolerable. Best-effort dedup via idempotency key + provider dedup IDs. Exactly-once is too expensive. → canvas 3

storage split

Cassandra + PostgreSQL + Redis

Cassandra for write-heavy time-series notifications/logs (TTL); PostgreSQL for small, strongly-consistent prefs/templates; Redis for dedup, rate limits & caches.

Glossary — one-liners

terms used above
At-least-onceevery message is delivered ≥ 1 time; duplicates possible, drops not
Idempotency keyclient-supplied ID; a repeat with the same key is deduped (Redis SET NX)
Priority topica Kafka topic per priority so critical traffic isn't stuck behind marketing
Consumer groupa set of workers that split a topic's partitions to consume in parallel
Fan-out (staged)batch worker chunks a segment and throttles publishing to avoid flooding
DLQdead letter queue — parks messages after retries/permanent failures
Quiet hourswindow (e.g. 10 PM–8 AM) where non-critical notifications are deferred
Frequency capmax notifications per user/channel/day to prevent fatigue
Webhookprovider callback (SES/Twilio/FCM) that reports final delivery status
AP (CAP)favour Availability + Partition-tolerance over strong Consistency
