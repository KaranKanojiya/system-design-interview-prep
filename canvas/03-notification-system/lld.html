B

Priority ordering & the send → process → retry loop

Notification · PriorityQueue · processQueue
the code (verbatim)
// Notification implements Comparable — lower value wins
public int compareTo(Notification other) {
  return Integer.compare(
      this.priority.getValue(),
      other.priority.getValue());
}

// eligible for another attempt?
public boolean isRetryable() {
  return retryCount < maxRetries
      && status == NotificationStatus.FAILED;
}

// InMemoryPriorityQueue — non-blocking drain
public Notification dequeue() {
  return queue.poll(); // null when empty
}

Priority = CRITICAL(0), HIGH(1), MEDIUM(2), LOW(3). The PriorityBlockingQueue keeps a heap ordered by compareTo, so the smallest value is always dequeued first.

worked example — mixed priorities + one retry
// enqueue order (as they arrive)
enqueue  LOW(3)  · CRITICAL(0) · HIGH(1) · MEDIUM(2)

// heap re-orders by priority.value
dequeue → CRITICAL(0)   ■ SENT     ✓ delivered
dequeue → HIGH(1)       ■ FAILED   retry 1/5
        └ isRetryable? 1<5 && FAILED → re-enqueue
dequeue → MEDIUM(2)     ■ SENT     ✓ delivered
dequeue → LOW(3)        ■ SENT     ✓ delivered
dequeue → HIGH(1)*      ■ SENT     ✓ delivered  (the retry)

// IN_APP maxRetries = 0 → isRetryable never true

On failure the service calls markAsFailed() → incrementRetry(); if isRetryable() it re-enqueues, where the same priority puts it back ahead of lower-priority work.

Exponential backoff (conceptual). The production retry delay is BASE_DELAY_MS · 2^retryCount → 2s, 4s, 8s, 16s, 32s, spacing attempts so a flaky provider is not hammered. The in-memory demo re-enqueues immediately (no scheduler); channel caps are PUSH=5, EMAIL=5, SMS=3, IN_APP=0. Once retryCount == maxRetries the notification is left FAILED — in production it moves to a Dead-Letter Queue for investigation and replay.
C

Channel handlers (Strategy pattern)

swap the channel, not the service

PushNotificationHandler — simulates FCM / APNs. supportedChannel() = PUSH · maxRetries 5

  • Success: 90% (random.nextInt(100) < 90) → status SENT, response FCM:msg_id_….
  • Failure: response FCM:device_not_registered → FAILED, retried up to 5×.
  • Returns a DeliveryAttempt (never throws) so the worker loop stays simple.

EmailNotificationHandler — simulates AWS SES. supportedChannel() = EMAIL · maxRetries 5

  • Success: 95% → status SENT, response SES:message_id_….
  • Failure: response SES:bounce_invalid_address → FAILED.
  • Highest reliability of the external channels; cheap enough for 5 retries.

SmsNotificationHandler — simulates Twilio. supportedChannel() = SMS · maxRetries 3

  • Success: 85% (the noisiest channel) → response Twilio:SM_….
  • Failure: response Twilio:undeliverable → FAILED.
  • Only 3 retries — SMS is expensive, so we give up sooner than push/email.

InAppNotificationHandler — writes an in-app record, no external call. supportedChannel() = IN_APP · maxRetries 0

  • Success: always — returns SENT with stored:notif_….
  • isAvailable() is always true; no provider to be down.
  • maxRetries 0 → isRetryable() can never be true (nothing to retry).

Not in the repo, but the interface makes them drop-in — implement NotificationHandler and register in AppConfig:

  • WhatsApp / Slack: add a Channel enum value + one handler + one registry entry. Zero changes to the service.
  • Circuit breaker: isAvailable() is the hook — flip it false when a provider errors repeatedly so the service skips and re-queues rather than hammering a dead endpoint.

The pattern: NotificationService holds a Map<Channel, NotificationHandler> and never branches on channel type — it does handlers.get(notification.getChannel()).send(notification), an O(1) dispatch. Adding a channel is a new class + one EnumMap entry in AppConfig, with zero changes to the service, controller, queue, or repository (Open-Closed Principle).
D

Data model detail

Notification · DeliveryAttempt · UserPreference · Template
Notification — the queued entity
id          String   // 8-char UUID (KEY)
userId      String
templateId  String
channel     Channel     // PUSH/EMAIL/SMS/IN_APP
priority    Priority    // CRITICAL..LOW, orders queue
status      NotificationStatus
subject     String   body String
data        Map<String,String>
scheduledAt LocalDateTime // null = immediate
sentAt / deliveredAt  LocalDateTime
retryCount  int   maxRetries int
createdAt   LocalDateTime

id, required fields and timestamps set through the Builder; only status, subject, body, sentAt, deliveredAt, retryCount mutate. Keyed by id in the ConcurrentHashMap store; implements Comparable on priority.value for the heap.

DeliveryAttempt — append-only audit
notificationId   String
attemptNumber    int    // retryCount + 1
status           NotificationStatus  // SENT/FAILED
providerResponse String // "FCM:msg_id_ab12cd34"
timestamp        LocalDateTime

Fully immutable (all-args constructor, all fields final). Held in DeliveryTracker's Map<notificationId, List<DeliveryAttempt>> — one list per notification, appended on every attempt. In production this is an append-only event stream keyed by notificationId.

UserPreference — the send gate
userId            String
channelEnabled    EnumMap<Channel,Boolean>  // all true by default
quietHoursStart   int  // default 22
quietHoursEnd     int  // default 8  (wraps midnight)
dailyFrequencyCap EnumMap<Channel,Integer>  // PUSH50 EMAIL10 SMS5 INAPP100

isQuietHours(now) handles the overnight wrap (22→08) with an OR test. PreferenceService.canSend() reads only channel-enabled + quiet-hours today; the frequency cap is modelled but not yet enforced.

NotificationTemplate — content, decoupled
id                String   // "order-confirmation"
name              String
channel           Channel
subjectTemplate   String   // "Order {{orderId}} Confirmed"
bodyTemplate      String   // "Hi {{name}}, ..."
requiredVariables List<String> // ["name","orderId",...]

Stored in TemplateRepository and rendered at send time by SimpleTemplateEngine. subjectTemplate may be null (e.g. the SMS OTP template) — the engine simply returns null for it.

Status lifecycle: PENDING → QUEUED → SENDING → SENT → DELIVERED on the happy path; a handler failure goes SENDING → FAILED and, if retries remain, back to QUEUED. NotificationStatus.isTerminal() marks DELIVERED / FAILED / BOUNCED / CANCELLED as done.
E

Request handling sequence

which class does what, in order

POST /api/notifications/send  →  accept & enqueue

Controller.handleSend(request)
  └─ NotificationService.send(request)
       for each userId in request.getUserIds():
       1  preferenceService.canSend(userId, channel, now)
            false? → print [SKIP], continue   // opted out / quiet hours
       2  templateService.renderTemplate(templateId, data)
            → validate required vars → [subject, body]
            (missing template → TemplateNotFoundException)
       3  maxRetries = switch(channel){PUSH,EMAIL→5; SMS→3; IN_APP→0}
       4  new Notification.Builder()...build()   // status PENDING
       5  repository.save(notification)
       6  notification.setStatus(QUEUED); queue.enqueue(notification)
  └─ return  id  |  "batch:N"  |  "none:all_skipped"

The accept path never delivers — it validates, renders, persists and enqueues, then returns fast. Batch is just the same loop over many userIds; skipped users don't abort the batch.

PROCESS  →  drain the queue & deliver

Controller.handleProcessQueue(maxBatch)
  └─ NotificationService.processQueue(maxBatch)
       loop up to maxBatch times:
       1  notification = queue.dequeue()        // poll(); null → break
       2  handler = handlers.get(notification.getChannel())
            null? → markAsFailed, save, continue
       3  notification.setStatus(SENDING)
       4  attempt = handler.send(notification)   // DeliveryAttempt
          deliveryTracker.record(attempt)
       5  attempt.status == SENT ?
            yes → markAsSent(); markAsDelivered(); save
            no  → markAsFailed(); incrementRetry(); save
                  isRetryable()? → queue.enqueue(notification)  // [RETRY]
                                 else → [EXHAUSTED]
  └─ return processed count

Highest-priority notifications come off the heap first. A re-enqueued retry rejoins the heap at its own priority, so a CRITICAL retry still beats a fresh LOW.

POST /api/notifications/retry  →  sweep failures

Controller.handleRetryFailed()
  └─ NotificationService.retryFailed()
       1  repository.findRetryable()   // FAILED && retryCount < maxRetries
       2  for each: setStatus(QUEUED); queue.enqueue(n)
       3  print "Re-enqueued N failed notifications"
  └─ a later processQueue() picks them up again

A batch sweep complements the inline retry inside processQueue — it re-collects everything still eligible (e.g. after a provider outage) straight from the repository and puts it back on the queue.

F

Design patterns used

GoF-categorized
Creational
  • Builder — Notification.Builder. Readable construction of a 15-field entity; build() enforces required userId & channel and defaults id/priority/status.
  • Factory — AppConfig builds the EnumMap<Channel,Handler> registry and wires the whole graph (composition root).
Behavioral
  • Strategy — NotificationHandler + Push/Email/Sms/InApp. The centrepiece: swap the channel without touching the service.
  • Template Method — the fixed pipeline canSend → render → build → enqueue → send → track; only send() varies per channel.
  • Observer — handlers emit a DeliveryAttempt that DeliveryTracker records; in production a Kafka delivery-events topic.
Architectural / Concurrency
  • Producer-Consumer — send() enqueues; processQueue() drains. Accept and deliver are decoupled by the queue.
  • Repository — three interfaces (Notification / Preference / Template) over ConcurrentHashMap impls; swap in DynamoDB / Cassandra with no service change.
  • Dependency Injection — constructor injection everywhere, wired by hand in AppConfig.
Why they cluster: Strategy + Factory + DI deliver the Open-Closed Principle — new channels are additions, never edits. Producer-Consumer + PriorityBlockingQueue keep the accept path fast and priority-aware; Observer via DeliveryTracker keeps delivery and tracking separable; Repository keeps storage swappable. → scaling & the fan-out / DLQ follow-up on canvas 3
