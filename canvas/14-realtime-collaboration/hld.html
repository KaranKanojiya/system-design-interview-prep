Real-time Collaboration (Google Docs · Figma · Notion) — High-Level Design

Use case 14 · Canvas 1 of 3. Two planes, one design: the edit plane (CP — OT engine + document-level lock, no divergence allowed) and the presence plane (AP — Redis cursors + heartbeat, stale is OK). WebSocket keeps 5 M sockets warm with sticky sessions by documentId; the OT engine transforms a late-arriving INSERT(pos=6) against the ops that already applied. Snapshot every 100 ops + operation log = O(1) document load. Click a component, then step both flows.

A

Problem & requirements

edit CP · presence AP
functional
  • Real-time co-editing — 3–50 users on one doc; every keystroke propagates in < 100 ms.
  • Convergence — every client applies the same total order of ops → identical final content.
  • Cursor + selection sync — coloured caret + highlight per user, throttled to ~50 ms.
  • Presence — join / idle / left states; user avatars in the doc header.
  • Version history — snapshot every 100 ops (or 5 min); browse + restore any prior revision.
  • Undo / redo — per-user, correctly handling concurrent edits from others.
  • Comments — anchored to text ranges (start/end + anchor_revision); resolve / reply.
  • Permissions — OWNER / EDITOR / COMMENTER / VIEWER; link sharing with role + expiry.
  • Offline editing — buffer ops locally; sync + transform on reconnect.
non-functional
  • Sync latency p99 < 100 ms edit propagation · < 150 ms cursor.
  • Doc load p99 < 500 ms (snapshot + replay ≤ 100 ops).
  • Convergence — zero divergence tolerance. Every client must end at the same content.
  • Durability — zero edit loss after server ACK (Kafka append-before-PG-commit).
  • Availability 99.99 % overall · 99.9 % on edit plane (CP — refuse if unsure).
  • Scale 5 M concurrent WebSocket connections · 100 M ops/sec platform-wide.
  • Consistency split — causal for edits (server total order), eventual for presence.
  • Correctness — OT transforms must satisfy TP1 (apply(A, B') = apply(B, A')).

Why 100 M ops/sec sounds worse than it is: ops partition perfectly by documentId. 100 M ops/sec ÷ 50 ops/sec per active doc = 2 M independent shards. A single Collab Service node handles ~1 000 docs (~50 K ops/sec); 50 nodes cover the fleet. The scary number is per-doc concurrency — 50 editors on one doc = 50 ops/sec on one shard, and the document-level lock (~1 ms hold) tops out at ~1 000 ops/sec. That's 20× headroom, but a "town hall" doc with 500 editors hits the limit → mitigations kick in (op batching · broadcast throttling · cursor sampling).
The convergence non-negotiable: if two clients end up with different content, the doc is corrupted silently — no error, no rollback, just Alice sees "Hello Earth" and Bob sees "Hello World". This is why CP for edits and why the server is the total-order authority. A 200 ms delay is annoying; a divergence is the end of the product.

API design

REST + WebSocket frames
REST (document CRUD + version)
EndpointPurpose
POST /documentsCreate empty / template doc; auto-grant OWNER perm
GET /documents/{id}Load — snapshot + replayed ops + revision
PATCH /documents/{id}/opsBatched op submit (fallback for HTTP-only clients)
PUT /documents/{id}/permissionsGrant / revoke role or link share
GET /documents/{id}/historyList snapshots with metadata + labels
POST /documents/{id}/restoreRestore to a prior revision (creates NEW ops)
POST /documents/{id}/commentsAdd anchored comment (start, end, anchor_revision)
WebSocket protocol (wss://collab/ws/documents/{id})
// Client → Server
OPERATION       { type, ops[], base_revision, local_op_id }
CURSOR          { position, selection:{start,end} }
PRESENCE        { status:"ACTIVE" }        // heartbeat every 30 s
UNDO            { base_revision }
REDO            { base_revision }

// Server → Client
DOCUMENT_STATE  { content, revision, active_users[] }
OPERATION_ACK   { local_op_id, server_revision }
REMOTE_OPERATION{ user_id, ops[], server_revision }
CURSOR_UPDATE   { user_id, position, colour }
PRESENCE_UPDATE { user_id, status, active_users_count }
ERROR           { code, message, current_revision }
                // e.g. REVISION_MISMATCH → client resync

Correctness contract: every OPERATION carries base_revision (client's last-seen server rev) + local_op_id (client UUID). Server transforms against ops (base_revision, current_revision], assigns a new revision, and echoes local_op_id in the ACK so the client can move the op from "pending" → "confirmed" — the CRDT idempotency pattern applied to OT.

Data model — persistent vs ephemeral

Postgres for truth · Redis for now
persistent (Postgres, sharded by docId)
documents                      // 100 M rows
  document_id (PK)
  title
  owner_id, workspace_id
  current_revision  BIGINT     // monotonic per doc
  content_snapshot  TEXT       // latest full content
  snapshot_revision BIGINT     // rev at snapshot time
  status ENUM                   // ACTIVE/ARCHIVED/DELETED

operations                     // ~5 B rows/day, 30-d retention
  operation_id (PK)
  document_id, user_id
  revision BIGINT              // server-assigned
  op_type ENUM                  // INSERT/DELETE/RETAIN
  position INT, content TEXT
  length INT, attributes JSONB
  base_revision, client_id, local_op_id
  created_at
  // idx (document_id, revision) — fetch tail

versions                       // snapshots + labels
  version_id (PK)
  document_id, revision
  content TEXT, label
  contributing_users JSONB

permissions                    // role per (doc, user)
  document_id, user_id, role, expires_at

comments                       // anchored ranges
  comment_id, document_id, user_id
  anchor_start, anchor_end
  anchor_revision   // re-anchor on later ops
  content, status
ephemeral (Redis, TTL-backed)
presence:{docId}               // Sorted Set
  score = heartbeat epoch ms
  member = userId
  TTL 120 s                    // auto-evict LEFT users

cursor:{docId}                 // Hash
  field  = userId
  value  = {pos, selection, colour, ts}
  TTL 120 s

user_presence:{userId}         // Hash
  document_id, status
  display_name, avatar_url
  cursor_colour
  connected_server, last_heartbeat

ws_conn:{userId}:{docId}       // String
  {serverId, connectedAt}
  TTL 120 s

lock:{docId}                   // String, SETNX
  {serverId, acquiredAt}
  TTL 5 s                      // auto-release on crash

perm:{docId}:{userId}          // String
  role, TTL 60 s               // invalidate on revoke
Rule of thumb: if data survives a full cluster reboot without pain, it's Postgres. If losing it means "the UI is a bit stale for 60 s," it's Redis. This is why cursors are Redis (a stale cursor is fine) and permissions are Postgres (a stale permission grants access after revoke — not fine).
F

Key design choices (deep-dived on canvas 3)

defend these
algorithm

OT (centralised) as primary

Google Docs' proven approach. Server is the single order authority; late ops transform against pending. CRDT swappable for offline-heavy clients via strategy. → canvas 3 · OT vs CRDT

consistency

CP edits · AP presence

Convergence non-negotiable → edits refuse under partition. Cursors stale is fine → presence stays available always. → canvas 3 · CAP split

concurrency

Doc-level Redis lock (SETNX)

Serialises ops per doc (~1 ms hold, ~1 000 ops/s ceiling). Cross-doc ops fully parallel. 20× headroom over the 50 ops/s per-doc peak. → canvas 3 · concurrency

transport

WebSocket + sticky sessions

Persistent duplex < 100 ms; 50 K conns/node × 100 nodes = 5 M. Sticky by docId keeps editors co-located → in-process broadcast. → canvas 3 · WS scaling

storage

Snapshot + op replay

Snapshots every 100 ops → doc load in O(≤ 100 ops) instead of O(N). Event-sourcing for full audit trail; compaction after 7 days. → canvas 3 · snapshot cadence

fan-out

Kafka per-doc topic

Ordering per partition = ordering per doc. Non-authoring gateways subscribe only to docs they host. Durable, replayable on gateway restart. → canvas 3 · fan-out

Glossary — one-liners

OT (Operational Transform)algorithm that adjusts a concurrent op's position so both orders converge to the same doc
TP1Transformation Property 1: apply(A, B') = apply(B, A'). The correctness proof for OT
CRDT (RGA)char has unique (siteId, counter) ID → ops commute → no transform needed → offline works
Tombstonedeleted char kept in the CRDT so later parent-references still resolve; GC'd after all sites ACK
base_revisionthe server rev the client had seen when it created the op; server transforms against (base_rev, current_rev]
Doc-level lockRedis SETNX with 5 s TTL — one op processed at a time per doc → total order
Sticky sessionhash(docId) routing → all editors of one doc land on the same gateway pod
Snapshot cadenceevery 100 ops or 5 min — bounds doc-load replay cost to O(≤ 100)
Causal consistencyif op B was created after seeing A, every client applies A before B (enforced by revision numbers)
Cursor transformsame rules as text ops — remote INSERT before cursor → cursor shifts right by insert length
Op compactioncoalesce N single-char INSERTs into one paragraph INSERT after 7 days; 60–70 % storage cut
REVISION_MISMATCHserver error when client's base_revision is too old to transform (past retention) → client resync
