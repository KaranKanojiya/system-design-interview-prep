TP1 (Transformation Property 1): apply(A, B') = apply(B, A'). The correctness guarantee for OT with 2 concurrent ops.

Doc: "HELLO"
Alice: INSERT(pos=2, "X")   Bob: INSERT(pos=4, "Y")

Server receives Alice first.
  1) apply(HELLO, alice) = "HEXLLO"
  2) transform(bob, alice) → bob':
       localPos(4) > remotePos(2) → shift bob by +1 = INSERT(pos=5, "Y")
  3) apply("HEXLLO", bob') = "HEXLLYO"

Server receives Bob first (parallel universe).
  1) apply(HELLO, bob) = "HELLYO"
  2) transform(alice, bob) → alice':
       localPos(2) < remotePos(4) → alice unchanged = INSERT(pos=2, "X")
  3) apply("HELLYO", alice') = "HEXLLYO"

Both universes converge to "HEXLLYO" — TP1 holds.
TP2 is the trap: with 3+ concurrent editors, transforms must ALSO satisfy transform(transform(A, B), C') = transform(transform(A, C), B'). Google Docs has hit divergence bugs here for 15 years — the workaround is centralised OT (server is always the linear authority; TP2 never needs to hold because ops are always applied in a fixed order). This is why our design refuses to do decentralised OT.

CRDT convergence proof: operations are functions that commute, are associative, and are idempotent (an "ACI"-style structure). Given two nodes with the same set of ops (in ANY order), state is identical. This is Strong Eventual Consistency (SEC) — proved mathematically, not by unit-test.

RGA (Replicated Growable Array) — the CRDT for text:

Char node: { id: (siteId, counter), value: "X", parent: (siteId, counter), tombstone: bool }

INSERT "X" between (A,1) and (A,2):
  new char: { id: (B,1), value: "X", parent: (A,1) }

Order: sort chars by DFS traversal from ROOT.
  Siblings under same parent → tie-break by id lex order.

Concurrent inserts under same parent (both siteId=A(1) parent):
  Site B inserts (B,1) → linked after (A,1)
  Site C inserts (C,1) → linked after (A,1)
  Merge: both nodes see both children.
    Sort children by id: (B,1) then (C,1). Both nodes converge.

DELETE "X" (say char (B,1)):
  Set (B,1).tombstone = true.
  DO NOT remove the node — others may reference it as parent.
  Rendering skips tombstoned chars.

Why "conflict-free": operations reference immutable IDs, not positions. There is nothing to conflict on. The trade-off: every char is now a node in a linked list with (siteId, counter) — that's ~30 bytes of metadata per char.

Causal consistency: if op B was created after seeing op A, every client must apply A before B.

OT — server total order
Server maintains monotonic version.
Each op carries base_revision.

Server rule (in doc-level critical section):
  if op.baseRev < server.rev:
    for pending in ops(baseRev, serverRev]:
      op' = transform(op', pending)
  apply(op'); assign server.rev++
  broadcast op' with new revision.

Client applies incoming ops in strict revision order.
If rev=8 arrives before rev=7, buffer 8 until 7 lands.
CRDT — vector clocks
Each op carries a vector clock:
  { alice: 5, bob: 3 }  means
  "I've seen alice's first 5, bob's first 3."

Delivery rule:
  Deliver Alice's op with { alice: 6, bob: 3 } only if:
    - I've seen alice: 1..5
    - I've seen bob:   1..3

If either dependency is missing → buffer.

This is Lamport / Fidge–Mattern causality —
same shape as OT's baseRevision, just per-site.

Both algorithms enforce causal order. OT uses a single global counter (the server rev). CRDT uses per-site counters (vector clock). Same semantics, different data plane.

The tombstone tax: in a CRDT, deleted chars are kept as markers so future ops can still resolve their parent references. Long-lived docs accumulate thousands of tombstones.

Delete "B" from "ABC":
  Mark (siteA, 2) as tombstone. Rendering: "AC".
  Internal: 3 nodes still linked.

Multiply by 100 K deletions over a doc's life → 100 K tombstoned nodes.
Memory: 100 K × ~30 B = 3 MB of metadata for a 10 KB doc.
Wire: sending the initial state to a new joiner now includes the tombstones.

Garbage collection: a tombstone can be physically removed once all sites have acknowledged the delete op. Ack-tracking is via vector clock — every site periodically publishes its clock; the GC picks tombstones whose "delete op" version is ≤ the min of all published clocks.

Yjs mitigation: uses a Doubly Linked List with Structs (DLLS) + delta encoding — tombstones for consecutive deletes coalesce into a single "range tombstone." Cuts memory by 10–100× vs naïve RGA. This is the sort of engineering CRDT libraries do that hand-rolled implementations skip.
Does the product NEED offline editing (hours, not minutes)?
├─ YES → CRDT. Metadata overhead + tombstone GC is worth it.
└─ NO  → next question ─▶
   Do we have a reliable central authority (single doc = single region)?
   ├─ YES → Centralised OT. Simple, fast, well-understood. ← ours
   └─ NO  → next question ─▶
       Multi-master requirement? (rare — most collab tools pin a doc to one region)
       ├─ YES → CRDT. Peer-to-peer merge without coordinator.
       └─ NO  → OT (with a primary + async region mirrors).

Practical guidance: if you're building a text editor in 2026 with a small team, use Yjs (a CRDT library). If you're at Google-scale and already have OT running, don't rewrite for CRDT — the engineering cost isn't recouped. Notion migrated to Yjs from a custom OT engine and reported that offline sync was the main win.

Consistency — split by subsystem

not one CAP for the whole system
document state (strong)
presence + cursors (eventual)
permissions (bounded)
comments (eventual)
during network partition

Document state (ops + revisions): strongly consistent, causally ordered.

  • Server is the single total-order authority (revision counter is monotonic).
  • Doc-level lock via Redis SETNX ensures serial op application per doc.
  • Op-persist + revision-bump is a single Postgres transaction.
  • Read replicas (used only for doc load) may lag ~100 ms — clients tolerate via WS resync on REVISION_MISMATCH.
  • Under partition (rare in-cloud): refuse ops. Better a "reconnecting…" spinner than a divergent doc.

Presence + cursors: eventually consistent, best-effort.

  • Redis sorted-set presence:{docId} — heartbeat-scored, 60 s IDLE, 120 s LEFT.
  • Cursor updates throttled to 50 ms client-side → 20 updates/sec cap per user.
  • Broadcast via same Kafka path as ops (topic presence.{docId}) — at-least-once, dedup by (userId, timestamp).
  • Stale by 1–2 s → invisible to users. Stale by 30 s → cursor looks "ghosted"; UX still fine.
  • Under partition: continue serving. Show last-known cursor + a "reconnecting…" hint on the affected avatar.

Permissions: read-side eventually consistent (60 s cache TTL); write-side strongly consistent.

  • Permission cache: Redis perm:{doc}:{user} → role with 60 s TTL.
  • Grant / revoke writes go to Postgres and invalidate the cache immediately (best-effort — TTL bounds the risk).
  • Revoked user could theoretically keep editing for up to 60 s. In practice: (a) most collab attacks aren't over seconds; (b) revoke also disconnects any active WebSocket from that user.
  • Strong consistency required for OWNERSHIP transfer — cache-bypass path used.

Comments: eventually consistent — anchored to a text range at a specific revision.

  • Anchor = (anchor_start, anchor_end, anchor_revision).
  • When later ops shift text, the comment stays anchored to its original revision; UI re-projects the anchor by transforming through the intervening ops.
  • New comment writes are Postgres single-row inserts — safe under load.
  • Comment visibility can lag doc state by ~1 s (Kafka fan-out latency) — acceptable UX.

For collab, the document is CP because divergence corrupts data; presence is AP because a stale cursor is just cosmetic. If someone tells you the whole system is CP, ask them what happens to cursor updates during a partition — the answer 'we block them' is the wrong answer."

Presence & cursor sync — Redis heartbeat + throttle

the AP plane
the data flow
Client ─── PRESENCE(status=ACTIVE) every 30 s ───▶ WS Gateway
                                                     │
                                                     ▼
Gateway updates Redis (atomic pipeline):
  ZADD presence:{docId} {epochMs} {userId}
  HSET user_presence:{userId} last_heartbeat {epochMs}
  EXPIRE user_presence:{userId} 120

Background sweeper every 10 s:
  ZRANGEBYSCORE presence:{docId} -inf {now - 60_000}
    → mark IDLE  (client hasn't pinged in 60 s)
  ZRANGEBYSCORE presence:{docId} -inf {now - 120_000}
    → mark LEFT  (client hasn't pinged in 120 s)
  On state change, publish to Kafka
    presence.{docId}: PRESENCE_UPDATE

Every WS Gateway consumes presence.{docId}
  → for local sockets on this doc, push PRESENCE_UPDATE.
cursor throttling
Client-side (browser JS):

let lastSentAt = 0;
onCursorMove(pos, selection) {
  const now = Date.now();
  if (now - lastSentAt < 50) {
    // Coalesce: overwrite pending, don't send yet
    pendingCursor = { pos, selection };
    scheduleFlush(50 - (now - lastSentAt));
    return;
  }
  send(CURSOR({ pos, selection }));
  lastSentAt = now;
}

Result:
  Without throttle: cursor events every ~30 ms (arrow-key drag)
    = 33 messages/sec × 5 M clients = 165 M msgs/sec of cursor spam
  With 50 ms throttle: 20 msgs/sec cap
    = 100 M msgs/sec ceiling — same order as ops
  Human perception: 50 ms is imperceptible.
cursor transform (rare, forgotten in interviews)
  • Remote INSERT at pos P, len L: if cursor ≥ P → cursor += L; else no change.
  • Remote DELETE at pos P, len L: if cursor ≥ P + L → cursor −= L; else if cursor is inside [P, P+L) → cursor = P (collapse); else no change.
  • Implemented server-side in PresenceService.adjustCursors — called by Facade after each broadcast op with excludeUser = author.
  • Client-side ALSO applies the same transform to its own cursor when it receives a REMOTE_OPERATION — server + client agree because the transform rules are deterministic.
hot-doc mitigations (500-user town hall doc)
  • Cursor sampling — show only the 10 most-recently-active cursors, or the "viewport-nearby" ones. 500 cursors = visual noise anyway.
  • Broadcast batching — batch cursor events per 50 ms window into one composite CURSOR_UPDATE frame.
  • Presence coarsening — cap presence list to "n other viewers" once above 20 shown. Reduces WS message size linearly.
  • Read-replica presence — non-editors can subscribe to a read replica of the Kafka topic; only editors go through the primary path.

Snapshots + compaction — the storage discipline

event sourcing done right
snapshot cadence — the trade-off
CadenceLoad timeStorageBest for
Every 10 ops~1 ms (replay ≤ 10)10× doc size overheaddemo · tiny docs
Every 100 ops ← ours~10 ms (replay ≤ 100)1× doc size overheadGoogle Docs default
Every 1 000 ops~100 ms (replay ≤ 1 000)0.1× overheadarchives · read-cold docs
Every 5 min (time-based)variablebounded by edit ratequiet docs that rarely need loading

We combine every 100 ops OR every 5 min OR on last-editor-leaves — whichever fires first. Ensures new joiners always load in < 100 ms even for hot docs; cold docs still snapshot on idle.

compaction schedule
Active period    (0–7 days):
  Keep ALL individual ops (per-keystroke granularity)
  Snapshots every 100 ops
  → enables fine-grained undo, per-keystroke history

Recent period    (7–30 days):
  Snapshots every 100 ops (kept)
  Coalesce individual char INSERTs into paragraph-level ops
  → ~60–70% reduction

Archive period   (30–365 days):
  Daily snapshots only
  Individual ops deleted
  → users see day-granular history, not keystroke

Purge period    (> 365 days):
  Weekly snapshots for 1 more year
  Then monthly indefinitely (retention policy)
The math that justifies cadence: at 50 ops/s × 100 B/op × 100 M active docs × 86400 s/day = ~500 GB/day of op log. A snapshot every 100 ops = 1 snapshot per 2 seconds per doc; at ~5 KB per snapshot × 2 M active docs × 30 snaps/min = ~50 GB/min of snapshot writes at peak. Snapshots go to S3 Standard-IA (~$0.0125/GB/mo). Storage cost of aggressive snapshotting is negligible vs the load-time win.

35-minute interview walkthrough

the answer, timed
phase 1 · clarify (2–3 min)
  • "How big — mid-scale (Notion) or Google-scale? I'll assume 100 M docs · 10 M DAU · 5 M concurrent WS."
  • "Do we need offline? A little — buffer & reconcile is fine. Not Figma-level."
  • "Real-time cursors + selections? Yes."
  • "Latency budget? Edit p99 < 100 ms, cursor < 150 ms, doc load < 500 ms."
  • "Rich text? Same OT with FORMAT ops on top — I'll gloss over rich-text specifics."
phase 2 · draw architecture (5–7 min)
  • Client → LB (sticky by docId) → WS Gateway → Collaboration Service → OT engine → Op log (Postgres).
  • Kafka fan-out to other WS Gateways → REMOTE_OPERATION to other clients.
  • Redis for presence, cursors, doc lock, permission cache.
  • Snapshot job → S3. Version Service uses snapshots for history.
phase 3 · OT deep dive (8–10 min)
  • Whiteboard: "HELLO" + Alice INSERT(2,"X") + Bob INSERT(4,"Y") → walk through transform.
  • Server assigns revision; late op transforms against pending ops sequentially.
  • TP1: apply(A, B') = apply(B, A'). TP2 for > 2 users → why centralised OT avoids it.
  • Doc-level lock (Redis SETNX) → single writer per doc → total order.
  • Mention CRDT as alternative (Figma / Yjs); tombstones + commutativity.
phase 4 · scale & failure (5–7 min)
  • 5 M WS ÷ 50 K/node = 100 gateway nodes. Sticky by docId → local broadcast.
  • Kafka per-doc topic; gateways subscribe only to docs they host.
  • Snapshot every 100 ops → doc load O(≤ 100).
  • Hot-doc mitigations: op batching, cursor sampling, broadcast throttle.
  • Failure: gateway crash → clients reconnect via LB draining; new gateway replays recent ops from Kafka.
phase 5 · trade-offs defended (5–8 min)
  • Why OT not CRDT (centralised, simpler payload, dominant in prod; CRDT plugged in for offline).
  • Why doc-level lock not lock-free (correctness + audit; 1000 ops/s/doc ceiling is 20× peak).
  • Why Kafka not Redis Pub/Sub (durability for gateway replay; ordering per partition).
  • Why CP for edits, AP for presence (convergence vs cosmetic).
  • Why sticky sessions (co-locate editors → local broadcast; mitigate imbalance with virtual nodes).
phase 6 · what would you do differently (2–3 min)
  • "At Figma-scale offline needs, I'd migrate to Yjs — CRDT with delta encoding."
  • "I'd add a block-level model (Notion-style) so hot docs partition naturally into sub-doc streams."
  • "I'd move the doc-level lock from Redis to a Rust in-process actor per doc — sub-100 µs hold."
  • "I'd add per-user ML-based conflict prediction — pre-transform on the client to avoid round-trip on obvious cases."
30-second pitch: "Real-time collab is fundamentally a conflict-resolution problem. I use centralised OT — server is total-order authority; late ops transform against ops that already committed; per-doc Redis lock serialises. WebSocket fan-out via Kafka per-doc topic; Redis for cursors + presence (AP). Snapshot every 100 ops + op replay for O(≤ 100) doc load. CP for content (divergence = data loss), AP for presence (stale cursor = UX nit). CRDT (Figma / Yjs) is the alternative — natural offline, mathematically proven convergence, but higher metadata cost. Swap in via the SyncStrategy interface for offline-heavy clients."
Interview red flags to avoid:
• "I'd replace the whole document on each edit." (fatal — last-writer-wins loses concurrent edits silently)
• "I'd use HTTP polling." (latency > 1 s; can't achieve < 100 ms)
• "The whole system is CP." (breaks presence during partitions unnecessarily)
• "Peer-to-peer OT." (TP2 is famously unimplemented; decentralised OT = divergence bugs)
• "One server per document." (single point of failure; no scale plan)
• "Delete tombstones as soon as ops apply." (CRDT correctness bug — future ops need the parent reference)
• "Skip the doc-level lock." (races → divergence → silent corruption; a divergence bug takes weeks to find)
