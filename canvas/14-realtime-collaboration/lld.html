from service/CollaborationService.java
public Document processOperation(String docId, String userId, Operation op) {
  // Step 1: Validate permission
  if (!permissionService.canEdit(docId, userId)) {
    throw new PermissionDeniedException(userId, docId, "edit");
  }

  // Step 2: Retrieve the document
  Document doc = documentService.getDocument(docId);

  // Step 3: Get operations since the client's base version (for OT transform)
  List<Operation> pendingOps = operationService.getOperationsSince(docId, op.getBaseVersion());

  // Step 4: Apply via sync strategy (OT transforms or CRDT direct-apply)
  List<Operation> broadcastOps = syncStrategy.applyOperation(doc, op, pendingOps);

  // Step 5: Persist the operation
  operationService.saveOperation(op);
  persistenceStrategy.saveOperation(op);

  // Step 6: Broadcast to other connected users
  for (Operation broadcastOp : broadcastOps) {
    broadcastService.broadcastOperation(docId, broadcastOp, userId);
  }

  // Step 7: Update cursor positions
  // The editing user's cursor moves to the end of their edit
  int newCursorPos = op.getPosition() + op.getInsertLength();
  presenceService.updateCursor(userId, docId, newCursorPos);

  // Adjust OTHER users' cursors based on the applied operation
  for (Operation broadcastOp : broadcastOps) {
    presenceService.adjustCursors(docId, broadcastOp, userId);
  }

  // Step 8: Periodic snapshot
  opsSinceSnapshot++;
  if (opsSinceSnapshot >= SNAPSHOT_INTERVAL) {
    versionService.createSnapshot(doc);
    opsSinceSnapshot = 0;
  }

  return doc;
}
from strategy/sync/OTSyncStrategy.java
public List<Operation> applyOperation(
    Document doc, Operation op, List<Operation> pendingOps) {

  Operation transformedOp = op;

  // Step 1: Transform against every pending op (SEQUENTIAL)
  if (op.getBaseVersion() < doc.getVersion() && !pendingOps.isEmpty()) {
    for (Operation pendingOp : pendingOps) {
      TransformResult result =
          conflictResolver.transform(transformedOp, pendingOp);
      transformedOp = result.getTransformedLocal();
      conflictsResolved++;
    }
  }

  // Step 2: Apply to the document (dispatch on OpType)
  applyToDocument(doc, transformedOp);

  // Step 3: Bump revision (atomic in Document)
  doc.incrementVersion();

  // Step 4: Return the transformed op — this is the broadcast payload
  return List.of(transformedOp);
}
from strategy/sync/CRDTSyncStrategy.java (alt)
public List<Operation> applyOperation(
    Document doc, Operation op, List<Operation> pendingOps) {

  // CRDT: no transform needed. Apply directly.
  // In a real CRDT, unique char IDs make ops commute.
  switch (op.getType()) {
    case INSERT -> doc.applyInsert(op.getPosition(), op.getContent());
    case DELETE -> {
      if (op.getLength() > 0 &&
          op.getPosition() + op.getLength() <= doc.getLength()) {
        doc.applyDelete(op.getPosition(), op.getLength());
      }
    }
    case RETAIN -> { /* no-op */ }
  }

  doc.incrementVersion();
  return List.of(op);   // broadcast the op as-is
}
Why the transform is sequential: each pending op adjusts positions based on the previous transform's result. If Alice's op is base_rev=5 and server is at rev=8 (three pending: op6, op7, op8), we compute t' = transform(alice, op6), then t'' = transform(t', op7), then t''' = transform(t'', op8). Reordering breaks convergence. This is why the doc-level lock exists — no two ops can race the sequence.

both users insert — position + tie-break by userId
private void transformInsertInsert(Operation local, Operation remote,
                                    Operation localPrime, Operation remotePrime) {
  int localPos  = local.getPosition();
  int remotePos = remote.getPosition();
  int localLen  = local.getInsertLength();
  int remoteLen = remote.getInsertLength();

  if (localPos < remotePos) {
    // Local inserts before remote → remote must shift right
    remotePrime.setPosition(remotePos + localLen);
  } else if (localPos > remotePos) {
    // Remote inserts before local → local must shift right
    localPrime.setPosition(localPos + remoteLen);
  } else {
    // Same position — tie-break by userId (lexicographic).
    // Smaller userId "wins" (gets applied first).
    if (local.getUserId().compareTo(remote.getUserId()) <= 0) {
      remotePrime.setPosition(remotePos + localLen);
    } else {
      localPrime.setPosition(localPos + remoteLen);
    }
  }
}

Example: doc = "HELLO", Alice INSERT(pos=2,"X"), Bob INSERT(pos=4,"Y"). Alice's pos (2) < Bob's (4), so Bob's shifts by +1 → Bob'.pos = 5. Applying Alice first: "HEXLLO"; then Bob' at 5: "HEXLLYO". Applying Bob first would need Alice unchanged (2 < 4 still). Both converge to "HEXLLYO".

local INSERT vs remote DELETE — three sub-cases
private void transformInsertDelete(Operation local, Operation remote,
                                    Operation localPrime, Operation remotePrime) {
  int insertPos = local.getPosition();
  int deletePos = remote.getPosition();
  int deleteLen = remote.getLength();
  int insertLen = local.getInsertLength();

  if (insertPos <= deletePos) {
    // (a) Insert BEFORE delete → delete shifts right by insertLen
    remotePrime.setPosition(deletePos + insertLen);
  } else if (insertPos >= deletePos + deleteLen) {
    // (b) Insert AFTER delete range → insert shifts left by deleteLen
    localPrime.setPosition(insertPos - deleteLen);
  } else {
    // (c) Insert INSIDE deleted range → move insert to delete boundary.
    // The inserted text will appear at the start of the deletion span.
    localPrime.setPosition(deletePos);
  }
}

Sub-case (c) is the interesting one: "ABCDEFGHI" — Alice inserts "X" at pos=4 (in the middle of D..F); Bob deletes pos=3..6 ("DEF"). We snap Alice's insert to the delete boundary (pos=3) → "ABCXGHI". Alice's text is preserved even though the surrounding characters are gone.

local DELETE vs remote INSERT — mirror of INSERT × DELETE
private void transformDeleteInsert(Operation local, Operation remote,
                                    Operation localPrime, Operation remotePrime) {
  int deletePos = local.getPosition();
  int deleteLen = local.getLength();
  int insertPos = remote.getPosition();
  int insertLen = remote.getInsertLength();

  if (insertPos <= deletePos) {
    // Remote insert BEFORE local delete → delete shifts right
    localPrime.setPosition(deletePos + insertLen);
  } else if (insertPos >= deletePos + deleteLen) {
    // Remote insert AFTER delete range → insert shifts left
    remotePrime.setPosition(insertPos - deleteLen);
  } else {
    // Remote insert INSIDE delete range → insert moves to delete start
    remotePrime.setPosition(deletePos);
  }
}

Symmetry: INSERT × DELETE and DELETE × INSERT are the same problem viewed from opposite sides. Keeping the code symmetric (rather than "clever") makes bugs easy to spot when they surface — and OT bugs are the worst kind because they manifest as silent divergence.

both users delete — overlap needs range shrink
private void transformDeleteDelete(Operation local, Operation remote,
                                    Operation localPrime, Operation remotePrime) {
  int localPos = local.getPosition();  int localLen = local.getLength();
  int localEnd = localPos + localLen;
  int remotePos = remote.getPosition();  int remoteLen = remote.getLength();
  int remoteEnd = remotePos + remoteLen;

  // Compute overlap [max(starts), min(ends)]
  int overlapStart = Math.max(localPos, remotePos);
  int overlapEnd   = Math.min(localEnd, remoteEnd);
  int overlapLen   = Math.max(0, overlapEnd - overlapStart);

  if (overlapLen == 0) {
    // No overlap — shift the later delete left by the earlier length
    if (localPos <= remotePos) remotePrime.setPosition(remotePos - localLen);
    else                       localPrime.setPosition(localPos - remoteLen);
  } else {
    // Overlapping deletes — SHRINK both lengths by overlap.
    // Reasoning: chars in the overlap are already gone; deleting
    // them twice would eat into surviving text.
    if (remotePos < localPos) {
      int removedBefore = Math.min(remoteLen, localPos - remotePos);
      localPrime.setPosition(localPos - removedBefore);
    }
    if (localPos < remotePos) {
      int removedBefore = Math.min(localLen, remotePos - localPos);
      remotePrime.setPosition(remotePos - removedBefore);
    }
    localPrime.setLength(localLen - overlapLen);
    remotePrime.setLength(remoteLen - overlapLen);
  }
}

The subtle bug this prevents: "ABCDEFGH" — Alice DELETE(2,3) removes "CDE"; Bob DELETE(4,2) removes "EF". Both want char E gone. Overlap = pos 4..5 (len 1). Without shrink: Alice deletes CDE, then Bob deletes 2 chars starting at (4-3)=1 → deletes BC (wrong!). With shrink: Bob's transformed op is DELETE(1, 1) — deletes only "F". Final: "AH". Alice + Bob's intents preserved.

from ot/CRDTResolver.java — the transform is a NO-OP
public TransformResult transform(Operation local, Operation remote) {
  operationCounter++;

  // CRDT ops reference GLOBALLY UNIQUE character IDs, not integer positions.
  // Because IDs are immutable, ops commute — no position adjustment needed.
  // The underlying RGA / LSEQ / Yjs sequence handles ordering internally.
  Operation localPrime  = new Operation(local);
  Operation remotePrime = new Operation(remote);

  // In a real RGA:
  //   localCharId  = local.userId + ":" + operationCounter;
  //   remoteCharId = remote.userId + ":" + (operationCounter + 1);
  // The linked list of char nodes is ordered by (siteId, counter).
  // Both nodes eventually see all char nodes; sort → same content.

  return new TransformResult(localPrime, remotePrime);
}

The compression: 200 lines of OT position math ↔ 5 lines of CRDT commutativity. But the cost lives elsewhere: every char carries a unique-ID metadata, deleted chars become tombstones (memory leak until GC'd), and the correctness proof lives in the data-structure invariants rather than in the transform table.

production: per-doc Kafka topic + gateway subscriber map
// Producer side — inside Collaboration Service after persist
kafka.send("ops." + docId, docId /* key */, opJson);

// Consumer side — inside each WS Gateway pod
onKafkaMessage(topic, key, opJson) {
  String docId = key;
  Set<WsSession> sessions = localSessions.get(docId);   // docs this pod hosts
  if (sessions == null) return;                          // no editors here → discard
  Operation op = deserialize(opJson);
  for (WsSession s : sessions) {
    if (!s.userId.equals(op.getUserId())) {              // don't echo author
      s.send(REMOTE_OPERATION(op));
    }
  }
}

Subscription trick: each gateway subscribes ONLY to Kafka topics matching docs it currently hosts (rebalances on WS connect/disconnect). Prevents every gateway from consuming every op — else we'd move 10 GB/s × 100 nodes = 1 TB/s of gateway ingress. With filtered subscribes, ingress ≈ what leaves the pod's sockets.

multi-region: local-first, cross-region async
// One doc can have editors in us-east + eu-west + ap-south simultaneously.
// Strategy: pin the doc's PRIMARY region (author's home region),
// mirror ops asynchronously to secondary regions.

Region primary = docLookup.getPrimaryRegion(docId);
if (currentRegion.equals(primary)) {
  // Same-region editors — full OT loop < 50 ms.
  processOperation(docId, userId, op);
  crossRegionMirror.publish(docId, op);   // async, best-effort
} else {
  // Remote-region editor — forward to primary, then apply mirror.
  primaryProxy.processOperation(docId, userId, op);   // ~120 ms cross-region
  // Client sees local echo (optimistic) + ACK when primary confirms.
}

Trade-off: for docs with cross-region editors, one region pays the round-trip cost. Alternative: multi-master OT — needs TP2 (transformation property 2), notoriously hard. CRDT would solve this naturally but at metadata cost. Most tools (Google Docs · Figma) pin one region per doc.

Client-side OT state machine

SYNCHRONIZED → AWAITING_ACK → AWAITING_ACK_WITH_BUFFER
the three states + transitions
SYNCHRONIZED
  no pending op · local state == server state
  ┌─ local edit ─▶ send to server ─▶ AWAITING_ACK
  └─ remote op received ─▶ apply, stay SYNCHRONIZED

AWAITING_ACK
  one op sent, waiting for ACK · local = server + pending
  ┌─ ACK, no buffer      ─▶ SYNCHRONIZED
  ├─ ACK, buffer present ─▶ send buffer, stay AWAITING_ACK
  ├─ local edit          ─▶ enqueue in buffer ─▶ AWAITING_ACK_WITH_BUFFER
  └─ remote op           ─▶ transform pending against remote, stay
                              (apply transformed remote locally)

AWAITING_ACK_WITH_BUFFER
  one op sent + more buffered · local = server + pending + buffer
  ┌─ ACK ─▶ send buffer as composite op ─▶ AWAITING_ACK
  ├─ local edit ─▶ merge into buffer, stay
  └─ remote op  ─▶ transform BOTH pending AND buffer against remote
why exactly three states?
  • Only ONE op in flight at a time. Prevents the server from having to reorder ACKs — it always echoes local_op_id in the ACK; client matches to remove from pending.
  • Buffer = merged view of every local edit since we sent the last op. When the ACK arrives, we ship the whole buffer as one composite op (batched — cheaper for the server, less network chatter).
  • Remote ops must transform against pending AND buffer. Otherwise our next batch would fight the server's already-applied ops. This is where TP1 shines: apply(remote, pending) = apply(pending', remote') — same final state either way.
  • Reconnection: re-enters SYNCHRONIZED after full resync. Buffered ops replay with the new base_revision the server assigns.
Interview point: a client-side state machine like this is why OT feels magic to the user — they type, they see it, they never wait. All the network-round-trip complexity is hidden behind these three states. The trap for interviewers: candidates describe the server-side transform without ever explaining the CLIENT OT machine, so their design "works" only in the perfect-connectivity case.

Latency budget for this frame: Alice keystroke → local apply (< 1 ms) → WSS send (~10 ms RTT/2) → permission cache (~0.2 ms) → doc fetch (~1 ms) → pending fetch (~1 ms) → OT transform (~0.5 ms) → apply + version bump (~0.5 ms) → persist to op log (~2 ms) → broadcast local + Kafka publish (~2 ms) → REMOTE_OPERATION out to Bob (~10 ms RTT/2). Total ~30 ms server-side + network — well under the 100 ms p99 budget.
