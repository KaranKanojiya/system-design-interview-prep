Adaptive bitrate — the core algorithm

ThroughputBasedABR.selectResolution()
the code (grounded in source)
public Resolution selectResolution(
        long bandwidthKbps, double bufferSeconds,
        List<Resolution> available) {
  if (available == null || available.isEmpty())
      return Resolution.P240;         // floor
  // only trust 80% of the measured pipe
  long usable = (long)(bandwidthKbps * 0.8);
  Resolution selected = available.get(0); // lowest fallback
  for (Resolution res : available) {   // ascending bitrate
    if (res.getBitrateKbps() <= usable)
        selected = res;                 // keep climbing
  }
  return selected;
}

Rungs (Kbps): P240=400 · P360=750 · P480=1000 · P720=2500 · P1080=4500 · P4K=12000.

worked example — 6 Mbps link, full buffer
// player measured 6000 Kbps this tick
usable = 6000 * 0.8 = 4800 Kbps

P240   400 <= 4800 ? yes → selected=P240
P360   750 <= 4800 ? yes → selected=P360
P480  1000 <= 4800 ? yes → selected=P480
P720  2500 <= 4800 ? yes → selected=P720
P1080 4500 <= 4800 ? yes → selected=P1080
P4K  12000 <= 4800 ? no  ■ keep P1080

chosen rung → P1080  (4.5 Mbps)

The 4.5 Mbps rung fits inside the 4.8 Mbps safety budget; 4K's 12 Mbps blows past it. The 20% headroom is the buffer against a bandwidth dip before the next tick.

The other core algorithm — parallel transcode. A 1080p source fans into 5 lower rungs. SequentialTranscodingStrategy runs them one-by-one → wall-clock = 2+3+5+8+12 = 30 min (sum). ParallelTranscodingStrategy submits all 5 to a 6-thread ExecutorService and blocks on Future.get() → wall-clock = max(2,3,5,8,12) = 12 min. Same O(N) compute, but latency drops from O(N) to O(1) rungs — a 2.5× speedup, and exactly why YouTube transcodes across a distributed worker fleet.
C

Three strategy axes (Strategy pattern ×3)

swap the algorithm, not the service

TranscodingStrategy — HOW a raw video becomes multiple rungs. held by TranscodingService

  • ParallelTranscodingStrategy (default) — every rung submitted to a fixed thread pool; wall-clock = max of the individual times. Production choice.
  • SequentialTranscodingStrategy — one rung at a time; wall-clock = sum. Budget tier / comparison baseline.
  • Cost: both O(N) compute; parallel trades peak resource use for lower latency.

ABRStrategy — WHICH rung the player fetches next. held by StreamingService

  • ThroughputBasedABR — highest rung ≤ 80% of measured bandwidth. Aggressive, maximizes quality, YouTube-style; risks rebuffering on a sudden dip.
  • BufferBasedABR — maps buffer fullness to rung (<5s → lowest, >30s → highest, else interpolate). Conservative, Netflix BBA; avoids stalls.

RecommendationStrategy — WHICH videos to suggest. held by RecommendationService

  • TrendingRecommendation — recent uploads sorted by viewCount desc; solves the cold-start problem for new/anonymous users.
  • PersonalizedRecommendation — category affinity from WatchHistory × recency × popularity; better for logged-in users with a history.

Not in the repo, but the interfaces make them drop-in — implement the interface and register in AppConfig:

  • DistributedTranscodingStrategy — fan jobs across a worker fleet (Kubernetes pods running FFmpeg) instead of one JVM's thread pool.
  • HybridABR — blend throughput and buffer signals; the industry direction (e.g. MPC/BOLA).
  • CollaborativeFilteringRecommendation — "users like you watched…" via embeddings + cosine similarity.

The pattern: each service holds a single strategy field and calls it without branching on type. Adding a new algorithm is a new class + one line in AppConfig — zero changes to the service, controller, or model (Open-Closed Principle). Three orthogonal axes means each can be A/B tested per user cohort independently.

Data model detail

Video · Resolution · TranscodeJob · Manifest · WatchHistory
Video — the pipeline entity (Builder + State)
videoId            String   // final, "vid_"+uuid8
title, uploaderId  String   // final, required
description        String
durationSeconds    int      // final
fileSizeBytes      long     // final
originalResolution Resolution
availableResolutions List<Resolution> // grows
codec              Codec    // H264 default
status             VideoStatus  // volatile — state m/c
createdAt, transcodedAt  LocalDateTime

Identity fields are final; only status is mutable (volatile). Transitions go through guarded methods — markUploaded / startTranscoding / markReady / markFailed / delete — each throwing IllegalStateException on an illegal jump. State machine: UPLOADING → UPLOADED → TRANSCODING → READY, with FAILED retry back to TRANSCODING and DELETED as terminal.

Supporting models
// Resolution — enum with bitrate (Kbps)
P240..P4K (label, width, height, bitrateKbps)

// TranscodeJob — one rung of one video
jobId, videoId, targetResolution, targetCodec
status  // QUEUED→PROCESSING→COMPLETED|FAILED
progress int  // 0-100, volatile

// StreamManifest — the HLS/DASH .m3u8/.mpd
videoId, protocol, List<StreamVariant>
  StreamVariant(resolution, codec,
                bitrateKbps, List<String> segmentUrls)

// WatchHistory — feeds recommendations
userId, videoId, watchedAt,
watchDurationSeconds, completionPercent

VideoChunk and VideoMetadata (viewCount/likeCount as AtomicLong) round out the set. Metadata lives in a shared Map keyed by videoId so Analytics, Search, and both recommenders read the same counters.

Why split Video from VideoMetadata? Video holds identity + pipeline state that changes rarely; VideoMetadata holds discovery + engagement data (viewCount increments on every watch). Different write frequencies → different caching and indexing in production (Postgres for Video, a hot counter store for metadata).

Request handling sequences

which class does what, in order

POST /videos/upload  →  upload + transcode

VideoController.handleUpload(...)
  └─ VideoService.uploadVideo(user, title, desc, size, res)
       1  new Video.Builder(id, title, user)…build()  // status=UPLOADING
       2  videoRepository.save(video)
       3  uploadService.initiateUpload(video)   // ceil(size / 5MB) chunks
       4  for i in 0..N: uploadService.uploadChunk(id, i, data)
       5  video.markUploaded()                  // UPLOADING → UPLOADED
       6  transcodingService.transcodeVideo(video)
            video.startTranscoding()            // UPLOADED → TRANSCODING
            targets = buildResolutionLadder(source)
            strategy.transcode(video, targets, codec)  // parallel
            video.markReady()                   // TRANSCODING → READY
  └─ [201] videoId

The demo drives chunk upload synchronously; in production chunks arrive over many requests and getMissingChunks() powers resume after a dropped connection.

GET /videos/{id}/stream  →  ABR playback + CDN

VideoController.handleStream(id, user, bandwidthKbps)
  └─ VideoService.streamVideo(id, user, bandwidth)
       1  getVideo(id)  // else VideoNotFoundException
       2  streamingService.simulateStreaming(video, user, bw, 60s):
            generateManifest(video, "HLS")     // one variant per rung
            each tick:
              abrStrategy.selectResolution(bw, buffer, available)
              fetch segment → CDNService.getChunk(id, res, i)
                edge HIT  → return <10ms
                edge MISS → origin S3, cache at edge (LRU), return
       3  analyticsService.recordView(id, user, 60)  // viewCount++, WatchHistory
  └─ [200] streaming log

ABR runs the selection every tick; the CDN's access-ordered LinkedHashMap keeps hot segments at the edge and evicts the least-recently-used, driving the ~85% edge hit rate.

GET /recommendations  →  suggest videos

VideoController.handleRecommendations(userId, limit)
  └─ RecommendationService.recommend(userId, limit)
       └─ RecommendationStrategy.recommend(userId, limit)
            Trending      → recent uploads, sort by viewCount desc, top N
            Personalized  → watch history → category affinity
                            → score unwatched → sort desc → top N
  └─ [200] ordered List<Video>
F

Design patterns used

GoF-categorized
Creational
  • Builder — Video.Builder. Required (videoId/title/uploaderId) enforced at construction; many optional fields, immutable identity result.
  • Factory — AppConfig is the composition root; the only place concrete classes are new-ed, wired layer by layer.
Behavioral
  • Strategy ×3 — Transcoding / ABR / Recommendation. The centrepiece: three orthogonal, swappable axes.
  • State — VideoStatus + guarded markUploaded/startTranscoding/markReady; illegal jumps throw.
  • Observer — AnalyticsService reacts to view/like events, decoupled from the emitter.
  • Template-style flow — transcodeVideo fixes start → transcode → ready; the varying step is the injected strategy.
Structural / Architectural
  • Facade — VideoService hides Upload/Transcoding/Streaming/CDN/Analytics behind one API.
  • Repository — Video/User/WatchHistory interfaces over ConcurrentHashMap; swap to Postgres/Cassandra with no service change.
  • Pipeline — transcoding as a DAG: validate → split → parallel transcode → stitch → manifest → store → notify.
Why they cluster: Strategy + Repository + Factory together deliver the Open-Closed Principle — new algorithms and storage backends are additions, never edits. Facade keeps the controller thin; State keeps the pipeline honest; Builder keeps the entity immutable and validated. → scaling trade-offs & the CDN/transcode-fleet follow-up on canvas 3

terms used above
