A

Scaling strategy

what to shard & how
delivery tier

CDN does the heavy lifting

95% of bytes are video segments served from edge PoPs. Scaling playback = scaling the CDN (edge → regional shield → S3), not app servers. The origin only sees ~1% of segment requests.

app tier

Stateless → horizontal

Streaming / upload / metadata services are stateless behind the LB — any instance serves any request. Auto-scale independently; transcoding workers scale on queue depth, not request rate.

metadata DB

Shard + read replicas

PostgreSQL/Vitess sharded by video_id; read replicas absorb metadata reads (title, duration, manifest URL). Analytics runs off Redshift/BigQuery so aggregations never touch the playback path.

metadata sharding — pick a partition strategy

Hash-based partitioning ← chosen for metadata

Route each row by hash(video_id) % N. Reads and writes are point lookups by video_id (from the manifest URL), so a random hash spreads load evenly — no hot shard even when one video goes viral, because viral reads hit the CDN, not the DB.

shard = hash(video_id) % N   // even spread, point lookups
verdict
  • Even load — natural fit for key-value metadata lookup by video_id.
  • Viral videos don't create a hot shard: playback is a CDN read, DB sees only the first cache-miss.
  • Resharding pain: changing N remaps most keys → Vitess resharding / consistent hashing avoids it.

Range by upload time

Assign contiguous uploaded_at ranges to shards (this month → shard N, last month → shard N-1). Great for "recent uploads" scans and time-window analytics.

2026-07 → shard 12
2026-08 → shard 13   // newest shard is always hottest
verdict — avoid for metadata
  • Hot partition: the newest shard takes 100% of fresh uploads and their early (highest) view traffic.
  • Useful only for the watch-history / analytics time-series store (Cassandra), not video metadata.
  • The interview red flag: "range-on-time causes a hot tail shard."

Shard by uploader / channel

Co-locate all of a channel's videos on one shard. Cheap "list my channel's videos" and per-creator analytics without scatter-gather.

shard = hash(channel_id) % N   // creator locality
verdict — niche
  • Celebrity skew: a channel with millions of videos + views overloads its shard.
  • Good for Creator Studio queries; pair it with hash-on-video_id for the playback path.
  • Watch-history is separately sharded by user_id in Cassandra (time-series writes).
Replicas & read-your-writes: metadata reads fan out to replicas, but right after an upload the creator is pinned to the primary (or a sync replica) so they always see their just-uploaded video — replication lag would otherwise show "video not found". View counts live in Redis (INCR), not the DB, so they never hit the sharding hot path.

Caching deep-dive

CDN is THE cache
multi-tier CDN — the segment read path
GET /{videoId}/{res}_{codec}/segment_{N}.ts
  ├─ EDGE PoP  → HIT  → serve      // <5ms · ~95%
  │             MISS ↓
  ├─ REGIONAL SHIELD → HIT → serve // <30ms · +4%
  │             MISS ↓
  └─ ORIGIN (S3) → serve + backfill// <100ms · ~1%

Zipf: 10% of videos = 90% of views, so a modest edge cache serves nearly all traffic. Segments are immutable → 1-year TTL, never invalidated. The origin shield collapses N edge misses into one origin pull (thundering-herd protection).

TTL policy by content type
video segments (VOD) → 1 year   // immutable
HLS/DASH manifest VOD→ 5 min    // rare re-package
HLS manifest (live)  → 2 sec    // < segment duration
thumbnails           → 24 h     // versioned ?v=2 busts
player JS/CSS        → 1 year   // versioned filenames
API metadata         → no CDN   // served from Redis

Live gotcha: manifest TTL must be shorter than segment duration. 2 s TTL for 4 s segments — a longer TTL makes the player stall on a segment that "doesn't exist yet" at the edge.

metadata cache — Redis, cache-aside

meta:{videoId} · 5-min TTL

Video page load does one HGETALL round-trip. Miss → read PostgreSQL → HSET + EXPIRE 300. On edit → DEL meta:{videoId} and let the next read repopulate. View count is not in this hash — it has its own counter.

HGETALL meta:vid-42        // <1ms hit
  miss → SELECT ... FROM videos
       → HSET meta:vid-42 ...
       → EXPIRE meta:vid-42 300
view counts — write-behind

Redis INCR + 30 s flush

A viral video does 50K+ views/s. Every view is an O(1) INCR plus a dirty-set mark; a background job flushes deltas to the DB every 30 s with atomic GETSET. Turns 50K writes/s into one UPDATE per video. Staleness ≤ 30 s — invisible at "1.2M views".

INCR viewcount:vid-42
SADD viewcount:flush:pending vid-42
// every 30s:
delta = GETSET viewcount:vid-42 0
UPDATE videos SET view_count += delta
cache warming — beat the herd

Pre-push viral segments

On a big-creator upload, push the first ~10 segments of each rendition to the top ~50 PoPs before the first viewer arrives. Predictive warming fires when view-velocity > 100/min and accelerating. Recommendations are pre-warmed per DAU before peak hours.

// trending detected → warm edges
push seg_000..009 → top 50 PoPs
warm recs:{userId} before 7AM peak
Cold storage tiering: S3 Standard → Standard-IA (30 d idle) → Glacier IR (90 d, <100 ms) → Glacier Deep (365 d). ~72% storage savings; Glacier IR serves fast enough that users never notice, and first-access re-tiers the object back to Standard. → full cache layering on canvas 1 · HLD
C

Bottlenecks & solutions

click a card to open

Thundering herd on origin (viral cold start)

Impact: a video shared to millions at once — every one of 400+ edge PoPs cache-misses simultaneously and hits S3 with 400× the load, saturating the origin and causing rebuffering on the first segment.

Fix: a regional origin shield collapses all edge misses in a region into one origin pull; the first viewers absorb a 100 ms miss, then every edge is served from the shield. Combine with cache warming (pre-push first 10 segments to top 50 PoPs) so the herd never reaches S3.

Transcoding is the write-path bottleneck

Impact: one uploaded video becomes 20 renditions (5 resolutions × 4 codecs); a 15-min sequential transcode makes users wait far too long and pins compute. YouTube ingests 500 hours/minute — sequential is a non-starter.

Fix: a parallel DAG (Step Functions Map / Kafka-fed FFmpeg workers) — wall-clock = the slowest single job (~15 min), not the sum (~120 min). Priority transcoding produces 720p/1080p H.264 first (3–5 min → playable), the rest complete in the background. 90% of videos get fewer views than the AV1/4K break-even, so those renditions are lazily triggered by a view threshold.

Duplicate transcoding jobs (race)

Impact: two workers both read state UPLOADED and both start transcoding the same video — double compute cost and conflicting writes to the manifest.

Fix: optimistic locking on the state machine — UPDATE videos SET status='TRANSCODING', version=version+1 WHERE video_id=? AND status='UPLOADED' AND version=?; only one worker gets rows=1, the loser gets 0 and backs off (guarded by Video.startTranscoding). A Redis SET lock:transcode:{videoId} NX EX 600 dedupes concurrent starts, and deterministic S3 output paths make duplicate work idempotent.

View-count write storm

Impact: incrementing a DB row on every view (SELECT ... FOR UPDATE) means 50K row-locks/second on a single "Despacito" row — the DB becomes the bottleneck and latency cascades.

Fix: write-behind — Redis INCR on the hot path (O(1)), atomic GETSET flush to the DB every 30 s. 50K writes/s collapse into one batched UPDATE; staleness ≤ 30 s is invisible.

Live-stream manifest staleness

Impact: if the live media-playlist TTL exceeds the segment duration, the edge serves a manifest missing the newest segment — the player stalls waiting for a segment that "doesn't exist yet," and rebuffers.

Fix: set manifest TTL to ~half the segment duration (2 s TTL for 4 s segments) so the newest segment is always listed, backed by an origin shield to avoid hammering origin with per-PoP refreshes. Glass-to-glass latency ≈ segment_duration + manifest_TTL.

Uploader sees "video not found" (replica lag)

Impact: creator uploads, metadata lands on the primary, they refresh and hit a read replica that hasn't replicated yet → their own video appears missing.

Fix: read-your-writes — tag the session with an upload timestamp; while it's within the replication-lag window, route that user's reads to the primary; after the window, fall back to replicas. Other viewers stay on eventual consistency (fine).

CDN bandwidth cost explosion

Impact: egress is the #1 cost — 1M viewers × 30-min sessions ≈ 900 TB/day. At commercial CDN rates that's hundreds of thousands per month, billions/year at Netflix scale.

Fix: better codecs cut per-view bytes (AV1 ≈ 60% smaller than H.264 for popular videos), aggressive edge caching keeps bytes off origin, and above ~100M DAU a custom ISP-embedded CDN (Netflix Open Connect) eliminates vendor markup.

Origin / region failure mid-playback

Impact: S3 origin or a whole region drops offline while millions are watching.

Fix: AP delivery — a circuit breaker at the shield serves stale-but-cached segments (immutable, so "stale" = correct) during an origin outage; S3 is 11-nines durable and cross-region replicated. Because segments never change, the CDN can keep serving indefinitely without the control plane.

CAP & consistency — AP stream, CP where it counts

pick two; P is not optional
the choice

P is mandatory in any distributed deployment, so the real decision is A vs C during a partition. Playback must always work — a buffering spinner or "video unavailable" is worse than a view count that's 30 s stale, and every failed play is lost watch-time and ad revenue. So streaming + metadata are AP. But a handful of operations cannot tolerate a stale read and go CP.

  • AP: segments, metadata, view/like counts, search, recommendations, watch history.
  • CP: upload-chunk tracking, transcoding state machine, subscription/billing.
  • PACELC → PA/EL for playback: partition → Availability; else → Latency. Netflix loses engagement per 100 ms.
CP corner — exactly-once via idempotency
// upload chunks: no lost/duplicate chunk
INSERT INTO upload_chunks(video_id,chunk_no,status)
resume: SELECT MAX(chunk_no) ... status='RECEIVED'

// state machine: optimistic lock (one winner)
UPDATE videos SET status=?, version=version+1
  WHERE video_id=? AND status=? AND version=?

// transcode: at-least-once + idempotent output
SET lock:transcode:{vid} NX EX 600   // dedupe

Exactly-once is impossible in a distributed system (FLP), so transcoding is at-least-once with idempotent output: deterministic S3 paths mean a duplicate job overwrites with identical bytes — last-writer-wins, no corruption. A Redis lock keeps it at-most-one active worker → effectively exactly-once.

Saga for upload→ready: create record → upload chunks → assemble → transcode → READY, each step with a compensating action (delete record, delete S3 objects, revert status). If any step fails, compensations run in reverse and the video lands in a retryable FAILED state — never a half-published video.
