A

Problem & requirements

clarify first
functional
  • Upload — chunked, resumable upload (5 MB chunks, presigned URLs, direct-to-S3) of files up to 256 GB.
  • Transcode to a resolution ladder (240p–1080p) × codecs (H.264, VP9) → HLS/DASH segments.
  • Stream on demand with adaptive bitrate — quality follows bandwidth, zero rebuffer on drops.
  • Search, recommendations, like/comment, watch history & resume; live streaming (conceptual).
non-functional
  • Playback startup < 2 s p99; rebuffering < 1% of playtime — the #1 churn driver.
  • Availability 99.99%; durability zero data loss on uploaded source + variants.
  • CDN cache-hit > 95% — miss ratio directly drives origin bandwidth cost.
  • Scale 500M DAU, 1B watch-hours/day; AP for views/likes, CP for upload chunk state.
B

Back-of-envelope estimation

500M DAU · 500 hrs uploaded/min
DAU500 M
Uploads / day~720 K
Peak concurrent~50 M
Peak egress~250 Tbps
CDN hit ratio> 95%
Total storage~3 EB
Variants / video5 × 2 = 10
Startup p99< 2 s
Derivation: 500 hrs/min uploaded ÷ 10 min avg × 60 × 24 ≈ 720K videos/day ≈ 720 TB raw/day. Each video → 10 variants ≈ ~3 GB, so ~2.2 PB transcoded/day → across 1B videos ≈ ~3 EB total. Streaming: ~50M concurrent viewers × 5 Mbps ≈ 250 Tbps peak egress; a >95% CDN cache-hit leaves only ~12.5 Tbps hitting origin (S3). → full cost math on canvas 3 & F3 · Estimation

Data model

metadata in DB · bytes in S3
Video + VideoMetadata (DynamoDB)
video_id     STRING  // PK (Snowflake)
user_id      STRING  // creator FK
status       ENUM    // UPLOADING→…→READY
source_url   STRING  // S3 assembled source
duration_sec INT
visibility   ENUM    // PUBLIC/UNLISTED/PRIVATE
title,tags,category,thumbnail_url
view_count,like_count  // approx (Redis)

Key-value lookup by video_id. Co-locate metadata for single-read hydration. Counters are eventually consistent. Video, VideoMetadata.

Resolution / VideoChunk · TranscodeJob
resolution_name  // 240p…1080p
codec            // h264 / vp9
bitrate_kbps, width, height
storage_url_prefix  // s3://…/1080p/h264/
segment_index    // 0-based, ~10s each
--- TranscodeJob ---
job_id, video_id, status, priority
worker_id, retry_count, progress_pct

Segments are S3 objects (not DB rows). One TranscodeJob per variant tracks the DAG. Resolution, VideoChunk, TranscodeJob.

F

Key design choices (deep-dived on canvas 3)

defend these
ingest

Chunked, resumable, direct-to-S3

5 MB chunks + presigned URLs upload straight to storage — the API server never touches bytes. A Redis chunk bitmap enables resume. → canvas 2 · LLD

transcode & deliver

DAG pipeline + ABR over CDN

Parallel resolution×codec ladder → HLS/DASH segments; client ABR switches quality per segment. Multi-tier CDN + shield serves 95%+.

consistency & cost

AP stream · CP upload · tiered storage

Buffer a few segments (AP); chunk state must be exact (CP). Hot→IA→Glacier tiering + custom CDN dominate the cost story. → canvas 3

Glossary — one-liners

terms used above
HLS / DASHHTTP adaptive-streaming protocols; a manifest lists quality variants + segment URLs
ABRAdaptive Bitrate — player picks a variant per segment from measured bandwidth + buffer
Manifest.m3u8/.mpd playlist mapping resolutions/codecs to segment URLs
Segmenta ~10 s independently-decodable chunk of one variant
Transcodingre-encoding the source into a resolution×codec ladder (via FFmpeg)
DAG orchestrationtasks as a dependency graph: split → transcode (fan-out) → package → finalize
Presigned URLtime-limited signed link letting the client PUT a chunk directly to S3
Resumable uploada chunk bitmap lets a dropped upload restart from the last completed chunk
Origin shieldsingle CDN tier that talks to origin — collapses the thundering herd
Cache-hit ratio% of bytes served from CDN cache; >95% keeps origin bandwidth cheap
Pre-warmingpushing hot content to edges before release so launch doesn't hit origin
Storage tieringStandard→IA→Glacier as videos cool; 80% of views hit the first 7 days
Open ConnectNetflix's custom ISP-embedded CDN — 90%+ traffic, near-free bandwidth at scale
AP / CPstreaming favours availability (AP); upload chunk state must be consistent (CP)
