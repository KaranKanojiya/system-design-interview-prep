B

Deduplication — the star of the interview

saves $24 M/month at Dropbox scale
how dedup wins so hard

Content-addressable storage → key = SHA-256(content). Two identical files (same node_modules, same OS installer, same viral meme) upload from N users → stored once. Reference count tracks 'who is using this block' — the block is freed only when the last file referencing it is permanently deleted.

Where the savings live:

  • Cross-user dedup — same installer / video / meme uploaded by many. ~20–30 % savings.
  • Cross-version dedup (CoW) — a 100 MB file with 10 % edited on save reuses 90 % of blocks. ~15 % savings on active users.
  • Cross-folder dedup — same photo saved in "vacation" and "family" folders → one block.
  • Total measured (Dropbox blog): ~40 % average, up to 75 % for corporate accounts (shared file sets).
worked example — 10 users, one common file
// 10 users each upload the SAME 100 MB video (25 chunks of 4 MB)

Naive:            10 × 25 × 4 MB = 1000 MB
Content-dedup:    1  × 25 × 4 MB = 100 MB  (refCount = 10 on each chunk)
Savings:          90 %

// Then user 3 deletes their copy:
softDelete(user3.file)      → hides from tree, isDeleted=true
                             → no blocks touched (soft)

// 30 days later, cron runs permanentDelete:
for each chunk in user3.file.chunks:
  blockStore.deleteBlock(hash)
    refCount 10 → 9   // bytes still there, 9 users need it

// User 3's tree is gone. All 10 chunks still live. No data loss for the other 9.
The ref-count catastrophe — undercounting is permanent data loss. If two DCs both decrement refCount 2→1 during a partition (each thinking the other hasn't run), the reconciled value becomes 0 and the block is GC'd — but Charlie's file still references it. On next download: NULL bytes. This is why refCount operations MUST be serialized (CP path — single-leader). Overcount is only a storage leak, harmless.
The killer to dedup: client-side encryption. Different keys ⇒ different ciphertexts ⇒ different hashes ⇒ no dedup. Mitigation: convergent encryption — key = SHA-256(plaintext) — same plaintext still produces the same ciphertext hash. But this leaks 'you have this file' to the server (Dropbox chose this trade-off; Boxcryptor and Cryptomator did not).

Chunked resumable upload — the flow that survives flaky networks

10 GB uploads over hotel WiFi
the full protocol
1) Client hashes: SHA-256 whole file + SHA-256 per 4 MB chunk
2) POST /upload/chunked/init { fileName, totalChunks, chunkHashes[] }
3) Server checks each hash against BlockStore index:
   → { existingChunks: [0,1,4,5,6,8,11],   // ~40 % dedup hit
       missingChunks:  [2,3,7,9,10,12],
       presignedUrls:  { 2: "...", 3: "...", ... } }
4) Client PUTs missing chunks in parallel (up to 4 concurrent)
   → each PUT goes DIRECT to S3 (bypasses our servers)
   → S3 verifies signature + Content-Length + optional MD5
5) If a PUT fails (network hiccup): client retries THAT chunk only
   → no need to redo the 5 that succeeded
6) POST /upload/chunked/{uploadId}/complete
7) Server verifies all chunks present, creates FileMetadata + Version #1
8) Server publishes file_created to Kafka → sync fan-out
why the client does the hashing
  • Bandwidth savings — client sends 32-byte hashes first; server tells it what to skip. A user re-uploading a slightly changed file might send < 5 % of bytes.
  • Server CPU savings — no re-hashing after upload; server just verifies S3's returned hash matches what the client claimed.
  • Presigned URLs bypass app servers — the actual bytes never touch our compute. At 1.16 GB/s ingress, this saves several thousand cores worth of network I/O.
  • Resume works across sessions — server tracks state in Redis (TTL 24 h); client restarts, sends init again with hashes → server responds with the same 'missing' list minus what's now uploaded.
The 10 GB upload success story: a 10 GB file = 2 560 chunks. Even at 1 % chunk-level failure rate → ~26 chunks need retry, not the whole file. Without chunked resumable, one dropped connection at byte 9.9 GB = start over. Chunked = ship the last ~100 MB and move on.

Delta sync — edit locally, propagate globally

< 10 s cross-device target
The 14-step sync flow
Cursor protocol
Conflict resolution
WebSocket vs long-poll
1) Desktop client detects file change via inotify/FSEvents/RDCW
2) Client re-chunks the file with rolling hash → knows which chunks changed
3) Only changed chunks travel (20 MB edit ⇒ ~8 MB uploaded, not 20 MB)
4) Client uploads changed chunks via chunked-init/PUT flow
5) Client POSTs new-version metadata (chunkHashes list — mostly OLD hashes)
6) MetadataService creates FileVersion #N+1 (old version preserved via CoW)
7) UploadService publishes file_modified event to Kafka
8) Sync Service consumes event (partitioned by userId)
9) Sync Service holds WebSocket connections for user's other devices
10) For each connected device, push { fileId, changedChunks: [2, 4] }
11) Phone / tablet receives push, requests GET /sync/changes?cursor=X
12) Sync Service returns the event list + new cursor
13) Client downloads ONLY the 2 changed chunks (8 MB, not 20 MB)
14) Client reconstructs new file locally: 3 cached chunks + 2 new chunks
the sync cursor is just an opaque server timestamp
Client stores { deviceId, cursor="2026-04-26T10:34:59.123Z" }

// SyncService (Java, from real code):
public SyncResult getChangesSince(String userId, Instant lastCursor) {
  List<SyncEvent> userEvents = eventsByUser.getOrDefault(userId, ...);
  List<SyncEvent> newEvents = userEvents.stream()
      .filter(e -> e.getTimestamp().isAfter(lastCursor))
      .collect(toList());
  Instant newCursor = newEvents.isEmpty() ? lastCursor
                              : newEvents.get(newEvents.size() - 1).getTimestamp();
  return new SyncResult(newEvents, newCursor);
}

// Cursor is idempotent — sending the same cursor returns the same events.
// Client stores the RETURNED cursor as its next 'last seen'.

Why opaque: the server can change the internal cursor format (timestamp → LSN → vector clock) without breaking clients. Clients treat it as a black box.

CAP theorem — the split answer

CP for metadata & refCounts · AP for sync & quota
The interview-winning insight: file storage isn't 'pick CP or AP globally'. Metadata (file tree) and dedup ref-counts MUST be CP — inconsistency = data loss or orphan files. Sync notifications and quota SHOULD be AP — being 8 s stale is better than users staring at a spinner.

F

Bottlenecks & mitigations

8 failure modes · defence against each
S3 partition hot-spotting (hash-prefix)

Symptom: 503 SlowDown from S3 on a specific prefix under sustained > 5 500 PUT/s or 3 500 GET/s per partition. Manifests as elevated tail latency and retry storms.

Mitigations: use SHA-256 as the S3 object key (uniform random distribution). Widen prefix if you have hot 2-char prefixes (e.g., every hash starting 00). Enable Transfer Acceleration for cross-region uploads. Pre-warm partitions with S3 support ticket for known bursts.

Metadata shard hot-spotting (power user)

Symptom: one Postgres shard at 90 %+ CPU while others idle — usually a corporate account with millions of files.

Mitigations: (1) Read replicas per shard for read-heavy load (folder listing, search). (2) Split the shard — introduce a new shard, migrate half the userId range via double-write + backfill + cutover. (3) For a single mega-user, sub-shard by (userId, folderPrefix).

Ref-count race → permanent data loss

Symptom: file downloads return corrupt bytes or 404s for chunks that 'should' exist.

Root cause: two concurrent deletes both saw refCount=2 → both decremented to 1 → net refCount=0 without atomicity → block GC'd.

Mitigations: ref-count ops MUST use atomic INCR/DECR in a single-leader store (Postgres row-lock, Redis DECR, DynamoDB conditional update). Never eventual consistency for refCount. Add staged deletion: mark block pendingDelete for 24 h before actually removing bytes — one last chance to catch races.

Sync notification lag > 10 s

Symptom: user edits on laptop, opens phone, still sees old version 30 s later.

Mitigations: (1) Add Kafka partitions for the file.events topic (partitioned by userId — same user always same partition ⇒ ordering). (2) Scale Sync Service consumers horizontally. (3) Enable partition-affinity routing — a user's WebSocket connection lands on the same Sync Service instance consuming their event partition (removes internal hop).

Upload storm on Monday 9 AM

Symptom: upload traffic 5× spike as everyone starts their workday.

Mitigations: (1) Presigned URLs mean the app server is not in the byte path — spike hits S3, which auto-scales. (2) Upload-init endpoint scales horizontally on stateless nodes. (3) Client SDK exponential-backoff for 429s. (4) Regional presigned URLs to the user's nearest S3 region.

Dedup cache miss cliff

Symptom: Redis dedup-cache hit rate falls from 95 % → 60 % overnight; every upload now hits Postgres index → latency spikes.

Mitigations: (1) Bloom filter in front — sized for ~1 % false-positive rate on 300 B hashes ≈ 2 GB. False positives just fall through to Postgres; false negatives impossible ⇒ correct. (2) Warm cache with hot hash set on Redis restart. (3) Auto-scale Redis Cluster based on eviction rate.

Quota reconciliation drift

Symptom: a user's shown 'used storage' differs from the sum of their file sizes by > 100 MB.

Mitigations: quota is intentionally AP — a background job every hour re-computes SUM(size) WHERE userId = X AND isDeleted = false and reconciles the cached counter. For heavy uploads/deletes, accept short drift. Bill on the reconciled value at month-end.

Fat file → CDN cache thrash

Symptom: 500 MB training-data file gets viral traffic; CDN cache-fill dominates edge bandwidth.

Mitigations: (1) Origin shield (Cloudfront) — one regional cache absorbs origin fetches. (2) Longer TTL — since content is content-addressed (hash in URL), it's provably immutable — set TTL to 30 days. (3) For truly viral files, pre-warm popular POPs.

Interview walkthrough — 8 phases

45-min structure · green & red flags
phase 1 — clarify (2 min)

Ask: max file size? free vs paid? sync latency SLA? global or regional? end-to-end encryption?

Green: "50 GB max, 15 GB free / 2 TB paid, sync < 10 s, global, plaintext dedup". Red: skipping straight to architecture without pinning scale.
phase 2 — estimation (3 min)

500 M users × 5 GB = 2.5 EB raw → 1.5 EB after 40 % dedup. 100 M uploads/day = 1 160/s avg; 300 M downloads. 125 TB metadata across ~100 Postgres shards.

Green: quote dedup savings ($24 M/mo). Red: 5 000 GB when you mean 5 TB.
phase 3 — API sketch (3 min)

POST /upload/chunked/init → PUT presigned URLs → POST /complete. GET /download (Range). GET /sync/changes?cursor. POST /files/{id}/share.

Green: explain why chunk-init returns 'existing' vs 'missing'. Red: single POST /upload with 10 GB body.
phase 4 — data model (5 min)

File ← FileVersion ← FileChunk → BlockStore. Materialized path on Folder. SharePermission per (resource, principal, role).

Green: draw the join, explain ref-count on BlockStore. Red: storing chunks inline in the File row.
phase 5 — architecture (10 min)

Client (chunk+hash) → API GW → Upload Service → Dedup → BlockStore (S3). Metadata → Postgres. Sync via Kafka → WebSocket. CDN for hot files.

Green: metadata/blob split, presigned URLs bypass app tier. Red: routing all bytes through the app server.
phase 6 — deep dives (15 min)

Pick 2–3: dedup (content-addressable + refCount), delta sync (rolling hash + changed-chunks push), versioning (CoW). Draw the code path.

Green: verbatim storeChunk pseudocode with refCount++. Red: hand-wavy "we deduplicate".
phase 7 — CAP & failures (5 min)

CP for metadata + refCounts (undercount = data loss). AP for sync + quota (stale is fine, frozen is not). 8 bottlenecks with fixes.

Green: "we split — CP where correctness matters, AP where availability matters". Red: "we chose CP" (globally, without split).
phase 8 — extensions (2 min)

Client-side encryption (kills dedup unless convergent). Global data residency (per-tenant region pinning). Real-time collab editing (use case 14). ML content indexing.

Green: name the trade-off (encryption vs dedup). Red: "we can add anything easily".

Glossary — deep-dive terms

Convergent encryptionencryption key derived from plaintext hash → same plaintext always encrypts to same ciphertext → preserves dedup at the cost of confirming-a-guess attacks
Rolling hasha hash that can be updated in O(1) as a sliding window advances by 1 byte (Rabin fingerprint, Gear hash)
Content-defined chunkingchunk boundaries determined by hash of a rolling window matching a magic pattern, not by fixed offset — resilient to insertions
Presigned URLa time-limited signed URL letting a client PUT / GET S3 objects without app-server bandwidth or credentials
Origin shielda regional CDN cache that absorbs origin fetches so edge PoPs don't all hit S3 directly during a cache-fill
Copy-on-write (CoW)a new version reuses unchanged blocks; only writes new blocks for the changed regions
Delta syncupload/download only the chunks that changed since the client's last sync cursor
Reference countthe number of files pointing at a given block; block is GC'd only when count hits 0
Materialized pathfull folder path stored as a string on each Folder row for O(1) ancestor walks (vs recursive JOINs)
Sync cursoropaque token (server timestamp) telling the server 'I have seen changes up to X' — enables catch-up-on-connect
