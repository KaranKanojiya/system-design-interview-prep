The core loop — DeduplicationService.storeChunk

verbatim · <20 LOC
from service/DeduplicationService.java
/** Store a chunk with deduplication. Returns true if it was a duplicate. */
public boolean storeChunk(FileChunk chunk, byte[] data) {
  if (strategy.isDuplicate(chunk.getHash())) {
    // Chunk already exists — skip storing bytes,
    // but DO increment refCount so we know another file uses it.
    blockStore.storeBlock(chunk.getHash(), data);

    if (strategy instanceof HashBasedDedup hashDedup) {
      hashDedup.recordDuplicate(chunk.getSizeBytes());
    }
    return true;   // was a duplicate
  }

  // New chunk — store bytes and register hash
  blockStore.storeBlock(chunk.getHash(), data);
  strategy.registerHash(chunk.getHash());
  return false;    // was NOT a duplicate
}
from store/InMemoryBlockStore.java — refCount is where the magic happens
public void storeBlock(String hash, byte[] data) {
  if (blocks.containsKey(hash)) {
    // Block already exists — just bump refCount.
    // Same hash = same content, so no need to re-store bytes.
    refCounts.get(hash).incrementAndGet();
  } else {
    blocks.put(hash, data);
    refCounts.put(hash, new AtomicInteger(1));
  }
}

public void deleteBlock(String hash) {
  AtomicInteger refCount = refCounts.get(hash);
  if (refCount == null) return;

  int remaining = refCount.decrementAndGet();
  if (remaining <= 0) {
    // No more references — safe to free bytes.
    blocks.remove(hash);
    refCounts.remove(hash);
  }
  // If remaining > 0, other files still reference this block — keep it.
}
The correctness invariant: a block is deleted only when the last file referencing it is permanently deleted. This is why TrashService calls deleteBlock(hash) per chunk on permanent purge instead of doing bulk clean-up — the refCount arithmetic must be exact.

from strategy/chunking/FixedSizeChunking.java · CHUNK_SIZE = 4 MB
public List<FileChunk> chunk(String fileId, byte[] data) {
  List<FileChunk> chunks = new ArrayList<>();
  int offset = 0, chunkIndex = 0;

  while (offset < data.length) {
    int end = Math.min(offset + CHUNK_SIZE, data.length);
    byte[] chunkData = Arrays.copyOfRange(data, offset, end);

    // SHA-256 hash of the chunk content — content-addressable key
    String hash = sha256(chunkData);

    chunks.add(new FileChunk(
        UUID.randomUUID().toString(), fileId, chunkIndex,
        hash, chunkData.length));

    offset = end;
    chunkIndex++;
  }
  return chunks;
}

Pros: simple, predictable chunk count = ceil(size / 4 MB), deterministic offsets. Great for aligned uploads.
Cons: inserting 1 byte at offset 0 shifts every boundary — 100 MB file → all 25 chunks become new content → dedup benefit ~0 %.

from strategy/chunking/ContentDefinedChunking.java · Gear hash · avg ~4 MB
// Parameters (matching FastCDC-style content-defined chunking)
private static final int WINDOW_SIZE  = 48;               // sliding window
private static final int MIN_CHUNK    = 1 * 1024 * 1024;  // 1 MB
private static final int MAX_CHUNK    = 8 * 1024 * 1024;  // 8 MB
private static final long BOUNDARY_MASK = 0x3FFFFF;       // avg ~4 MB

// Gear table: 256 pre-computed random longs for a fast rolling hash
private static final long[] GEAR_TABLE = new long[256];
static { // deterministic LCG seed for reproducibility
  long seed = 0xABCDEF0123456789L;
  for (int i = 0; i < 256; i++) {
    seed = seed * 6364136223846793005L + 1442695040888963407L;
    GEAR_TABLE[i] = seed;
  }
}

// Inside chunk(): scan bytes with a rolling hash and cut when
// (rollingHash & BOUNDARY_MASK) == 0 — a content-defined boundary.

Pros: insertion invalidates only the chunks near the edit point (usually 1-2), everything else remains dedup-eligible. Dropbox reports it doubles their dedup ratio vs fixed-size.
Cons: more CPU per byte (rolling hash), variable chunk sizes (harder for parallel offset math), MIN/MAX guards required to avoid pathological cases.

Deduplication strategy — swap in AppConfig

Strategy pattern · 2 impls
HashBasedDedup (production)
NoDedup (baseline)
measured savings
from strategy/dedup/HashBasedDedup.java
public class HashBasedDedup implements DeduplicationStrategy {
  private final Set<String> knownHashes = new HashSet<>();
  private int  deduplicatedCount = 0;
  private long savedBytes = 0;

  public boolean isDuplicate(String hash) {
    return knownHashes.contains(hash);
  }

  public void registerHash(String hash) {
    knownHashes.add(hash);
  }

  public void recordDuplicate(long chunkSizeBytes) {
    deduplicatedCount++;
    savedBytes += chunkSizeBytes;
  }
}

In production: the in-memory Set<String> is replaced by a distributed store — Redis (hot set) + Postgres (durable index) + Bloom filter in front for the negative-lookup fast path. At 300 B unique hashes × 64 B = ~20 TB index — manageable but big.

from strategy/dedup/NoDedup.java — the baseline
public class NoDedup implements DeduplicationStrategy {
  public boolean isDuplicate(String hash) { return false; }
  public void registerHash(String hash) { /* no-op */ }
  public int getDeduplicatedCount() { return 0; }
  public long getSavedBytes() { return 0; }
}

Why it exists: the value of dedup only becomes obvious when you turn it off. Swap this in and re-run the upload demo — storage inflates ~1.6× (matches Dropbox's ~40 % dedup savings). Also useful for compliance modes where cross-tenant dedup is disallowed.

Conflict resolution — Strategy pattern

Google Drive vs Dropbox
LastWriterWinsStrategy (Google Drive)
KeepBothStrategy (Dropbox)
trade-off
from strategy/sync/LastWriterWinsStrategy.java
public ConflictResolution resolve(FileMetadata localFile, FileMetadata remoteFile) {
  if (localFile.getUpdatedAt() == null && remoteFile.getUpdatedAt() == null)
    return ConflictResolution.KEEP_REMOTE;   // tie-break: server wins
  if (localFile.getUpdatedAt() == null)  return ConflictResolution.KEEP_REMOTE;
  if (remoteFile.getUpdatedAt() == null) return ConflictResolution.KEEP_LOCAL;

  // Compare timestamps: most recent wins
  if (localFile.getUpdatedAt().isAfter(remoteFile.getUpdatedAt()))
    return ConflictResolution.KEEP_LOCAL;
  else
    return ConflictResolution.KEEP_REMOTE;   // tie → server wins
}

Simple, deterministic. Losing side's changes silently discarded. Google Drive's choice — cleaner folder, but "I edited it on my laptop AND on my phone" produces one lost edit.

from strategy/sync/KeepBothStrategy.java
public ConflictResolution resolve(FileMetadata localFile, FileMetadata remoteFile) {
  // Both sides preserved: create "file_conflict_<user>_<date>.ext"
  return ConflictResolution.KEEP_BOTH;
}

// Downstream: SyncService renames the losing side to
//   "document (alice's conflicted copy 2026-04-26).pdf"
// User sees both files, must merge manually.

Never data loss — but cluttered folders and manual merge. Dropbox's choice. Best for professional-user files (code, docs) where a lost edit is catastrophic.

The right answer in interviews: for a general-purpose product, offer BOTH — LastWriterWins by default (matches user expectation for photos/casual files), KeepBoth for files marked as 'important' or in shared team folders.

      1. FileMetadata meta = metadataService.getFile(fileId)
