A

Problem & requirements

clarify first
functional
  • Upload / download — files up to 50 GB. Small (< 4 MB) = single PUT; large = chunked.
  • Chunked resumable upload — split into 4 MB chunks, upload parallel (up to 4), retry only failed chunks, SHA-256 per chunk.
  • Delta sync across devices — detect local change, upload only changed chunks (Δ), notify other devices via cursor protocol.
  • Versioning — keep last 30 versions; copy-on-write via chunk sharing (unchanged chunks reused between versions).
  • Sharing — files/folders shared with users OR public links; roles Viewer / Editor / Owner; folder perms inherit.
  • Folders — 20-level nesting; materialized path; move / rename / soft-delete recursively.
  • Trash — soft-delete, 30-day recovery, then permanent purge (chunks garbage-collected by ref count = 0).
  • Quota — 15 GB free / 2 TB paid; enforce at upload start; reserve/release on partial upload.
non-functional
  • Upload latency < 5 s for a 10 MB file (chunked + parallel).
  • Download first-byte < 2 s (CDN edge).
  • Sync latency < 10 s cross-device (edit → notify → download Δ).
  • Durability ≥ 99.99 % — S3 offers 11 nines via erasure coding across 3 AZs.
  • Availability 99.9 % — reads / writes survive AZ loss.
  • Throughput 100 M uploads/day (~1 150/s avg, ~3.5 K/s peak); 300 M downloads/day.
  • Storage efficiency 30–50 % savings via block-level dedup.
  • Consistency — strong for file tree/metadata (CP); eventual for sync notifications (AP).

The dedup insight: Dropbox's blog revealed ~75 % storage savings at their scale — the same "chunk 0" of every fresh Mac OS install, every Node.js node_modules, every Chrome download, every meme image lives in ONE blob referenced N times. At 2.5 EB × $0.023/GB S3 = ~$60 M/month, cutting 40 % is $24 M/month saved. This one design choice pays for the entire eng team.
Separate metadata from blobs: file records (250 B rows @ 500 B ≈ 125 TB) live in Postgres (indexed, transactional, small rows). Blobs (2.5 EB) live in object storage (S3/GCS — cheap, immutable, presigned URLs bypass the app). Very different scaling curves — never mix them in one system.

Data model

7 core tables · the split matters
Metadata side (Postgres — 125 TB)
File                     // 250 B rows · shard by userId
  fileId, userId, folderId
  name, size, mimeType
  currentVersion, checksum
  isDeleted, deletedAt

Folder                   // 50 B rows · shard by userId
  folderId, userId, parentId
  name, path              // materialized path
  depth                   // 0–20 max
  isShared, isDeleted

FileVersion              // 750 B rows · shard by fileId
  versionId, fileId
  versionNum              // 1, 2, 3 …
  size, checksum
  modifiedBy, changeNote
  createdAt

FileChunk                // version ↔ blockHash mapping
  chunkId, versionId
  chunkIndex              // position in file
  blockHash               // FK → BlockStore
  size
Blob side + shared (S3 · Redis)
BlockStore               // 300 B unique blocks in S3
  blockHash (SHA-256)     // content-addressable key
  storageUrl              // s3://bucket/{prefix}/{hash}
  size
  referenceCount          // # of FileChunk rows
  createdAt

ShareLink / SharePermission
  shareId
  resourceId, resourceType (FILE|FOLDER)
  sharedByUser, sharedWithUser
  role (VIEWER|EDITOR|OWNER)
  linkUrl, passwordHash, expiresAt

SyncCursor               // per-device sync position
  cursorId, userId, deviceId
  cursorToken             // opaque server timestamp
  lastSyncAt

StorageQuota
  userId, totalLimit, usedStorage
  planType (FREE|BASIC|PREMIUM|ENTERPRISE)
The critical relationship: File → FileVersion → FileChunk → blockHash → BlockStore. FileChunk rows are the join table that lets many versions AND many users share the SAME blockHash. Deleting a version decrements referenceCount; hitting zero triggers S3 delete.
F

Key design choices (deep-dived on canvas 3)

defend these
the split

Metadata (Postgres) vs blob (S3)

Different scaling curves — 125 TB of small indexed rows vs 1.5 EB of immutable bytes. Never one system for both. → canvas 3 · storage split

dedup

Content-addressable blocks

Key = SHA-256(content). Same file → same key → stored once. ~40 % storage saved. → canvas 3 · dedup math

chunking

Fixed 4 MB vs content-defined (Rabin)

Fixed is simple (Google Drive); Rabin fingerprint tolerates insertions without shifting every boundary (Dropbox). Strategy pattern — swappable.

upload

Presigned URLs — direct to S3

Client uploads bypass our app servers. Zero bandwidth cost, zero CPU cost. S3 verifies signature + checksum.

sync

Cursor protocol + delta chunks

Opaque server timestamp; client polls or long-polls. On modify, only changed chunks travel — 20 MB edit ⇒ ~8 MB uploaded.

versioning

Copy-on-write via chunk sharing

New version = new FileChunk rows, most pointing at OLD blockHashes. Save cost ≈ delta, not full file. Rollback = one int swap.

Glossary — one-liners

terms used above
Content-addressable storagestorage keyed by hash of the content itself
Chunkfixed-size (4 MB) piece of a file, hashed independently
Blockthe on-disk representation of a unique chunk (one per hash)
Deduplicationstore each unique block once regardless of how many files reference it
Reference counthow many FileChunk rows point to this block; 0 = garbage-collect
Presigned URLtime-limited signed S3 URL letting the client PUT/GET without app-server bandwidth
Delta syncupload/download only chunks that changed since last sync
Sync cursoropaque server-time token telling 'I have seen events up to X'
Rabin fingerprintrolling hash of a sliding window; used to find content-defined chunk boundaries
Copy-on-write versioninga new version reuses unchanged blocks; only writes new blocks for changes
Materialized pathfull folder path stored on each Folder row for O(1) ancestor walks
Last-writer-winson sync conflict, keep the version with the newest timestamp (Google Drive)
