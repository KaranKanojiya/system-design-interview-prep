A

Problem & requirements

clarify first

A distributed cache stores key-value data across many in-memory nodes to serve sub-millisecond reads, shield the database from load, and scale horizontally. It sits between the application and the database; the database stays the source of truth.

functional
  • Put / Get / Delete a key-value pair; optional per-key TTL (expired keys never returned).
  • Eviction when a node hits its memory limit — LRU, LFU, or random.
  • Bulk multi-get / multi-put; lightweight exists probe; atomic CAS.
  • Spread data across nodes and rebalance as nodes join / leave.
non-functional
  • Read latency < 1 ms p99 · write latency < 2 ms p99 — 10–100× faster than the DB.
  • Availability 99.99% — a cache outage cascades load onto the DB (→ AP system).
  • Hit rate > 95% · even spread < 10% variance across nodes.
  • Survive a single-node failure with auto-failover; scale linearly by adding nodes.

Derivation: 200M keys × (64 B key + 1 KB value + ~56 B metadata) ≈ 230 GB; replication factor 2 → ~460 GB; 5 nodes × 64 GB = 320 GB per replica set fits comfortably. Metadata (TTL, LRU pointers, version) ≈ 56 B / ~1,144 B ≈ 4.9% overhead. By Pareto, 20% of keys serve 80% of traffic; an L1 Caffeine cache in the app absorbs 50–80% of reads before Redis. → full math on canvas 3 · Estimation

Reality check: production caches speak a compact binary protocol (Redis RESP / Memcached binary) over a single TCP command, not HTTP. This REST surface is for illustration — the latency budget (< 1 ms) would not survive HTTP parsing per request.

F

Key design choices (deep-dived on canvas 3)

defend these
partitioning

Consistent hashing + 150 vnodes

Only K/N keys move when a node joins/leaves (vs ~80% for hash % N); vnodes keep spread within ~2%. → canvas 2 · LLD

eviction

LRU + TTL (default)

LRU handles memory pressure, TTL handles staleness (Redis allkeys-lru). LFU for stable hot keys. → canvas 3

consistency

AP · async replication

A cache must never block on durability — DB is authoritative, so losing the last few writes on failover is fine. → canvas 3

layered caching

L1 Caffeine → Redis → CDN

Each tier is faster and closer; L1 absorbs 50–80% of reads before a Redis round-trip.

write pattern

Cache-aside + invalidate

On write, update DB then delete the key (not update) — deleting avoids concurrent-write races leaving stale data.

resilience

Stampede & hot keys

Thundering herd on expiry → request coalescing / logical TTL; a viral key → L1 cache + replica reads. → canvas 3

Glossary — one-liners

terms used above
Consistent hashingkeys & nodes on a ring; a key goes to the next node clockwise, so adding/removing a node moves only K/N keys
Virtual node (vnode)many ring positions per physical node (150) so load spreads evenly
Cache-asideapp checks cache first; on miss reads the DB and backfills the cache
LRUevict the least-recently-used entry — HashMap + doubly-linked list, O(1)
LFUevict the least-frequently-used entry — frequency buckets + min-freq pointer
TTLper-key time-to-live; expired keys are lazily (on read) + actively (sampling) removed
AP (CAP)favour Availability + Partition-tolerance; a cache stays up even if slightly stale
Async replicationmaster acks before the replica confirms — fast, risks losing the last few writes
CAScompare-and-swap; write only if the current value matches the expected one
Hit ratefraction of reads served from cache; below ~95% the cache earns its keep poorly
Thundering herdmany requests stampede the DB when a hot key expires at once
L1 cachein-process cache (Caffeine) inside the app, in front of the distributed cache
