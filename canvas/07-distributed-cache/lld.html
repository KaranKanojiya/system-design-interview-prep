B

The two core algorithms — O(1) LRU & the hash ring

LRUEvictionStrategy · ConsistentHashStrategy
LRU in O(1) — HashMap + doubly-linked list
// map: key → Node   ·   sentinel head/tail
public String evict() {          // least-recently-used
  Node lru = tail.prev;          // node next to tail
  if (lru == head) return null;  // empty list
  removeNode(lru);               // unlink  — O(1)
  map.remove(lru.key);
  return lru.key;
}
private void removeNode(Node n){
  n.prev.next = n.next;          // no null checks —
  n.next.prev = n.prev;          //  sentinels absorb edges
}
private void addAfterHead(Node n){ // = most-recently-used
  n.next = head.next; n.prev = head;
  head.next.prev = n; head.next = n;
}

Every onGet/onPut does removeNode + addAfterHead (move-to-front). The node touched longest ago sinks to tail.prev — so eviction is a single unlink. Sentinels mean zero edge-case branches.

worked example — route a key on the ring
// ConsistentHashStrategy: 3 nodes × 150 vnodes
hash(key) = MD5(key)[0..3] as int   // uniform

getNode("user:42"):
  h = hash("user:42")      = 1_732_500_900
  e = ring.ceilingEntry(h)          // first vnode ≥ h
        → VirtualNode[hash=1_749_003_11.., node-2#87]
  if (e == null) e = ring.firstEntry()  // wrap around
  return e.getValue().getPhysicalNode()  // → node-2

// remove node-2  → only its ~1/N keys move,
// they slide clockwise to the next vnode's node.

ceilingEntry is the clockwise walk in O(log n); firstEntry closes the ring. 150 virtual nodes per server keep each server's slice of the ring even, so no single node becomes a hotspot.

Why O(1) matters & why a ring beats mod. LRU's HashMap + DLL keeps get / put / evict all constant-time — a priority-queue LRU would be O(log n) per touch on the hot path. Consistent hashing replaces key % N, where changing N remaps (N−1)/N of all keys (a stampede that hammers the backing store), with a ring where adding or removing a node moves only ~1/N keys. Virtual nodes turn a lumpy 3-point ring into a smooth 450-point one. LFU reaches the same O(1) with frequency buckets + a tracked minFreq instead of a linked list.

Pluggable strategies — Strategy pattern ×2

swap the algorithm, not the service

LRUEvictionStrategy — evicts the key untouched for the longest. getEvictionPolicyName() = "LRU" · the AppConfig default

  • Structures: HashMap<String, Node> + custom doubly-linked list with sentinel head/tail.
  • Cost: onGet / onPut / evict / remove all O(1) — hand-built, not LinkedHashMap, to expose the internals and control the node references.
  • Best for: temporal locality — recently used data is likely to be needed again (the common case).

LFUEvictionStrategy — evicts the least-frequently accessed key. getEvictionPolicyName() = "LFU"

  • Structures: keyToFreq + freqToKeys: Map<Integer, LinkedHashSet<String>> (frequency buckets) + a tracked minFreq.
  • Tie-break: LinkedHashSet preserves insertion order, so at equal frequency the oldest key goes first (FIFO) — iterator().next().
  • Best for: frequency skew — a few hot keys should stick; new keys start at freq 1, so a burst can't evict a proven-popular key.

TTLEvictionStrategy — evicts by expiry time. getEvictionPolicyName() = "TTL"

  • Structures: TreeMap<LocalDateTime, Set<String>> expirationIndex (sorted by expiry) + a keyToExpiration reverse index.
  • Two modes: lazy — isExpired() checked on every get; active — a cleanup pass drains expirationIndex. evict() first frees expired keys, then the earliest-expiring.
  • Best for: time-sensitive data — sessions, tokens, rate-limit counters. Exactly how Redis expiration works.

The second Strategy axis — HashingStrategy.getNode(key, nodes) decides which node owns a key, independent of eviction:

  • ConsistentHashStrategy: TreeMap<Integer, VirtualNode> ring, 150 vnodes/node, MD5 hashing → ~1/N keys move on topology change. The production choice.
  • ModHashStrategy: hash(key) % nodeCount — an anti-pattern shipped for contrast: one node change remaps (N−1)/N of all keys.

The pattern: CacheService holds one EvictionStrategy field and never branches on policy — it just calls strategy.onGet(key) / strategy.evict(). NodeAwareCacheStore holds one HashingStrategy. Adding an ARC or 2Q eviction policy, or a rendezvous-hash router, is a new class + one line in AppConfig, with zero changes to the service, store, or controller (Open-Closed Principle). Strategy is used twice — independently variable axes.
D

Data model detail

CacheEntry · CacheNode · VirtualNode · CacheConfig
CacheEntry — the value wrapper (Builder)
key            String   // KEY
value          Object
createdAt      LocalDateTime
lastAccessedAt LocalDateTime  // mutable — touch()
expiresAt      LocalDateTime  // null = never
frequency      int            // LFU signal, ++ on touch
sizeBytes      long           // memory estimate

Immutable except lastAccessedAt / frequency, both bumped by touch() on every hit. Why a wrapper? LRU needs lastAccessedAt, LFU needs frequency, TTL needs expiresAt — one metadata-rich entry lets the store stay policy-agnostic. Built via CacheEntry.builder().key(..).value(..).ttlSeconds(..).build() so 7 fields never get swapped.

Topology — CacheNode · VirtualNode · CacheConfig
// CacheNode — a physical server
nodeId  String   // "node-1"
host    String   port int
status  NodeStatus  // UP · DOWN · DRAINING

// VirtualNode — one ring point (150 per node)
physicalNode  CacheNode
replicaIndex  int    // 0..149
hash          int    // ring position

// CacheConfig — one immutable config (Builder)
maxSize · defaultTtlSeconds · evictionPolicy
numVirtualNodes(150) · replicationFactor(3)

The ring is a TreeMap<Integer, VirtualNode>: 3 nodes × 150 vnodes = 450 points for smooth distribution. CacheConfig is built once by AppConfig and shared read-only across every component (conceptual Singleton) — no magic numbers, no drift.

Metadata drives eviction. The store keeps only String → CacheEntry; each eviction strategy keeps its own tracking structure (DLL / frequency buckets / expiry TreeMap) keyed by the same String key. That separation is why CacheStore never changes when you swap policies — the entry carries the signals, the strategy owns the index.
E

Request handling sequence

which class does what, in order

get(key)  →  hit, miss, or lazy-expire

CacheController.handleGet(key)
  └─ CacheService.get(key)
       1  entry = store.get(key)          // ConcurrentHashMap / routed
            null? → stats.recordMiss() → return null   // 404
       2  entry.isExpired()?              // lazy TTL
            yes → store.remove(key)
                  eviction.remove(key)
                  stats.recordMiss() → return null     // 404
       3  entry.touch()                   // lastAccessedAt, frequency++
       4  eviction.onGet(key)             // LRU→head · LFU→freq+1
       5  stats.recordHit()
       6  return entry.getValue()
  └─ [200 OK]

Lazy expiration is Redis's trick: don't scan for expired keys, just evict them the moment they're touched. The eviction strategy is notified after the value is confirmed valid.

put(key, value, ttl)  →  insert with capacity eviction

CacheController.handlePut(key, value, ttlSeconds)
  └─ CacheService.put(key, value, ttlSeconds)
       1  store.contains(key)?            // update vs insert
            no + store.size() >= maxSize → evictOne():
                 victim = eviction.evict()   // policy picks
                 store.remove(victim)
                 stats.recordEviction()
       2  CacheEntry.builder().key(key).value(value)
              .ttlSeconds(ttl > 0 ? ttl : config default).build()
       3  store.put(key, entry)
       4  eviction.onPut(key, entry)      // register in index
       5  stats.recordPut()
  └─ [201 Created]

Capacity is checked only for a genuine insert — updating an existing key never evicts. The victim is chosen by whichever EvictionStrategy is wired; the service never knows which.

distributed put  →  routing through the Proxy

CacheService.put(...)  → store is a NodeAwareCacheStore
  └─ NodeAwareCacheStore.put(key, entry)          // «Proxy»
       1  target = hashingStrategy.getNode(key, nodes)
             ConsistentHashStrategy:
               h = hash(key)                       // MD5 → int
               vnode = ring.ceilingEntry(h)        // or firstEntry()
               target = vnode.getPhysicalNode()    // e.g. node-2
       2  nodeStores.get(target.getNodeId())       // its InMemoryCacheStore
             .put(key, entry)
       3  target.incrementAssignedKeys()           // per-node stats
       (opt) ReplicationService.replicateToFollowers(key, entry, ...)
  └─ caller sees a single cache — topology hidden

The Proxy implements CacheStore, so CacheService is identical in single-node and distributed mode — only what AppConfig wires in changes.

F

Design patterns used

GoF-categorized · 8 patterns
Creational
  • Builder — CacheEntry.builder() & CacheConfig.builder(). Readable construction of 7-field objects; can't swap createdAt and lastAccessedAt.
  • Factory — AppConfig is the composition root; a switch on EvictionPolicy creates the strategy. The only class that says new.
  • Singleton (conceptual) — one immutable CacheConfig shared by every component; no duplicated magic numbers.
Behavioral
  • Strategy ×2 — EvictionStrategy (LRU/LFU/TTL) and HashingStrategy (Consistent/Mod). Two independently variable axes — the centrepiece.
  • Observer — CacheStats records hit/miss/eviction/put via AtomicLong, keeping metrics out of the service.
Structural
  • Facade — CacheService hides store + eviction + stats + TTL behind get / put / delete.
  • Proxy — NodeAwareCacheStore looks like a CacheStore but routes each op to the right node via consistent hashing.
  • Repository — CacheStore / CacheRepository decouple logic from storage; swap in Redis with no service change.
Why they cluster: Strategy + Factory + Facade + Repository together deliver the Open-Closed Principle — new eviction policies, hashing algorithms, and storage backends are additions, never edits. Observer keeps metrics orthogonal; Proxy makes the jump from one node to many invisible to the Facade; Builder keeps entities immutable and thread-safe; the ConcurrentHashMap store and per-strategy ReentrantLock keep the hot path lock-light. → CAP, replication & hot-key trade-offs on canvas 3
