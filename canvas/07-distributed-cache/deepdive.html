A

Scaling strategy

how to shard & replicate the cache
app tier · L1

Stateless + local Caffeine

App servers are stateless behind the LB. Each carries an in-process L1 (Caffeine / ConcurrentHashMap, ~10K entries, 10–30 s TTL) that absorbs 50–80% of hot-key reads with no network hop (~100 ns vs ~1 ms).

L2 · horizontal

Add cache nodes

Grow the distributed L2 past one node's RAM by adding cache nodes. Keys are spread by a hashing strategy so any app server routes a key to the same node. A 32 GB node at ~600 B/entry holds ~40 M entries.

replicas · HA

Async primary → replica

Each master has ≥1 replica fed by async replication (~1 ms writes). On master failure the replica promotes (Sentinel / Cluster). Replicas also serve reads to shave hot-key load off the primary.

key distribution — pick a partition strategy

Modulo hashing

Route each key by hash(key) % N where N is the node count. Trivial to reason about and evenly spread while N is fixed.

node = hash(key) % N   // fine — until N changes
verdict — avoid at scale
  • Reshard storm: add/remove one node and % N changes for almost every key.
  • 3→4 nodes remaps ~75% of keys; 99→100 remaps ~99% — a cluster-wide miss storm that stampedes the DB.
  • Only safe for a fixed-size, never-resized cluster.

Consistent hashing ← chosen

Nodes and keys map onto a hash ring (a TreeMap<Long,Node>). To place a key, hash it and walk clockwise to the first node. Adding/removing a node only remaps the keys in that node's arc.

// only ~1/N keys move when a node joins/leaves
node = ring.ceilingEntry( MD5(key) )
       ?: ring.firstEntry()   // wrap around
verdict
  • Elastic: 3→4 nodes moves only ~25% of keys (K/N) — not 75%.
  • Virtual nodes (~150 per physical) smooth the ring: variance drops from ~40% at 3 vnodes to ~5% at 150.
  • MD5, not hashCode() — uniform distribution even for similar node IDs.
  • Same key → same node also gives natural read-your-writes.

Redis Cluster hash slots

Redis fixes the ring at 16384 slots: CRC16(key) % 16384 → a slot, and slots are assigned to masters. Clients cache the slot→node map and follow -MOVED redirects when topology changes.

slot = CRC16(key) % 16384   // e.g. slot 7629 → Master B
verdict — the production form
  • A fixed slot count makes rebalancing = move slots, not rehash keys.
  • Automatic failover: a replica promotes on master loss.
  • Effectively consistent hashing with a fixed 16384-point ring — the model to name in an interview.
Eviction under memory pressure: cap each node at ~75% of RAM, then evict by policy — LRU (temporal locality: sessions, recent views), LFU (frequency locality: hot config, popular items), or volatile-TTL. Watch eviction rate > 5% and hit rate < 80% as the "cache too small" signals.
B

Caching deep-dive

100 ns vs 10 ms lives here
cache-aside — the default read path
GET key from L1 (Caffeine)
  ├─ HIT  → return                      // ~100 ns, no network
  └─ MISS → GET from L2 (Redis)
             ├─ HIT  → promote to L1 → return   // ~1 ms
             └─ MISS → read DB → SETEX L2 → L1   // ~10 ms, self-heals

The application owns cache + DB independently; the cache never talks to the DB. Cache failure degrades gracefully to a DB read. First access to a key is a miss that backfills every layer.

write patterns — pick per data shape
cache-aside  write DB → invalidate cache   // default; avoids races
write-through write cache + DB sync         // strong, 2× latency
write-behind  write cache, async flush DB    // fastest, data-loss risk

On update we invalidate (delete) rather than rewrite the cache — deleting sidesteps the write-write race. Write-through when consistency matters and reads dominate; write-behind only when write latency must be near-zero and loss is tolerable.

hot-key problem

L1 + key replication

A celebrity key at 100K req/s saturates its one node while others idle. Per-server L1 absorbs the spike; for extreme cases replicate the key to all nodes and read a random one, or shard the key with a random suffix.

Caffeine.newBuilder()
  .maximumSize(10_000)
  .expireAfterWrite(10, SECONDS);
thundering herd

Singleflight lock

When a hot key expires, hundreds of misses fire identical DB queries. First request grabs a per-key lock (or Redis SETNX), fetches once, backfills; the rest wait and re-read the cache.

// only one DB call per expiry
ok = redis.setnx("lock:"+key, 1, EX 10)
  ok  → load DB, put cache, del lock
  !ok → sleep 50ms, re-GET cache
cache warming

Preload top keys

A fresh/empty cluster sends 100% traffic to the DB. Before cutting over, bulk-load the top ~10K keys by access count, then shift traffic gradually (or shadow reads to the new cluster).

SELECT key FROM hot_keys
ORDER BY access_count DESC
LIMIT 10000;   // MSET into L2
Multi-layer: L1 Caffeine (~100 ns) → L2 Redis Cluster (~1 ms) → Database (~10 ms). Each layer catches a tier of traffic; keep L1 TTL short (10–30 s) so cross-server staleness is bounded, or push Redis Pub/Sub invalidations to L1. → full layering on canvas 1 · HLD

Bottlenecks & solutions

click a card to open

Thundering herd (cache stampede)

Impact: a popular key expires and hundreds of concurrent misses fire identical queries at the DB in the same instant — timeouts and cascading failure (Facebook's 2010 Memcached outage).

Fix: per-key mutex / singleflight so only one thread loads (others wait then read cache); Redis SETNX lease for cluster-wide dedupe; stale-while-revalidate; probabilistic early expiration; TTL jitter to desynchronize expiry.

Hot key (celebrity key)

Impact: a single trending key routes 100K+ req/s to one node while its neighbours idle — the node hits 100% CPU and becomes the bottleneck.

Fix: per-server L1 Caffeine (10–30 s TTL) absorbs most reads with zero network hop; replicate the hot key to all nodes and read a random one; or key-split with a random suffix (key:0..9) at the cost of write amplification. Detect proactively by counting per-key request rate.

Modulo-hash reshard storm

Impact: with hash(key) % N, adding one node remaps ~75% of keys (3→4) — a near-total miss storm that dumps the whole cache's traffic onto the DB.

Fix: consistent hashing with ~150 virtual nodes — only ~1/N keys move on rebalance. Redis Cluster's fixed 16384 slots achieve the same by migrating slots rather than rehashing keys.

Cache node failure

Impact: a node dies; its keys are suddenly unreachable and every request for them misses.

Fix: health check removes the node from the ring; its keys reroute to the next node clockwise (only K/N affected) and self-heal via cache-aside; an async replica serves reads during the transition and promotes to master. No data loss — the DB is the source of truth.

Split brain on partition

Impact: a partition isolates a master; a replica is promoted, so two masters accept conflicting writes. When it heals, the old master's ~30 s of writes are lost — the AP trade-off.

Fix: accept it (cache is not source of truth) and let TTL expiration converge both sides to the DB value. To lean toward CP for critical keys: min-replicas-to-write 1 and min-replicas-max-lag 10 so a master refuses writes without healthy replicas.

Cold-start stampede after deploy/restart

Impact: a fresh cluster (or a recovered node with an empty cache) sends 100% of traffic to the DB — the DB melts before hit rate recovers.

Fix: pre-warm the top ~10K keys from the DB before cutover; gradual/blue-green traffic shift (10% → 100%) or shadow reads to warm silently; Redis RDB+AOF restores prior state on restart.

Memory pressure & eviction thrash

Impact: the working set exceeds RAM; eviction rate climbs, hit rate falls, and the cache degrades into an expensive proxy for the DB.

Fix: cap maxmemory at ~75% of RAM; choose the right policy (LRU/LFU/volatile-TTL); size for ~2× raw data on JVM caches; alert when eviction > 5% or hit rate < 80% — then scale nodes or trim TTLs. LFU pollution → decay/windowed LFU.

Stale L1 across servers

Impact: server 1 updates L2, but server 2's in-process L1 still holds the old value until its TTL expires — users hit different app servers and see different data.

Fix: keep L1 TTL short (5–30 s) so staleness is bounded; or broadcast a Redis Pub/Sub invalidate:key event that each server applies to its L1. Never use L1 for strong-consistency data.

D

CAP & consistency — why AP

stale is annoying; down is catastrophic
the choice

P is mandatory in any distributed deployment, so the real decision is A vs C during a partition. A cache is not the source of truth — the DB is. Serving a slightly stale value for a few seconds is an inconvenience; refusing to serve causes latency spikes and a DB stampede. So we pick AP.

  • AP: both sides of a partition keep serving; stale reads over errors.
  • PACELC → PA/EL: partition → Availability; else → Latency. Fast reads always.
  • TTL is free conflict resolution: after a partition heals, conflicting entries just expire and the next miss refetches the DB value — no vector clocks needed.
tunable consistency & convergence
// default: async replication (AP, ~1 ms)
jedis.set("user:1", v);

// WAIT moves toward CP for critical keys
jedis.set("user:1", v);
n = jedis.wait(1, 100);   // ≥1 replica acked, 100 ms cap

// quorum overlap: W + R > N  (2 + 2 > 3)

Async replication is the AP default; Redis WAIT gives semi-sync (read-your-writes) when a key matters. Consistent hashing routes the same key to the same node, which naturally provides read-your-writes and monotonic reads for a session.

When to break AP: distributed locks (use RedLock / ZooKeeper / etcd — an AP cache can grant the same lock to two clients during a partition), session tokens after logout, and inventory / financial counts (read the DB, never the cache). For those, use a CP store or bypass the cache.

phase-by-phase
  • P1 Clarify (2–3): small objects vs blobs (changes eviction & serialization), reads/writes per sec, staleness tolerance, persistence?, single vs multi-region, which eviction policies.
  • P2 Architecture (5–7): three layers — L1 local (Caffeine) + L2 distributed (Redis, consistent hashing) + DB source of truth; async replication. Justify L1: absorbs 50–80% of hot reads, ~1 ms → ~100 ns.
  • P3 Deep dive (8–10 · CORE): LRU = HashMap + doubly-linked list, O(1) everything; LFU = frequency buckets + minFreq, O(1); consistent hashing ring with ~150 vnodes, "only K/N keys move".
…and finish strong
  • P4 Scaling & edges (5–7): thundering herd → per-key lock; hot key → L1 / replicate / split; node failure → reroute + replica; cold start → pre-warm + jittered TTL.
  • P5 Code (5–8): Strategy (eviction / distribution / replication), Facade (CacheService.get/put), Builder (CacheEntry), Repository (CacheStore) — interface-driven, ConcurrentHashMap + AtomicLong for thread safety.
  • P6 Trade-offs (3–5): LRU vs LFU (temporal vs frequency locality), AP vs CP ("stale is fine, downtime is not"), Redis vs Memcached, cache-aside as default.
