A

Problem & requirements

clarify first

A rate limiter controls how many requests a client may send within a time window — the front-line defense against abuse, runaway scripts, noisy tenants, and cascading overload. It runs as middleware in front of every service, not as a standalone REST product.

functional
  • Enforce X requests per Y window per key — key = user ID, IP, API endpoint, or composite (user+endpoint).
  • Return HTTP 429 Too Many Requests with Retry-After when a limit is exceeded.
  • Allow-list (VIPs bypass) & deny-list (always reject); configurable rules per endpoint & per tenant.
  • Multiple algorithms selectable per rule; Admin CRUD for rules with hot-reload.
non-functional
  • Latency < 5 ms overhead per request — it sits on every hot path.
  • Availability 99.99% — a broken limiter blocks (or floods) the whole platform.
  • Scale 10M+ req/s; consistency eventual — brief over-count < blocking legit users.
  • Fail-open if Redis is down; hot-reload rules without redeploy.

Derivation: every request = 1 check → 10M ops/s. A Redis node does ~150K ops/s, so pure-Redis needs ~67 nodes. Serve the hot 80% from a local counter/cache → only 2M/s hit Redis → ~14 nodes. ~50M active client-keys × ~100 B (key + counter + TTL) ≈ 5 GB (~15 GB at 3× replication). Rules are tiny: 10K rules × 1 KB ≈ 10 MB — fits any DB. → full math on canvas 3 · Estimation

API design

middleware, not a service

The limiter is invoked internally on every request; it also exposes an Admin CRUD for rules. Client-facing, it only adds response headers (and 429 on reject).

Endpoint / callPurposeResponse
isAllowed(clientId, endpoint, ts)internal hot-path check (called per request)RateLimitResult { allowed, remaining, retryAfterMs, limit, resetAtMs }
POST /admin/rate-limitscreate a rule201 + rule id
GET /admin/rate-limits[/{id}]list / fetch rules200 + rule(s)
PUT /admin/rate-limits/{id}update a rule (triggers hot-reload)200
DELETE /admin/rate-limits/{id}delete a rule204 No Content
Response headers (added to every proxied response): X-RateLimit-Limit · X-RateLimit-Remaining · X-RateLimit-Reset — plus Retry-After on a 429.
E

Data model

tiny rules · ephemeral counters
RateLimitRule (Postgres → local cache)
id             VARCHAR     // rule id (defaults to key)
key            VARCHAR     // user_id | ip | endpoint | composite
max_requests   INT         // e.g. 100
window_size_ms BIGINT      // e.g. 60000
algorithm      ENUM        // TOKEN_BUCKET, SLIDING_WINDOW_COUNTER…
burst_capacity INT         // defaults to max_requests
enabled        BOOLEAN

Matches RateLimitRule (Builder pattern) in src. ~10K rows, ~10 MB — bulk-loaded on startup, cached per node.

Redis counter (ephemeral, per key)
// key = rl:{clientId}:{endpoint}:{window}
rl:user-123:/api/orders:202607281430
   value = 47            // INCR per request
   TTL   = window_size   // EXPIRE — self-cleaning

// Sliding Window Log variant → Sorted Set
ZADD  rl:user-123  <ts>  <uuid>
ZREMRANGEBYSCORE  rl:user-123  0  <win_start>

Counters never persist — EXPIRE reclaims them at window end. ~50M keys × ~100 B ≈ 5 GB.

F

Key design choices (deep-dived on canvas 3)

defend these
algorithm

Sliding Window Counter

Weighted average of two fixed windows — ~99.97% accurate, O(1) memory, no boundary spike. Token Bucket is the other default (natural bursts). All 5 in canvas 2 · LLD.

distributed counting

Redis + Lua (atomic)

One shared counter per key; a Lua script does check-and-increment atomically to kill the read-then-write race across nodes. → canvas 3

failure mode

AP · fail-open

Redis down → allow rather than block everyone; circuit-breaker + local fallback + alerting. Brief over-count beats a platform outage.

Glossary — one-liners

terms used above
Token Bucketbucket of tokens refilled at rate R; allows bursts up to capacity B
Sliding Window Counterweighted blend of current + previous window counts; O(1), ~99.97% accurate
Fixed Windowcounter per time bucket; simple but allows a 2× spike at the boundary
Lua scriptRedis-side code that runs atomically — no interleaving between read and write
Composite keyrate-limit key combining fields, e.g. userId + endpoint
Fail-openif the limiter can't check, allow the request (vs fail-closed = deny all)
429HTTP "Too Many Requests" — returned with a Retry-After header
AP (CAP)favour Availability + Partition-tolerance; counters are eventually consistent
Read-then-write racetwo nodes both read 99, both allow → count hits 101 over the limit
Hot-reloadapply new rules live via Pub/Sub invalidation — no redeploy
