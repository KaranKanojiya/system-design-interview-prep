A

Scaling strategy

where the counters live & how they shard
app tier

Stateless middleware

The rate-limit check is a filter in front of business logic — no local state, so any app node serves any request. Auto-scale behind the LB; correctness never depends on which node a client lands on because the counter is shared in Redis.

counter tier

Redis Cluster hash-slots

The rate-limit key (e.g. user:123:POST:/api/orders) is hashed to one of 16,384 slots so the same key always lands on the same shard. Single-threaded per shard → atomic INCR/Lua, no cross-node coordination.

rules tier

Read replicas off the hot path

Rules are read thousands/sec but written a few times a day. Serve reads from a local cache; point the admin CRUD API at the primary and let replicas absorb any reporting queries. The hot path never touches the DB.

counter distribution — pick how nodes share the count

Centralized Redis ← chosen

Every app node increments the same key on the same shard. Redis is single source of truth; atomic INCR (or a Lua script) means no race, regardless of how the LB spreads traffic.

INCR ratelimit:{key}:{window}   // atomic, sub-ms
shard = HASH_SLOT(key)             // same key → same shard
verdict
  • Exact global count — works with any LB strategy, no client can game it.
  • +0.3–1 ms per check over a local network — negligible vs 50–500 ms business logic.
  • Redis becomes a critical dependency → Sentinel/Cluster for HA + fail-open in the app.

Local counter with periodic sync

Each node counts in memory and flushes to a global store every ~1 s. Fastest possible check (no network hop), but between syncs nodes disagree.

Node A local=30 ─sync 1s→ Redis total=90
Node B local=25 ─sync 1s→ Redis total=90   // drift between flushes
verdict — approximate only
  • Over-limit drift ≈ nodes × sync_interval × rate before nodes converge.
  • Good for coarse edge/DDoS shaping where approximate is fine.
  • Also the shape of the fail-open fallback: a degraded local bucket when Redis is unreachable.

Sticky sessions (route client → node)

The LB pins each client to one node, which tracks only "its" clients in local memory. No shared counter needed.

client ──hash──▶ always Node A   // local memory, exact
verdict — avoid at scale
  • Uneven load — a hot client saturates its pinned node while others idle.
  • Failover loses counters — a node crash resets every client it owned.
  • Breaks when one client rotates across many API keys / IPs.
Multi-region: a global Redis (e.g. ElastiCache Global Datastore) is simplest but adds cross-region latency; the practical choice is per-region limits — give each region a fraction of the global cap (3 regions → 33% each). Global fairness costs coordination latency a hot path can't afford.
B

Caching deep-dive

what to cache — and what NOT to
rules — DO cache locally
check(ctx, rule):
  rule = ruleCache.get(key)   // ConcurrentHashMap, ~100 ns
    ├─ HIT + fresh → use it
    └─ MISS/expired → DB read → cache (TTL 30–60 s)

Rules change a few times a day, so per-request DB reads are pure waste. Local map lookup is nanoseconds; worst case an admin change is stale for one TTL. RuleRepository behind an in-memory cache does this.

counters — do NOT cache locally
counter lives ONLY in Redis
  INCR / Lua → shared source of truth
  // local counter = each node counts alone
  // 4 nodes × limit 100 → user gets 400

The whole point of rate limiting is accurate shared counting. A local counter cache means every node has its own view and the global limit is silently multiplied by the node count.

Redis IS the cache

No DB behind counters

A common misconception is "cache the counters." Redis is already an in-memory store — counters live in the fastest possible place. They're ephemeral: if Redis restarts, counters reset and users briefly get one extra window, which is acceptable.

EXPIRE key {window}   // auto-cleanup, no GC job
// AOF persistence optional; loss = brief over-limit
rule hot-reload

TTL + Pub/Sub invalidation

TTL alone means up to 30 s stale. For urgent changes (blocking an abuser) publish an invalidate event over Redis Pub/Sub so every node drops that key within milliseconds. Best of both: TTL floor + event-driven precision.

admin update → publish {invalidate, key}
  → all nodes ruleCache.invalidate(key)
pipelining

Batch multi-rule checks

A request often checks several rules — global + per-user + per-endpoint. Pipeline them into one round trip instead of N, so 3 checks cost ~1 ms instead of ~3 ms.

pipeline: EVALSHA×3 → sync()   // 1 RTT
naive:    3 separate RTTs      // ~3 ms
Latency budget per check: local rule lookup ~100 ns (cache hit) + Redis counter check 0.3–1 ms = < 1.5 ms total. A cache miss (TTL expiry) adds a 2–5 ms DB read but is rare. → full layering on canvas 1 · HLD
C

Bottlenecks & solutions

click a card to open

Redis is a single point of failure

Impact: the counter store is on every request's hot path. If Redis is unreachable, no check can complete — and blocking all traffic turns a protection layer into a self-inflicted outage.

Fix: fail-open — on RedisConnectionException/timeout, return allowed, fire a rate_limiter.fail_open metric + alert, and optionally fall back to a per-node local bucket as degraded mode. Run Redis Sentinel/Cluster for HA. Fail-closed only for billing/security paths.

Race condition on read-then-write

Impact: two nodes both GET count 99, both see "under 100", both SET 100 → the limit is silently exceeded. INCR+EXPIRE as two separate commands is not atomic either.

Fix: atomic INCR for simple counters; a Lua script for multi-step algorithms (Token Bucket read-refill-consume-write) so nothing interleaves on the single-threaded shard. MULTI/EXEC can't read-then-use a value mid-transaction — Lua can.

Clients gaming multiple nodes

Impact: with local counters and a round-robin LB, a client spread across N nodes gets up to N× its limit before any node rejects.

Fix: centralized Redis counters — every node increments the same key, so distribution doesn't matter. Sticky sessions are only a partial mitigation and bring uneven load + failover loss.

Clock skew across nodes

Impact: if Node A is 2 s ahead of Node B they disagree on which window a request belongs to (Fixed Window) or compute different refills (Token Bucket).

Fix: use Redis server time (TIME) inside the Lua script so all window math shares one clock; NTP-sync nodes as a backstop; prefer time-delta algorithms (Token Bucket) that tolerate small skew.

Fixed-window boundary burst / thundering herd

Impact: Fixed Window lets 2× the limit through at a window edge (5 at 1:00:30 + 5 at 1:01:00), and all counters resetting at once creates a synchronized boundary spike.

Fix: use Sliding Window Counter (weighted previous+current window, no hard reset) or Token Bucket (gradual refill); add jitter to window boundaries. The algorithm is selectable per rule in RateLimitRule.

Stale rules after an admin change

Impact: an admin lowers a limit from 1000 to 100 but nodes keep serving the cached old rule for up to a TTL.

Fix: keep the TTL short (30 s) and publish a Pub/Sub invalidation event on change so nodes update within milliseconds; expose a force-refresh admin endpoint for emergencies.

Rule-cache stampede on TTL expiry

Impact: many threads discover the same rule expired at once and all hit the DB to reload it.

Fix: lock-based refresh — one thread reloads while others serve the stale value; probabilistic early expiry and a background refresher are complements. Bound the cache size with LRU to cap memory.

D

CAP & consistency — why AP

pick two; P is not optional
the choice

A rate limiter must always respond allow/deny. During a partition the real decision is A vs C, and here the cost of blocking legitimate users (an outage) far outweighs briefly serving 10–20% over-limit. Protection, not precision.

  • AP: during a partition each node keeps deciding on its local view rather than erroring.
  • Partitioned nodes can each pass up to their own limit → in the worst case ~N × limit, typically 110–120% for brief splits.
  • A rate limiter that causes an outage is worse than no rate limiter at all.
fail-open vs fail-closed
// Redis down — which way do we fail?
general API  → FAIL-OPEN   allow + alert   // AP
billing/auth → FAIL-CLOSED reject to be safe // CP

Fail-open is the production default: worst case a free user gets extra requests. Fail-closed is reserved for paths where an overage costs real money or breaks security — payments, login attempts, SMS/email sends. Many systems run both layers.

Redis single-key consistency: a single shard is single-threaded, so INCR on one key gives sequential consistency with no locks — "good enough for 99% of rate limiting." Replica reads can lag, so read counters from the primary (or accept slight inconsistency).
