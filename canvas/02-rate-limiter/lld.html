B

Token Bucket — the core algorithm

TokenBucketStrategy
the code (verbatim)
public RateLimitResult tryConsume(String key, RateLimitRule rule) {
  TokenBucket b = buckets.computeIfAbsent(key,
    k -> new TokenBucket(rule.getBurstCapacity(),
                        rule.getMaxRequests(),
                        rule.getWindowSizeMs()));
  synchronized (b) {                 // per-key lock
    long now = System.currentTimeMillis();
    b.refill(now);                     // += elapsed * rate
    if (b.tokens >= 1.0) {
      b.tokens -= 1.0;
      int rem = (int) b.tokens;
      return RateLimitResult.allowed(rem, ...);
    } else {
      long retry = (long)((1.0 - b.tokens) / b.refillRatePerMs);
      return RateLimitResult.rejected(..., retry, ...);
    }
  }
}

refillRatePerMs = maxRequests / windowSizeMs; the bucket starts full at capacity = burstCapacity (which defaults to maxRequests).

worked example — rule: 5 req / 10 s, 7 rapid hits
// capacity=5, rate = 5/10000 = 0.0005 tok/ms
// bucket starts full: tokens = 5.0

req 1  tokens 5.0 >= 1 → ALLOW  tokens=4.0
req 2  tokens 4.0 >= 1 → ALLOW  tokens=3.0
req 3  tokens 3.0 >= 1 → ALLOW  tokens=2.0
req 4  tokens 2.0 >= 1 → ALLOW  tokens=1.0
req 5  tokens 1.0 >= 1 → ALLOW  tokens=0.0
req 6  tokens 0.0 < 1  → DENY   429
         retryAfter = (1-0)/0.0005 = 2000 ms
req 7  tokens 0.0 < 1  → DENY   429

result → 5 allowed, 2 denied

Wait 2 s and one token refills (2000ms × 0.0005 = 1.0), so the next request is allowed again. Bursts up to capacity are absorbed; the long-run rate stays at 5 / 10 s.

Why Token Bucket as the default? It gives the smooth long-term rate of a leaky bucket plus a configurable burst allowance (burstCapacity), all in O(1) state per key — just a token count and a last-refill timestamp. Refill is computed lazily on read (elapsed × rate) rather than by a background thread, so there is nothing to schedule. That combination is why AWS API Gateway, Stripe, and most gateways reach for it first.
C

The five algorithms (Strategy pattern)

swap the algorithm, not the service

TokenBucketStrategy — tokens refill at a steady rate up to capacity; each request spends one. algorithm() = TOKEN_BUCKET · the default rule uses it

  • Bursts: yes — up to burstCapacity, then throttled to the refill rate.
  • Memory: O(1) per key (token count + last-refill time).
  • Best for: API gateways that want smooth average rate with headroom for spikes.

LeakyBucketStrategy — a FIFO queue drained at a constant rate; overflow is rejected. algorithm() = LEAKY_BUCKET

  • Bursts: no — output is perfectly smoothed to a constant rate.
  • Memory: O(N) per key — holds queued request timestamps.
  • Best for: traffic shaping / protecting a downstream that needs a steady feed.

FixedWindowCounterStrategy — one counter per fixed window; reset on window rollover. algorithm() = FIXED_WINDOW

  • Accuracy: low — the boundary spike lets a client push up to 2× the limit across a window edge.
  • Memory: O(1) per key — a single AtomicInteger + window start.
  • Best for: simple, cheap counters where approximate limits are fine.

SlidingWindowLogStrategy — a sorted timestamp log; evict-then-count on every request. algorithm() = SLIDING_WINDOW_LOG

  • Accuracy: exact — no boundary problem at all.
  • Memory: O(N) per key — one entry per in-window request (can be millions).
  • Best for: precise billing / quotas where every request must be counted exactly.

SlidingWindowCounterStrategy — weighted blend of the previous and current window counts. algorithm() = SLIDING_WINDOW_COUNTER

  • Accuracy: high — prev*(1-overlap)+current catches the spike, within ~0.003% of an exact log.
  • Memory: O(1) per key — just two counters and a window start.
  • Best for: production APIs — the accuracy of a log at the cost of a fixed window.

The pattern: RateLimiterService holds a Map<Algorithm,RateLimiterStrategy> and never branches on algorithm type — it just does strategies.get(rule.getAlgorithm()).tryConsume(key, rule). Adding a sixth algorithm is a new class + one put in AppConfig.createStrategies(), with zero changes to the service, controller, or repository (Open-Closed Principle). Because the algorithm is read from the rule per request, an admin can even switch a key's algorithm live — the next request picks the new strategy.
D

Data model detail

RateLimitRule · RateLimitResult · RequestContext
RateLimitRule — the config entity (Builder)
id            String   // defaults to key
key           String   // "clientId:endpoint"
maxRequests   int      // > 0 (validated)
windowSizeMs  long     // > 0 (validated)
algorithm     Algorithm // default TOKEN_BUCKET
burstCapacity int      // -1 → maxRequests
enabled       boolean  // default true

Fully immutable — set once through builder(key, maxRequests, windowSizeMs) and never mutated. build() enforces the two positivity invariants; the -1 burst sentinel means "no separate burst, use maxRequests". In a SQL store this is a rules table with PRIMARY KEY(key).

RateLimitResult — the check outcome
allowed       boolean
remaining     int      // tokens/slots left
retryAfterMs  long     // 0 when allowed
limit         int      // rule.maxRequests
resetAtMs     long     // epoch ms of reset

// factories
allowed(remaining, limit, resetAtMs)
rejected(limit, retryAfterMs, resetAtMs)

Immutable, private constructor, two named factories. getHeaders() maps the fields to X-RateLimit-Limit / -Remaining / -Reset and adds Retry-After only when denied — the exact headers the controller writes back.

The key is the whole game: RequestContext.getRateLimitKey() returns clientId + ":" + endpoint, so limits are per-user-per-endpoint by default. That same string is the lookup key into the rule store and the per-key bucket/counter map inside each strategy — one identifier threads through resolution, rule lookup, and state. Change the key shape (IP-based, API-key-based, per-tenant) and the entire granularity of the limiter changes with it.

Request handling sequence

which class does what, in order

Request ALLOWED  →  200 OK

Controller.handleRequest(ctx)
  └─ Service.checkRateLimit(ctx)
       1  key = ctx.getRateLimitKey()      // "alice:/api/orders"
       2  rule = ruleRepository.findByKey(key)
              .orElse(defaultRule)          // fall back if unset
       3  rule.isEnabled()? no → allowed(max, max, 0)
       4  strategy = strategies.get(rule.getAlgorithm())
              null? → IllegalStateException  // config error
       5  strategy.tryConsume(key, rule):
              computeIfAbsent(key) → bucket
              synchronized(bucket): refill → tokens >= 1
              tokens -= 1 → RateLimitResult.allowed(rem, ...)
  └─ result.getHeaders() → X-RateLimit-* printed
  └─ [200 OK]  remaining = rem

Request REJECTED  →  429 Too Many Requests

Controller.handleRequest(ctx)
  └─ Service.checkRateLimit(ctx)
       1  key = ctx.getRateLimitKey()
       2  rule = ruleRepository.findByKey(key).orElse(defaultRule)
       3  strategy.tryConsume(key, rule):
              synchronized(bucket): refill → tokens < 1.0
              retryAfter = (1 - tokens) / refillRatePerMs
              return RateLimitResult.rejected(limit, retryAfter, resetAt)
  └─ headers include Retry-After: <ms>
  └─ [429 Too Many Requests]

Note the controller returns the RateLimitResult either way — it is the caller (a real filter) that would short-circuit the chain on 429 and never invoke business logic. The service itself is pure: context in, result out, no side effects beyond the per-key counter.

Admin switches a key's algorithm  →  live, no restart

RuleService.updateRule(key, newRule)   // algorithm=SLIDING_WINDOW_COUNTER
  1  repository.exists(key)? no → RuleNotFoundException
  2  repository.save(newRule)                // map.put(key, newRule)

═══ next request from that key ═══
Service.checkRateLimit(ctx)
  → findByKey(key) = newRule
  → strategies.get(SLIDING_WINDOW_COUNTER)   // different impl
  → tryConsume(...)                          // new algorithm in effect

Because the strategy is resolved per request from the rule's algorithm field, changing the rule instantly changes the algorithm — no redeploy, no restart.

F

Design patterns used

GoF-categorized
Creational
  • Builder — RateLimitRule.builder(key, max, window). Required fields via constructor, optional fields with defaults, validation in build().
  • Factory — AppConfig static methods (createStrategies, createDefaultService, createController) centralise all wiring — the composition root.
Behavioral
  • Strategy — RateLimiterStrategy + the five algorithms. The centrepiece: swap the algorithm per rule without touching the service.
  • Chain of Responsibility — the limiter is one link (auth → rate-limit → authorization → business logic); a 429 short-circuits the chain. Conceptual here, a Filter/Interceptor in production.
  • Template Method — every tryConsume follows the same skeleton: get-or-create state → refill/rotate → decide → build result.
Architectural (not GoF)
  • Repository — RuleRepository → InMemoryRuleRepository. Decouples logic from storage; swap in Redis/Postgres with no service change (Dependency Inversion).
  • Dependency Injection — constructor injection throughout, wired by hand in AppConfig (Spring @Configuration in production).
Why they cluster: Strategy + Repository + DI together deliver the Open-Closed Principle — new algorithms and new rule stores are additions, never edits. Builder keeps the rule immutable and self-validating; the ConcurrentHashMap + per-key synchronized/AtomicInteger keep each key's counter thread-safe without a global lock. → distributed counters (Redis + Lua) & fail-open vs fail-closed on canvas 3
