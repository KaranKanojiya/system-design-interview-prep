B

What C, A, P each mean

precise definitions
C · Consistency

Every read receives the most recent write — or an error. This is linearizability, the strong kind, not "eventual consistency."

The system behaves as if there is one single copy of the data and all operations are atomic and instantaneous.

A · Availability

Every request to a non-failing node gets a response — with no guarantee that it is the most recent value.

"A response, not necessarily the right one." A timeout or an error is not available.

P · Partition tolerance

The system keeps operating despite arbitrary message loss between nodes — the network splitting into groups that can't talk.

Not optional: cables cut, switches fail, GC pauses look like partitions. You must tolerate them.

C

The real rule — you choose CP vs AP, not "two of three"

partitions are a given
why CA can't exist
// Two nodes A, B. A partition sits between them.
Client writes  x = 1  to A
Client reads   x      from B

// B cannot contact A. It must either…
CONSISTENT  → B errors / waits  // not Available
AVAILABLE   → B returns x = 0    // not Consistent

// You cannot have both C and A during a partition.
// And partitions happen. So: pick CP or AP.
  • P is not a choice — in a distributed system the network will split. You only choose what to do when it does.
  • CP = when partitioned, drop A: block or error rather than serve possibly-stale data.
  • AP = when partitioned, drop C: keep answering, reconcile later.
  • "CA" = a single node with no network to partition (one Postgres box). Add a replica and you're back on the CP/AP edge.
  • CAP is per-operation, not per-system. One service can be CP for writes and AP for reads — e.g. E-Commerce inventory (CP) vs product catalog (AP).
Nuance that scores points: CAP is not binary or system-wide. Say "the order book is CP" not "the whole system is CP." Different components make different choices.

PACELC — the trade-off you live with every day

beyond CAP

CAP only describes behaviour during a partition. But partitions are rare — most of the time the system is healthy. PACELC (Abadi, 2012) adds the Else case: with no partition, you still trade Latency vs Consistency on every request.

if (Partition)  choose  A  or  C   // same as CAP
else            choose  L  or  C   // the new, everyday tradeoff

Consistency-models spectrum — strong → eventual

expand each

"Consistency" is not one thing. It's a ladder: stronger models are easier to reason about but harder and slower to scale; weaker models scale freely but push complexity onto your app. Top of the list is strongest.

1 · Linearizability (strong) — strongest

Behaves as if there is one single copy of the data; every operation appears atomic and instantaneous at some point between its call and return. A read always sees the latest completed write, respecting real-time order. This is the "C" in CAP. Cost: coordination on every write (Raft/Paxos leader, quorum) → higher latency, no availability during partitions. Used by etcd, ZooKeeper, Spanner.

2 · Sequential consistency

There exists one total order of all operations that every process agrees on, and each process's own operations keep their program order — but that global order need not match real (wall-clock) time. Weaker than linearizability precisely because it drops the real-time requirement.

3 · Causal consistency

Preserves the order of causally related operations (if A happened-before B, everyone sees A before B), while concurrent operations may be seen in different orders by different nodes. Enough to make comment-reply threads and chat make sense without full coordination. Implemented with vector clocks / dependency tracking.

4 · Read-your-writes (session)

A session guarantee: after you write a value, your subsequent reads always reflect it (you never lose your own update), though other users might still see the old value briefly. This is how "you see your own tweet immediately" is delivered on an otherwise-eventual feed.

5 · Monotonic reads

Time never appears to go backwards for a reader: once you've seen a value, later reads never return an older version. Prevents the "refresh and the new item vanishes, refresh again and it's back" flicker caused by hitting replicas with different lag.

6 · Eventual consistency — weakest

The weakest useful model: if no new writes happen, all replicas eventually converge to the same value. No bound on "eventually" — but in practice milliseconds to seconds. Reads can be stale in the meantime. The default for AP stores (Cassandra, DynamoDB) and the norm for feeds, caches, and click counts.

Leaderless stores (Dynamo-style) skip a leader entirely and use quorums to tune where they sit on the CP↔AP line.

the quorum rule
N = total replicas
W = nodes that must ACK a write
R = nodes that must respond to a read

W + R > N   // read & write sets overlap
              // → read always sees latest write
WRNResult
2234>3 — strong (default)
1132≯3 — stale possible (AP)
313fast reads, slow writes
133fast writes, slow reads
worked example — N=3, W=2, R=2
// Write x=5 — need W=2 ACKs
Write x=5 → {A, B} ACK   // C still has old x=3

// Read — need R=2 responses
Read ← {B, C}
   B returns x=5   // fresh
   C returns x=3   // stale
⇒ client keeps newest version (by timestamp/version) = x=5 ✓

// Why it works: write set {A,B} and read set {B,C}
// overlap at B. R+W = 4 > N = 3 guarantees ≥1 shared node
// that holds the latest write. That overlap = strong reads.
Sloppy quorum trades this away: if a designated node is down, write to any live node (a "hint") and hand off later. Boosts availability (more AP) but the R+W>N overlap may not hold, so reads can go stale.
